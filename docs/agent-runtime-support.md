# Agent-runtime version and compatibility baseline

Recorded: 2026-10-03; aligned with the first-release decisions on 2026-10-07 (see [contract](../.scratch/codebase-tools-omp-v1/contract.md)). This is the single authority for agent-runtime/package version compatibility, not a claim that the in-repository runtime framework or certified adapters already exist. Exact versions below record observations; the first-release admission policy is decided: an exact supported-version enumeration, an unlisted version warned about once per main session and then allowed to continue, and a missing required semantic rejected **fail-soft** (reported on a non-model channel, not bound, no partial registration, agent runtime continues; never silently weakened).

## Shared-source deployment prerequisite

The framework lives once in `my-agent-toolkit/framework/`; extensions import that source directly instead of depending on a separately published framework package. The first release configures only OMP to scan `entrypoints/omp/`; the pi discovery root is deferred with the pi adapter. The OMP root contains independent thin extension entrypoints importing implementations under `extensions/`, which in turn use the shared framework source. The implementation and framework directories are not extension discovery roots.

Before claiming this deployment works, exercise the actual installed OMP loader with an entrypoint importing TypeScript outside its discovery root. Decision 03 verified source/dependency resolution, independent extension discovery, and Markdown text import on OMP 18.5.0; the pi loader remains deferred and unverified. Record the tested repository revision, dependency lockfile, and agent-runtime versions instead of an independently released framework version. Simultaneous activation of an extension's original and replacement is prevented by load-source mutual exclusion (an explicit-only root during development/acceptance, and removal of the superseded implementation before the permanent cutover).

Source co-location supports direct editing and debugging but does not establish hot reload or breakpoint mapping. The first release promises only whole-process restart; hot reload is deferred, so verification of reload/cache visibility is deferred with it. One source tree does not create shared in-memory State across agent-runtime processes. These are deployment prerequisites, not a claim that the source layout or framework has been implemented.

## Planned agent-runtime-qualified capability: subagent State inheritance

Design decision recorded on 2026-10-04, aligned with decisions 03/04 on 2026-10-07; this is not implementation or runtime certification. The first release implements only codebase-tools-style live following of the owning main session's activation value, with independent branch-derived injection progress in each session. Other inheritance strategies are deferred until there is a concrete need.

| Agent-runtime path | First-release scope |
| --- | --- |
| OMP built-in subagent path | **Targeted for the first release.** Decision 03 runtime-exercised the built-in subagent path (identity, factory rebinding, inheritance, independent init); decision 04 decided the owner contract (nearest main ancestor, `parentId` + `AgentRegistry`, live following). Framework implementation remains pending. |
| pi | **Deferred.** The first release ships no pi adapter, so pi subagent State inheritance is unimplemented; no pi subagent implementation is selected or integrated. |

This does not declare pi incapable of running subagents. It limits the framework's supported integration paths. Extension loading, State inheritance, and MCP availability are separate concerns. The framework owns the State contract and its agent-runtime mapping, not a replacement subagent scheduler or MCP implementation.

A future pi adapter may explicitly accept codebase-tools operating in a pi session without inheritance, subject to its other required contracts; the first release ships no pi adapter, so this is a deferred policy rather than first-release behavior. When implemented, notify the user once at the extension's first activation in that session that the framework will not propagate its activation to subagents; the notification transport is the extension UI notification channel (a stderr line when no UI is available) and the notice is never inserted into model instructions or conversation history. This is not a general permission to ignore missing required capabilities, and required role and insertion semantics are not relaxed.

### Subagent mechanism evidence and its limits

Source observations checked on 2026-10-04 against the local checkouts; these do not certify installed-agent-runtime behavior:

- **OMP rebinding is not business State copying.** [`bindExtension`](../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/loader.ts#L439) creates an extension/API binding and runs the prepared factory; [`bindPreparedExtensions`](../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/loader.ts#L491) creates a new runtime for the binding set. OMP's [extension guidance](../../oh-my-pi/docs/extensions.md#L1048) explicitly says module globals are shared by parent/child bindings, while session-specific state belongs in the factory closure or persisted session entries. This explains how shared activation and independent injection progress can coexist; it does not define arbitrary extension State inheritance.
- **Use identity, not depth alone.** [`ExtensionAgentIdentity`](../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts#L464) provides `kind: "main" | "sub"`, `id`, `name`, `depth`, and optional `parentId`. Its comments explicitly allow subagents at depth zero. Mapping this identity to a State owner still belongs to the framework adapter; a process-global variable does not encode that relationship.
- **The ordinary pi subagent example has a different process boundary.** The [example's arguments](../../pi/packages/coding-agent/examples/extensions/subagent/index.ts#L300) include `--mode json -p --no-session`, and it [spawns a separate process](../../pi/packages/coding-agent/examples/extensions/subagent/index.ts#L346). The example's process cannot inherit the parent's JavaScript module variable merely by importing the same source. This observation concerns that example, not every possible pi subagent implementation.
- **Do not conflate pi's experimental durable path with ordinary extensions.** The [durable harness](../../pi/packages/durable/README.md#L3) is explicitly experimental. Its [subagent implementation](../../pi/packages/coding-agent/src/experimental/durable/subagent.ts#L34) creates a task-owned child conversation through durable interfaces. It is a distinct possible integration path, not evidence that a pi adapter supports inheritance (the first release ships no pi adapter).

### codebase-tools extension-logic probe

During this design discussion, a throwaway Bun probe imported the actual [`codebase-tools` extension factory](../../my-omp-toolkit/extensions/codebase-tools/index.ts#L45) and `__resetCodebaseToolsForTests`. It supplied minimal agent-runtime substitutes for hook/command registration, session entries, agent identity (`"main"` / `"sub"`), and UI calls. It invoked both factories and their `session_start` handlers while activation was off, then invoked the main command and child `before_agent_start` handlers in this order:

| Step | Observed child result |
| --- | --- |
| Child turn before main activation | No contributed message |
| Main toggles on; the already-created child runs | `codebase-tools:init` |
| Same child runs again | `codebase-tools:reminder` |
| Main toggles off; same child runs | No contributed message |

The process exited with code 0 and no stderr. The child substitute recorded one non-LLM state entry containing `{ on: true, initInjected: true }` for the **original** implementation. The observed stop after main deactivation comes from reading `globalOn` on the next hook call, not from replacing that child entry. The probe established live following rather than a creation-time snapshot, and separately maintained child injection progress, for the existing extension logic. The replacement does not preserve this contract: it persists only `{enabled}` and derives injection progress from the branch (decision 05), and persistence compatibility is abandoned in both directions.

This was **not** a real OMP task spawn or a pi subprocess test. It does not verify native loader behavior, real session persistence/resume, provider message roles, MCP availability, multi-owner isolation, parent disappearance, or future framework behavior. The probe ran directly from an inline script and left no probe file. Framework implementation must replace accidental process-global ownership with an explicit owner relationship; decision 03 later exercised the real OMP extension path and decision 04 decided the owner contract, but the replacement-side contract scenarios remain to be implemented and accepted.

The record shape is uniform; each feature retains its own semantic contract and implementation strategy. ## Meaning of the support list

This file concerns agent-runtime/package version compatibility, not which tools an agent may call. The first-release admission policy is decided: support is an exact version enumeration; an unlisted installed version is warned about once per main session and then allowed to continue without claiming support; a missing required semantic rejects the affected capability fail-soft. The check runs at extension load/binding, before commands and contributions are registered; platform and runtime are recorded but not gated. The support record uses four states — `verified-supported`, `verified-unlisted`, `unverified`, and `unsupported` — each with its evidence and conditions. Current declarations: OMP 18.5.0 (checkout `@9348320`) + Windows x64 + Bun 1.4.2 is `verified-supported` for the paths exercised in decision 03; other installed versions are `verified-unlisted`; openai-codex layer-2 delivery and TUI visual acceptance are `unverified` until their evidence exists; the pi adapter and same-process multi-main are `unsupported` in the first release.

The first release requires strict history preservation: no mutation or reordering of existing conversation entries, and no alteration of their history-derived request content. Request-context filtering, even of the extension's own earlier messages, is deferred. It permits new messages to be appended through the agent runtime's normal recording path; once recorded, they receive the same protection. Non-persisted request contributions are not included in the first release, so their placement remains undecided. Mechanism availability in the table above does not by itself establish policy compliance.

## Compatibility rules already agreed

- Common framework behaviors must be satisfiable across all declared supported agent-runtime targets, possibly through different adapter implementations. Additional agent-runtime-qualified framework capabilities are permitted with explicit support conditions and visible absence; first-release subagent State inheritance targets OMP, not pi.
- Required semantics must not be silently weakened. An unmet required semantic rejects the affected capability fail-soft: it is reported on a non-model channel, not bound, and leaves no partial registration while the agent runtime continues.
- Version claims must retain their evidence level. Source inspection, executable startup, and exercised behavior are distinct.
- Cross-agent-runtime semantic contract scenarios are regression alarms: a failure signals an incompatibility to investigate, while a pass never automatically approves an agent-runtime version. A framework maintainer reviews the changed agent-runtime source and/or further test evidence and explicitly decides whether to declare support.

## Decisions still open

- Admission of a new agent runtime (for example pi) without silently weakening already-established common contracts; the first release ships no pi adapter.
- Cross-agent-runtime prefix stability and a system-prompt stability policy.
- Shared-file concurrency, configuring State persistence media, request-only contribution placement, and the remaining control kinds (all deferred beyond the first release).

The following are **decided** for the first release and are no longer open: the supported set is the exact combination `@oh-my-pi/pi-coding-agent@18.5.0` (checkout `@9348320`) + Windows x64 + Bun 1.4.2; an unlisted installed version is not refused — it is warned about once per main session and then continues; mode/provider constraints are the verified providers `deepseek/deepseek-flash` (`openai-completions`) and `openai-codex/gpt-6-luna` (`openai-codex-responses`, shape-only layer 1 and real-credential layer 2 per decision 08); upgrade regression runs the framework suite on isolated candidate installs on demand, and a pass never automatically approves a version. Future support declarations still require an explicit maintainer decision based on source review and/or exercised scenarios for the declared target; passing tests alone is not that decision. OMP 18.5.0 is runtime-verified only for the extension-path behaviors exercised in decision 03; other versions and provider paths are not certified by that evidence.
