# Harness version and compatibility baseline

This document owns the maintained harness support states, integration conditions and reproducible verification procedures. A support declaration is scoped to its exact harness artifact, source/dependency combination, platform and provider paths; a passing test run never promotes support automatically.

Normal startup follows [independent compatibility verification](#independent-compatibility-verification): no version-membership warning, required-native-interface admission check or verification-report gate runs at startup. Configuration and business error handling remain. Human acceptance and formal deployment cutover are not implied by implementation or scripted checks.

## pi codebase-tools adapter evidence

The pi codebase-tools adapter is implemented within the mapped scope below; it does not promote pi to the OMP `verified-supported` baseline.

- Scoped reference combination: `@earendil-works/pi-coding-agent@1.2.0` Node bundle, Windows x64, Node 22.19.0, Bun 1.4.2. Use `PI_NODE` to select that Node executable for the reproducible smoke. Other Node versions and real-provider paths remain unverified.
- Mapped scope: session boundaries and branch records required by State, run-initiation prompt delivery, commands, marker and feedback. Round, Turn and user-input subscriptions in this scoped adapter are explicitly refused; it supplies no model-catalog, provider-access or viewed-session outlet. pi entry labels are not extension diagnostic labels.
- Hidden custom messages serialize as `user` on the local OpenAI-compatible path. Local capture establishes serialization, not real-service delivery, developer/system authority or cache hits. Agent-observed TUI frames do not replace maintainer visual acceptance.
- Windows/Node 24.18.0 has an observed libuv `UV_HANDLE_CLOSING` failure on multi-request/EOF paths, including without extensions. Do not suppress its exit failure or claim this combination supported.
- Node text loading is installed at the adapter boundary, once per process and limited to this repository's extension Markdown resources. Bun needs no hook. Hot reload and concurrent main-session instances remain uncertified.
- Subagent following is a separately qualified assembly/provider integration, not a guarantee of this original scoped adapter; see the capability-difference register.

### Fixed verification baseline and dock

The single checkable record of *what* runs acceptance, and of the source combination it is pinned to, is [`harness-baseline.json`](harness-baseline.json): the revision anchor (local checkout `@9348320` = 18.5.0), the run/acceptance artifact (isolated exact install `@oh-my-pi/pi-coding-agent@18.5.0` with the byte-identity conclusion reused from decision 03), and the dependency lockfiles of this repository and of the `my-omp-toolkit` behavior oracle. Support status stays in this document; the record only holds that correspondence, and everything in it is re-checked rather than restated.

Runs execute through the dock in [`tests/harness-dock/`](../../tests/harness-dock/index.ts):

- `cd <repo> && bun install` (once) then `bun run test:dock`; the checked dock files run four isolated Bun workers at a time. Each worker owns its temporary agent state, run, session and capture directories, while the materialised baseline and patched-host prefixes are installed atomically and then reused by the workers. Use `bun run test:dock:serial` when diagnosing shared state, on a machine that cannot host four real sessions at once, or once after a harness version or host patch changes so the shared prefixes are warmed before a parallel run. The isolated install lands in the gitignored `.cache/omp-baseline/<version>` prefix.
- The version under test is the recorded supported version by default; `OMP_TEST_VERSION=<v>` selects a candidate, which materialises into its own prefix (`.cache/omp-baseline/<v>`) instead of reusing or overwriting the fixed one.
- The dock materialises the recorded install, starts a controlled session (`--mode rpc --no-extensions -e <extension path>`), executes commands and turns, reads the session JSONL back, captures full outbound request JSON at a local capture endpoint, captures stderr, and reports argv/run root/stderr/frame tail when a run fails.
- Every run uses a temporary agent state directory, session directory, working directory and capture directory under the OS temp root. The environment is stripped of resolution offsets (`OMP_PROFILE`, `PI_PROFILE`, `OMPCODE`, `PI_CONFIG_FILES`, `XDG_*`, `PI_CODING_AGENT_DIR`, `OMP_AUTH_BROKER_*`) and `PI_CODING_AGENT_DIR` is pointed at that temporary directory, so the default global install, formal configuration and any running agent are untouched.
- The local checkout is a source/revision anchor only: it cannot run a full session because its native addon is not built, and acceptance never builds natives. The install ships prebuilt win32-x64 natives.
- The harness materialises its session file lazily, so JSONL read-back happens after a turn and a graceful exit (`stop()` closes stdin and waits for exit code 0); a command-only session may leave nothing on disk.

The exact command sequence, candidate record, pi smoke options and evidence rules are collected in the [version verification runbook](#version-verification).

## Upgrade standard and triggering

**Scope — framework capabilities only.** The long-term upgrade standard covers the framework capabilities C1–C15 as exercised by [`tests/framework/`](../../tests/framework). Extension capabilities are deliberately **outside** it: an extension's own behavior is covered by [`tests/codebase-tools/`](../../tests/codebase-tools), which runs permanently against the fixed supported version, plus the human user acceptance at the end of development. A green framework alarm says nothing about an extension. This remains a narrower framework regression alarm, not the complete extension/harness verification report required by the assembly revision; full report coverage and cutover are selected in acceptance.

**Trigger — on demand only.** Another version is verified only when a maintainer proposes a candidate. Default and CI always run the fixed supported version (`18.5.0`); a scheduled or CI candidate run is explicitly rejected.

**Basic verification (regression alarm) — P34.** `OMP_TEST_VERSION=<v>` selects a candidate. The dock installs that exact version into its own isolated prefix `.cache/omp-baseline/<v>` and runs the framework suite against it; [`scripts/verify-omp-candidate.ts`](../../scripts/verify-omp-candidate.ts) performs the install, runs the suite and writes a checkable result record to `.cache/omp-baseline/<v>/candidate-verification.json` — a local, gitignored artifact next to that install, evidence for the maintainer's decision and never a committed support claim. The exact commands, prerequisites and evidence rules are in the [version verification runbook](#version-verification).

**Extension regression.** `bun test tests/codebase-tools` runs permanently against the fixed supported version; it is not part of the candidate alarm.

**Human TUI spot check (trigger).** When the upgrade touches an **extension-visible surface** — marker rendering, the command, contribution order or role, session resume — the maintainer appends one human interactive TUI spot check to the candidate suite. When it does not, the candidate suite alone is the alarm.

**Explicit replacement — never automatic.** Independent report results are maintainer input, not automatic support promotion. A support replacement records the selected harness/package revision, environment, framework/extension source and lockfile plus exercised scope in this record and harness-baseline.json. Baseline metadata remains a verification input, not a new production version gate. Detailed full-extension coverage and a patched Viewed session host version remain acceptance decisions; the old procedure of changing a runtime admission list is superseded by the independent-verification policy.

**Isolation conditions.** Candidate work never touches the default global install, the formal configuration, or a running agent: installation is confined to `.cache/omp-baseline/<version>` (gitignored), every controlled session runs the isolated install under a temporary agent state directory, and the dock strips the resolution offsets (`OMP_PROFILE`, `PI_PROFILE`, `OMPCODE`, `PI_CONFIG_FILES`, `XDG_*`, `PI_CODING_AGENT_DIR`, `OMP_AUTH_BROKER_*`) before starting one.

## Version verification runbook

This is the operating manual for the checks behind the support record. It collects the commands that previously lived in the README: sections A–C correspond to the former steps 1–2, section F is step 3 (the TUI spot check) and section G is step 4 (replacing the supported version). It does not change any support state: a green run is evidence for a maintainer decision, never a promotion. Structural adapter completeness is a different check — see [static integration check](integration-check.md). The OMP baseline/candidate runs and the automated extension suite are mechanical and may be run by a human or an agent; the interactive TUI spot check and the support replacement are human/maintainer actions.

### What each check establishes

| Check | Establishes | Does not establish |
| --- | --- | --- |
| `verify:omp-candidate` | The framework suite (C1–C15) still passes on one exact installed harness version; a scoped, machine-readable result record. | Extension behavior, native semantic correctness, or support of that version. |
| `test:dock` / `test:dock:serial` | The selected OMP version's controlled sessions, including real-host dock scenarios and the baseline correspondence. | pi behavior; provider-account truth; visual TUI quality. |
| Extension suites and smokes | The named extension scenarios on the recorded or explicitly selected host. | Other extensions, other versions, or support promotion. |
| `verify:provider-account` | What a real provider account answered beside what the host drew, for the named scenario. | A model request, billing correctness, or other providers/accounts. |
| `pi-tui-acceptance` | A human operator's visual acceptance of the fixed TUI scenario. | Automated certification, other widths/terminals, or a candidate version's support. |

### Prerequisites and isolation

- Run these commands from the repository root. Windows x64, Bun **1.4.4** (the root `package.json` test-runtime selection), and an installed dependency tree (`bun install` once) are required for the repository's own checks. The historical acceptance environment in `harness-baseline.json` remains Bun 1.4.2; the current test-runtime selection does not replace that support evidence. The fixed baseline is `@oh-my-pi/pi-coding-agent@18.5.0`, checkout `@9348320`, recorded in [`harness-baseline.json`](harness-baseline.json).
- The OMP checks materialise the exact harness under `.cache/omp-baseline/<version>` (gitignored). Every controlled session uses a temporary agent state, session directory, working directory and capture directory; the default global install, formal configuration and any running agent are never touched. The local checkout is a source/revision anchor only — its native addon is not built, so acceptance runs the isolated install with prebuilt win32-x64 natives.
- The pi smokes need a separately installed pi CLI and use the repository's pinned `pi-subagents` dependency from `package.json`. Pass the CLI with `--pi <path>` or `PI_CLI=<path>` (the bundle `dist/bundle/cli.js`, a `pi`/`pi.cmd` shim, or the binary). For a script/shim CLI, set `PI_NODE` to the Node executable; on Windows the verified combination is Node **22.19.0**. Node 24.18.0 hit a Windows/libuv `UV_HANDLE_CLOSING` assertion in the recorded multi-request probe, with or without extensions; do not suppress that failure.
- `verify:provider-account` is the only script here that reads a real credential. All other runs use local OpenAI-compatible capture endpoints or run without a provider; those prove wiring/protocol, not real-service delivery.

### A. OMP fixed baseline

```sh
bun install
bun run test:dock
bun run verify:omp-candidate
bun test tests/harness-dock/baseline.test.ts
```

- `bun run test:dock` (with `OMP_TEST_VERSION` unset) runs the dock partition (four isolated Bun workers at a time) against the version the baseline record selects. The baseline check re-reads the revision anchor, acceptance artifact, byte-identity hashes and lockfiles.
- `bun run verify:omp-candidate` with `OMP_TEST_VERSION` unset verifies the recorded supported version: it ensures the isolated exact install, runs `bun test tests/framework`, and writes the result record. Use it when you need the framework alarm on the fixed version without relying on the dock's test selection.
- `bun run test:dock:serial` is for diagnosis on machines that cannot host four concurrent real sessions, and is run once after a harness version or host-patch change so the shared prefixes are warmed before a parallel run. It is not a per-commit requirement.
- On a local `core.autocrlf=true` checkout, the dock requires the recorded files at their committed LF bytes and `HERDR_BOT_BINARY` for the patched OMP binary; see the earlier dock conditions in this document.

### B. OMP candidate

```sh
OMP_TEST_VERSION=18.6.1 bun run verify:omp-candidate
OMP_TEST_VERSION=18.6.1 bun run verify:omp-candidate --dry-run
OMP_TEST_VERSION=18.6.1 bun run verify:omp-candidate --install-only
OMP_TEST_VERSION=18.6.1 bun run test:dock
```

- The candidate script accepts only `--dry-run`, `--install-only`, `--help`/`-h`. `--dry-run` prints the resolved version, prefix, install spec and suite command without installing or running; `--install-only` materialises the isolated install without running the suite.
- It installs exactly `OMP_TEST_VERSION` into `.cache/omp-baseline/<version>`, runs only `bun test tests/framework`, and writes `.cache/omp-baseline/<version>/candidate-verification.json`. The record contains the requested/recorded versions, selection source, prefix, installed version, revision anchor, source base commit/dirty state/working-tree digest, lockfile comparison, environment, isolation assertions, install result, framework suite counts, executed/unverified coverage, the alarm verdict and an explicit non-certification statement.
- Exit codes: `0` for a successful dry run/install-only or a green suite; `1` when the isolated install fails; otherwise the framework suite's own nonzero exit code is propagated (a normal test failure is 1); `2` is used for script-level refusal such as an unknown flag or a prefix outside the isolated base. A green result is a regression alarm for the framework suite only.
- The candidate never enters [`harness-baseline.json`](harness-baseline.json), never changes the support record, and must not be added to CI. Default and CI run the fixed supported version only. The `test:dock` candidate run exercises the dock scenarios for that version; it does not turn them into an extension certification.

### C. Extension regression on the fixed version

```sh
bun run test:codebase-tools
```

- This suite runs permanently against the fixed supported version; it is not part of the candidate alarm. A framework-suite green says nothing about an extension.
- When a change touches a real-host extension path, run the corresponding dock partition (`bun run test:dock` or the relevant scenario file) in addition to the focused suite. The historical evidence sections above record which dock scenarios covered which extension; do not substitute a list of test names for actually exercised coverage.

### E. Provider account reading

```sh
bun run verify:provider-account
bun run verify:provider-account --scenario deepseek-balance
bun run verify:provider-account --model deepseek/deepseek-flash
bun run verify:provider-account --out .cache/provider-account --keep
bun run verify:provider-account --prepare
```

- `verify:provider-account` runs the loaded model-cost extension on the installed pi against a real account and writes a desensitized, timestamped report (default `.cache/provider-account/readings-*.json`). It reads the machine's own credential (or the prepared isolated state) but prints it only as a fingerprint.
- It makes **no model request**, installs/logs in/switches nothing, and reports a missing credential as `blocked`, with the login step that would supply it. Scenario outcomes are `observed`, `blocked` or `failed`; exit code is `1` only when a scenario ran and failed, and `0` when scenarios are observed or blocked.
- `--scenario` selects one scenario; `--model <provider>/<model>` states the model pair the scenario's session should run; `--agent-dir` points at the machine's pi store; `--prepared-agent-dir` points at a prepared isolated store; `--out` selects the report directory; `--keep` retains run roots; `--prepare` prints the login steps a missing provider needs, without logging in or installing anything.
- Limits are recorded in the report: one machine, one account, the pi version the run names, the machine's network path; a balance move is not a request cost; the Codex scenario remains blocked without a usable `openai-codex` credential. The historical DeepSeek reading observed 1 scenario, 1 blocked, 0 failed.

### F. Human TUI spot check

When an upgrade touches an **extension-visible surface** — marker rendering, the command, contribution order or role, session resume — append one human interactive TUI spot check to the candidate checks. For OMP use the codebase-tools H1 acceptance checklist; for pi use `bun scripts/pi-tui-acceptance.ts --interactive` (or capture the fixed widths with `--widths 120,80,60`). A human operator judges content, spacing and narrow-width readability. ## Contract-driven agent pre-review

An upgrade review must examine whether the assumptions behind an adapter's semantic mappings still hold, not merely whether native method names and types remain unchanged. An accepted approximation can cease to satisfy a framework contract as native behavior evolves. Agent pre-review filters evidence and risks for a maintainer; it does not certify compatibility, promote support or replace behavior verification.

### Review inputs and mapping rationale

Provide the exact old and candidate harness revisions/artifacts, the current framework and adapter source, relevant dependency/provider revisions, and the framework contracts and decision records. Use the actual source diff and relevant callers, dispatch and teardown paths, not release notes alone. Record unavailable source and unexamined paths as review limitations.

For each relevant minimal integration contract, locate or document:

- the framework's semantic promise and interaction mode, including ordering, await and result-handling obligations;
- the native facts, events, queries or effects used to satisfy it;
- accepted differences between the native meaning and the framework meaning, and their applicable conditions;
- the assumptions that make those differences acceptable within the promised scope;
- the rationale and alternatives behind significant trade-offs, linking existing decisions rather than duplicating the contract;
- changes that would invalidate those assumptions, together with existing source or behavioral evidence and its limits.

Do not infer historical approval from an implementation's existence. If rationale or assumptions cannot be recovered, report them as missing and request maintainer judgment; do not invent a justification. Keep shared semantics in the framework contract and harness-specific approximations in their mapping rationale.

### Review checklist

For each affected mapping, ask whether the candidate changes:

- **Trigger and coverage:** when facts are emitted, which native paths emit them, or whether a formerly covered path is omitted.
- **Ordering, waiting and results:** whether handlers are awaited, what runs before/after them, who applies their results, and whether required resources survive until completion.
- **Identity and scope:** actual session, parent and Owner attribution, process topology, and observation versus effect authority.
- **Data meaning:** measurement basis, units, timestamps, completeness, missing/unknown values and distinctions from known zero.
- **Multiplicity and continuation:** duplicate delivery, retries, queued work, automatic continuation and the assumptions behind deduplication or settled-state decisions.
- **Lifetime:** registration and release, disposal, binding replacement and resource ownership.
- **Failure and cancellation:** propagation, final facts and cleanup on success, cancellation, terminal failure and interrupted execution.

Apply these questions to the mapping's recorded assumptions and accepted differences. A change in an upstream caller, event dispatcher or downstream teardown can matter even when the adapter's imported symbol is unchanged. Interaction mode alone does not establish semantic equivalence.

### Required pre-review output

Name the compared revisions, adapter/framework source and reviewed scope. For each finding, provide the affected contract, old/new source locations and concrete change evidence, the assumption or promise potentially invalidated, the impacted adapter path, and a proposed human check or focused behavioral observation. Separate observed source changes from inferred semantic risks and confirmed violations. List unresolved rationale, unavailable evidence and unreviewed paths explicitly.

“No risk found in the reviewed scope” is not a compatibility proof. A maintainer reviews the findings and selects further verification under the existing upgrade process; source inspection, executed behavior and support approval remain separate. This guide introduces no automatic upgrade runner, scheduled review, startup check or multi-version interface mechanism.

## Shared-source deployment prerequisite

The framework lives once in `my-agent-toolkit/framework/`; extensions import that source directly instead of depending on a separately published framework package. The first release configures only OMP to scan `entrypoints/omp/`; the pi discovery root is deferred with the pi adapter. The OMP root contains independent thin extension entrypoints importing implementations under `extensions/`, which in turn use the shared framework source. The implementation and framework directories are not extension discovery roots.

Before claiming this deployment works, exercise the actual installed OMP loader with an entrypoint importing TypeScript outside its discovery root. Decision 03 verified source/dependency resolution, independent extension discovery, and Markdown text import on OMP 18.5.0; the pi loader remains deferred and unverified. **That loader smoke is automated**: the migration's loader and binding step (L2) is no longer a separate manual step. `tests/framework/deployment.test.ts` runs the isolated install's own loader against this repository's layout — the configured root's discovery, each thin entrypoint loaded alone and together (its shared source and Markdown text resolving with 0 errors), both extensions binding (connect-bot's binding included, which is where its declared `extensions/connect-bot/config.yaml` is read and validated), and the same-named pair that load-source mutual exclusion keeps apart — and it remains the automation precondition of the human acceptance round.

An extension's declared configuration file is resolved against the **extension repository root its assembly supplies** — the convention path `extensions/<id>/config.yaml`, overridable through `config.path` — so a run that expects connect-bot to load needs no particular working directory. Connect-bot's OMP assembly derives its repository root from its own module location (`import.meta.url` under `extensions/connect-bot/harnesses/`) and hands the framework that directory as plain data, which is what lets the same load bind from a user's project directory as from this repository. A relative declaration with no directory supplied — an assembly that names none — resolves against the process working directory, the behavior the framework had before that seam existed; an absolute `config.path` is used as declared either way. Record the tested repository revision, dependency lockfile, and harness versions instead of an independently released framework version. Simultaneous activation of an extension's original and replacement is prevented by load-source mutual exclusion (an explicit-only root during development/acceptance, and removal of the superseded implementation before the permanent cutover).

Source co-location supports direct editing and debugging but does not establish hot reload or breakpoint mapping. The first release promises only whole-process restart; hot reload is deferred, so verification of reload/cache visibility is deferred with it. One source tree does not create shared in-memory State across harness processes. These are deployment prerequisites, not a claim that the source layout or framework has been implemented.

### Load-source mutual exclusion

One extension's original and replacement implementations must never be discovered into the same process. The mechanism is **load-source mutual exclusion**, and the alternatives are rejected on the fixed baseline:

- **Name deduplication — rejected.** `discoverExtensionPaths` does not deduplicate by extension name: pointing discovery at both the original and the replacement returns both paths, each carrying the extension name (`codebase-tools`, and `connect-bot` for the second extension's pair), and binding that set binds both factories. Name matching therefore cannot keep them apart, and nothing relies on it.
- **`disabledExtensions` — rejected.** It matches `extension-module:<name>`, so disabling the one extension name would disable the replacement as well.
- **Harness identity probing — rejected.** No source, path, or identity probe runs at load; the loader does not distinguish implementations with the same name.

What is used instead: development and acceptance run explicit-only (`--no-extensions -e <repo>/entrypoints/omp` with a temporary agent state directory), and the permanent cutover — performed by the user only after acceptance — removes the superseded implementation *and* adds the new discovery root before restarting. Until that cutover the original implementation keeps its own discovery entry, so the two never meet in one load set. Such a run needs no particular working directory: connect-bot's declared configuration file resolves against the repository root its assembly derives from its own module location, whatever `--cwd` names. `tests/framework/deployment.test.ts` starts the real CLI with `--cwd` in a directory outside this repository — carrying no `extensions/connect-bot/` in one run and a decoy file at the convention path in another — and observes the extension register its command either way.

**Only a whole-process restart takes effect.** The discovery root is not swapped inside a running process, extension module caching/reload is not a switching mechanism, and the first release promises no hot reload. The tested deployment seam (discovery, out-of-directory imports, each extension's binding, mutual exclusion) is recorded in the framework suite at `tests/framework/deployment.test.ts`, against the isolated install.

## Harness-qualified capability: subagent State inheritance

Decided on 2026-10-04, aligned with decisions 03/04 on 2026-10-07 and with the per-field State lifecycle of decision 02 on 2026-10-07; the decided contract is implemented in the first release, and coverage of the exercised shape is not a certification of native behavior outside it. Inheritance is a per-field axis: the default `none` makes a subagent read the field's declared default, and a field that declares `follow` makes it read the owning main session's current activation value live. The first release implements exactly that following for the field that opts in — codebase-tools declares `follow` — with independent branch-derived injection progress in each session. Other inheritance strategies are deferred until there is a concrete need.

| Harness path | First-release scope |
| --- | --- |
| OMP built-in subagent path | **Targeted for the first release.** Decision 03 runtime-exercised the built-in subagent path (identity, factory rebinding, inheritance, independent init); decision 04 decided the owner contract (nearest main ancestor, `parentId` + `AgentRegistry`, live following), which decision 02 made per-field and opt-in (`follow`). The first release now implements that resolution and the read-only following for a field that declares `follow`, exercised against this path; the multi-main disambiguation stays deferred (see the limitation below). |
| pi | **Deferred.** The first release ships no pi adapter, so pi subagent State inheritance is unimplemented; no pi subagent implementation is selected or integrated. |

This does not declare pi incapable of running subagents. It limits the framework's supported integration paths. Extension loading, State inheritance, and MCP availability are separate concerns. The framework owns the State contract and its harness mapping, not a replacement subagent scheduler or MCP implementation.

A future pi adapter may explicitly accept codebase-tools operating in a pi session without inheritance, subject to its other required contracts; the first release ships no pi adapter, so this is a deferred policy rather than first-release behavior. When implemented, notify the user once at the extension's first activation in that session that the framework will not propagate its activation to subagents; the notification transport is the extension UI notification channel (a stderr line when no UI is available) and the notice is never inserted into model instructions or conversation history. This is not a general permission to ignore missing required capabilities, and required role and insertion semantics are not relaxed.

### First-release limitation: one main session per process

Owner resolution walks the harness's own facts — `ctx.agent.parentId` plus the injected `AgentRegistry` — up the parent chain to the nearest top-level main session, so a subagent follows the value its owner holds *now*, read-only, level by level through nesting, and resolves to nothing when that chain leaves the process. That resolution is unambiguous only while one main session exists in the process.

Two main sessions in one process — an ACP/cmux/embedded host, or a subagent that outlives `/new` — are **not supported** in the first release: the registry then holds more than one main agent, and a resolution may name the wrong owner. This is a recorded limitation and explicitly **not** a passing result: no test in this repository asserts behaviour for that shape, and a green suite for the supported shape says nothing about it. Disambiguation (a parent-side `spawnKey → ownerKey` edge recorded at `before_subagent_spawn`) remains on the [backlog](semantic-extension-framework-backlog.md).

When no owner resolves at all, the affected session stays off, its activation cannot be toggled, and the adapter reports that once per binding on the non-model channel (stderr when the session has no UI). That notice is best-effort and refuses nothing: the extension stays bound either way.

### Subagent mechanism evidence and its limits

Source observations checked on 2026-10-04 against the local checkouts; these do not certify installed-harness behavior:

- **OMP rebinding is not business State copying.** [`bindExtension`](../../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/loader.ts#L439) creates an extension/API binding and runs the prepared factory; [`bindPreparedExtensions`](../../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/loader.ts#L491) creates a new harness for the binding set. OMP's [extension guidance](../../../oh-my-pi/docs/extensions.md#L1048) explicitly says module globals are shared by parent/child bindings, while session-specific state belongs in the factory closure or persisted session entries. This explains how shared activation and independent injection progress can coexist; it does not define arbitrary extension State inheritance.
- **Use identity, not depth alone.** [`ExtensionAgentIdentity`](../../../oh-my-pi/packages/coding-agent/src/extensibility/extensions/types.ts#L464) provides `kind: "main" | "sub"`, `id`, `name`, `depth`, and optional `parentId`. Its comments explicitly allow subagents at depth zero. Mapping this identity to a State owner still belongs to the framework adapter; a process-global variable does not encode that relationship.
- **The ordinary pi subagent example has a different process boundary.** The [example's arguments](../../../pi/packages/coding-agent/examples/extensions/subagent/index.ts#L300) include `--mode json -p --no-session`, and it [spawns a separate process](../../../pi/packages/coding-agent/examples/extensions/subagent/index.ts#L346). The example's process cannot inherit the parent's JavaScript module variable merely by importing the same source. This observation concerns that example, not every possible pi subagent implementation.
- **Do not conflate pi's experimental durable path with ordinary extensions.** The [durable harness](../../../pi/packages/durable/README.md#L3) is explicitly experimental. Its subagent implementation (historical source location: `pi/packages/coding-agent/src/experimental/durable/subagent.ts:34`; no longer present at that path in the current adjacent checkout) was observed creating a task-owned child conversation through durable interfaces. It is a distinct possible integration path, not evidence that a pi adapter supports inheritance (the first release ships no pi adapter).

## Meaning of the support list

This file owns harness/package version evidence and compatibility policy, not which tools an agent may call. The fixed supported record stays unchanged; normal startup no longer evaluates version membership, emits compatibility/version warnings, checks required native Interface availability or dynamically chooses a capability subset. The current decision is [independent compatibility verification](#independent-compatibility-verification), and the framework's former admission route has been cut over: no production module declares a supported-version list, publishes a version notice or judges a capability surface at binding (2026-10-13; that cutover handed off the residual independent-verification summary, the human checks and the manual switch/rollback checklist as human work, never auto-certified).

The first release requires strict history preservation: no mutation or reordering of existing conversation entries, and no alteration of their history-derived request content. Request-context filtering, even of the extension's own earlier messages, is deferred. It permits new messages to be appended through the harness's normal recording path; once recorded, they receive the same protection. Non-persisted request contributions are not included in the first release, so their placement remains undecided. Mechanism availability in the table above does not by itself establish policy compliance.

### Integration completeness is a separate stage

Static extension↔adapter completeness is documented in [static integration check](integration-check.md):
`check:integrations` derives demand from source and compares actual adapter bindings and reachable
delivery construction, while `generate:integrations` only creates missing assembly references to implementations.
Neither command installs a harness, reads verification reports, executes extension code or establishes
behavioral correctness/version support. Conversely, the version and behavior checks in this document
do not establish adapter structural completeness. The former two-sided subagent arrays and manual
supply catalogs are removed.

Normal startup never invokes those commands or consumes their results. User notices, feature
availability, accounting and extension loading are unchanged. Conditional pi child integration is a
structural supply status, not a runtime probe for provider presence, successful child loading or
connection health.

### Independent compatibility verification

Confirmed old-to-new ruling: assembly Q10a and Q19 (2026-10-13) — the user required taking the verification stage out into an independently runnable script (or another independently executable form) producing a report, and adding no verification logic beyond business needs at normal startup; Q19 confirmed the resulting organization. Former policy evaluated installed-version membership during execution, warned about unlisted versions, and checked required native Interface shape at binding. The user explicitly replaced this with independently runnable verification and reports so normal startup carries no compatibility verification unrelated to business.

- Development defines the complete contract needed by an extension/harness integration; the adapter and harness-specific implementation must satisfy it before support is advertised. Source-derived contract demand is verification input, not a runtime switch or fallback route.
- An independent entrypoint checks declared/implemented interfaces and exercises actual framework contract and extension integration/behavior scenarios on the selected harness; checking method existence is insufficient semantic evidence. Reuse the existing candidate script/dock rather than building a parallel verifier.
- The report names exact harness version/revision, framework and extension source revision, dependency version/lockfile and environment; it records executed scenarios and passed/failed/unverified coverage. A missing credential, skipped UI, shape-only network fixture or absent platform test is unverified, not full passing. A pass is scoped to that combination and coverage, never a guarantee for later source or harness changes.
- Only complete verification of the declared supported scope, followed by explicit maintainer support declaration, establishes support. A narrow framework alarm alone cannot do this; final verification coverage, host patch revision and cutover belong to the acceptance decision (resolved 2026-10-13): patch the minimal public Viewed-session outlet on the existing supported baseline first, freeze the exact revision/artifact, run the split verification, and keep the support record unchanged until the maintainer declares support.
- Normal startup performs necessary configuration handling, creation/binding and business initialization/error handling, but does not check harness compatibility/native capability shape or version membership, dynamically negotiate partial features, execute probes, invoke the verifier automatically, or read its report as a startup gate.
- This does not remove input/configuration validity or business error handling, does not fabricate values when observations are unavailable, and does not silently upgrade the supported baseline. The migration clean-cut the old production admission path and migrated its meaningful checks to independent verification (see below).

The approved policy is published and implemented: the former startup admission route — version membership, the unlisted-version notice and the required-semantics refusal — is gone from the framework source, and the checks that were meaningful now live in the independent verification (the dock suites on the isolated harness, and the candidate script's record). Old implementation observations in this record are historical evidence only and cannot override this topic.

## Compatibility rules already agreed

- Common framework behaviors must be satisfiable across all declared supported harness targets, possibly through different adapter implementations. Additional harness-qualified framework capabilities are permitted with explicit support conditions and visible absence; first-release subagent State inheritance targets OMP, not pi.
- Required contracts must be satisfied in development/integration and demonstrated by independent verification before the matching extension/harness combination is declared supported. No partial runtime capability negotiation or silent semantic weakening is allowed; native capability/refusal checks are not added to normal startup. Missing observations or business failures are handled by their existing operation rules, not mistaken for incomplete implementation.
- Version claims must retain their evidence level. Source inspection, executable startup, and exercised behavior are distinct.
- Cross-harness semantic contract scenarios are regression alarms: a failure signals an incompatibility to investigate, while a pass never automatically approves a harness version. A framework maintainer reviews the changed harness source and/or further test evidence and explicitly decides whether to declare support.

## Decisions still open

- Support for a new harness (for example pi) without silently weakening already-established common contracts; the first release ships no pi adapter.
- Cross-harness prefix stability and a system-prompt stability policy.
- Shared-file concurrency, configuring State persistence media, request-only contribution placement, and the remaining control kinds (all deferred beyond the first release).

The historical first-release supported record remains 18.5.0 (@9348320) + Windows x64 + Bun 1.4.2 with only its recorded provider/evidence scope. Current startup policy is the independent-verification revision above, not the old warn/continue or required-semantics refusal route. A candidate framework-suite pass does not certify an extension, promote a version or certify newly patched Viewed session support. Final patched revision, report coverage and formal cutover remain with the acceptance decision; the stored baseline is not automatically changed by this planning publication.
