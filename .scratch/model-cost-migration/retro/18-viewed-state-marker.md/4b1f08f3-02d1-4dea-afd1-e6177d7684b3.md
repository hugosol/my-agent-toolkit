## 1. 仓库没有任何 guardrail（lint / CI / hook）——最高

【事实】本次恰好撞到该类规则的实例：`tests/harness-dock/viewed-marker.test.ts` 旧代码把外部 RPC 帧 `frame.widgetLines as readonly string[] | undefined` 直接断言成合法数组，而宿主把「清空」编码成缺省属性/空值——这个断言既不校验也不报错，我用了两轮打印才排除它的干扰。同类断言写在临时诊断里时，是会话侧规则先提示、而不是任何仓库检查拦下的。

【事实】复发主题：`.scratch/model-cost-migration/retro/` 下 04、05、10、14 四份既有复盘都已引用 `builtin-defaults`。也就是说这条不是本票独有，而是反复出现的环境缺口。

## 2. dock 帧断言缺「屏障 + 观测点」约定，harness 无 settled 原语

【事实】本次最强的一条断言（「子 binding 绑定后 Owner 仍渲染两行、且全程不被清空」）第一次加上去时是**假通过**：`markerRenders()` 在 `prompt()` 返回时读取帧列表，而真实宿主的一部分发布（子会话迟到的事实变更）还没到；同一个场景用 scratch 驱动 + `sleep` 就能看到清空帧。最终改成三步才稳定：delegation 后再跑一次 Owner prompt（把观测点推到「子 binding 已绑定之后」）、用 `request({type:"get_state"})` 往返做屏障、再断言 `rendered[rendered.length-1]` 与「窗口内无清空」。同一改动在故障注入下从「有时通过」变成「必然失败」。

【事实】`tests/harness-dock/session.ts` 的文件头只描述 start/prompt/frames/stderr/stop，没有一句关于 stdout 顺序/何时读取才完整；5 个 dock 测试文件各自实现 widget 帧读取（`detail-tree`/`model-cost-balance`/`model-cost-modes`/`viewed-marker`/`viewed-session-total`），本次的 `markerLines()` 只在其中一个文件里。

**建议**：

1. 给 `ControlledSession` 加一等原语 `settled()`（或 `waitForFrame(predicate)`），语义是「宿主已写出此前所有帧」；至少把「后续 request 的应答即可作为屏障，因为宿主单 stdout 有序」写进 `session.ts` 的类文档。
2. 把 widget 帧读取抽到 `tests/harness-dock/`（例如 `widgets.ts`：`widgetFrames()` + `widgetLines()`，把「清空」统一成 `undefined`，并校验帧载荷而不是 `as` 断言），5 个文件共用。
3. 在 dock harness 的文档里写明约定：**帧窗口断言必须在屏障之后取，且必须固定一个「只能由目标事件产生」的观测点**（本次即「子 binding 已绑定之后的一次 Owner 渲染」）。

## 3. 渲染/计数类断言可被「陈旧的上一次渲染」满足

【事实】故障注入轮里，我的新用例 1、用例 3 一开始仍**通过**：`lastRender()` 读到的还是上一次（绑定之前）的渲染，守卫提前返回、什么都没发布，断言因此满足。直到补上 `expect(double.widgets.length).toBeGreaterThan(before)`（即「必须发生一次新发布」）才三条同时失败。

**建议**（review 期判断类，落 `CODING_STANDARDS.md` 或 tests 文档，由 reviewer 执行）：凡是断言「某状态被重新投影/重新发布/被刷新」，除内容相等外必须同时观察一次**增量**（发布次数、widget 调用数、帧序号），否则该断言可能被陈旧状态满足。附本次正例与反例各一行，便于 reviewer 直接引用。

【推断】这条不只适用于 marker/dock：任何「上游事件应当引起一次下游写入」的断言都有同样漏洞。
