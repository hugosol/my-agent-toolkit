## 1. 仓库没有任何 lint/guardrail，未绑定方法调用只能靠真机集成测试兜住（最高）

**事实**
- `package.json` 的 scripts 只有 `test` / `test:dock` / `test:framework` / `test:codebase-tools` / 三个 `smoke:*` / `verify:omp-candidate` / `typecheck`；**没有 `lint`**。
- 仓库内无 `eslint.config.*`、`biome.json`、`.oxlintrc*`；无 `.github/**`（无 CI）；无 `.husky/**`（无提交钩子）。`typecheck`（`tsc --noEmit`）是唯一静态检查，而它抓不到「方法被摘下后调用」。
- 本轮最贵的一次故障正是它：适配器桥里写了 `const notify = manager.onSessionNameChanged; … notify(() => …)`。真实 harness 的 `SessionManager` 是类实例、成员读写 `#` 私有字段，摘下调用即 `this` 丢失 → `TypeError: undefined is not an object (evaluating 'this.#sessionNameChangedCallbacks')`，抛在适配器的原生 `session_start` 钩子里 → 框架再也没看到该会话的 start → 扩展永不初始化 → 一个字节都不保存。
- 代价：整套 dock 用例先全红（每例 ~23s 超时、错误信息只说「没有出文档」）、一次关桥对照跑、一次开桥复现跑、两轮生产代码内临时埋点与两次临时 diag run，合计至少 5 次 ~25s 的真实宿主运行与十余次工具调用才定位到根因。同一错误在最早的探针 fixture 里也犯过一次，害我一度误判「宿主从不发改名通知」。
- 单元 seam 帮不上忙：`tests/framework/session.test.ts` 的 OMP api double 把 `sessionManager` 建成**箭头函数对象字面量**，摘下调用与正常调用在那里毫无区别。（本轮我为新用例给该 double 补的 `onSessionNameChanged` 同样是箭头属性。）

**推断**：error 的私有字段名与兄弟检出源码一致，说明抛出者确实是真实 `SessionManager`；harness 没有把该 hook 异常报到 dock 能看到的任何通道（stderr 空、失败运行的 harness 日志里也没找到记录，见「未验证」）。

**建议**
- 加一条 lint 步骤（`unbound-method` 类规则）并挂在 pre-commit 或 CI 上。这是**机械违规**，不该由 reviewer 或真机集成测试承担；仓库当前「零 guardrail」本身就是发现，而不是中性默认值。
- 次级防御：把该 double 的 `sessionManager` 建成类实例（或明确写下「double 只支持箭头函数成员，类实例语义须在 dock 验」），让单元 seam 也能复现这类绑定错误——本轮它只能在 25s 一轮的 dock 里暴露。

## 2. dock 失败信息把诊断材料藏起来，且失败即销毁现场（高）

**事实**
- `savedDocument()` 失败时抛 `no consumption document the case expects was published at …: undefined`，**不带** `session.diagnostics()`（后者本已包含 stderr、argv、最后若干 RPC 帧）。
- `finally` 里 `runRoot.dispose()` 删除整个 run root，于是 harness 自己的日志（`user-home/.omp/logs/omp.<date>.<pid>.log`）与 session JSONL 在失败后不复存在——本轮我是靠临时写一个 diag 测试并保留 run root 才找到日志目录的。
- 定位那次根因时，可用材料是「子进程 stderr」，而它只能靠临时在生产适配器里 `try/catch + process.stderr.write` 才流到 dock 捕获的通道上。

**建议**：把 `session.diagnostics()` 并入该错误；失败时打印/保留 run root 与 harness 日志路径（`listRunArtifacts` 已存在）。这一条能把本轮数轮 25s 的盲试压成一次读错误信息。
