## 1.（高）仓库没有仓库级 guardrail：无 lint 脚本、无 CI、无 pre-commit，且 `check` 命令不存在 **[事实]**

`package.json` 的 scripts 只有 `test` / `test:dock` / `test:framework` / `test:codebase-tools` / 三个 `smoke:*` / `verify:omp-candidate` / `typecheck`；根目录无 `.github/`、无 `biome.json*` / `eslint.config*` / `.husky*` / `lefthook*` **[事实，本轮 `ls` 确认]**。也就是说 `bun test` 与 `bun run typecheck` 都要靠 agent 自觉调用，没有任何地方会在提交或 CI 上兜底。

本轮 harness 自带的规则至少拦下三类机械问题（都已发生并被要求返工）：`ts-no-test-timers`（我在 dock 套件里写了 `Bun.sleep(20)` 轮询）、`ts-promise-with-resolvers`（测试里用 `new Promise(resolve => …)`）、`ts-no-inline-cast-access`（`(document as {harnesses?…}).harnesses` 式取字段）。这三条都是**规则形式**、在工具调用时才提示，等于把检查放到最贵的位置（写完再看） **[事实]**。

建议（按成本递增）：
- 立刻：`"check": "bun run typecheck && bun test"`；把 `ts-no-test-timers` / `ts-promise-with-resolvers` / `ts-no-inline-cast-access` 对应到仓库自带 linter（biome 或 eslint 任一，规则配置一次即可），让同样的拦截在写文件时就发生。
- 再加一个 CI job（或最少 pre-commit）跑 `bun run check`，并让 `bun test` 的失败名默认落到 `.cache/full-suite.log`（见第 5 条）。

## 2.（高）`ompAdapter` 必须在模块层创建一次的隐含契约，只在 framework 一处函数注释里，三个装配各写各的 **[事实 + 推断]**

本票几乎 2/3 的真实宿主调试成本都花在这里：`extensions/model-cost/harnesses/omp.ts` 原本在 `export default function modelCost(pi) { ompAdapter(MODEL_COST, {…})(pi) }` 内创建 adapter，即**每个 binding（每个 Session／子代理）新建一份 adapter 与业务 runtime**；framework 只在“自身是 Owner 的 Session”节点跑初始化，于是子代理那份 runtime 从未 `load()` baseline，其请求静默不入账（无 notice、无记录、无异常）。本会话为此跑了 4 次真实宿主（其中 3 次把临时 `console.error` 诊断**改进了测试文件**）才定位 **[事实]**。

契约本身是写在代码里的：`framework/adapters/omp.ts` 的 `ompAdapter` 文档说 “An assembly that wants the instance to be the process's creates its adapter once, at module load, as `entrypoints/omp` does” **[事实]**。但对照三个装配：`extensions/codebase-tools/harnesses/omp.ts` 用 `const bindCodebaseTools = ompAdapter(CODEBASE_TOOLS);`（模块层，正确），`extensions/connect-bot/harnesses/omp.ts:186` 与 `extensions/model-cost/harnesses/omp.ts`（修改前）都在导出函数体内创建 **[事实]**。三个兄弟文件给出两种写法、没有一个本地注释指出哪种是承重的，而“子代理 binding 永不初始化”这条会放大错误的 framework 事实只写在 `framework/behaviors/lifecycle.ts` 头部 **[事实]**。

建议：
- **机械检查优先**：在 framework 侧加一条永久测试——“同一 `ompAdapter(def, …)` 的结果被两次 bind，业务工厂只被调用一次”（用 port double／假 `pi` 驱动即可，本会话未实现，**[推断]** 可行）；这条检查不依赖任何扩展的自觉，且正好覆盖本次缺陷的类。
- 或退一步：给 `ompAdapter` 调用点加 lint 规则（必须位于模块顶层），并在三个 harness 装配的本地注释里点明“模块层创建一次＝进程单例，写在函数里＝每 binding 一份”，把契约放到犯错的位置而不只在被调用方。

## 3.（中高）dock 捕获端点的脚本约定脆弱，且失败是静默的 **[事实]**

`tests/harness-dock/turn-facts.test.ts` 建立了两条约定：`messages[1]` 是会话开场、`messages.length === 2` 代表该会话首个请求。本票沿用后，官方 `deepseek` provider 的请求体里**有两段 system 消息**（`["system","system","user"]`，实测捕获），于是脚本永远不匹配 → 端点回 prose → 委派没发生 → 只有 1 次请求。表现只是一个 `Expected length: 5, Received length: 1`，没有任何线索指向索引假设 **[事实]**。修正为“首个 `role==="user"` 的消息”＋“尚无 assistant 消息才是首请求”后才正确 **[事实]**。

建议：把这条判断收进 `tests/harness-dock/capture-server.ts`（该文件正是注释 `respond` 脚本的地方），导出例如 `openingUserMessage(request)` / `isOpeningRequest(request)`，并让 `turn-facts.test.ts` 与新套件共用；同时在文档里写明“prose 兜底＝静默错脚本”，让下一个作者知道这类失败长什么样。

## 4.（中）port double 的 owner 语义陷阱：fixture 把子代理写成 Owner 会真的销毁实现 **[事实 + 推断]**

我在 S2 套件里用 `double.deliverSession(OWNER, { session: CHILD_A, event: { kind: "session_end", reason: "disposed" } })` 模拟子会话结束，结果 framework 认为“被服务的 Owner 结束了”，销毁了扩展实现，后续真实请求全部消失（一例红灯）。真实宿主里子代理的 delivery 解析为 `inherited`（同 key），只有 `owner.kind === "owner"` 才触达清理 **[事实：`framework/behaviors/binding.ts` 的清理条件 + dock 里 `ownerKind: ["owner","inherited","inherited"]` 的实测]**。

建议：`tests/framework/support/harness-port-double.ts` 的 `deliverSession` 在未显式传 owner 时**从 session facts 推导**（`kind === "main"` → `owner`，否则 `inherited`，同一 key），或在 `owner.kind === "owner" && session.kind === "sub"` 时直接抛错并给出解释。这既省掉每个 fixture 作者重写 `ownerOf()`（本票就写了这个 helper），也把“误建模＝真销毁”变成可读的报错。

## 6.（中）测试运行成本：全仓套件跑了两次，其中一次纯为拿失败名；缺少 `test:model-cost` 与日志化脚本 **[事实]**

## 7.（低）dock 断言失败时不自带现场，逼出“改测试打诊断”的习惯 **[事实]**

第一次 dock 失败只有 `Expected length: 5, Received length: 1`，捕获的请求体、stderr、文档一个都不在信息里，我只能**改测试文件**加临时 `console.error`（三次），且每次都担心留下残骸 **[事实]**。反面样板已经存在：本票新套件里的 `savedDocument` 会把观察到的文档塞进错误信息，`observedEventually` 会塞 stderr；`tests/model-cost/*` 的同类 helper 也如此 **[事实]**。

建议：把这条做法升格为 dock 套件的约定（例如 `capture-server.ts` 或 dock index 提供 `expectEventually(…, context)` 之类助手，或要求在断言消息里带 `session.stderr()`），并在 dock 的 README／模块头写一句“失败信息必须自带现场，禁止把诊断写进测试”。
