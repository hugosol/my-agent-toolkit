# 复盘：ticket 13「Codex 响应 headers 与独立额度窗口」retry 轮

范围：本 session 的 TDD 实现轮（`13-codex-windows-headersmd-2`），依据本轮实际工具调用与输出。父 session、其他票据、以及本轮之前的实现历史不在范围内。每条按严重度排列，分「事实 / 推断 / 未验证」标注，建议均未执行。

## 1. 仓库没有任何 guardrail：检查脚本存在，但没人自动跑（最高）

**事实**：`package.json` 里有 `test`、`test:dock`、`test:framework`、`test:codebase-tools`、`typecheck`(`tsc --noEmit`)、两个 smoke 和一个 verify 脚本；仓库根找不到 `.github/`（无 CI workflow），也没有 husky/lefthook 之类 hook，`git config core.hooksPath` 未设置。本轮 `git status --short` 有 102 项未提交改动——也不存在「提交时触发检查」这条路径。

**影响**：唯一保证「类型/测试没坏」的东西是每个 agent 自觉手动跑脚本。本轮有实例：新写 smoke 用了 `Array.prototype.at`，`bun run typecheck` 报 7 条 `TS2550`，全靠我主动跑才发现；若跳过，错误会静默留在共享工作区，并被后续票据继承。

**建议**：加一条最小 CI job（或 pre-commit hook）跑 `bun run typecheck` 与 `bun test tests/framework tests/model-cost tests/harness-dock`；若既有红挡住流水线，先按第 3 条显式隔离，而不是让流水线常红。

## 2. pinned install 的宿主源码与 host-patch 约定没有任何指针

**事实**：`AGENTS.md` 全文 11 行，只有三条指针（issue tracker / triage labels / domain docs），不含 `host-patches/`、`.cache/omp-baseline/`、`tests/harness-dock`。01 号票的 retro 已建议加 `host-patches/` 指针，本轮核实**仍未加入**。

**本轮的定位成本**：要回答「Codex 的响应事实从哪来」，必须跨四层读源码——`framework/adapters/omp.ts` 的 `after_provider_response` → `pi-coding-agent/src/sdk.ts` 的 `onResponse` → `pi-agent-core/src/agent-loop.ts` 的包装 → `pi-ai/src/utils/provider-response.ts`；还要确认 `openai-codex-responses.ts` 在**安装目录**（不是 checkout）里，并确认它属于另一个已安装包 `@oh-my-pi/pi-ai`——这个结论直接决定了 patch root 是 `node_modules/@oh-my-pi` 而不是包自身根目录，从而决定了物化器的设计（多包 patch root）。

**建议**：`AGENTS.md` 加一条导航指针，例如「宿主行为问题在 pinned install 前缀里读；host patch 一律放 `host-patches/<pkg>-<ver>-<concern>/`，含 `patch.diff`+`record.json`+README，并用共享物化器 + 薄 harness 物化」。再把「provider 事实管线」这一条链落进 `tests/harness-dock` 或 `host-patches/` 的 README，省掉每次重推四层。

## 3. 既有红只存在于某张票的 scratch 证据里，机器不可判

**事实**：`bun test` 全仓 752 pass / 4 fail（2 例 `harness-dock/baseline.test.ts` anchor 漂移 + 2 例 connect-bot 真实面板 P23/P25），这 4 条在 12 号证据里记过；但仓库里没有「已知失败」清单或指向它的文档。本轮为了确认那 2 例 connect-bot 就是老红，额外跑了 `bun test tests/connect-bot`（56.4s）。

**影响**：每张票都要重付「这是我弄坏的吗」的判定成本。本轮还出现一次近失：整目录 dock 运行里 `session-recovery` 超时，我第一时间怀疑是自己的改动（见第 4 条）。

**建议**：二选一——修/隔离它们（`test.skip` + 链接原因，让「绿即绿」），或在 `AGENTS.md` 指到的文档里维护一份带**测试名**的「已知失败」清单，`bun test` 输出里的红都能直接对上号。

## 4. dock 目录级并发负载 vs 邻居的固定墙钟等待

**事实**：把 smoke 拆成 4 个真实会话时，`bun test tests/harness-dock` 连续两次都是 3 fail，多出的一例是 `session-recovery.test.ts` 重启用例在 20s 内没等到第二进程的 save；把 smoke 合成「一次会话三份报告」（3 个真实会话）后，整目录回到 2 fail（只剩 anchor 红）。

**判定成本**（全部为本轮真实耗时）：整目录 3 次（95.9s / 99.8s / 74.5s）+ 排除本文件 1 次（71.1s）+ 两文件对照 2 次（17.6s / 17.9s）≈ 370s，外加多轮推理。

**推断**：该用例等待固定 20s，而 dock 目录并发跑 15 个真实 CLI 会话文件；并发量一变就能把它推过线。

**未验证**：无法排除还有别的机制（例如 Windows 下文件替换竞争）；我没有去改那张票的等待预算。

**建议**：dock README 写明「目录级运行会并发起真实 CLI 进程，重文件可能饿死邻居的固定 deadline」；提供一条串行入口（如 `test:dock:serial`），让 agent 能把「负载」与「行为」分开判定；该用例自身（10 号票文件）改成由与负载无关的信号驱动。

## 5. 宿主 patch 的 TypeScript 谁都不编译

**事实**：`tsconfig.json` 的 `include` 是 `framework, extensions, entrypoints, tests, scripts`；被 patch 的 `pi-ai` 源码既不参与 typecheck 也不参与打包。本轮 patch 加了 2 个可选参数与 1 次调用，其正确性只靠 dock smoke 在运行期验证。01 号票的 retro 记过同类问题。

**建议**：物化器里加一步最便宜的类型检查（对补丁后文件跑 `tsc --noEmit`，或 `bun build` 一次），或至少在 patch README 明写「该 artifact 只有运行期验证，没有静态检查」。

## 6. 观察行的语义没写明：一次变化会重绘多次

**事实**：本轮从 fixture stderr 里看到，一次报告后 `quota`/`estimate` 行各重复出现 4 次（启动失败阶段 3 次）。合并用例时我按位置断言 `readings[1]`，结果失败；为看清真实行，临时在测试里插入 `await Bun.write(".cache/…", stderr())`，看完再删掉。

**影响**：位置断言是隐形的坑；「临时改测试来打日志」有忘记还原的风险（本轮还原了，但这是靠纪律而非机制）。

**建议**：(a) fixture 文档加一句「观察行是**重绘**，不是事件：断言用集合或首/末项，不要用序号」；(b) 提供文档化的调试开关（如 `OMP_DOCK_DUMP_STDERR=1` 在失败时打印子进程 stderr），把「看输出」从改代码降级为设环境变量。

## 7. `tsconfig` 是 ES2020，而运行期是 Bun

**事实**：`target: ES2020` 让 `Array.prototype.at` 报 `TS2550`（本轮 7 条），但 Bun 运行期支持它。修法是改回索引取值，一次编辑 + 一次 typecheck。

**建议**：把 `target`/`lib` 提到 ES2022（或 ESNext），一次性消掉这类「运行时可用、类型检查拦下」的假红。

## 8. 「不要自行验证」与票据/技能要求冲突

**事实**：本轮任务的顶层指令写「NEVER verify your changes unless your assignment explicitly instructs it」，而票据正文与 tdd skill 明确要求跑检查并汇报命令结果；我的处理是跟票据走。

**建议**：把例外写进规则本身（「除非票据/任务明确要求」），或在任务模板固定一句「本票要求运行 X/Y/Z 并汇报结果」，消掉每次运行的判断成本。

## 9. 下游契约在别的票里，而隔离规则禁止读那张票

**事实**：retry 要求「至少两份 report 驱动已有 14 估计 sourcepair」，同时要求不读其他票据文件。我通过给 14 号 peer 发消息拿到确切规则（同一响应六个 header、50pp/上行/未饱和门槛、比值写盘节流），并据此设计断言。

**推断**：协调通道是有效的（这条值得保留），但代价是一次往返；我最终断言的是 peer 口述的契约，没有独立核对代码或票据。

**建议**：handoff 引用下游**接口**（具体文件或断言）而不是票号；或明确允许只读打开下游票。

## 10. 词汇/ADR 指针存在，但票据正文没点名文件（低）

## 值得保留的部分

- **隔离装置**：每轮都是独立 prefix + `createRunRoot` 临时目录，全程未触碰正式 OMP、未用真实凭据；这一条是本轮能安全跑真实 loader/RPC 的前提。
- **patch 冻结模式**：`patch.diff` + `record.json`（前后 hash）+ 物化器校验，成本低（首次物化 8.75s，重建后 11.1s），并且让「补丁真的生效」有可复核证据。
- **peer 协调**：第 9 条里的往返虽然是一次成本，但它避免了按猜测实现下游契约。
