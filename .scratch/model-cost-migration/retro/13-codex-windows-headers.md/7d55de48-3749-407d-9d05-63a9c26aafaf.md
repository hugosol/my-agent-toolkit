## 1（高）宿主能力事实在实现**之后**才被发现，整条运行期路径因此空转

**事实**：本票验收项要求「真实 adapter 接入使用正常 Turn headers」。我先把业务模块、runtime 接线、S2 用例、捕获端点、dock fixture 全部写完并跑绿，然后用真实隔离宿主跑 Codex 模型，才发现基线根本不发这条事实：Turn 交付为 `unavailable: ["HTTP response facts"]`。此后才回到 OMP 源码核对（`notifyProviderResponse` 的调用点只在 `openai-completions`／`openai-responses`／`anthropic`／`pi-native-client`／factory-droid Gemini；`openai-codex-responses` 既不调它也不调 `onResponse`）。从「发现」到「定位到宿主源码」又花了约 10 次 grep/read。

**为什么昂贵**：这条事实决定了「P39 的运行期一半在本基线不可达」，属于该在写第一行代码前就落地的判断；放在最后发现，等于让一整轮实现与文档措辞（H2、证据）都建立在一个错误前提上，并且直接改变交付结论。

**建议**

- 在仓库 `AGENTS.md`（或本迁移的导航文件）加**导航指针**，一行两分支：
  「宿主能力事实与宿主补丁：`framework/docs/harness-support.md`（能力差异表：本 OMP 基线在**各 provider 路径**上报告／不报告什么）与 `host-patches/`（已批准的宿主最小补丁先例）。」
- 让**前置票的证据资产**声明逐 provider 路径的覆盖：本票只依赖票 05，而 05 的证据资产里 `providerRequestId="capture-1"` 全部来自 chat 路径，从未说明「Codex 路径未交付 HTTP 事实」。一句话的「本票验证了哪些 provider 路径、哪些没有」即可让下游票在开工前判定前提是否成立。
- 验收项若依赖某条宿主事实，建议在票面加一个**前置检查步**：「先跑一次隔离真实宿主，确认该事实确实被交付；未交付则报缺口，不进入实现」。

**未验证**：若当时有第三方通道（如 OMP 会话状态里已存在的 rate-limit 窗口）可用，本票无需宿主补丁——我只查了扩展 API 面（`ExtensionContext` 成员），未穷尽其他宿主出口。

## 4（中）dock fixture 的约定没有文档，观察通道是重新发明的

**事实**：本票需要观察生产 runtime 的只读结果，而现有 fixture 只覆盖 Turn/Round/Session 事实。我从 `tests/harness-dock/fixtures/turn-facts/entrypoint.ts` 反推做法，自己造了 `fixtures/codex-quota/entrypoint.ts`（用 `ompAdapter` 绑定生产 definition＋runtime，把只读结果与每个 Turn 的 HTTP 事实有无各打一行 JSON 到 stderr，再让用例解析 stderr）。同时给 `capture-server.ts` 新增 `responseHeaders` 才能让端点把 `x-codex-*` 挂在真实响应上（端点原本只支持 `balance`／`usage`／`respond`／`failureStatus`）。

## 5（中）自动化门禁的范围与信号强度未被记录

**事实**：仓库有 `bun run typecheck` 与 `bun test`（并已验证 typecheck 真会失败：注入一行类型错误 → TS2322／exit 1）。全仓 `bun test` 本次为 725 pass / 4 fail，4 个失败与本票无关且在改动前即存在（2 个 `harness-dock/baseline.test.ts` 与本机 `oh-my-pi` checkout 锚点不符、2 个 connect-bot 真实面板用例）。我执行过 `tests/model-cost`＋`tests/framework`（511 pass）与 dock 相关 5 文件（16 pass），全仓运行在预算末尾才拿到结果。

**未验证**：本会话从未查看 `.github/`／hooks，因此**不能断言**仓库是否有 CI／pre-commit 在跑这两个命令。

**建议**

- 若确有门禁：把「4 个已知失败的白名单／原因」写进门禁文档，或修掉 sibling checkout 锚点，否则 `bun test` 的输出永远是「4 fail」，信号被钝化。
- 若无门禁：这是本仓最大的自动化缺口——`bun run typecheck && bun test` 是现成命令，接一个 CI job／pre-commit 即可覆盖本次唯一真正的机械风险（类型与跨票调用方迁移）。
- 另：全仓 `bun test` 被重定向时整段缓冲（我的 `.cache/full-suite-13.log` 在结束前只有 1 行），中途查日志没有信息量；要监控进度需用 `tee` 或 per-file 输出。建议在一条注释里写明「全仓运行约 3–4 分钟且输出缓冲」。

## 6（低）本轮 TDD 的顺序是「先实现后补 red」，靠故障注入补偿

**事实**：本票是全新业务模块，我先把 `codex-quota.ts` 写完才写第一个用例；随后用 6 次定点注入证明用例敏感（±5% 带失效 1 fail、去 provider 门 1 fail、缺失改为清空 3 fail、reset 状态分支移除 3 fail、去 `started` 守卫 1 fail、去秒→毫秒换算 4 fail），全部还原后 15 pass。就证据强度而言可接受，但不符合 tdd 技能的 red→green 顺序。

**建议**：对「新建业务模块」的票，在票面加一行首个动作：「先在生产 seam 写第一个红用例（如启动查询的出站形态）」。这是把技能的通用要求落成本票可执行的第一个 tracer bullet 的最省成本方式。

## 7（低）跨票测试迁移会静默改变**早先票的证据数字**

**事实**：我的改动使 `tests/model-cost/provider-balance.test.ts` 出现 11 个失败（该文件的 access double 原本对任意 provider 都答同一份资料，而扩展新增了第二个 provider 查询），同票迁移后复原为 137 pass。票 12 的证据资产记录的是 `tests/model-cost` 122 pass。

**建议**：迁移行应顺手写明「本迁移使票 N 证据中的计数 X 变为 Y」，或在证据模板里注明「计数为当次运行快照」。同时本轮我已把该迁移行写进本票证据的文件表——可把它固化成模板要求。

## 8（低）票面把「行为」与「证据」混在一行，逼出解释成本

**事实**：如「运行期无 API TTL／兜底／轮询／切换额外查询；mock 与出站捕获验证位置交换、单窗、缺失和更新次数，真实 adapter 接入使用正常 Turn headers」——前半是行为、后半是证据要求，中间那句「mock 与出站捕获验证…」我读了两遍才确定它约束的是「无额外查询」＋「窗口规则」。

**建议**：票模板把每个验收项拆成 `行为：` 与 `证据：` 两半。纯格式改动，直接减少实现轮的阅读歧义。
