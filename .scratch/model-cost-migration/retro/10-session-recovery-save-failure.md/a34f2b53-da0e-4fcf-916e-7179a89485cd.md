## 候选改进（按严重度）

### 1. `bun test` 在干净机器上永远带 4 条固定失败（已知噪声），使「全仓绿」不可作为判据

- **事实**：本次三次全仓运行都是这 4 条；其中两条 `baseline.test.ts` 失败输出的是记录锚点与本机 artifact 的 sha256 差异；两条 connect-bot 失败是超时（20.2s／15.0s）。08、09、10 三张票的证据都被迫用一段文字解释它们。
- **影响**：每个 ticket 的验证都要额外解释噪声；真实回归与既有噪声混在一起；全仓运行白白花掉 ~35s 在必然失败的用例上；也直接导致 666/5 这类运行间差异需要额外排查。
- **建议**：
  - connect-bot 两条：`tests/connect-bot/support/omp-bot.ts` 已经知道如何解析真正的外部面板二进制（`OMP_BOT_BINARY` 或 sibling checkout 的 release build）。在解析不到时按该文件已承诺的风格**明确 skip 并打印缺失路径与构建方法**（`test.skipIf(...)`），而不是让 15/20s 的 fence 超时先落下。真实面板可达时仍照常运行，不降低互操作证据强度。
  - `baseline.test.ts` 两条：锚点比对依赖本机 sibling 检出与 artifact，属环境条件项；同样加条件（例如仅在检出存在且 `OMP_BASELINE_STRICT=1` 时断言，否则 skip 并打印当前 sha 差异），保留差异输出供排查。
  - 目标：干净机器 `bun test` = 0 fail，任何失败都值得看。

### 2. 仓库没有任何 guardrail，而本次恰好出现了「机械违规且审查也看不出」的情况

- **事实**：无 CI、无 hook、无 lint；只有 `typecheck`（本次跑过，exit 0）。本次出现三类机械违规：`sed -i` 单点编辑（违反硬规则）、inline-cast 成员访问、一次性小函数——前两类由 agent 规则文件事后提醒，第三类靠人工回看。
- **影响**：`sed -i` 这类违规**在最终文件里完全不可见**，diff 审查无法发现；规则提醒是「事后、不中断」，违规内容已经落盘。实现轮的 context 压力最大，靠实现 agent 自律维持机械标准正是审查/检查该承担的事。
- **建议**：
  - 仓库加一个 `check` 脚本：`bun run typecheck && bun test tests/framework tests/model-cost tests/codebase-tools tests/connect-bot tests/harness-dock`，并用 `.githooks/pre-commit`（或 lefthook）接上 `bun run check`（第 1 项做完后这才可能恒绿）。
  - 机械规则落成 lint：`ts-set-map`（静态字面表用 `Record`）、`ts-no-inline-cast-access`、`ts-no-tiny-functions` 这三条本由宿主 `builtin-defaults` 规则文件承载，能在 AST 上判定；给仓库配 oxlint/biome 的自定义规则（或最小化的 grep 级 hook）比留在 agent 提醒里可靠。
  - 宿主侧（超出仓库）：把这类 MUST 规则从「提示」改成**拦截**，至少对 `sed -i`／`perl -i`／原地写文件这类调用；否则规则只在违规之后出现，静默成本为零。

### 3. 隔离宿主的行为约束没有被记录，每张 dock 票都要重新踩

- **影响**：每张后续 dock 票（12／15／22／23／24…）都会重复这一段摸索；且踩错时症状是「用例超时/取消」，不容易反推到宿主规则。
