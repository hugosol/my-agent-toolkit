## 建议（按严重度）

### 1. dock 套件默认带红：兄弟 checkout 已离开记录锚点

**事实。** `bun test tests/harness-dock` 每次都有 2 个失败，全部来自 `baseline.test.ts` 的 `the checkout is at the recorded revision anchor` 与 `the run artifact stays byte-identical to the anchor for the recorded contract files`；它们比对的是 `../oh-my-pi` 的 `extensibility/extensions/runner.ts`、`types.ts`、`session/session-manager.ts`、`config/model-registry.ts`，与本票改动无关。本环境 `../oh-my-pi` 停在 `579da1d6…`，记录锚点是 `9348320c…`；仓库自己的 `viewed-session.test.ts` 注释已承认「checkout 本身已经前移」。

**代价。** 这是最贵的一类噪声：一个"套件本来就红"的仓库让 agent 每次都必须先花轮次判定"这是不是我造成的"，而在同一个套件里，真实回归会淹没在这两条恒红里。本次我为此额外跑了整目录套件并逐条核对失败内容。

**建议。** 二选一，改动都很小：把该 sibling checkout pin 到记录 commit（最符合该断言的原意），或把这两条锚点断言收进专用命令/环境开关（例如 `bun run test:anchor`，或仅在 `OMP_TEST_ANCHOR=1` 时断言），让 `test:dock` 成为干净信号。仓库已有 `verify:omp-candidate` 之类专用脚本可循。

### 2. fault injection 是流程硬要求，但仓库零支持；我的临时脚本既留下过未还原的源码，又给过一次假阴性

**事实。** `skill://tdd` 要求每条新断言做过针对性注入验证。仓库没有对应工具，我手写 python 单元执行注入：3 次脚本迭代 + 1 次定向重跑。其中：

- 第 1 次在 `subprocess` 启动 `bun` 失败（Windows 下 `CreateProcess` 找不到 `bun`），异常发生在还原循环之前，**`framework/adapters/omp.ts` 被留在注入态**；我事后单独检测并还原。
- 第 2 次因 `NoneType` 异常中断（该次有 `finally`，文件已还原）。
- 第 3 次对 "toolUse 不结束 Turn" 的注入用了 `replace(..., 1)`，锚点片段在文件里先出现在 `message_update` 处理器中，于是注入打在了错误的处理器上，结果报 `13 pass / 0 fail` ——**假阴性**；我是靠"计数可疑"才发现，随后改用唯一锚点重跑才得到预期失败。

**代价。** 这是本次唯一可能污染工作树的失误类别，而且两种失败模式都是静默的（留下变更 / 谎报敏感性）。

**建议。** 增加一个仓库脚本（如 `scripts/mutation-check.ts`）：接受 `{file, find, replace, command}`，强制 `try/finally` 还原，结束前用 `git diff --exit-code <file>` 自证工作树已复原，并在注入未命中（`find` 出现次数 ≠ 1）时直接报错。此项同时解决"锚点非唯一"和"异常即泄漏"两个缺口。

### 3. 仓库整体没有 guardrail

**事实。** 无 CI workflow、无 git hook；`typecheck` 与三套测试只是 `package.json` 脚本，没有任何机制自动跑。`tsconfig` 已 `strict: true`。

**代价。** typecheck/测试是本仓库唯一可自动化的质量门（且它们确实有效：我在本轮每次编辑后手动跑），未接线等于每个 agent 都要靠自律。

**建议。** 最小改动是 pre-commit hook（或一个 CI job）跑 `bun run typecheck && bun test tests/framework`；dock 套件因第 1 条与材质化成本可留在 CI 的独立 job。若担心 hook 拖慢本地提交，可只对改动路径跑 `typecheck`。

### 4. 宿主的 coding rules 只在违规之后才出现

**事实。** 本轮我在写入测试/实现后先后收到 `ts-no-tiny-functions`、`ts-set-map`、`ts-no-inline-cast-access`、`ts-no-test-timers`、`ts-no-return-type` 的注入式提示（来源标注 `builtin-defaults:*`，不在仓库内）。其中 `ts-no-tiny-functions` 明确导致我回头把 `bashToolStep` 内联、并调整了新写用例的结构。

**代价。** 这些规则大多是**机械可判定**的（一行函数体、`Record` vs `Set/Map`、内联 cast 成员访问、测试里真实计时器）。以"事后提示"形式存在，意味着 agent 一次只学到一条，且编辑已经落盘；对实现 agent（context 压力最大的一方）尤其不友好。

**建议。** 把可判定的规则落成仓库内真实 lint（本仓库尚无 linter，加一个 biome/eslint 配置 + `lint` 脚本，交给第 3 条的 guardrail 运行），失败在写入时或提交时出现；仅剩真正需要判断的规则留在规则文件里，并让 agent 在写代码前可读（AGENTS.md 一行指针即可）。

### 5. 已就绪的 codebase-memory 索引本轮使用 0 次，而 `read` 的"先大纲再重读"模式反而更贵

**事实。** 索引 `ready` 且在本 run 期间刚刷新过，但 151 次工具调用里 0 次 MCP；同时 38 次 `read` 中有多次是"读 >100 行文件 → 只得到声明大纲（正文以 `…` 省略）→ 再按范围 raw 重读整段"，例如 `framework/behaviors/turn-events.ts`、`tests/framework/turn.test.ts`、`framework/adapters/omp.ts`。宿主在 ticket 文本后追加的"优先用 memory graph"提醒读起来像样板文字，未被采纳。

**代价。** 调用图/调用者/符号大纲/片段这几类需求，用 `read`+`bash grep` 的组合要多花 1–3 轮；本轮的 `bash` 75 次里有相当一部分是 `grep -rn`、`sed -n`、`cat`、`wc -l`、`ls -R` 这类专用工具能替代的形态。

**建议。** 在 `AGENTS.md` 里加一行**按分支**的导航指针（不是泛泛的"优先 MCP"）：需要调用关系/调用者/跨服务路径 → `trace_path`；需要符号清单/文件大纲 → `get_file_outline`/`search_graph`；需要符号源码片段 → `get_code_snippet`；**字面串/正则/配置文本** → `grep`/`read`。认领这类工作前先 `index_status` 确认覆盖。

### 6. 真实隔离宿主的知识埋在 `.scratch` 资产里，且没有指针；脚本化模型技术靠试错换来

**事实。** 要写出本票的 dock 用例，必须先知道：`task` 工具在 RPC 宿主下是 batch 形态 `{context, tasks:[…]}`、`async.enabled=false` 才阻塞委派、`yield` 才终止子代理、以及"按每个 session 自己的 opening 消息（`messages[1]`）选脚本答案、`messages.length === 2` 才代表该 session 首次请求"。前三条事实写在 `.scratch/model-cost-migration/assets/omp-subagent-round-findings.md`，我是靠列举 assets 目录才找到的；第 4 条没有任何文档，我经历了 4 次探针运行才拿到正确的委派链，其中一次因为用字符串直取 user 消息内容（真实内容是带 `<system-reminder>` 前缀的 text block 数组）而**静默**变成"没有委派"的假成功。

**代价。** 试错本身很便宜（单次 dock run ~1.4 s），但"假成功"会让人写出错误结论；若没有第 4 条的第 4 步，本票的真实子/孙贯通就交不出来。

**建议。** 新增 `docs/agents/harness-dock.md`（或给现有 `docs/agents/*` 增一节）并在 `AGENTS.md` 的后缀指针里点名，内容只需四件事：隔离宿主怎么起、脚本化模型怎么按 session 区分、委派/工具怎么造、以及两个坑（首条 user 消息是 text block 数组；batch 需要 `context`）。这些是环境事实，属于"agent 自己看代码看不出来"的缓存型内容。

### 7. 同一 ticket 的 peer 身份与状态有歧义，被迫用 mtime 判活

**事实。** 我的 id 是 `05-actual-session-turn-factsmd-2`，roster 只列出 `05-actual-session-turn-factsmd`（标记 running），而该 peer 的 `agent://` 输出是一份**已完成**的报告，其 retro 记录 `tdd_status: completed`。为判断"是否有人在同时编辑我要动的同一批文件"，我不得不在动手前 `stat` 我准备编辑的文件 mtime，并读取 peer 输出与 retro json 交叉比对。

**代价。** 约 4 轮用于协调判断；更实质的风险是并发编辑同一测试文件（本轮没有实际冲突，但那是运气，不是机制）。

**建议。** 二选一：在派发提示里直接说明"本 ticket 是否已有/并行他在跑，你负责哪些文件"；或让 roster/history 暴露"最后编辑时间 / 文件租约"，让 agent 一眼判断活体而不是猜。

### 8. retry 指令措辞偏禁止式，缺少正面目标

**事实。** 本轮的 retry 段落几乎全部是禁令（"不要透传 native/ctx 或测试专用 dispatch"、"不要简单写未验证"、"不能以局部 adapter double 证明完整实际正常事实"），正面要求只在"独立 retry 补真实隔离主/子/孙 loader/RPC/local capture…贯通"一句里。

**代价。** 按 `writing-for-agents` 的 negation 讨论，禁令会把被禁行为一起拖进上下文；本次我确实花了一轮确认"native observer fixture 是否算透传 native"。

**建议。** 把同一要求改写成可观察的完成条件，例如"用一个直接订阅宿主 `turn_end` 的独立 dock fixture 记录该事件、并断言它落在两个 Turn 之间；production 与 framework 公共面不得新增任何宿主对象参数"。禁令只保留为无法正面表述的硬护栏。

### 9. 无临时测试目录约定

**事实。** 探索用的探针文件放在 `tests/harness-dock/__probe-subagent.test.ts`（因为它要 `import ./baseline`），我全程只用显式路径运行它，最后删除；它一旦与 `bun test tests/harness-dock` 同跑就会进入套件。
