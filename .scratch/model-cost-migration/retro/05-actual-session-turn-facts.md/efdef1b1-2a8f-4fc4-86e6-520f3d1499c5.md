## 发现（按严重度）

### 1.【高】文档行号锚点是手写维护的，本次公共契约变更使其大面积失效，且没有任何检查会发现

**事实**：`framework/docs/framework-capabilities.md` 用 `framework/core/protocol.ts#L<N>` 形式引用源码（本次统计：102 处、约 40 个唯一行号）。我把 `protocol.ts` 从 718 行改到 1075 行后，所有 `L≥126` 的锚点全部偏移（例：`SessionDelivery` 由 L126 变 L190，`SessionEventDelivery` L183→L255，`RoundDelivery` L252→L331，`HarnessPort` L621→L964）。我尝试用「按已写内容重建改动前文件 + `git diff --no-index -U0` 算偏移」自动修正，重建结果 722 行 vs 原 718 行、推得的映射在 `SemanticEvent` 处差 2 行，判定不可靠后放弃，只对本次改写过的行／新增章节给出正确锚点，其余保留旧值，并在 05 evidence 的「未验证／限制」里明确记录为已知缺陷。02 票的 evidence 同样记录了「the doc's line anchors for the files this round touched were resynced」——说明这是**每一票都要重复支付的机械税**，而且付错时文档会指向错误位置（比缺失更糟）。

**建议**：把锚点从行号改为**符号锚**（`protocol.ts#SessionFacts`），或保留行号但由脚本生成；并加一个**可执行检查**（例如 `scripts/sync-doc-anchors.ts --check`，或一个 `tests/framework` 用例断言「doc 里的每个 `file#L<n>` 处确实出现文档正文提到的那个符号」），漂移即失败。顺带在 `framework-capabilities.md` 的 "Maintaining this index" 一节写明锚点的生成方式。

**预期效果**：删除每票的机械税；文档不会再把 agent 引到错误行（本会话我确实因为读到过期锚点而多做了两次定位）。

### 2.【高】原生宿主命名空间没有一张可查的「符号清单」，只能跨 gitignored 安装与无关 `.d.ts` 拼凑

**事实**：本会话最大的探索开销在于确认 18.5.0 到底提供什么：可用钩子名（`before_provider_request`、`after_provider_response`、`message_end`/`message_update`、原生 `turn_start`/`turn_end`）、`ctx` 是否给 session name 与 model、usage 的 wire 形状（`prompt_tokens`/`cached_tokens`）、以及 `ReadonlySessionManager` 成员。为此我在 `.cache/omp-baseline/18.5.0/node_modules/@oh-my-pi/pi-coding-agent/src/extensibility/**` 与 `pi-ai`/`pi-catalog` 的 `.d.ts` 上做了十余次 `grep`/`sed`。**事实**：`framework/docs/harness-support.md#capability-difference-register` 记录的是「能力决策与策略」，不是原生符号清单；`framework/adapters/omp.ts` 的 `OmpSessionContext` 是框架自己的窄化声明，不是权威面。

**建议**：在 `harness-support.md` 增一节简短的「18.5.0 native surface inventory」（一张表：事件名与触发时机、`ctx` 成员、message/usage 形状，加一句「权威来源 = 隔离安装 `.cache/omp-baseline/18.5.0/node_modules/@oh-my-pi/pi-coding-agent/src/extensibility/extensions/types.ts`」），并从 `framework/README.md` 的布局表／adapters 段加一行指针指向它。

**预期效果**：下一个「接入一种新的宿主语义」的票先读一页表，而不是先做十几次 grep（本票至少省下 10 次调用量级的探索）。

**不是这条理由的旁证**：我一度怀疑 register 里 `../../../oh-my-pi/...` 这类相对链接是否失效；本次实际执行 `ls -d ../oh-my-pi ../pi` **有输出**（同级 checkout 存在），所以那些链接不是坏链接——此建议只针对「原生符号清单无处可查」。

### 3.【中高】仓库内没有 guardrail 运行 typecheck／tests，也没有 lint；机械规则只能靠宿主事后提示

### 4.【中】公共契约的机械迁移没有固定手法，本次靠一次性脚本，且有漏点

**事实**：`ExtensionImplementation.events` → `subscriptions: [{ scope, events }]` 需要改 6 个测试文件 + `extensions/connect-bot/harnesses/omp.ts` 共约 30 处；我用一段 Python 括号匹配脚本一次改完（成功），但在 `tests/framework/round.test.ts` 漏掉了「变量形式」的 `const events = {...}` + `factory: () => ({ events, commands })`，直到跑整套测试才发现（表现为 10 个用例失败、现象是 round handler 完全没触发）。**事实**：宿主的任务说明里把 `xd://ast_edit` 列为「结构重构优先」的工具，我这次没有用它。

**建议**：在 ticket 模板或 `AGENTS.md` 加一行约定——「公共 interface／成员名变更 → 用 AST 改写（`ast_edit`／ast-grep），改完全套 framework 测试」；并把「迁移调用方后跑一次整仓／整套 framework 测试」写成显式验收项。

**预期效果**：少一次「漏掉变量形式 → 10 个用例失败再回头找」的往返。

### 5.【中】并发 peer 在同一 checkout 上跑测试会制造与本票无关的失败，且容易被误判为自己的回归

**事实**：我把整仓消费方测试放后台运行的同时，`bun test tests/framework` 报 `files.test.ts > a document another process writes > republishing a document never shows a reader a partial one` 失败（363 pass / 1 fail of 364）；单独跑该文件 17/17 通过，空闲后整套 364/364。该文件确实是「另一个进程写同一文件」的跨进程协调测试。**事实**：会话早期 `git status` 显示 `?? framework/modules/`（该文件属其中的在制品），与本会话并发的第 04 票正在同一 checkout 工作。**推断**：那次失败来自并发写竞争，而非本票代码。

**建议**：在该测试文件头部或 framework 测试约定里写明「本文件的失败可能来自同仓其他进程的写竞争；先单独重跑再判定」；条件允许时把这类跨进程用例安排在独立临时目录或串行组。**预期效果**：避免 agent 花时间重跑与解释，更避免它去「修」别的 peer 正在改的文件。
