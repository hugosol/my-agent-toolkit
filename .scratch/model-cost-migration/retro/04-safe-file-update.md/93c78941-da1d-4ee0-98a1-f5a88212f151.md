## 4. 中高：Windows/运行时事实只能现场探针取得，而一次性探针在仓库里没有安放位置

**事实**

- 本会话写了 6 个一次性探针（在 `.scratch/tmp-probe/`），因为它们直接决定实现：`process.kill(pid,0)` 对已退出 pid 报 `ESRCH`（我最初的假说是「Bun on Windows 可能不支持」）；`fs.linkSync` 的原子独占性（EEXIST）；Windows `rename` 覆盖已存在文件可用；**被 reader 占用时 writer 的 rename 报 EPERM（隔离探针实测 1984/6927 次被拒）**；**把发布换成 200KB 非原子就地写，reader 15716 次读仍未观察到部分文档**；`stat().ino` 是「替换会变、就地重写不变」的可用判据。
- 其中两条**直接改变了交付物**：因为 reader 会拒 rename，发布处加了有限步进重试；因为非原子写在本平台不可被 reader 观察，验收证据改用文件身份（`ino`）而非「读到的内容是否完整」。也就是说这些不是顺手验证，而是设计输入。
- 仓库已有收集宿主/平台事实的先例：`framework/docs/harness-support.md`（含 capability difference register）、`framework/docs/harness-baseline.json`、`.scratch/model-cost-migration/assets/*-evidence-*.md`。
- 另外：`.gitignore` 只忽略 `node_modules/`、`.omp/`、`.codebase-memory/`、`.cache/`，**不忽略 `.scratch/`**；我在 `.scratch/tmp-probe/` 放探针后必须手动清理（本轮已删）。此外该 shell 是 Windows 环境，`/tmp/...` 传给 `bun` 会报 `Module not found`（本轮第一次探针就这样白跑一次），必须用 `os.tmpdir()` 或仓库内路径。

**建议**：在 `framework/docs/` 下增设一页平台事实（或并入 harness-support.md 的既有事实区），每条附可重跑的最小命令：`process.kill(pid,0)`→ESRCH 的生存判据、`fs.link` 原子独占、被占用者的 rename EPERM 率与重试策略、`stat().ino` 语义、`/tmp` 不可用应改 `os.tmpdir()`。同时约定一次性探针的落点（例如 `.scratch/probes/` 并加入 `.gitignore`，或明确「只放 OS 临时目录」）。

落点：`framework/docs/platform-facts.md`（新）或 `harness-support.md`；`.gitignore`。预期效果：下一个碰文件/进程语义的 ticket（本仓库还有 codex-windows-headers、http-transport-smoke 这类）不必从零探针，也不会把探针误留在仓库里。
