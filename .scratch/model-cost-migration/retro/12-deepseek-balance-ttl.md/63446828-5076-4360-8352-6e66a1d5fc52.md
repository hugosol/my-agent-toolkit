# 复盘：ticket 12 — DeepSeek 余额成功 TTL 与在途合并

范围：仅本次 ticket（P38）实现轮的 TDD 对话与工具结果。父 session、其他 ticket 执行不在范围内；无法从本次历史确认的内容不补造，已分别标注「事实 / 推断 / 未验证」。以下只提建议，不改代码、检查、技能或指令。

## 1. 仓库没有把已有的检查接起来（最高）

**事实**：`package.json` 已有 `typecheck`、`test`、`test:dock`、`test:framework`、`smoke:*`、`verify:*`；`.github` 目录不存在（无 CI）；无 eslint／biome／oxlint 等任何 lint 配置；`.git/hooks` 只有 `*.sample`（无 pre-commit）。
**事实**：本次改动跨 framework／extensions／tests 二十余文件，全程唯一拦住错误的是我自己记得跑 `bun run typecheck` 与 `bun test`（typecheck 确实在早期抓到了 `usageSettled` 缺声明、以及测试文件的空壳报错）。
**事实**：本仓配置的两条用户规则（`ts-no-tiny-functions`、`ts-promise-with-resolvers`）只以「工具调用后提醒、不中断」的形式到达，出现在我写完 `tests/model-cost/provider-balance.test.ts` 之后；若下一轮不再写代码，这次违规就会留在文件里。
**建议**：建一个 CI job（或最便宜的 pre-commit hook）跑 `bun run typecheck && bun test`；把上述两条规则落成仓库自己的确定性检查（引入完整 lint 成本高时，一个针对这两个模式的小脚本即可）。分类：机械规则 → 检查，而不是留在评审记忆里。

## 2. provider 协议事实只存在于仓库之外（信息访问）

**事实**：本票要兑现的 endpoint 路径 `/user/balance` 与响应形态（`balance_infos[].currency` / `total_balance`，取 CNY）在 contract、spec、lighthouse 中都没有；规格只写到「去掉末尾 `/v1` 后余额路径」和「取 CNY」。我通过 `web_search` 取 DeepSeek 公开 API 文档，据此写解析器与测试字面值，并在证据文档里注明来源。
**推断**：同批的 ticket 15（Codex 额度）会遇到同类缺口——它的 endpoint／headers／窗口识别同样只在 Lighthouse 里以散文提及，具体协议形状仍需外部查询。
**建议**：在 `extensions/model-cost/docs/` 增一份 provider 协议参考（DeepSeek 余额：路径、字段、CNY 选择；Codex 额度：endpoint、headers、窗口识别），并从 `definition.ts` 头注释或扩展 README 以导航指针指向它。这正是「把一次昂贵且易错的外部查询缓存进仓库」的正当情形——仓库里已有先例（`framework/docs/harness-baseline.json`、`docs/model-data-maintenance.md`）。

## 3. dock 夹具被复制六份（导航 / 重复）

**事实**：`isolateHome` 在 `tests/harness-dock/model-cost-accounting.test.ts`、`-balance.test.ts`、`-modes.test.ts`、`-store.test.ts`、`round-facts.test.ts`、`session-ownership-tree.test.ts` 各有一份；每个文件还各自实现 `startRun` / `disposeRun`。本次我抄了又一份（balance），并重新推导了「run root 里要不要预置 baseline 文档、periodId 与 `holiday` 取什么」。
**推断**：这些副本已出现分歧（有的写 baseline 文档、有的不写；periodId 各不相同），是漂移的温床。
**建议**：抽出共享的 `tests/harness-dock/model-cost-run.ts`（`isolateHome` / `startRun` / `disposeRun`，以及「run root 必须含什么」的单一说明），六个套件改为复用。收益是下一次写 dock 用例不再需要重抄与重推。

## 4. ticket 头部没有指向已批准合同的指针（导航）

**事实**：ticket 正文引用「批准 S1–S5 seams」「P38」「P58／P52 按本票具名责任执行」，但既无 seam 定义也无链接。S1–S5 的定义在 `contract.md` 的 “Seam decisions” 表，P52／P58 在 Promises 表。我为此分别读了 `contract.md`、`lighthouse/09-refresh-lifecycle.md`、`decision/04-provider-access.md`、`lighthouse/10-assembly-layout.md`、`assets/current-state.md` 才拼齐语义。
**建议**：在 ticket 模板（生成 implementation ticket 的地方）加一行固定头部，例如 `Contract: [seams & promises](../contract.md#seam-decisions)`，并在正文用到的编号旁并列合同锚点。这是纯导航指针：一行成本，把「解码编号」从多文件检索变成一次跳转。注意同批 ticket 的**证据文档**已带 `Contract: [approved contract](../contract.md) — seams S2, S5` 这类行——把同一条约定前移到 ticket 本身即可。

## 5. 「默认值 + YAML 可配置」与声明式配置要求的张力（隐藏依赖）

**事实**：框架的 `ExtensionConfigDeclaration.fields` 语义是「文件必须携带每个声明 key」（`framework/docs/framework-capabilities.md` 行 37 有写，但埋在一张长表里），而 ticket 要求 `balanceTtlMs` 默认 30000 且「沿既有扩展 YAML 机制可配置」。实际落地成了三件套：`config.yaml` 必须写上 30000、runtime 仍保留一个 code default（直接构造 runtime 的测试不带该 key）、以及 8 处测试里手写的 config 字符串／声明断言全部同步。
**推断**：下一位实现者（ticket 15 若要加同类可配置项）会重走这一整套推导。
**建议**：把这条约定写到它会被读到的地方——`framework-capabilities.md` 的 Extension configuration 一节，或 `extensions/model-cost/definition.ts` 的头注释：「声明字段即必需；扩展侧的『默认』= 随包 YAML 值 + 直接构造时的代码回退」。若希望真正表达「可选 + 默认」，那需要框架侧支持（属合同层修订，本票范围外，仅记录）。另：把 model-cost 测试的 config reader 抽成一个共享 helper，避免多处字面量靠手工同步。

## 6. 全仓套件与故障注入的先后（小）

**事实**：green 之后我启动全仓 `bun test`（211.6s，转入后台），随后想按 tdd 技能做定向故障注入，却必须等它跑完才能改源文件——注入会污染正在运行的套件。tdd 技能把故障注入列为 green 后的检查，但没规定它与全仓套件的先后。
**建议**：在 tdd 技能的 Completion 一节写明顺序：先做定向故障注入（局部套件、秒级、编辑—验证—还原）→ 最后跑一次全仓套件。这样「等全仓」不会变成串行空转。
