## 1. 仓库没有 guardrail：`typecheck`／`test` 已存在但没有任何自动运行点（高）

**现象（事实）**：`package.json` 里有 `typecheck`、`test`、`test:dock`、`test:framework`、`test:codebase-tools`、两个 smoke 脚本，但本轮我三次靠**手工**运行 `bun run typecheck` 才发现类型错误：

- `Object.hasOwn` 在 `target: ES2020` lib 下不可用（新代码首次 typecheck 才发现）；
- 测试里 `MAIN.name`（`string | undefined`）与 `TurnOutcome` 的窄化错误，两次都是 `bun test` 全绿、`tsc` 才红；
- 仓库根目录列表里没有 `.github/`、没有 `.githooks/`、没有 lint 脚本（这是我在根目录列目录观察到的；仓库树之外是否存在 CI 未核实，见末节）。

**代价**：三次「测试绿、类型红」的往返，且这类错误对**其他 ticket** 同样只靠人记得运行才暴露。

**建议落点**（机械项，默认建检查而不是写规则）：

- 新增最小 CI job（如 `.github/workflows/checks.yml`）运行 `bun run typecheck && bun test`；`test` 已知有 4 个环境性失败（connect-bot 需本机面板、`harness-dock/baseline.test.ts` 与本地检出漂移），CI 要么跳过这两个文件、要么把已知失败显式 allowlist，避免「红的天天红」而失去信号。
- 加 pre-commit hook（或 `prepare` 脚本）跑 `bun run typecheck`——它是本轮真正抓到东西的那条命令，且秒级。
- 若暂不建 CI：在 `AGENTS.md` 里加一条**导航指针**（不是长文）说明「交付前跑 `bun run typecheck && bun test`，已知 4 个环境失败属预期」，让实现轮不必靠运气想起来。

## 2. dock 的「内置 provider 改道」机制不可见，且测试进程没有网络隔离护栏（高）

**现象（事实）**：

- 我按 `tests/harness-dock/fixtures/extension-root/provider.ts` 的写法用 `registerProvider("deepseek", { baseUrl: capture.baseUrl, apiKey })`，结果请求打到 **`api.deepseek.com`** 并返回 401（provider 名已被 catalog 认识时，catalog 的 baseUrl 不被覆盖，只吃到了我的 apiKey）。这意味着我无意间对真实服务发了一次出网请求，而本 ticket 的约束明确要求隔离、永久测试用 mock。
- 正确的机制是 `tests/harness-dock/agent-config.ts` 的 `writeProviderOverride`（写隔离 agent state 的 `models.yml` → `providers.<name>.baseUrl`），它的文件头注释解释得很清楚；但 `tests/harness-dock/index.ts` 只是 `export *`，没有任何指针说明「什么时候用哪个」，且 `writeProviderOverride` 在 `tests/harness-dock` 内**没有**任何使用先例（只有 `tests/codebase-tools/outbound-role.test.ts` 用）。

**代价**：一次真实出网（虽无真实凭据、无副作用，但违反隔离承诺）；约 4–6 次 12–30s 的 dock 运行 + 两轮诊断脚本才定位。

**建议落点**：

- 在 `tests/harness-dock/index.ts` 或 `agent-config.ts` 顶部加**导航指针**（一句话）：把模型跑在内置 provider 上（deepseek/openai-codex/opencode-go…）必须用 `writeProviderOverride`；只对 catalog 不认识的 provider 名用 fixture 的 `registerProvider`。
- 给测试进程加**护栏**（推断可行，需要 spike）：bun 的 `--preload` 里包一层 `fetch`/`net.connect`，非 loopback 目标直接抛错；或至少提供一个 `assertLoopbackOnly()` helper 让 dock 用例开机即断言。这条对「迁移期不触碰正式环境」是长期风险，值得一次性投入。

## 3. `round_end` 在真实 RPC 宿主不可达这件事，没有可以「查到」的落点（高）

**现象（事实）**：按规格把保存点定在 `round_end` 后，我用临时 stderr 探针确认：真实隔离 OMP 里 `agent_start` → `round_start` 有，但 `agent_end` 处 `ctx.isIdle() === false`（同时 `hasPendingMessages()=false`、`getAsyncJobSnapshot().running=[]`），因此 `framework/adapters/omp.ts` 的 `quiescent()` 判定不成立、**`round_end` 从不派发**；两次 prompt 后 `consumption.json` 都不出现。规格写的是「非续跑原生结束先提交候选…framework 在下一任务轻量复查静止」（设计意图），adapter 里没有实现该复查。

**代价**：约两次 30s+ 的 dock 运行、一次 65s 运行、两轮探针与一次 12s 基线运行；更关键的是**ticket 06 的证据文档**写着「round_end 的端到端保存属于 07/08/09/10」，让我预期这一环在本票可见——这条预期落空且无处可查。

**建议落点**：

- 在 `framework/docs/framework-capabilities.md` 的 round/run axis 段落加一行**已知缺口**（事实 + 边界）：OMP adapter 只在原生 run 结束处判静止，该处会话尚未 idle，因此 RPC/无 UI 会话不产生 `round_end`；规格里的「下一任务复查」尚未实现。同样一句写进迁移规格的 Round 条目，避免它读起来像已实现。
- 给实现票的验收模板加一格：**「本条的宿主可观察路径」**（哪个真实入口能看到结果；若某环在真实宿主不可达，实现轮必须点名）。本票 criterion 7 的「保存累计」就是假设了这样一条路径而没有先验证。

## 4. hidden 模式是否记账：规格没写，实现轮被迫替上游做决定（中）

**现象（事实与推断）**：规格明确了 token-only「保留可靠四类 token、Session 累计…」（即记账），但对 hidden 只写了「不创建用量 widget、不阻止执行」。旧实现（冻结 oracle `cost-calc`/`index.ts`）的 `agent_end` 守卫把非官方 DeepSeek／非 Codex（含 token-only）全部排除出累计；本轮我据此判定 **hidden 不记账**（不累计 token、无金额、无提示），这也是保持 ticket 06 dock 用例「可读基线不被重写」成立的原因（推断：若 hidden 记账，那条既有断言会被改写）。

**代价**：如果选反，ticket 06 的 dock 断言、以及后续 16（Viewed session total）的 Sum 范围都要改；这一决定影响了别的 ticket 的既有证据。

**建议落点**：在 `spec.md` 的「模型覆盖、锚价与指标语义」加一句显式语义（hidden = 不记账、仅不阻止执行；token-only = 计 token 不计金额），并把「hidden 与未收录 ID 的差别」写成一句可断言的话。让上游回答一次，而不是每个实现 ticket 各自猜。

## 5. framework 文档与规格对「反馈级别」的表述冲突（中）

**现象（事实）**：`framework/core/protocol.ts` 的 `FeedbackLevel` 注释与 `framework/docs/framework-capabilities.md` 明确写「两个级别，因为扩展对操作者说的话分两类」，而批准的规格要求「Extension feedback 复用既有机制补齐 info／warning／error」。本票需要发布「跳过型」提示（缺 usage／缺价），既不是「发生了」也不是「失败」，我在权衡后同票加宽了公共契约（加 `warning`，无调用方需要改代码）并同步了文档行。

**代价**：约 4–6 轮推理与一次未列入计划的 framework 公共契约改动；若选择用 `error` 表达「跳过」，还会给后续 21（反馈级别）留下需要返工的语义。

**建议落点**：规格的这条实现决策里直接点名它改动的 framework 落点（「`FeedbackLevel` 增 `warning`，OMP adapter 已支持三级」）。这样下一个 agent 读到的是「已知待补」，而不是要在「已有文档说两级」与「规格说三级」之间自行裁决。

## 6. dock 内置 provider 的传输事实没有查找表（中）

**现象（事实）**：我尝试用 `opencode-go/deepseek-v4-flash`（数据里的 token-only 白名单 ID）做真实宿主用例，一次 prompt 触发 **22 次可重试失败**（该 provider 的 catalog 模型走 OpenAI responses 协议，而捕获端点只兑现 completions 流），每次失败都被扩展如实记为「没有可靠的 usage」。我随后删掉该用例并把它写进证据的「已知限制」。这类事实（哪个内置 provider 的模型走哪个 `api`、捕获端点支持哪些流）在 dock 里没有任何地方记录，只能靠实验发现。

**代价**：一次 65s 的 dock 运行 + 一次 12s 诊断运行（含 22 次重试的开销）；也让我对 token-only 的真实宿主贯通只留下「未覆盖」。

**建议落点**：在 `tests/harness-dock/agent-config.ts` 或 dock README 加一张小表：内置 provider → 模型 `api`（如 `deepseek` → `openai-completions`；`opencode-go` → `openai-responses`）→ 捕获端点是否兑现该流；并注明「不兑现的流会按可重试失败重试多次」。若捕获端点能补上 responses 终帧，顺带解锁 token-only 的真实宿主覆盖。

## 7. 两条 builtin 规则与本仓约束冲突时需要澄清（低）

**现象（事实）**：

- `ts-promise-with-resolvers`：本仓 `tsconfig.json` 是 `target: ES2020`，lib 里没有 `Promise.withResolvers`（用它即类型错误），因此该规则在本仓**不可满足**，我保留了执行器写法 `new Promise(resolve => setImmediate(resolve))`。
- `ts-no-test-timers`：本轮真正需要等待的是**另一个进程**的异步效果（Round 结束后落盘），且被测代码没有暴露可 await 的 promise；我改成「按条件轮询 + 事件循环让路（`setImmediate`）」。规则自带的例外（集成用例）已经允许，但没有说明这种「条件轮询」形态。
- `ts-no-return-type` 与 `ts-no-tiny-functions` 各触发一次，两者都在规则自身给出的例外内（具名类型、导出的领域查询），仅提醒信号略噪。

**建议落点**：给 `ts-promise-with-resolvers` 加一句「仓库 lib 早于 ES2024 时保留执行器写法」，给 `ts-no-test-timers` 的例外补一句「等待真实跨进程效果且无可 await 信号时，用条件轮询（含超时）而非固定时长」。两条都是把已发生的正确做法写进规则，避免下一次为满足规则而写出更差的代码。
