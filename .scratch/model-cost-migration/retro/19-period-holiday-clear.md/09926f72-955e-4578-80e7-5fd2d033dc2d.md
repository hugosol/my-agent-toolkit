# 复盘：ticket 19（`/budget holiday` 与 `/budget clear` 的完整周期切换）

范围：本 ticket 的 TDD 执行对话（含全部工具调用与结果）。事实、推断、未验证项分开标注；未读过的历史不补造。

## 1. 最严重：仓库没有任何 guardrail 会跑它自己的检查命令

**事实**
- `package.json` 只有分离的 `test`（`bun test`）与 `typecheck`（`tsc --noEmit`）等脚本，没有合并入口。
- 本仓库当前状态：无 `.github/workflows`、无 `.husky`／`.githooks`、`core.hooksPath` 未设置、`.git/hooks` 里没有生效的 hook、根目录没有任何 lint 配置（eslint／biome／oxlint／prettier 皆无）。
- 本轮的实证：第一刀（protocol 的 `provider`＋model-cost 的五个模块）之后，`bun test tests/model-cost/period-switch.test.ts` 只报 4 个**行为**失败；随后 `bun run typecheck` 报出 3 个类型错误，其中 `consumption-store.ts` 的 `archive: string | undefined`（TS2322）**不影响运行时**——`bun test` 剥掉类型后完全看不见它。也就是说：在本仓库，测试全绿不蕴含类型正确，只有手工记得多跑一条命令才能补上。
- 同一轮里，harness 注入的评审规则（`ts-no-any`、`ts-no-test-timers`、`ts-no-inline-cast-access`、`ts-no-tiny-functions`）是在我写完代码之后**以中途提醒**的形式到达的：它们抓到的正是「机械可判」的那一类（`as any`、测试里的真实计时器、内联 cast、单行包装函数）。仓库自己没有 linter，所以这类问题只能在事后打扰，不能在任何门禁上被拦下。

**建议**（选最便宜的一条即可，均不需要新依赖）
- 增加一个 `check` 脚本：`bun run typecheck && bun test`，并让**一个**门禁调用它——`.githooks/pre-commit`（配 `core.hooksPath`）或一个 CI job，二选一。
- 若 lint 依赖不符合本仓库「依赖极简」的风格：加一个约 20 行的 `scripts/check-steering.ts`，只做机械 grep（`as any`、`tests/**` 下非 dock 用例里的 `setTimeout(`／`setImmediate(`），并入同一个 `check` 脚本。
- **未验证**：这些评审规则是仓库自己的还是 harness 注入的（本轮没有读到它们的宿主）。若属 harness，则「搬进仓库检查」需要先确认归属，别把它们固化成第二份真相。

## 2. 严重：dock 用例失败时，第一件事是读这个 run 自己的记录

**事实**
- `tests/harness-dock/period-switch.test.ts` 第一次失败只给了 `Expected length: 1 / Received length: 0`。我做的**下一步**——打印该 run 的 extension notices——立刻给出真因：子进程自己的反馈「当前入口的消费保存尚未收口」。
- 尽管如此，我仍多花了一轮把 `console.error` 探针插进生产源码（`request-accounting.ts`、`period-switch.ts`，最后是 `framework/modules/files.ts`）才确认「保存确实在途、不是卡住」。这些探针必须逐字节回滚，成本高于收益。
- dock 早就具备这些信息：`ControlledSession.diagnostics()`／`stderr()` 会带子进程 stderr，notify 帧里就是扩展反馈（`session.ts` 头部也写了「任何失败都给出诊断所需原料」——我是靠 grep 才看到的）。

**建议**：在 dock 作者会看的地方（`tests/harness-dock/session.ts` 头部或一份短的 `tests/harness-dock/README.md`）放一句指针：dock 用例失败 → 先读 `session.diagnostics()`、notify 帧与 `session.stderr()`；子进程是真实进程，它已经在报告自己发生了什么，往生产源码插探针是第二选择。

## 5. 中等：steering 冲突——全局「NEVER verify」对上了本票指定的 tdd 红/绿环

**事实**：本 ticket 的提示词一边把 `tdd` skill 指派为执行程序（含「red→green」的验证要求），一边在 `<critical>` 里写「验证是主 agent 的事，NEVER 自己跑，除非任务明确如此要求」。我按「skill 即 assignment」解释并全程跑了测试；冲突本身没有造成错误动作，但每次跑测试都要重新判一次。

**建议**：在那句全局指令里补上豁免，例如「…除非所指定 skill 的程序本身要求运行」。一行改动，省掉每次的判断题。

## 6. 中等：judgement 规则留给 review 侧，机械规则留给检查

**事实**：`ts-no-tiny-functions`、`ts-no-inline-cast-access` 打在我的**测试**代码上（单次使用的一行 helper、索引上的 inline cast），我按规则改为内联与显式窄化；`ts-no-test-timers` 打在一个 `setImmediate` 轮询 helper 上，我据此把该用例改成等真实信号（mock 的 `onQuery`、port double 新增的 `CommandRun.completion`）——这次改造实打实提升了用例质量。
**注意**：dock 既有实践（`waitFor(deadlineMs)`、`GATE_WINDOW_MS`、`expectNoArrival(window)`）本身就是真实时间，规则自带的例外条款覆盖了它。**推断**：不写明这一点，下一个作者要么过度修正（把真实进程的等待改成假时钟），要么被规则挡住。

**建议**：需要 judgement 的留进 CODING_STANDARDS（给 review agent）；每条机械规则配一个最便宜的确定性检查（见第 1 条）。真实时间例外在 dock 相关文档里点名。

## 7. 低：两处工具 papercut（都是我的习惯问题，无需改仓库）
