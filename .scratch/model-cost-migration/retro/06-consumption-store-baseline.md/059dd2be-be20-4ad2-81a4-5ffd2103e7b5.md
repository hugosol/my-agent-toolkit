## 06 消费文档安全保存与存储基线 — 复盘建议

范围：本 ticket 的 TDD 实现会话（`06-consumption-store-baselinemd`），不含父 session 与 retro 轮。每条区分事实、推断与未验证项；只给建议，不执行。

---

### 1（最高）仓库没有任何护栏在跑它自己的检查命令

**事实**：仓库根无 `.github/`、无 `.gitlab-ci.yml`/`Jenkinsfile` 等 CI 配置；`.git/hooks` 只有 sample 文件；`git config core.hooksPath` 为空；`package.json` 只有 `test`/`test:dock`/`test:framework`/`test:codebase-tools`/`smoke:*`/`verify:*`/`typecheck`，没有 `lint`/`check`，也没有任何 lint 配置（eslint/biome/oxlint 均无）。README 已写明检查命令是 `bun run typecheck` + `bun run test`，但没有任何东西自动执行它们。

**推断**：这是本票最大返工来源。新增 `entrypoints/omp/model-cost.ts` 与 `extensions/model-cost/` 后，`tests/framework/deployment.test.ts` 里 6 条“仓库形状”断言（deployed entrypoint 集合、发现计数 2→3 / 3→4、绑定标签集合）直到最后一次全仓运行才暴露；此前按目录运行的套件全绿。07–25 各票都会继续触碰 `extensions/model-cost`，同类断言的暴露时机会重复。

**建议**：(a) 加 CI job（或 `.githooks/pre-push` + `git config core.hooksPath .githooks`）跑 `bun run typecheck && bun test`；(b) `package.json` 增加 `check` 脚本把两条串起来，并在实现票收尾流程里引用它。

**验证方式**：故意改坏一条部署断言，观察提交/推送前是否失败。

---

### 2 仓库形状断言没有指针，只能靠“最后跑一次全仓”发现

**事实**：`tests/framework/deployment.test.ts` 显式固定“每个扩展一个薄入口 / 只发现本仓库实现 / 绑定标签集合”，文件里出现 `codeBaseTools`、`connectBot` 字面量；`README.md` 的 Document index 与 ADR-0002 的源码布局都没提它。第一次看到它失败是在最后一次全仓运行的摘要里。

**推断**：即使加上护栏（第 1 条）也只能事后发现；一条指针能把返工变成开工即可预判的动作。

**建议**：在 `README.md` Document index（或 ADR-0002 布局旁）加一行“deployed extension/entrypoint 集合的断言在 `tests/framework/deployment.test.ts`”；实现票模板加一条 checklist：新增 `entrypoints/omp/<id>.ts` 或 `extensions/<id>/` 时同步该文件。

**未验证**：把该断言改为“从 `entrypoints/omp/*.ts` 派生期望集合”是否可行、是否削弱“显式固定仓库形状”的意图——未验证取舍，建议先加指针，不动断言。

---

### 3 全仓 `bun test` 的失败输出不可归因

**事实**：全仓运行约 160–165s，失败夹在输出中、摘要只给数量；为枚举 10 个失败必须再跑一次 `bun test | grep -E "^\(fail\)"`（另 160s）。最终 600 pass / 4 fail 的归因能成立，是因为恰好存在 `.cache/full-suite.log`（含一次更早的全仓记录，4 个失败完全相同），我先 `grep "(fail)" .cache/full-suite.log` 才敢判定“与本票无关”。

**未验证**：该日志由谁生成（内容确为全仓输出；生成者未验证）。

**建议**：`package.json` 增加 `test:summary`（`bun test 2>&1 | grep -E "^\(fail\)|^ *[0-9]+ (pass|fail)$|Ran "`），并把“已知环境相关失败”写进 `framework/README.md` 一个小节：两条 connect-bot 面板用例需要本机 127.0.0.1:8787 的 omp-bot 面板；两条 `baseline record` 用例需要本地 `../oh-my-pi` 检出与记录逐字一致。这样一次运行即可归因，也不必依赖 gitignored 的旧日志。

---

### 4 仓库导航中枢没有随新扩展更新，且没有检查

**事实**：根 `README.md` 首段与 Contexts 表只列 framework / connect-bot / codeBaseTools（Document index 无 model-cost、无 `tests/model-cost/` 行）；同一 README 明确写“per-extension runbooks are in each extension's own README”，而 `extensions/model-cost/` 目前只有 `GLOSSARY.md`。本票未创建 `extensions/model-cost/README.md`，也未改根 README。

**推断**：这是仓库自己的成文约定被漏掉，不是可选美化；新扩展与新 suite 在导航上是隐形的。

**建议**：把约定变成机械检查——断言“每个 `extensions/*/config.yaml` 的 id 都出现在根 README 的 Contexts 表且存在 `extensions/<id>/README.md`”，失败信息直接指向要补的两行。若认为扩展 README/runbook 归属别的票（很可能是 25 收口票），先在根 README 补行并在该票落 README。

**未验证**：model-cost 扩展 README / runbook 的归属票（推断属验收/交接票）。

### 6 实现票本身不带“权威指针”

**事实**：`implementation/06-consumption-store-baseline.md` 只给 P 编号与验收项，没有任何指向 `spec.md`、`contract.md`、`lighthouse/06`、`lighthouse/10` 的链接；指派文本只泛泛提到“参考 approved contract/spec”。实际读了 `spec.md`(274)、`contract.md`(119)、`map.md`(85)、`lighthouse/10`(168)、`lighthouse/06`(339) 与两份 GLOSSARY(~330)，约 1200+ 行，而真正约束本票的细节集中在 `lighthouse/06` Q17–Q25（存储根与物理 schema）与 `lighthouse/10`（布局/工厂）约 60 行内。

**推断**：规格刻意要求“读权威以免静默缩范围”，问题不是“少读”，而是“没有入口”，入口成本高。

**建议**：每张实现票头部加一行 `Authorities:`，例如 `lighthouse/06 Q17–Q25（存储根+物理 schema）；lighthouse/10（布局/工厂/订阅）；contract P44/P45/P47/P51`。不改承诺，只把“从哪读起”写死。

### 7 工具与实验纪律（低，但有一次真实泄漏）

**事实**：(a) `du -sh .cache/* host-patches/*` 用了 90.85s 并被自动后台化——真正需要的只是“隔离安装是否已缓存”，同一条命令里的 `ls` 已足够；(b) 为定位一条断言的归属跑了 `bun test tests/codebase-tools`（41.23s）迂回，随后一条 `grep -rln` 立刻给出答案；(c) 会话中 4 次全仓 `bun test`，其中两次在我又改了文件之后才返回（结果陈旧），两项 160s 级套件一度重叠运行；(d) 注入验证时 `cp /tmp/…` 恢复失败（bash 的 `/tmp` 与内置 Python 的 `\tmp\` 不是同一处），而先前那次恢复用了对未跟踪文件无效的 `git checkout … || true`，导致被改动的生产文件一度留在树上（3 个用例短暂变红），最后靠 Python 恢复。

**推断**：(d) 的风险等级高于另外三条——改动曾真实存在于生产文件中并进入测试运行。

**建议**：注入副本放在工作区内（或由同一解释器写入并恢复），恢复后用同一条命令确认；收尾验证必须是恢复之后的最后一次动作；判断“某断言属于哪个 suite”先 `grep -rln "<字面量>" tests/` 再决定跑什么；一项重型全仓测试未结束前不启动第二项。

### 不应改动（本会话已验证有效）

隔离 OMP 安装的缓存让 3 条真实 harness 用例只需 ~5.2s，`tests/harness-dock` 本身很稳；根 `README.md` 的 Quick start + Document index 是有效导航指针；harness 侧 TS 规则（`ts-no-tiny-functions`/`ts-no-return-type`/`ts-no-inline-cast-access`/`ts-set-map`）以书写时提醒形式出现，本次 4 次命中都被及时纠正——这些是资产，不建议重做；仓库侧缺的是对应的机械检查，不是这些规则本身。
