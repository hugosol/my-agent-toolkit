## 5. 全局指令里“批量替换 vs 单点编辑”的边界模糊，诱发一次结构性 sed 事故（严重度：中）

**类别**：Global instructions（steering）锐化 / tool economy。

**事实**：系统提示同时给出 “NEVER use `sed`/`perl`/`python` via bash to issue **individual** edits; MUST use `edit`” 与 “Same replace in several files → `sed -E -i 's/…/…/g'`”。前 8 个测试文件的**标识符重命名**属后者、顺利；随后我漂移到 `sed -i -E '/^const panelAnswer/,/^}\);$/c\…'`——一次**结构性多行编辑**——GNU sed 对 range 内每行各输出一份替换文本，5 个文件各生出 4 份重复块，修复又花了约 4 次工具调用。

**推断**：边界词是 “individual/bulk”，而实际操作里是 “单行模式替换 vs 多行结构编辑”；前者可机械判定，后者**永远**该走 `edit`/`ast_edit`。

**建议**：把规则改写成可判定的两句话（单行模式 → sed；任何多行/结构 → `edit`/`ast_edit`，无例外），放在全局 steering 或本仓 `docs/agents/`。这条能直接把那次事故变成不可能。

**事实**：一次跨 8 个测试文件的 `grep` 返回 “124 matches… elided”，我随后用一串更窄的 grep / `sed -n` 原地转圈；另外早期一次 `cat` 多文件的命令产出 57k 行（5MB）artifact，几乎没带回可用信息（该调用本身违反“读文件用 `read`”，属操作者失误，但代价真实）。

**建议**：宽口径排查优先用 `grep -c` 先定位、再 `read` 精确区间；多文件 dump 不作为探测手段。属习惯规则，无仓库级改动。
