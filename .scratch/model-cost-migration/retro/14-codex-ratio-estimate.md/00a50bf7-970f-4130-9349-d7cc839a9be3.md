## 1.［高］交付触发、但框架不等待的异步写入，测试无法等待 —— PortDouble 丢弃 handler 的 promise

- **事实**：`framework/core/assembly.ts` 明确「A handler may return a promise, and the framework does not wait for it」；`tests/framework/support/harness-port-double.ts` 的 `deliverTurn`/`deliverRound` 同步调用 handler 并丢弃其返回值，`TurnBoundary`/`RoundBoundary` 只有 `hasUI`/`feedback`，没有任何「本次交付启动的异步工作已收口」的信号。
- **事实**：现有套件因此用真实时间轮询兜底：`tests/model-cost/session-recovery.test.ts` 的 `savedDocument`/`feedbackOf` 用 `Date.now() + 5_000` 死线与 `queuedWorkSettled()` 逐轮读文件；本工单最初的等待写法与此同源。
- **事实**：这张票为此付出的代价最大。estimate 的写入是 best-effort fire-and-forget，我逐轮 `readFileSync` 轮询估计文档时，框架的 rename 发布在 Windows/Bun 上被卡住 → 单测 5s 超时、约 15 次工具调用用于探针文件 / DEBUG 日志 / 二分等待策略；最终解法是让 `observe()` 返回「写入已收口」的 promise（对齐 `ConsumptionStore.commit`），并让文件断言只在该 promise 之后读一次。
- **推断**：卡住与「发布期间同步读取同一文件」相关（`publish` 的 in-use 重试是真实 25ms sleep，测试侧逐轮读会让重试持续撞上），但我没有把机制隔离到单一 syscall。
- **建议**：给 port double 一个可等待的交付面（例如把 handler 返回的 promise 收进 `boundary.settled`，或提供 async 变体），让套件等待**效果**而不是等待时钟；并在 `framework/docs/framework-capabilities.md` 的安全文件模块段落写下规则：**先 await 写方，再读目标**，以及「发布在途时同步读目标会拖住发布」这一平台现象。属于测试基建，不改变任何业务承诺，却能同时消掉各票自造的 `Date.now()` 死线。
