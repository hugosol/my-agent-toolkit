## S1（高）「套件全绿」与「criterion 已交付」之间没有自动关联，两个真实缺口就这样活过了一整轮

`事实`：上一轮报告 `bun test tests/model-cost` → **235 pass / 0 fail**，同时以散文形式在 `not_done` 里声明「视觉套件未写」。本轮新建 `tests/model-cost/widget-visual.test.ts`（20 例，79 expect）后，第一次运行就有 12 例失败，并暴露**两个已交付实现里的真实缺陷**：

1. `display.ts` 的 `budgetLine` 把 `Effort: high` 整段标为 `effort` emphasis，而 `paintedLine` 用 `piece.text` 当 level 调 `theme.getThinkingBorderColor(piece.text)` —— 于是主题收到的 level 是字符串 `"Effort: high"`，**两个问题一次**：标签也被上色，且 level 键本身是错的。规格 §135 与冻结旧实现都只给**值**着色。
2. `widget.ts` 的 `render()` 对 `component` 形态无条件交出 factory，`hidden` 模式因此被交给宿主一个「渲染为空数组」的组件；真实宿主 `extension-ui-controller.ts` 在 `widgets.size > 0` 时会加 `Spacer(1)` 并占位，与该文件自己写的「不创建、而是清空」相矛盾。

`事实`：这两处都不是「视觉细节」，而是可证伪的行为；它们的共同点是**没有任何测试文件拥有对应的 criterion**，所以 `235 pass` 与 criterion 之间没有连接。
`推断`：本轮之所以能发现，靠的是「先补套件、再逐 token 断言」，而不是任何检查。
**建议**（按能力排序）：

## S2（高）真实宿 dock 断言把「随时序变化的值」当稳定事实；同时「布尔化断言」把失败信息吞掉了

`事实`：`tests/harness-dock/detail-tree.test.ts` 因新增 accrued 行位次迁移失败后，我按「该 run 文档里所有 Session 的 `costCny` 之和」写死金额，三种读法分别得到：

```
¥0.02 [▏▏]（改动前那次 run 的 detail[1]）
¥0.0050 [▏]（同一 brief 帧，同时 Total 行是 Cost: ¥0.02、Prev 行是 Cost: ¥0.01）
¥0.0000（另一帧）
```

`事实`（代码原文）：`runtime.ts` 注释「the session records … as the last load or commit left them」；`consumption-store.sessions()` 返回 `#records`；`request-accounting.save()` 在 `storage.commit()` 返回 `saved`/`unchanged` 后**直接 return，不 announce**。所以某一帧的 accrued 金额取决于它落在哪次 commit 与哪次通知之间——**不是该 run 的稳定事实**。
`事实`：我第一版断言写成 `expect(String(line).startsWith(...)).toBe(true)`，失败只打印 `false`，为了看到实际行我不得不临时插一条 `expect(briefLines).toEqual(["<diagnostic>"])` 再跑一次 dock。
**建议**：
- 在 `tests/harness-dock/` 的共享说明（或 `baseline.ts` 顶部注释这类每个 dock 用例都会读到的位置）加一小段**稳定/时序相关**清单：稳定＝措辞、字段格式、金额单位、结构（Total/树/Round 的相对位次）；时序相关＝来自「已提交文档」的周期累计（accrued 行）、在途 vs 已提交消费。以 accrued 行为例写清「commit 不触发重绘」。
- `CODING_STANDARDS.md`（评审用）加一条**机械可判**的规则：测试断言必须断言值本体，不得断言由值派生的布尔（`.startsWith(...).toBe(true)` 等）；同时给 reviewer 一句「失败信息是否足以定位」。这条最适合评审 agent，因为它在 diff 上零成本可查。
- 旧 widget 在轮次结束提交后自行重绘并重读文件；本迁移的 accrued 读实例持有文档，两者在同一重绘时机读到同一份「已提交周期累计」。已在本轮 asset §3 如实记录，未改该来源。

## S8（中低）机械规则提醒精度：本轮 4 条提醒，0 条命中了需要改的代码

`事实`：本轮收到 4 条规则提醒（`ts-set-map`、`ts-import-type`、`ts-no-dynamic-import`、`ts-no-tiny-functions`），全部为「命中后不阻断」。逐条核对：`new Set` 用于动态增删监听者（规则允许）；文件通篇 `import type`，无 `import("…").T` 内联注解；`ts-no-dynamic-import` 命中的是我写在**字符串**里、交给子进程求值的脚本文本；`last<T>()` 有 7 个调用点（规则自己的豁免条款）。即 4/4 为合规或豁免，且提醒**没有给出匹配片段/行号**。
`推断`：这类误报不会直接花调用，但会诱使后续 agent 为「消除提醒」而去动本来就对的代码。
**建议**：提醒带matched snippet（或文件:行）；把规则作用域限定在源文件而非 tool-call 参数里的任意字符串内容；命中时先做一次豁免自检（调用点数量、是否在字符串字面量内）再提醒。
