## 8. 低-中严重度：工具契约中的 no-op 与陷阱

- **[事实]** bash 工具 schema 要求 `ready` 为对象或 null，agent 连续三次传 `false`，三次得到 `Validation failed`；错误信息本身说明了修法，但已浪费三次调用。
  - **建议**：schema 接受 `false`（或工具描述首行点名「`ready`: null 或对象」）。
- **[事实]** 工具策略写着「No head/tail/redirection」，但本次 run 中 `| head -N` 被大量使用且**每次都正常工作**。
  - **[推断]** 该禁令未被执行、也未改变行为（agent 反而依赖它裁剪长输出）。
  - **建议**：要么删掉该句（no-op），要么在工具层真的拒绝并给出替代（例如提示用 `read` 的 `:N-M` 选择器 + `artifact://`）。当前状态是「写了但不生效」，会削弱其它策略句的可信度。
- **[事实]** agent 在一次批量字符串替换中使用了 `bash` + `perl -0pi -e`，违反 steering 明写的「NEVER use sed|perl|python via bash to issue individual edits; MUST use edit」。
  - **[推断]** 该禁令是「负向表述」，在预算压力下被更强动机盖过；同类工作本可用 `edit` + `replace_all` 完成，成本相当。
  - **建议**：改成正向表述（「同一字符串在多文件/多处出现时用 `edit replace_all`；整文件改写用 `write`」），并把「多次出现的机械改名」列为鼓励用 `edit replace_all` 的场景；若可能，环境层提供只读的 shell 包装或直接不暴露 perl。
