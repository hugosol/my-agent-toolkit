## 1【高】仓库没有 guardrail 运行器；`bun test` 长期 4 红

**事实**
- `package.json` 只有 `typecheck`、`test`、`test:*`、`smoke:http-transport`、`verify:omp-candidate` 等脚本；仓库根无 `.github/`，`.git/hooks` 只有 sample（上一轮已查，本轮未发现变化）。
- 本轮之前 `tsconfig.json` 的 `include` 不含 `scripts`：新写的 smoke 类型错误可静默通过。**本轮已把它加入**（一行），并立即验证：`bunx tsc --noEmit` 覆盖到 `scripts` 的 3 个文件；临时放一个 `scripts/typecheck-probe.ts`（`const broken: number = "not a number"`）会报 `error TS2322`，删除后恢复 0 errors；加入后它**确实抓到本轮 smoke 里一处真实类型错误**（`upstream.on("error", () => socket.destroy())` → `Property 'destroy' does not exist on type 'Socket<…>'`，Bun 的 socket 类型只有 `end`/`close`/`terminate`），改为 `socket.end()` 后复绿。
- `bun run typecheck` 用 TS 7.0.2（native），全仓 **0.25s**。
- `bun test` 全仓 **495 pass / 4 fail，499 tests，58 files，119.9s**；四个失败与上一轮基线完全同名（connect-bot P23 panel 协议、connect-bot P25 注册窗口、harness-dock baseline anchor 漂移 ×2）。
- 本票的真实传输证据是一条**手动**命令 `bun run smoke:http-transport`（31.4s，且依赖 `openssl` 生成自签证书）；`bun test` 不会跑它，`tests/framework/http.test.ts` 全部注入 double、零网络。

**推断**
- 只要没人记得跑 smoke，"默认传输被换回 `fetch`"这类回归（正是上一轮的 P54 失败）在 `bun test` 全绿下完全不可见。
- 4 个长期失败使全仓套件的红/绿不再携带信息：agent 与维护者都会把 `4 fail` 当背景噪声，掩盖新真失败。

**建议（按成本升序）**
1. 加一个 `verify` 聚合脚本（一行）：`bun run typecheck && bun test && bun run smoke:http-transport`，并把 `scripts/http-transport-smoke.ts` 的缺失 `openssl` 情况保持为"报告 FAIL 并退出非零"（现在就是这样），不发绿灯。
2. 接线 git pre-commit hook 只跑 `bun run typecheck`（0.25s，成本可忽略）；`bun test`（120s）与 smoke（31s）放 CI 或显式 `verify`，不进 pre-commit。
3. 给出那 4 个历史失败的归属与处置：要么修（anchor 漂移是锚点与工作树字节漂移，看名字像是记录已过期），要么在仓库内钉一份"已知失败清单 + 归属票"，让新增失败一眼可辨。此事属验收/装配权威，建议由它裁定。

## 2【高】Bun 1.4.2 的传输／服务端平台事实没有权威落点

**事实**（本轮实测，均在工作树上真跑）
- `fetch(url, { proxy: false })` 在进程内有 `HTTP_PROXY` 时**仍走环境代理**（上一轮已证，本轮故障注入再次复现：smoke 第 1、2 项 `the ambient trap 1`，随后第 8 项以未捕获 `TypeError: Unable to connect` 中止）。
- `node:http` 客户端**不受** `HTTP_PROXY` 影响（同一进程、同一死端口：`ECONNREFUSED 127.0.0.1:1`）。
- `http.request(options)` 建好请求后**必须 `.end()`**，否则不发送：请求会挂约 12s 后以 `ConnResetException: socket hang up` 结束，且**目标完全没有记录到任何请求**（本轮第一版实现漏了 `call.end(init.body)`，这就是那次"所有直连用例 12s 后失败 + smoke 崩溃"的真因）。
- `http.request({ createConnection: () => socket, agent: false })` 在本机 Bun 下**不建立 CONNECT 隧道**（探针挂住不触发 `connect`）；`http.Agent` 子类在 `createConnection()` 里返回已建 socket 可行。
- `tls.connect({ socket, servername: "127.0.0.1" })` 抛 `Setting the TLS ServerName to an IP address is not permitted`；IP 目标必须不传 `servername`。
- 在**承载** `Bun.serve`／`Bun.listen` 服务的同一个进程里调用 `spawnSync` 会死锁：父进程事件循环被同步等待占住，子进程的请求永远拿不到应答（本轮两次探针各跑满 120s/180s 后被 kill，输出反而因超时丢失）。
- 运行期设置 `process.env.NODE_TLS_REJECT_UNAUTHORIZED = "0"` 对本运行时自己的 `node:tls` 生效（无需启动前设置）；`NODE_EXTRA_CA_CERTS` 在 spawn 时未见生效证据。
- `Bun.write(Bun.stdout, text)` 后再 `process.exit` 能保住子进程输出；`console.log` + 立即 `process.exit` 在重定向到文件时可能丢。

**推断**
- 这些事实每一条都对应一次以上的探针往返（本轮探针计 4 个文件、7 次运行，其中 2 次因死锁/超时白跑），下一个碰 HTTP／loopback 捕获／子进程的 agent（connect-bot 迁移、codex 捕获、harness-dock）会把它们重新发现一遍。上一轮 retro 已给出同样判断，**目前仍然没有任何权威文档落点**：`framework/docs/harness-support.md`（自称 harness observations and integration evidence）里 `proxy`／`HTTP_PROXY` 出现 0 次；HTTP 能力章节只写"不依赖环境变量"的政策，不写平台行为。

**建议**
- 在 `framework/docs/harness-support.md` 增一节（该文件已有 "recorded facts" 体例，与 provider-path role evidence 相邻），逐条记录上述 Bun 1.4.2 事实 + 最小复现（端口 1 死目标 + 本地陷阱即可判定）；从 `framework/docs/framework-capabilities.md#general-http-module` 与 `framework/modules/http.ts` 的模块注释各放一个指针指过去。政策与平台事实必须分开写，否则下一位读者会把"框架不读环境变量"误读成"平台也不会读"。
- `spawnSync` 死锁与"探针输出要同步落盘"两条，除文档外更值得进第 5 条的探针约定。

## 4【中】缺"平台默认不等于承诺兑现"的评审标准

**事实**：上一轮的失败在真实 smoke 里是可观察的（环境代理接走了显式直连的请求），但当时被记成 `NOTE 平台观察：… the framework states the path, this runtime's fetch decides the connection`，并配文"不是本票缺陷，交验收裁定"，于是那一轮以 `11 passed / 0 failed / 1 observation` 收场（本轮故障注入复现同一现象，但现在是 `FAIL`）。本轮修复后该承诺才在传输层成立。

**推断**：这类失败不是靠更严格的测试写法能防的，而是靠"评审时判定某项验收在**执行层**是否成立"。仓库现有的相关断言恰好是被本票禁止的形状（`expect(init.proxy).toBe(false)` 之类的参数转发），说明这条判断没有落点。

**建议**：给 review 阶段加一条**判断型**标准（不是机械可查的），大致措辞："一项验收若承诺的是**效果**（路径被兑现、超时覆盖正文、失败不外泄），则观察点必须在执行层（真实传输、真实时钟、真实进程），不得用'框架把参数传对了'或'平台默认如此'作为兑现；无法执行层验证时，验收项记为**未达成/未验证**，不得记为 observation/note。" 与上一轮 retro 第 3 条同源，建议合并成一条，落在 `CODING_STANDARDS.md`。

## 5【中】缺探针约定（落点、落盘、超时、spawnSync）

**事实**
- 本轮探针全部写在 `.cache/`（已被 `.gitignore`），但这是我自己的习惯，`AGENTS.md`（651B）没有这条约定。
- 两次探针因为"承载 loopback 服务的进程里 `spawnSync` 子进程"而**死锁**（120s／180s 后被 kill），其中一次的成对 `timeout 90 … | tail -20` 还使输出随超时一起丢失；改用异步 `Bun.spawn` 后立刻拿到结果。
- 成功的探针用了两个技巧：`appendFileSync` 同步落盘（崩溃也留下已得结论）、把判定做成"死端口 + 本地陷阱"这类不需要目标活着的最小复现。
- 长任务的输出易丢：`bash` 后台化后超时，系统只回 "the shell backend did not respond, so any output above may be incomplete"（本轮 bg_18/bg_19 即如此），结论全没了。

**推断**：探针是本仓库（HTTP 传输、loopback 捕获、dock 子进程）的高频动作，约定缺失时每个 agent 用自己的写法，代价落在白跑的分钟数上。

**建议**：在 `AGENTS.md` 加一行导航指针指向一段简短约定（或新建 `scripts/README` 一样的短文档）：①一次性探针放 `.cache/`（gitignored）；②结论 `appendFileSync` 落盘，不要只靠 stdout；③所有命令带 `timeout`，探针自带每步上界（`Promise.race` 计时器）；④**不在承载 `Bun.serve`/`Bun.listen` 的进程里 `spawnSync`**，用异步 spawn 并显式读 stdout/stderr/exitCode；⑤最小复现优先用"死端口 + 陷阱响应"判定路由，而不是断言转发参数。

## 值得保留（事实）

- **先读上一轮的证据与 retro**：两份共约 20KB，替我省掉了整套"重新发现失败"的过程；retry 场景应默认这样做。
- **故障注入**：把默认传输换回 `fetch` → 定向观察到第 1/2 项 FAIL、随后中止；还原后立刻复绿。成本 32s，是"我的证据抓不抓得到这个缺陷"最便宜的证明，也正好复现了被否决的形状。
- **同步落盘的探针**：崩溃也留下结论，比 stdout 可靠。
- **真实读数代替字面值**：smoke 每项打印目标/代理侧的真实记录与 `elapsedMs`（如 `TimeoutError after 202ms`、内置预算 `30007ms`、陷阱 `0 request(s)`），让"预算覆盖正文""无隐式代理"变成可核对的事实。
- **边界规则（hook 提醒）确实改善代码**：`ts-no-inline-cast-access` 促使我把对 JSON 的内联断言换成 `reachedPath`/`echoedFields` 形态的运行时收窄；`ts-promise-with-resolvers` 让探针与传输都改成 `Promise.withResolvers`；`ts-no-tiny-functions` 让 `portOf` 这类"具名计算"得以存在而删掉纯改名的包装。保持启用。
- **用临时配置文件驱动命名代理**：`createHttpModule({ configPath: <mkdtemp>/shared.yaml })` 让真实代理路由可在不写仓库文件、不碰正式 OMP 的前提下验证；共享文件属机器、缺文件语义两侧都有断言，这条边界值得写进同类票的做法。
