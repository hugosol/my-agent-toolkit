## 1【高】仓库没有 guardrail，且 `scripts/` 在 typecheck 之外

**事实**
- `tsconfig.json` 的 `include` 为 `["framework","extensions","entrypoints","tests"]`——不含 `scripts`。
- 本次新写的 `scripts/http-transport-smoke.ts` 存在真实类型错误（`observe(label, "fail", detail)` 与形参 `boolean | "note"` 不兼容）。`bun run typecheck` 始终报 **0 errors**；该错误只在手工 `bunx tsc --ignoreConfig --noEmit … scripts/http-transport-smoke.ts` 时才暴露。
- 后果是**静默**的：首次完整 smoke 输出 `SMOKE SUMMARY: 0 passed, 0 failed, 12 observation(s)`——12 条检查全部落到 `NOTE` 分支，命令**退出码为 0**。若我没有手工补跑 tsc，这一轮"证据"会以绿色收场。
- 仓库根目录无 `.github/`，`.git/hooks` 只有 sample，无 lefthook/husky 配置（已查）。
- 既有 `scripts/verify-omp-candidate.ts`、`scripts/capture-codex-outbound.ts` 在等价编译参数下**无错误**（已实测）。

**建议（按成本升序）**
1. 把 `"scripts"` 加进 `tsconfig.json` 的 `include`。代价一行，且已证实不会引入既有错误。
2. 给仓库加一个最小 guardrail：pre-commit 或 CI 跑 `bun run typecheck && bun test`。当前"检查存在但没接线"的状态意味着任何 typecheck/test 结论都依赖 agent 自觉。
3. 让新 smoke 类命令进入聚合入口（见第 6 条），否则"真实传输证据"会静默腐烂。

## 2【高】平台事实没有归属文档，而生产注释与平台行为相反

**事实**
- `extensions/connect-bot/shared-logic/panel/client.ts:41` 写着"Never route a panel request through an ambient/`http_proxy` proxy"，并把 `proxy: false` 送入 `bun` 的 `fetch`。
- 本次实测（Bun 1.4.2）：存在 `HTTP_PROXY` 时，`proxy: false` **仍然走环境代理**；`""`/`{}`/`null`/`0`/`respectNoProxy` 同样无效；`node:http` 客户端不受该变量影响。最小复现输出：`bun 1.4.2: fetch(..., { proxy: false }) -> "answered-by-the-ambient-proxy" through http://127.0.0.1:1856`。
- 该平台行为在文档里没有落点：`framework/docs/harness-support.md` 中 `proxy`/`HTTP_PROXY` 出现 0 次；ADR-0002 与 HTTP Lighthouse 记录的是**政策**（"不依赖全局代理环境"），不是**平台行为**。
- connect-bot 的 5 个测试文件（`arm`、`budget-regression`、`heartbeat`、`off`、`state-machine`）对代理只有 `expect(init.proxy).toBe(false)` 这类参数转发断言——永远抓不到该行为差异。

**代价（事实）**：本次约三分之一会话（probe1–probe6、client2、driver、nodehttp、tlsprobe）用于重新发现这条平台事实。

**推断**：ticket 22（connect-bot 迁移）与 Codex 相关票会继续消费 `proxy:false`／命名代理；若运行环境带 `HTTP_PROXY`，"省略即直连"的承诺在平台层不成立。本机环境只有 `PI_PROXY_OPENAI*`、无 `HTTP_PROXY`，所以正常使用不触发。

**建议**
- 把该观察写进它的既定归属 `framework/docs/harness-support.md`（该文件自称 "harness observations and integration evidence"），并从 HTTP 能力章节指过去（导航指针），使下一个 agent 一步可达。
- 由 connect-bot 的归属票修正 `client.ts:41` 的注释，并为其补一条真实传输断言（或明确标注"平台限制、未兑现"）。

## 3【中】缺"传输证明 vs 参数转发"的评审标准

**事实**：本票验收明确写"不能以参数转发断言代替传输证明"，而仓库现有测试正是该形状（见第 2 条）。本次我为此另写了 11 项真实 loopback smoke，但这条规则目前只存在于这张 ticket 的正文里，评审 agent 看不到。

**建议**：往 `CODING_STANDARDS.md` 加一条判断型标准（非机械可查），例如："mock 平台调用的断言只证明我们传了什么，不证明路由/超时/协议；同一主张需要一条真实传输 smoke，或显式记录为未验证。"交由 review 阶段执行——本票的教训是它属于"判断"而非"机械"类。

## 4【中】共享配置文件位置与是否入库靠推断

**事实**：HTTP Lighthouse 规定共享配置为 `framework/config.yaml`，并明确 YAML 示例"不是新增生产文件或实际地址"；但没有任何权威说**本仓库是否随包提交该文件**。我据此**推断**不提交（缺文件时直连照常、命名代理报配置错误，两者都已实现并两侧测试），并把该判断写在证据文档里。

**未验证**：验收环境是否预期仓库内存在 `framework/config.yaml`；若无而预期有，会被读成"交付不完整"。

**建议**：在 HTTP Lighthouse（或装配权威）补一行：文件位置、是否随仓库提交、缺文件时的语义。若本票的推断正确，也值得在验收票里显式确认一次，避免下一张 HTTP 消费票再推断一次。

## 5【中低】codebase-memory 与工作树不同步

## 6【低】探针卫生与聚合入口

**事实**：单个探针（`probe1.ts`）因转发代理自环，输出被截断为 "lines 1-958 and 1138-2094 of 2094"，一次工具结果冲掉大量上下文；随后又写了 6 个探针才收敛。`.cache/` 是天然落点（已被 `.gitignore`），但 `AGENTS.md` 未记录 throwaway 探针放这里。

**建议**：把"探针写进 `.cache/`、只记计数不记全量数组、用已关闭端口/不转发代理作判别"写成一行约定（导航指针或探针目录 README）。另：新 smoke 目前只挂在 `bun run smoke:http-transport`，`bun test` 不会跑它——建议并入某个 `verify:*` 聚合命令，否则真实传输证据无人续跑。

**过程自评（事实）**：我在最后一次代码改动**之前**启动了 119s 的全仓套件，导致必须重跑一次。聚合套件应放在改动冻结之后。
