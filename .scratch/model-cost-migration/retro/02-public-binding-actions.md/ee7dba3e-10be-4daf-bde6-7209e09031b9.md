## 1.（高）仓库仍无 guardrail，且"哪几项红与我无关"仍靠上一轮 retro 传递

事实：本会话的既定红灯判定来自 `.scratch/model-cost-migration/retro/.../02-*.md` 与 ticket 01 的 retro 文本，而非仓库内任何文件；`package.json` 有 `test`/`typecheck`，但没有 CI/pre-commit 强制点（本会话未见）；4 项红灯每次都有人重新推导。这是 ticket 01 retro 与第一轮 retro 都提过的同一条。

建议：落最小 guardrail（`bun run typecheck` + `bun test tests/framework` 进 pre-commit，dock 进 CI），并把"当前既定红灯集合 + 每项耗时"写进仓库（`tests/README.md` 或 CI allowlist）。这样下一位 agent 不必读别人的 retro 才知道哪些红是环境事实。

## 2.（高）并发跑测试会污染全仓基线：真实宿主/时序敏感用例必须串行

事实：我一边在后台跑全仓 `bun test`，一边跑 focused suite，得到 **7 fail**；其中 `tests/connect-bot/request-timeout.test.ts` 的 budget 用例 51.55ms 就失败，单独重跑 10/0（15.3s）；`tests/framework/admission-notice.test.ts` 的真实宿主用例也在那次失败；idle 重跑全仓回到 4 fail。为此多花了一次全仓（118.8s）+ 一次单文件（15.3s）才排除自伤。

建议：把"同一时间只跑一个 `bun test` 进程"写成仓库约定（AGENTS.md 或 tests/README 一行），并给真实宿主/时序敏感套件单独入口（如 `bun run test:dock`、串行跑），别让它们在并行套件里互相抢 CPU。

## 3.（高）故障注入要打到 criterion 具名的每个 seam，并让用例结束在"有区分度"的状态

事实：我最初的 dock case 顺序是"先 `new_session`，再切回首个 session"，注入第一轮的规则后它**仍然通过**——因为退出时正在服务的恰好是初始化实例的那个 owner；把"切回首个 session"挪到 `new_session` 之前（结束时正服务被切换过去的 session）后，注入立刻表现为 `cleanup instance=1` 0 次 vs 修好后 1 次。framework 侧同一注入则当场失败。

建议：在 `tdd` skill 的 fault-injection 段落加一条硬要求：criterion 点名多个 seam（本票 S1、S5）时**逐 seam**注入；并检查用例的**最终状态**是否就是判别态（否则该 case 只是"看起来在跑真实路径"）。

## 4.（中）宿主契约事实仍无仓库落点——本轮又去 grep 了一遍安装源

事实：为写真实宿主用例，本会话读了 `.cache/omp-baseline/18.5.0/.../src` 的 loader.ts（extension factory 每次 load 调用一次，`loader.ts:405`）、rpc-mode.ts / rpc-types.ts（`new_session` / `switch_session` / `branch` 的形状与 `data` 信封）、agent-session.ts（`branch` 会移到新的 session 文件；`switchSession` 用 `path.resolve`）、types.ts（生命周期 `on(...)` 无退订）等 8 处以上。附带成本：RPC 响应把结果放在 `data` 里，我用错字段白跑一次 5.8s dock。

建议：在 `framework/docs/harness-support.md`（或 `tests/harness-dock/README.md`）落一个 "recorded host contracts" 小节，一行一事实 + 文件:行 + 来源（源码阅读 / 实跑）。这是第一轮 retro 第 3 条的重复项，本轮出现第二次——重复两次说明它是稳定缺口。

## 值得保留的做法

- **先在安装源里确认宿主契约，再写真实宿主用例**：`new_session` / `switch_session` / `branch` / `set_model` / `set_thinking_level` 一次写对，dock 用例整体 5.8s，没有"盲试真实宿主"的迭代。

- **注入跑到每个 seam**：本轮最有价值的一步——正是它暴露了 dock case 顺序不敏感（第 3 条）。

- **改规则就同步其权威文本**：GLOSSARY / capabilities / README / ADR 四处一起改 + 行锚重同步，避免下一位读者被旧规则误导（第 5 条）。
