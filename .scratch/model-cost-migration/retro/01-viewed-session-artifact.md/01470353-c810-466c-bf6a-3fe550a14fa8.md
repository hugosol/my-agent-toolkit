# Retro — ticket 01（Viewed session 公开出口与冻结宿主）

Scope：本会话（`01-viewed-session-artifactmd-2`）的 TDD 执行轮。事实来自本会话工具结果；推断与未验证项已标注。

## 1.（高）仓库没有 guardrail，且现有 `bun test` 本身是红的

事实：
- 仓库根无 `.github/`、无 `.husky`、无 `.githooks`，无 biome/eslint 配置；`package.json` 有 `test`、`test:dock`、`test:framework`、`typecheck` 但没有任何自动触发点。
- 本会话实际运行整仓 `bun test`：**443 pass / 4 fail**（两次运行一致）。
- 4 项失败中 2 项是 `baseline.test.ts` 的 byte-identity：`../oh-my-pi` 的 HEAD 已是 `579da1d`（18.8.6），而记录锚点是 `9348320`（18.5.0）；另 2 项是 connect-bot panel 协议用例（20.2s / 15.0s，依赖真实 panel 双桩会话）。

推断：我花费 4 次工具调用（含一次 118s 整仓运行）才判定这 4 项失败与自己无关；后续 agent 每次都会重复这笔开销，也可能反过来“学会忽略红色”。

建议：
- 增加最小 CI（或 pre-commit）：`bun run typecheck` + 目标测试集。
- 让红色可执行：把 2 项锚点漂移检查改为“需要维护者显式重记锚点”的显式失败信息（或按验收流程更新记录），并确认 connect-bot panel 两项在当前环境是否应跳过；否则新 guardrail 从第一天起就是红的。
- 未验证：connect-bot 两项是否在本次改动前即失败（我只验证了它们只从 dock 导入 `REPO_ROOT`，未做暂存回滚对照）。

## 2.（高）宿主 patch 没有 typecheck —— 而这正是本次抓到真 bug 的检查

事实：`bun run typecheck` 覆盖 `framework/ extensions/ entrypoints/ tests/`；`scripts/` 与 `host-patches/` **不在 include 内**。被 patch 的宿主源码（`@oh-my-pi/pi-coding-agent`）完全不参与任何 typecheck。
本会话临时拼出 A/B typecheck（同一组入口文件，分别以基线安装与补丁 artifact 为 cwd）：基线 363 错 / 补丁 364 错，差集里是一条真错误——`src/session/agent-session.ts` 手工构造的 `ExtensionCommandContext` 漏了新成员；修好后 363 / 363（差异仅是安装路径），随后 11 个 test 全绿。

建议：把这套 A/B 检查固化为脚本（如 `scripts/check-host-patch.ts`，输出“新增错误”而非全量噪声），并入 `package.json` 与 dock 套件；同时把 `scripts/` 加进 `tsconfig.json` 的 `include`（一行修复）。
注意：被 patch 的宿主自身有约 363 条环境性错误（发布包不带 `.md`/`axe-core` 的 ambient 声明），所以检查必须是**差集**而非“零错误”。

## 3.（中）Windows 上打补丁的两条静默陷阱

事实：
- 在仓库内执行 `git apply -p1 <patch>` 时，git 按**工作树根**解析补丁路径而非 cwd，输出 `Skipped patch ...` 并以 **exit 0** 结束；我一度看到 `APPLIED` 却什么也没改。可用形式是 `--directory=<repo-relative pkg dir>`。
- 仓库 `core.autocrlf=true`：首次 apply 后 `viewed-session.ts` 出现 274 个 CR，而基线文件是 LF。改为 `git -c core.autocrlf=false` 生成并应用补丁后，`diff -r` 得到 `TREES-IDENTICAL`。

推断：这两条若不修，artifact 会以“看起来成功”的方式被悄悄改写（CRLF 版本、或未打补丁的副本）。

建议：把这条配方写入仓库级“host patch 配方”文档（本次已写进 `host-patches/omp-18.5.0-viewed-session/README.md`），并在物化器里加一条确定性断言：补丁后文件不得含 CR。（当前物化器已用 `--whitespace=nowarn` + `core.autocrlf=false` + sha256 校验，风险已受控；缺的是那条显式断言。）

## 4.（中）真正花时间的是“宿主事实”，而 dock 只有源码可读

事实：本会话为确认下列事实读了宿主 ~8k 行源码与多个 200+ 行区段：RPC 有 `request()`/`prompt()` 与哪些命令（`get_state`、`set_thinking_level`、`get_available_thinking_levels`、`new_session`）；模型必须 `reasoning: true` 才有可选 Effort，且设置**相同** level 不产生事件；focus/view 只存在于 TUI，RPC 无“查看目标”；扩展 factory 按 session 重绑而 view 是进程级。`tests/harness-dock/` 无 README，这套知识散在 12 个文件的 doc comment 里。
任务提示建议优先用 codebase-memory-mcp，但本会话**一次都没有调用**（事实）；它是否索引了 `../oh-my-pi` 未验证。

建议：
- 新增 `tests/harness-dock/README.md`：入口点（baseline/env/session/capture-server/run-root）、模式差异（RPC vs TUI）、驱动真实宿主的配方、以及“哪些事实只能在模块层覆盖”。

## 5.（中）机械性规则以“事后提醒”形式出现，仓库侧无确定性检查

事实：本会话中被 7 类规则提醒打断（`ts-set-map`、`ts-no-tiny-functions`、`ts-import-type`、`ts-no-dynamic-import`、`ts-no-test-timers`、`ts-no-inline-cast-access`、`ts-no-any`），每次各花一次修正编辑；仓库既无 linter 配置也无 `CODING_STANDARDS.md`，实现 agent 事前看不到这些规则。

推断：这类“固定语法模式”本应由确定性检查在提交前拦截，而不是在写入后作为提醒进入上下文。

建议：为该语言选定最省事的一种（biome/oxlint 或自定义 lint 规则）+ pre-commit/CI，把机械项下沉为检查；`CODING_STANDARDS.md` 只保留判断类标准。若这些规则来自全局默认集而非仓库，至少在仓库里声明哪些是本地硬约束，避免实现轮反复试错。

## 6.（低）工具经济

事实：
- `du -sh` 扫 915MB 前缀耗时 119s（后台），返回“包 60MB / src 23MB”，而最终方案是 `bun install` 新前缀（10.4s）——该查询在决策已定后才有价值。
- 整仓 `bun test` 跑了两遍（118s + 113s），第二遍只为列出 4 条失败；`grep -E "^\(fail\)"` 本可与第一遍合并。
- 环境摩擦各耗一次调用：`async` + 服务名被拒（“Service mode does not accept async or timeout”）、原生 git 看不到 `/tmp`、shell 无进程替换 `<(...)`、`file:///$PWD` 路径被拼坏。

建议（低优先，主要是习惯）：先问最小的量（单目录/单文件 sha 或 `ls -S`）再决定是否需要全量扫描；一次整仓运行就带上失败过滤器；Windows 下给 git/路径优先用仓库相对路径与 `file:///…` 绝对形式。

## 值得保留的做法

- 物化器 + 冻结记录（`record.json` 的 pre/post sha256 + 复用前校验）确实阻止了静默漂移：一次失败的 apply 也会被哈希校验按“不是冻结内容”拦下。
- 依赖既有 dock（explicit-only 加载、临时 run root、env offset 清洗、本地 capture endpoint）使得“真实宿主运行 + 无网络/无凭据”同时成立，无需新验证框架。
- 用未打补丁的基线安装做对照（同一探针报告“无出口”），以及故障注入（禁用变化监听后交付数 1→0，恢复后 1），把“测试是否真的敏感”变成了可观测事实而非信念。
