# Retrospective — ticket 05 authoring/Subagent TDD run

## High

### 1. The check commands exist; no in-repo guardrail runs them

**Fact:** `package.json` exposes `typecheck`, `test:framework`, `test:codebase-tools`, `test:dock`, `check:integrations`. The worktree contains no `.github` directory and `git config core.hooksPath` is empty. The run ran these commands by hand; the first post-move typecheck listed 27 `error TS…` lines, and the import-boundary test caught both the adapter re-export and the removed legacy exception.

**Recommendation:** add a pre-commit hook running `bun run typecheck` and `bun test tests/framework/import-boundary.test.ts` — both completed in well under a second in this run — and a CI job running typecheck plus the four partitions and the dock. The commands already exist, so this wires a guardrail rather than inventing one. External CI may exist outside the worktree; that is unverified. Within the repository, none was observed.

### 2. `framework-capabilities.md` line anchors are a maintenance trap

**Fact:** `framework/docs/framework-capabilities.md` is 1208 lines and carries 137 `#Lnnn` anchors. This run edited that file 28 times, largely to retarget anchors after declarations moved, and several source-location links were repointed. An ad hoc check found no missing files and no out-of-range anchors, but an in-range anchor pointing at the wrong line is invisible to that check.

**Inference:** the churn is structural, not incidental: the doc is the symbol→source index, and every declaration move rewrites the line numbers it cites. The next ticket touching these files will pay the same cost and can silently leave wrong anchors.

**Recommendation:** link to headings or symbols (or a generated symbol table) instead of `#Lnnn`; add a docs link check for missing files and out-of-range anchors to the existing script/test set. If line anchors stay, regenerate them from an outline in the same commit as the move. This removes the 28-edit class of churn and makes the index stable across refactors.

## Medium

### 3. `docs/agents/testing.md` is the right pointer but omits the worktree runbook

Four facts the run had to discover the hard way:

- **Bootstrap:** `bun run typecheck` failed with `bun: command not found: tsc`; `bun install --frozen-lockfile` fixed it. `testing.md` never says install first.
- **Capture:** the first attempt used Python `subprocess` and produced 29-byte logs (the Bun banner only) for framework/model-cost/connect-bot; the run re-ran all three with `(cmd 2>&1; echo exit=$?) | tee log | tail`, spending about 132 seconds redundantly. `testing.md` says save a run log but not how.
- **External binary:** `tests/connect-bot/support/omp-bot.ts` defaults to `<repo>/../omp-bot/backend/target/release/...`; a worktree's parent does not contain that checkout. The run used `OMP_BOT_BINARY` copied from ticket 04's evidence; `testing.md` does not name it.
- **Baseline record:** `framework/docs/harness-baseline.json` is named only in a comment in `tests/harness-dock/baseline.ts`; finding it took four calls. `testing.md` does not point at it.

**Recommendation:** add one "Worktree runbook" block to `docs/agents/testing.md` with those four facts, and resolve the omp-bot default from the main worktree/common directory when possible, keeping the environment variable as the override. This is exactly the cache testing.md should hold: facts no config file states. Do not move them into `AGENTS.md`; it is already a lean pointer file.

### 4. The authoring batch's dependency on Command declarations is implicit

**Fact:** the existing import-boundary rule (“capability interfaces depend on no framework implementation”) forbids `interface/details/implementation.ts` from importing `core/assembly` or `core/protocol`. Because `ExtensionImplementation` references command implementation types, the run had to create `framework/interface/command.ts` and move the public Command declarations here, before the Command batch. The run discovered this by reading the test, then implemented it; neither the ticket nor the spec names this prerequisite.

**Recommendation:** state in the spec/authoring documentation (or the ticket's “what to build”) that the authoring entry requires the Command declaration/implementation/delivery group to be canonical, while the Command runtime narrowing remains the next batch. Alternatively, make the import-check failure message name the target entry so the next agent does not reverse-engineer it. This is a planning/navigation gap; the resulting state typechecks and the boundary test is green.

### 5. The handoff evidence format lives only in prior artifacts

**Fact:** the run read `evidence/04-host-facts-verification/README.md` to learn the expected record: source state, commands and exit statuses, dependencies/lockfile, harness version and patch, environment, pass/fail/unverified scope. `testing.md` states completion evidence but not the record shape.

**Recommendation:** add a short template at `docs/agents/handoff.md` (or a comment in the evidence directory README) with those fields and one compact example, and point to it from `testing.md`. This is cheap and reduces variance between tickets.

## Low

**Fact:** `git config core.autocrlf` is `true`; `git add` emitted 16 LF→CRLF warnings for files touched with `sed`/`write`, and there is no `.gitattributes`.

**Recommendation:** add `* text=auto eol=lf` (or the repository's chosen policy) so the worktree stops warning and diffs stay stable across agents and operating systems. Low risk; the trade-off is that Windows editors may prefer CRLF.
