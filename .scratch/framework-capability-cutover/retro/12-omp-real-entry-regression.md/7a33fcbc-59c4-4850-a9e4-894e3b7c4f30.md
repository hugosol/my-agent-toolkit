### 2. [高] shell 读取工具反复替代专用工具，且 `cat` 输出被改写

**事实**
- 系统工具策略明确要求：文件读取用 `read`，结构/名称用 `glob`，正则/字面量搜索用 `grep`，不要用 shell 等价物。
- 实现轮仍有约 24 次 `bash` 命令包含读取类工具，例如：
  - `cat package.json && echo ===== && cat docs/agents/testing.md`
  - `grep -n 'test("' tests/codebase-tools/*.test.ts`
  - `sed -n '1,40p' tests/connect-bot/...`
  - `cat extensions/model-cost/config.yaml`
  - `sed -n '229,260p' .../model-cost-presentation-smoke.ts`
- `cat package.json` 的返回不是原始 JSON，而是被格式化成 `package.json: my-agent-toolkit`、`dependencies: 5 ...` 的摘要；随后 agent 不得不用 `read` 重读一次。session 日志第 36 行保留了这次输出。
- 其他 `cat`（如 `config.ts`、`config.yaml`）返回的是原始文本，说明格式化行为至少不是全局一致的；具体触发条件未验证。

**推断**
- 这是一条典型的“prose 规则是 no-op”：规则已经存在，仍然没有改变工具选择。再加一条规则不会解决问题，确定性 guard 或工具行为修正更有效。
- `cat` 的格式化输出让“shell 读取”变得不可预测；专用 `read` 至少有稳定的行号、截断和分页语义。

**建议**
- 在 bash 包装层对纯读取命令（`cat`、`sed -n`、`head`、`tail`、以及只读文件的 `grep`）做警告或拒绝，并直接提示对应的 `read`/`grep`/`find`。这是 deterministic check，优于 prose。
- 修正或移除 `cat` 的格式化行为，至少保证 `cat` 是原始字节；否则“读文件”在 shell 里永远有惊喜。
- 对“列出测试名/查找调用点”这类任务，专用 `grep` 工具已足够；本轮的 `grep -n 'test("'` 和 `grep -n "function payloadRecord"` 都可以用 `grep` 工具完成并保留路径/上下文。

**未验证/边界**
- `cat` 格式化是宿主包装层还是 shell 配置导致，未验证；本复盘只记录观察到的输出差异。
- 是否所有读取类命令都值得硬性阻断，需要权衡；短小的 `ls`/`wc`/`sha256sum` 可能仍是合理的 bash 事实查询。

### 10. [低] `verify:omp-candidate` 跑了两次

**事实**

- 在验证流程中明确：先提交证据，再跑 `verify:omp-candidate`；或者接受 `dirty=true` 并在 README 说明 changedPaths 仅为证据。
