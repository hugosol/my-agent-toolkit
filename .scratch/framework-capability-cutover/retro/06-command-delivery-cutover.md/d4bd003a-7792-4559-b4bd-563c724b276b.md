## 1. [高] 既有 flaky 用例会污染验收证据

**事实**
- 11:47 的 `bun test tests/model-cost` 为 **515 pass / 1 fail**；失败用例是 `tests/model-cost/harnesses/pi/pi-disposal-round-close.test.ts` 的「leaving a session for another one closes no Round…」，错误为 `no record for pi-disposal-child was published … it holds undefined`。
- 单独重复该文件 3 次：2 次通过、1 次失败；在 base `c5a8b2a` 的独立 worktree 重复 5 次：3 次通过、2 次失败，错误签名相同。最终本票树重跑为 **516 pass / 0 fail**。
- 该用例与 Command delivery 无调用关系。

**影响**：任何 ticket 在最终回归时都可能抽到红色，导致误归因、重复跑分区，或把既有 flake 记成本票回归；P52 的证据可信度也会被拖累。

**建议**
- 把 `savedRecord` / `harnessTask` 的固定 200 次 fake-timer + `setImmediate` 等待，改成等待实际写入完成或真实 I/O 轮次；若短期无法定位根因，明确 quarantine 并记录原因。
- 增加一个 `bun run test:repeat -- <file> --runs N`（或等价脚本），让 flake 在分配、交接和最终验收前可重复复现，而不是靠运气。

**证据状态**：flaky 与 base 复现为事实；根因未验证。

## 3. [中] 文档行号锚点没有自动检查

**事实**
- `framework/docs/framework-capabilities.md` 的 `HarnessPort` 链接指向 `protocol.ts#L590`，实际 `export interface HarnessPort` 在 604 行。
- 同一文件的 `OwnerCapabilityHandle.state` 行链接 state interface 的 `#L398`，实际 `export interface OwnerCapabilityHandle` 在 118 行。

**影响**：文档是扩展作者的导航面；锚点漂移会让 agent 跳到错误位置，随后用更多 `read`/`grep` 纠正。最终导航一致性虽由 ticket 11 复核，但没有自动检查时仍靠人工记忆。

**建议**：增加 `scripts/check-doc-anchors.ts`（或扩展 import-boundary 套件），对 Markdown 的 `path#Lnnn` 链接做“文件存在 + 行号在范围内 + 附近出现链接文本/符号”的轻量检查；或把符号链接改为不带行号的 `path` + 符号名。先跑一次现有文档，把存量漂移作为 ticket 11 的输入。

**证据状态**：具体行号漂移为事实；检查脚本的成本与误报率未验证。

## 4. [中低] 工具经济：一次 `read` 选择器和 `tail` 截断造成重复成本

**事实**
- `read` 调用 `docs/adr/0002-semantic-extension-framework.md:246:raw` 返回 **40,658 字符**（整段/近整文件），目标只是单行；工具文档要求精确行用 `:raw:246`。
- 发现 model-cost 失败时先用 `| tail -5`，失败详情被截掉，随后又跑了 `grep` 和两次完整日志才拿到错误上下文。
- 会话统计：244 次工具调用、约 81.6 万字符工具输出；`framework/interface/command.ts` 被完整读取两次（各约 15,080 字符）。

**影响**：单次 40k 字符约等于一万 token，且会挤占后续推理；`tail` 截断会把一次失败变成多次完整分区运行。两者都不改变正确性，但直接消耗 ticket 的时间和上下文预算。

**建议**
- 在 `read` 工具层让 `:N:raw` 与 `:raw:N` 等价，或对疑似顺序写反的调用返回一条明确的修正提示。
- 给测试分区提供默认 tee 日志的 wrapper（testing.md 已要求长跑保存日志），终端只打印摘要与失败用例；这样既保留完整证据，又不需要靠 `tail` 猜。
- 可选：本次 `list_projects` 只看到主仓（hyper-tdd / c5a8b2a），没有 worktree 项目；若 worktree 也建立索引，可能减少部分静态读取。**推断，未验证**其实际收益。

**证据状态**：字符数、调用数和重复读取为事实；wrapper 与 worktree 索引的收益未验证。

## 5. [低] 交接证据没有固定下一批的目标布局

**事实**
- ticket 05 的 evidence 称 flat `framework/interface/command.ts` 是 Command 的 canonical destination；Lighthouse 05/07 要求 `framework/interface/command/index.ts` + `details/definition.ts`、`details/implementation.ts`；本票 acceptance 没有写路径。
- 本次执行在 11:32–11:33 先判断“是否拆分”，最终按 Lighthouse 拆分并迁移消费者。

**影响**：本票成本很小，但同类交接会让下一批再次在“当前文件是否就是目标”上做一次判断；如果判断错，会留下需要后续 ticket 再搬的布局。

**建议**：在 implementation ticket 或交接 evidence 中引用 Lighthouse 的 ownership table 行，或直接写一行“本批结束时该 capability 必须位于 …”。这比在 evidence 里描述“canonical destination”更可执行。

**证据状态**：文档表述与最终布局差异为事实；对后续 ticket 的时间影响为推断。

## 6. [低] 没有单一 check 入口或门禁

**事实**：仓库无 `.github`、`.husky`、pre-commit hook；自动检查只有 `package.json` 的 `typecheck`、`test`、`test:framework` 等脚本。本票的 typecheck、四个分区和三个 dock 均由 agent 手动选择并运行，没有漏检错误。

**影响**：本次没有出错，但检查入口分散，主要靠 agent 阅读 testing.md 后自行拼装；未来的提交可能漏掉某个分区或 dock。属于预防性建议，不是本票缺陷。

**建议**：增加一个 `bun run check` 汇总入口（至少 typecheck + import-boundary + 受影响分区），并在 pre-commit 或 CI 中可选运行；若不做门禁，至少在 testing.md 的 ticket-completion 行列出固定命令组合。

**证据状态**：无 CI/hook 为事实；“加门禁能防止未来漏检”为推断。
