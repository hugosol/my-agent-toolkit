## 建议

### 1. 高：让 `patch.diff` 的 CRLF 不再阻断真实 dock，并禁止用切换 `core.autocrlf` 来修复

- 事实：首次五文件 dock 运行在 `patchTouchedFiles` 处报 `host-patches/omp-18.5.0-viewed-session/patch.diff touches no file`；该函数按 `\n` 切分并匹配 `^diff --git …$`，而 worktree 因 `core.autocrlf=true` 把补丁检出成 CRLF。恢复 LF 后同一组测试 19 pass / 0 fail。
- 事实：为恢复 LF，本次执行临时执行了 `git config core.autocrlf false`；随后 `git diff --stat` 把 18 个已跟踪文件显示为约 +5792/−5577 行的整文件改动（CRLF 与 LF 索引的差异）。在提交前恢复 `true` 后才回到真实的 +445/−104。若当时直接提交，会把大量文件整体改写成 CRLF。
- 推断：任何 Windows worktree 上的 dock 都会遇到前者；后者是一个容易误提交的仓库级风险。
- 建议：
  - 增加 `.gitattributes`，至少对 `host-patches/**/patch.diff` 指定 `text eol=lf`（必要时覆盖 `*.diff`）。
  - 让 `patchTouchedFiles` 使用 `split(/\r?\n/)`，并在找不到任何 `diff --git` 行时报告"补丁可能是 CRLF"而不是笼统的 "touches no file"。
  - 在 `docs/agents/testing.md` 的 worktree 段落写明：需要 LF 时用 `git -c core.autocrlf=false checkout -- <path>` 或 `git show :<path> > <path>` 物化，不要切换仓库级 `core.autocrlf`。
  - 可加一个轻量检查（pre-commit 或 CI）：对已跟踪文本文件检查 `git ls-files --eol` 没有意外的 `w/crlf`。

### 2. 高：pi smoke 的 Node 24/exit-9 环境阻塞需要被消除或显式分类

- 事实：`bun scripts/pi-codebase-tools-smoke.ts` 在 pi 1.3.0 下通过 34 项检查后，子进程以 exit 9 结束，stderr 为 `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c, line 94`；phase 3–7 未执行。ticket 01 的 baseline 也记录了同一个 Node 24.18.0 libuv 断言。
- 推断：这是 Node/pi 子进程关闭路径的环境问题，不是本次代码改动导致；但它让每个 ticket 的 pi 真实验收都停在半途。
- 建议：在 `tests/harness-dock/pi-session.ts` 或 smoke 的退出路径修复该关闭竞态；或固定一个已知可干净退出的 Node 版本（例如 Node 22 LTS）并记录在 `harness-baseline.json` 的环境段。若短期无法修复，给 smoke 一个"已知环境断言"分类，使 34 项已通过检查仍被记为可达证据，而不是混在普通失败里。

### 3. 中高：worktree 引导缺少依赖安装

- 事实：第一次 `bun run typecheck` 以 `bun: command not found: tsc` 失败；执行 `bun install --frozen-lockfile`（13 packages）后 typecheck 通过，`bun.lock` 哈希未变。
- 推断：每个新 ticket worktree 都会重复这一步，且它发生在 TDD 的第一个验证点，容易把环境失败误读为实现失败。
- 建议：把 `bun install --frozen-lockfile` 加入 ticket worktree 的创建流程（宿主脚本），或在 ticket 的"执行与验证约束"里写为第一条准备命令。

### 4. 中：仓库没有可见的自动 guardrail
