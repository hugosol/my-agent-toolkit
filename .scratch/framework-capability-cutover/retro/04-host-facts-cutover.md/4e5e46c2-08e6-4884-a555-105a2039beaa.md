## 发现（按严重度）

### 1. 高 — 冻结 patch 的 CRLF checkout 阻断真实宿主 dock，且没有确定性检查

**事实**

- `git config core.autocrlf` 为 `true`，仓库没有 `.gitattributes`（本 checkout 验证）。
- `host-patches/omp-18.5.0-viewed-session/patch.diff` 工作树内容为 CRLF；`tests/harness-dock/host-patch-artifact.ts` 的 `patchTouchedFiles` 按 `"\n"` 切分并用 `/^diff --git a\/(.+?) b\/(.+)$/`，尾随 `\r` 导致匹配失败。`bun test tests/harness-dock/model-cost-modes.test.ts` 首次运行抛出 `... patch.diff touches no file`。
- `host-patches/omp-18.5.0-viewed-session/record.json` 的冻结 sha256 `66195465...` 等于 HEAD 中 LF 版本经 `sha256sum` 的结果；即使修好解析，CRLF checkout 也会在冻结哈希检查处失败。
- 会话中把两个 `.diff` 本地归一化为 LF，`model-cost-modes` 6/6 通过；随后用 `git checkout --` 恢复，工作树干净。

**推断**

- 任何 Windows checkout 运行需要 host patch 的 dock 都会遇到同一问题；这是“必需真实宿主证据不可用”的环境阻塞，不是本票代码问题。

**建议**

- 在仓库根增加 `.gitattributes`：`host-patches/**/patch.diff text eol=lf`（如适用再加 `*.diff text eol=lf`）。已有 worktree 可能需要重新 checkout 或 renormalize 一次。
- 将 `patchTouchedFiles` 改为按 `/\r?\n/` 切分，或在 CRLF 时给出明确错误（“patch file has CRLF; expected LF”），避免“touches no file”的误导。
- 增加确定性检查：一个 `patchTouchedFiles` 的 CRLF 用例，以及一个在 checkout 上验证每个冻结 patch 可解析且 sha256 匹配的测试/CI job。
- 在 `tests/harness-dock/README.md` 记录该前提（与第 3 条合并）。

### 2. 高 — codebase-memory 的 “graph first” 指令在 ticket worktree 上不可执行

**事实**

- `list_projects` 返回 21 个项目：主仓库 `E:/Developer/myhub/my-agent-toolkit`（分支 `hyper-tdd`）以及另一个临时 worktree `hyper-ticket-wK2iNw-03`；没有 `C:/Users/hugos/AppData/Local/Temp/hyper-ticket-sgiHp5`。

- 用户消息两次要求“调用 grep 或 search 前先考虑 codebase-memory”；系统 MCP 说明也要求 graph first。

**推断**

- 该 worktree 未索引，graph 工具要么不可用、要么只能查主仓库的 `hyper-tdd` 状态，而不是本票分支；因此“先考虑 codebase-memory”在本环境是 no-op。agent 改用 grep/read 可以理解，但成本高，且存在查到错误分支状态的风险（本次未实际查询，故未发生错误结果）。

**建议**

- 对超过 100 行的源文件，优先 `get_file_outline`/`search_graph` 再读片段；read 工具的 elision 会迫使 ranged re-read。
- 不建议继续在 AGENTS.md 增加“请用专用工具”的散文；优先让专用工具成为最短路径（索引 + 一个 `bun run index:worktree` 辅助）。
