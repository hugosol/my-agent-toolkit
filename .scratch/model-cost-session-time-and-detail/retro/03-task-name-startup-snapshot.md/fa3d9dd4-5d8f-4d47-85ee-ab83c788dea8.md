## 1. 缺 `.gitattributes`：CRLF 工作树系统性打断真实宿主分区的自查（严重）

**事实**：仓库没有 `.gitattributes`（`ls .gitattributes` → 不存在），而本机全局 git 配置 `core.autocrlf=true`（`git config --show-origin --get core.autocrlf` → `file:D:/Program Files/Git/etc/gitconfig true`）。也就是说本机新建的任何 checkout 都会拿到 CRLF 工作树，而仓库里所有 blob 是 LF。

这直接命中仓库自己的"字节同一性"自查，我已复核机制：

- `framework/docs/harness-baseline.json` 记录 `sourceCombination.lockfile.sha256 = 9e9f4833…`；当前工作树 `bun.lock` 的 sha256 与之相同，且文件内不含 CRLF。三者同时成立说明**被记录的哈希是在 LF 字节上算的**。
- `tests/harness-dock/baseline.ts:217` 的 `sha256File()` 直接对工作树文件求哈希并被 `verifyLockfile` 使用（`baseline.test.ts:89-90` 断言 `matches === true`）。
- `host-patches/*/patch.diff` 三个补丁文件都是 LF（逐文件核验），而 dock harness 会把它应用到宿主安装上（`tests/harness-dock/host-patch-artifact.ts`）。

**继承报告**称该问题曾"让每个 dock 文件在 setup 阶段失败"，前任用"从已提交 blob 重写工作树文件"绕过——本轮的 dock 分区之所以能跑绿，正是因为那次重写已经在工作树里生效。我没有第一手复现失败（工作树已是 LF），但机制侧的证据足以确认这不是偶发。

**影响**：本机每一次新 worktree 都会重付这笔成本，而且失败点在真实宿主分区的最前面，症状是 setup 期哈希不匹配 / 补丁应用失败，和"这次改动的对错"无关，极易被误读为改动引入了回归。

**建议**：在仓库根提交一个 `.gitattributes`，例如 `* text=auto eol=lf`（更严格可用 `* -text`）。这是确定性、一行、可一次消灭整类问题的门禁；比写进任何 agent 指令都便宜。已有 CRLF 工作树需要重新检出才会生效，具体机制留给实施者决定。
