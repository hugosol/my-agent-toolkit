## 候选改进（按严重度）

### 1. 真实宿主测试分区在当前 Windows 配置下不可运行——且失败信息掩盖了已存在的守卫（事实）

**现象**：`ensureViewedSessionHarness` 在 `chainSteps` 阶段抛 `patch.diff touches no file`，`tests/harness-dock` 21 个用例全部 setup 失败。原因链完全可定位：系统级 `core.autocrlf=true` + 仓内无 `.gitattributes` → `patch.diff` 工作区变 CRLF → `patchTouchedFiles`（`split("\n")`，`/^diff --git a\/(.+?) b\/(.+)$/`）匹配失败返回 `[]`。

**为什么严重**：`docs/agents/testing.md` 规定"harness-facing changes 必须包含对应 real-host dock 文件"，而本票的验收明确要求真实 omp 来源证据；这等于把一个强制分区在 Windows 上整体废掉。而且 `ensurePatchArtifact` 本来有精确的冻结哈希守卫（`frozenEntry.sha256 !== step.sha256` → "re-freeze deliberately"），但它在 `chainSteps` **之后**才执行，所以永远不会触发——失败者是更早、更含糊的那一句。

**建议（机械修复，二选一或都做）**：
- 仓内 `.gitattributes` 加 `*.diff -text`（覆盖系统 autocrlf，保持 blob/工作区字节与冻结记录一致；已用哈希证明约定字节是 LF）。注意：新增属性后既有 worktree 需重新 checkout 才会得到 LF 字节（**推断**，未实测）。
- `patchTouchedFiles` 改为 `patchText.split(/\r?\n/)`——两行改动，让守卫按设计触发并给出可自诊的错误。
- 加一条读**真实文件字节**的检查（例如在 `baseline.test.ts` 断言 `sha256File(patch.diff) === record.patches[0].sha256`）。现有调用点（`viewed-session.test.ts:147`、`codex-response-artifact.test.ts:59`）读的也是同一批文件，因此同一个 guardrail 覆盖全部 patch fixture。

### 2. 缺少 worktree 预检，导致计划建立在错误前提上（事实 + 推断）

**事实**：本轮按顺序"踩"出三个环境事实——缺 node_modules、缺隔离安装、dock 不可运行——分别花了首个测试失败、一次 175s 后台复制、以及约 60% 预算后的整仓测试才暴露。
**推断**：若第 1 回合就知道"real-host 证据不可得"，agent 会把预算用于受控 seam + 文档 + 尽早向 Main 报阻塞，而不是把大量 token 花在读取 1450 行 `display.ts`、1447 行 omp adapter 与外部 checkout。

**建议**：加一条可执行预检（`bun run check:worktree` 或复用 `scripts/verify-omp-candidate.ts` 的"报告覆盖与环境"形态），一条命令打印：依赖是否已装；各 `isolatedHarnessLayout` 前缀是否存在（及其体量）；`patchTouchedFiles` 是否解析出文件；哪些测试分区本机可跑。把它写进 `docs/agents/testing.md` 的 tier 表上方（"开始前先跑"），同时把"隔离安装约 916MB、只在主 checkout 里"写进 dock 文档——本轮 agent 正是用 `du -sh` 去探这个体量，白耗一个 300s 作业槽。

### 3. 指令要求并行派发，运行时却禁用子代理（事实）

`task` 的 schema 明确 "Agent spawning is currently disabled."，而任务模板/工具策略写"用户说 `parallel` → MUST use `task` subagents"，本票本身也提示"探索阶段可委派"。结果是一次完全串行的大仓探索，预算在到达 dock 证据与文档同步前耗尽。
**建议**：让二者一致——要么这些 ticket 运行开启派发，要么在注入的 ticket 模板里去掉委派要求并显式说明"本运行串行，请据此裁剪范围/优先序"。这属于环境一致性，不是 agent 纪律问题。

### 4. 缺少"分区不可运行时的处置规则"与"交接必须绿树"的不变量（事实 + 推断）

**事实**：`b3eef9e` 留下 21 个 dock 失败，其中一部分正是本票行为变更（子代理行名从 agent 类别 `task` 变为 spawn handle、行内新增 `Model:`/`Effort:`）与 dock 字面断言不匹配；而 agent 无法运行该分区来验证修改。
**推断**：这会让 Main 拿到的分支处于"红树且不可自证"的状态。

**建议**：在 `docs/agents/testing.md` 增一节"分区不可运行时怎么办"，给出唯一处置：修复 fixture（首选）→ 否则改动字面期望时必须写明理由与未验证范围 → 否则回退该行为变更；禁止静默跳过。并明确"交接前，被自己改动影响的字面断言要么已更新、要么在报告中列为不可验证"。

### 5. 宿主事实的导航指针缺项（事实）

本 ticket 的核心是把 omp 的哪些原生读数映射成什么语义，而 agent 用了约 25 次调用才自己推出四个事实：spawn handle 就是 registry id（`task/index.ts:777` 的 `allocate(spawn.name ?? generateTaskName())` → `sdk.ts:4050 agentId`）、`ctx.agent.name` 是**定义类别**而非任务名、`pi.getThinkingLevel()` 返回已解析的有效强度（`types.ts:1623`）、`session_start` 不携带 reason（故"启动即证明"只能靠该事件的时间点）。
**建议**：这些事实的正当归属是 `framework/docs/harness-support.md` 的能力登记表（已有 `session.identity-facts`/`session.name-change`/`session.current-model-provider` 行）。补三行——`session.task-handle`（含"注册 id 即 spawn handle"及 `sdk.ts`/`task/index.ts` 引用）、`session.effective-thinking-level`（`getThinkingLevel` 语义、`auto` 不是 level）、`session.startup-signal`（`session_start` 无 reason，故 startup 只能在绑定首个 session 处读）——本票要求的"真实 omp 来源证据"就有了不复推的引用。同步项：`framework/docs/framework-capabilities.md` 的 `SessionFacts` 行（"session's identity, direct parent, latest name, and the name and id of the agent it runs" 已过时）与 `extensions/model-cost/README.md` 的 P11/P23 行（新 detail 行字段）。

### 8. 低严重度：规则误报与工具语义（事实）
