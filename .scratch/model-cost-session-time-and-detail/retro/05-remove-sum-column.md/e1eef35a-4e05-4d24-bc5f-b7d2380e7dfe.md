## 1. （高）仓库没有 `.gitattributes`，Windows 的 EOL 转换会静默破坏按 sha256 冻结的 host-patch fixture

**事实**

- `core.autocrlf=true`，来源 `D:/Program Files/Git/etc/gitconfig`（系统级）。
- 两份 patch 的**已提交 blob 是 LF**：`git show :host-patches/omp-18.5.0-viewed-session/patch.diff | grep -c $'\r'` → 0；而工作区副本是 CRLF（599 / 44 行带 `\r`）。
- `tests/harness-dock/host-patch-artifact.ts` 的 `patchTouchedFiles` 用 `split("\n")` + `^diff --git a/(.+?) b/(.+)$`。行尾的 `\r` 无法被 `.+` 吃掉，于是解析结果为 **0 个文件**，`chainSteps` 直接抛 `… patch.diff touches no file`。第一次 `bun test tests/harness-dock`：**39 pass / 15 fail**，22 个文件里凡是走 patched host 的全部死在 materialize 阶段。
- 即使只修解析也不够：`sha256File(entry.patchFile)` 要与 `record.json` 冻结的 sha 比对，而冻结的是 LF 字节。
- 同一根因还制造了另外两类失败：磁盘 `bun.lock` sha `7f5c82e6…`，LF 归一后 `9e9f4833…` = `git show e3a1d0e:bun.lock` = `harness-baseline.json` 录制值 → `session-driver.test.ts` 的 `verifyLockfile` 失败；`baseline.test.ts` 的字节一致性检查同理。
- 把工作区两份 `patch.diff` 归一为 LF 后（与 blob 逐字节相同，`git status` 仍干净），分区变为 **76 pass / 5 fail**，两份 patch 的 sha 重新与 `record.json` 一致。

**为什么算高**：它把「验证证据」变成假失败，且对 `git status` **不可见**（autocrlf 在比较时把 CRLF 归一），所以 agent 看到的是「代码坏了」。本轮为此花掉的排查（读 harness、比对 `record.json`、查 peer worktree、查 git config、逐文件 hash）是本会话最大的一块成本。

**建议（机械修复，非规则）**

```gitattributes
host-patches/**/*.diff -text
bun.lock text eol=lf
```

随后执行一次 `git add --renormalize .`。纵深防御可把 `patchTouchedFiles` 改成 `split(/\r?\n/)`，但要在注释里写明**它只改善报错信息，真正的修复是 attributes**（sha 校验仍然依赖字节）。

## 4. （中）交接报告可以只声称「验证通过」而不携带命令

**事实**：上一轮报告只有 `commit` 与一句 `result`（“real-host dock runs green”），没有任何命令；而本轮接手的树上，所有 patched-host dock 文件在 materialize 阶段即失败（39/15，见本轮第一次 dock 运行）。角色提示词其实已经要求报告验证命令，所以杠杆在**报告的 schema**而不是提示词。

**未验证/推断**：无法判断上一轮只跑了子集，还是它曾归一化 fixture 而 `host-patches/` 目录在 17:18 被重新 checkout 覆盖（目录 mtime 显示当时被动过）；两种解释都与现有证据一致。

**建议**：给实现报告 schema 加必填的 `commands` + `results` 字段（宿主侧），让「绿」与产生它的命令不可分离。这会让下一次接手从真实失败开始，而不是从矛盾开始。
