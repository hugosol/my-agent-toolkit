## 1. 【高】缺 `.gitattributes`：换行符检出直接打红基线测试，六个票据各自发明了绕行方案

**事实**

- `git check-attr text eol -- bun.lock host-patches/omp-18.5.0-viewed-session/patch.diff` → 三项全部 `unspecified`；`ls .gitattributes` → 文件不存在（`git log -- .gitattributes` 无记录）。本机 `core.autocrlf=true`（`git config --get core.autocrlf`）。
- 消费者只认 LF 字节：`tests/harness-dock/host-patch-artifact.ts:127-129` 用 `patchText.split("\n")` 解析 `diff --git` 行（CRLF 会让 `b/(.+)$` 捕获尾部 `\r`）；`tests/harness-dock/codex-response-artifact.test.ts:57` 与 `viewed-session.test.ts:165` 把磁盘文件 sha256 与 `record.json` 记录值相等比较；`tests/harness-dock/baseline.test.ts:81-84` 对记录里的 `{path, sha256}` 逐个比对（即上一轮报告的 `9e9f4833… vs 7f5c82e6…`）。
- 同一工作区在本次会话里已经是 LF（`bun.lock` 与两个 `patch.diff` 的 CR 计数均为 0），所以本轮全绿；但这是上一轮用 `git -c core.autocrlf=false checkout -- .` 重写工作区后的状态，即**当前工作区字节不等于一次干净检出**。
- 本次会话的 grep 结果里，01/02/04/06 票据各自记录了同类失败与不同绕行（临时去 CR 再按字节恢复、重写工作区、改用带 LF 的同级 junction）。同一根因被独立解决至少 4 次。

**建议**：在仓库根加 3 行 `.gitattributes`，把这两个字节敏感 fixture 钉死为不转换：

```
bun.lock -text
host-patches/**/patch.diff -text
```

这是机械且确定的修法（`-text` = 检出/入库都不做 EOL 转换），一次消除整类假失败，并让任何 `core.autocrlf` 的工作区、集成分支、评审者看到同一份字节。不建议改消费者（对记录 sha256 做 CRLF 归一化会引入"哈希对象"歧义）；若坚持改代码，必须让比较对象是归一化后的文本，且更新 record 的哈希语义。

**未验证**：加属性后 dock 全套是否在 CRLF 检出下真绿——我按代码路径推断成立，但本轮没有构造 CRLF 检出去实测（那会改工作区字节）。
