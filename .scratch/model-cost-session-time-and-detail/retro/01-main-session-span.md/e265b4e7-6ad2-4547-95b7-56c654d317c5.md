## 1（严重）CRLF 检出与 dock 录制件校验冲突，每个票据 agent 都要重新踩一次

**事实（可直接复现）**

- 本机 `core.autocrlf=true`，来源 `file:D:/Program Files/Git/etc/gitconfig`（系统级）；仓库**没有** `.gitattributes`（`git ls-files .gitattributes` 无输出；`git check-attr text eol -- bun.lock host-patches/omp-18.5.0-viewed-session/patch.diff` 全部 `unspecified`），所以 `bun.lock` 与 `host-patches/**/patch.diff` 在检出时被改写成 CRLF。
- `patchTouchedFiles`（`tests/harness-dock/host-patch-artifact.ts:127-135`）按 `"\n"` 切分并要求整行匹配 `^diff --git a\/… b\/(.+)$`；CRLF 行尾多出的 `\r` 让每个补丁都“touches no file”。我直接跑到：`bun test tests/harness-dock/model-cost-persistence.test.ts` → `error: …/omp-18.5.0-viewed-session/patch.diff touches no file`，在 `beforeAll`/fixture 装载阶段即失败。
- `verifyLockfile`（`tests/harness-dock/baseline.ts:371-378`）对工作区文件直接 `sha256File`，不做行尾归一，因此 `baseline.test.ts:88 "records the lockfiles of this repository and of the behavior oracle"` 与 `session-driver.test.ts` 的 lockfile 校验在 CRLF 检出下必然红。
- 归一（对这三份文件逐行去 CR，结果 sha256 与 `git show HEAD:<path>` 逐位一致）后，全分区 **84 pass / 0 fail**（23 files，974 expect，168.3 s，含上述两个文件）——这些红与本票行为无关。

**代价（事实）**：ticket 01 的 session 目录下有三份实现记录（`53d6f5ae`、`92c29ea8`、`e905fd47`），即该诊断被重复了至少三次；本轮为此额外花 4 次 bash 做归一+恢复，且最后一次恢复脚本被我写坏（`case` 塞进 `$( )`）导致三个录制件一度以归一后字节留在工作区——**存在把环境字节提交进票据的真实风险**（本轮靠 `git status` + 显式 `git add` 才没有发生）。上一轮报告的 81 pass / 2 fail 是二手引用，我未在未归一状态下跑完整分区。

**建议（按成本排序，都是机械修复，不需要写进编码标准）**

1. 加 `.gitattributes`：`*.diff -text` 与 `bun.lock -text`（或统一 `* text=auto eol=lf`）。让检出字节与已提交 blob 一致，录制 sha 与 `patchTouchedFiles` 立刻可用，同时修好任何 autocrlf 机器。根因修复，代价一个文件。
2. 让 dock 自己容错：`patchTouchedFiles` 用 `/\r?\n/` 切分；`verifyLockfile` 比较前把读出的字节做 LF 归一（录制 sha 的语义本来就是“已提交文本的 sha”，在失败信息里说明“归一后比较”）。这样机器差异不再进入判定。
3. 把这类环境不匹配用一个秒级前置检查指名（见第 4 条），而不是让 agent 花几分钟读到一句 `touches no file`。
