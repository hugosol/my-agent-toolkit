## 1（最高）CRLF 检出与“记录 sha 假定 LF”冲突，使宿主验证环境直接不可用

**事实**
- 本机 `core.autocrlf=true`（`git config core.autocrlf` 输出 `true`），仓库**没有 `.gitattributes`**（`cat .gitattributes` 无输出，`git check-attr` 无属性），因此 `host-patches/**/patch.diff`、`bun.lock` 等被检出成 CRLF，而记录在 `host-patches/*/record.json`、`framework/docs/harness-baseline.json` 里的 sha256 是 LF 内容。
- 后果链（可复现）：`patchTouchedFiles`（`tests/harness-dock/host-patch-artifact.ts:127`）按 `split("\n")` + `/^diff --git a\/(.+?) b\/(.+)$/` 解析，CRLF 行的行尾 `\r` 使 `$` 失配 → 返回空数组 → `ensurePatchArtifact` 抛 `... patch.diff touches no file` → **所有** patched-host dock 文件在 materialize 阶段即失败（我首次运行 `model-cost-persistence.test.ts` 就是这个报错，0 pass / 1 fail）。
- `verifyLockfile` 同样失配：`bun.lock: recorded 9e9f4833… but found 7f5c82e6…`，导致 `baseline.test.ts` 的 lockfile 用例与 `session-driver.test.ts` 的 “starts the isolated artifact…（含 verifyLockfile）” 稳定失败。这两例在把 `patch.diff` 归一为 LF 之后依然存在（LF 归一不改变 `bun.lock`），单独重跑这两文件即 2 例失败，与本次改动无关。
- 同一现象被 peer 独立遇到：票据 05 明确报告该环境问题并给出“全分区最终 76 pass / 5 fail，5 例全为环境”的基线；票据 03 报告“把 worktree 全部 tracked 文件从 blob 重写才跑得动”。本轮我的处置是临时把两个 `patch.diff` 归一为 LF、跑完再 `git checkout --` 恢复原状。
- `git status` 在归一后对这两个文件显示 ` M`（内容无差异，属 eol/stat 记账），意味着“归一的临时文件”很容易被误 `git add` 进提交。

**为什么值得最优先**：这不是某个代理的操作失误，而是仓库级守卫缺失。每个在本机工作的代理都要手工重写工作区字节，浪费的是每个 run 的前置时间，且带一个真实的误提交风险；一旦有人按 `baseline.test.ts` 的提示去“refresh framework/docs/harness-baseline.json”（见下条），还会把环境问题写进仓库记录。

**建议（按落地成本排序）**
1. 加 `.gitattributes`，一处确定性解决：至少 `host-patches/**/patch.diff -text` 与 `bun.lock -text`；若希望全仓一致，用 `* text=auto eol=lf`。（推断：这正是记录 sha 假定的字节形态；`git ls-files --eol` 现在对 patch.diff 显示 `i/lf w/lf` 时内容即与记录一致。）
2. 让解析器容忍 CRLF，把“环境差异”从“协议解析”里分出去：`patchTouchedFiles` 改 `patchText.split(/\r?\n/)`（或行尾 `\.trimEnd()`）；`verifyLockfile` 比对前对文本做 eol 归一。这样即使检出形态不同，判据仍然成立，而不是静默变成“0 个文件”。
3. 在 dock 加载前加一个 preflight：检出字节与记录字节不一致且差异**只**来自 eol 时，报“工作区为 CRLF，记录为 LF，请归一或设置 .gitattributes”，而不是抛“touches no file”。

**建议**：先确认现状；若确无守卫，则按 retro 惯例把它本身列为发现——最小可用版本是“提交前跑 `bun run typecheck` + `bun test tests/framework tests/model-cost`”，再加上第 1 条的 LF 归一检查（一个 `git ls-files --eol` 断言即可），本类环境问题就能在提交前自动暴露。

## 建议优先做的三件事（若只做三条）

1. `.gitattributes`（`host-patches/**/patch.diff -text`、`bun.lock -text`）+ `patchTouchedFiles` 容忍 `\r`：把本机 CRLF 从“每个 run 的入口障碍”变成无害。
2. 失败文案与 preflight 指向 eol 根因（不要把代理引去改记录 sha）。
3. 一条“改动面 → 受影响消费者/复跑套件”的导航指针，外加集成同步时的冲突处置一句话：直接省掉第 3、6、7 条里的大部分往返。
