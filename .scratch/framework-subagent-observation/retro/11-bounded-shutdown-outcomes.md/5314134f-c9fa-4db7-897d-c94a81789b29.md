# 票据 11（bounded-shutdown-outcomes）TDD 轮复盘：环境改进建议

## 1（高）仓库没有任何 lint 护栏，机械规则只能靠运行中被拦下

**事实**
- `package.json` 只有 `test` / `test:framework` / `test:codebase-tools` / `test:dock` / `typecheck` 一类脚本，没有 `lint` / `check` / `format`。
- 本 worktree 根目录不存在 `biome.json`、`eslint.config.*`、`.editorconfig`、`.gitattributes`、`.husky`、`.github`、`.gitlab-ci.yml`（`ls -a` 全量列出；`ls .github` 退出码 2）。
- 本轮两条**机械**违规由宿主规则在运行中拦下，而非仓库自己发现：
  - `ts-no-test-timers`：第一版 `tests/framework/close-out-deadline.test.ts` 用真实 `setTimeout(40)` 与 250–300ms 真实预算；改为 `vi.useFakeTimers()` 后反而得到更硬的证据（假时钟下可精确断言 `deadline === 进入收口 + budgetMs`、`remaining()` 逐毫秒下降、回答后 `vi.getTimerCount() === 0`）。
  - `ts-no-inline-cast-access`：`scripts/pi-close-out-smoke.ts` 中 `(request.json as {...}).messages` 是从既有 `scripts/pi-session-accounting.ts` **照抄**的写法 —— 换言之仓库现有代码同样违反该规则（推断：该规则全仓普遍未满足）。

**建议**：机械违规用确定性检查解决。加最便宜的一条护栏 —— 单一 lint 配置（biome 或 eslint），至少覆盖两类规则：测试文件禁用真实计时器、禁止内联 `as` 后直接取成员；再由 pre-commit hook 或 CI job 跑 `lint` + `typecheck` + 受影响分区。收益在本轮可见：我为此重写了测试的时间控制并重写了整段 JSON 读取，第一次就写对可省下这些返工。

**未验证**：本 worktree 之外是否另有 CI/流水线（仓库内未见配置，不等于全仓无护栏）。

## 4（中）`capture.stop()` 不取消 held completion，取证脚本会按 hold 时长滞留

**事实**：首次记录的 `bun scripts/pi-close-out-smoke.ts` 墙钟 **602s**，两相实际工作约 30s；当轮 `HELD_ANSWER_MS = 600_000`。`tests/harness-dock/capture-server.ts` 的 `answerDelayMs` 是 `await Bun.sleep(...)`，而 `stop()` 只做 `heldBalance.resolve()` + `server.stop(true)` —— 只取消 balance 的 hold。

**推断**：滞留由那条 600s completion hold 的定时器维持事件循环（改小常量后同脚本 61.8s）。

**建议**：把 completion hold 也做成可取消（与 balance hold 同样的 resolvable promise，并在 `stop()` 内 resolve），或在 `CaptureStep.answerDelayMs` 文档中明写「它比 `stop()` 活得更久，hold 时长即驱动进程的滞留时长」。

**未验证**：是否另有机制同时滞留（仅由时长与常量吻合推断）。

## 5（中）运行日志不自证其树状态；本轮因此重跑了整个分区

**事实**：`docs/agents/testing.md` 要求「Keep runs attributable」，但 `bun test` 日志没有 revision / 工作树状态；我在 framework 分区运行期间编辑了 `framework/public.ts`（导出顺序），随后判定该结果不可用并**重跑** framework 与 model-cost 两个分区（约 42s / 16s）以取得归属清晰的证据。另有事实：新增日志时 git 警告「LF will be replaced by CRLF」，而仓库无 `.gitattributes`（见条目 1），且 `framework/docs/harness-support.md` 已记录 LF 字节/CRLF 的历史坑。

**建议**：(a) 提供 `scripts/run-tests.ts`（或 npm `test:*` 的前缀包装）在运行前后打印 `git rev-parse HEAD` 与 `git status --porcelain`，让每份日志自带树身份；(b) 加 `.gitattributes` 让 `*.log`（及已记录 LF 要求的文件）保持 `-text` / `text eol=lf`，避免证据日志被工作树转换改写。

**未验证**：外部 CI 是否已记录树身份。

## 6（低）分区没有对应 npm 脚本，环境阻塞与回归在命令层面无法区分

**事实**：`package.json` 有 `test:framework` / `test:codebase-tools` / `test:dock`，没有 `test:model-cost` / `test:connect-bot`（本轮按文档直接 `bun test tests/model-cost`）；`OMP_BOT_BINARY` 缺失时 connect-bot 呈现为「5 fail」而非「阻塞」。

**建议**：补齐两个 `test:*` 脚本（connect-bot 那个先检测变量/二进制，给出构建指令后 fail fast），让「该跑什么命令」从环境（`package.json`）可查，而不是从文档句子推断。

## 7（低）只存在于样本里的两条约定：注释语言与有界等待的设计口径

**事实**：(a) framework 模块头与诊断是英文、model-cost 操作者通知是中文（既有与本次新增皆然），该约定无成文位置；(b) 本轮必须自行发明一条设计口径 ——「框架强制一个截止时，必须让它所界定的工作在截止内结束**并被观测到**」—— 落成 `framework/modules/files.ts` 导出的 `WAIT_RESOLUTION_MS`（把工作预算提前一个观测分辨率）。缺了它，「可靠取消 → 未提交」的结论会落在宿主已被回答之后（本轮故障注入 `WAIT_RESOLUTION_MS = 0` 时该用例确实失败，可作反证）。

**建议**：(a) 作为一条 reviewer 规则写入标准文档（语言判定难机械化）；(b) 把 (b) 提炼为更一般的设计规则放入 framework 贡献文档：「有界等待必须预留其所界定工作的观测分辨率，且不得声称截止无法知道的结局」，让下一位实现者无需从零推导。

**未验证**：该口径是否已在未读到的 framework 文档中表述（本轮只读了 `framework/docs/framework-capabilities.md` 与 `harness-support.md` 的相关段落）。
