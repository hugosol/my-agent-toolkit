## 高严重度

### H1 “先语义检索”的强制路径在本环境不可用，且失败被呈现为“无结果”

【事实】`find` 的判定模型被区域封锁（451），25/25 请求失败，而对外只回 “no hits for …”。【事实】被推荐替代的 `codebase-memory-mcp.get_file_outline` 需要 agent 不知道的 `project` 参数。系统提示又要求“调用 grep/search 前考虑 codebase-memory-mcp”“读 >100 行源码前先用它看大纲”。

**影响**：一次误读代价极高——“no hits” 是*证据缺口*与*工具故障*两种相反结论的同一输出，agent 可能据此断定“不存在”。本轮的两次尝试各浪费一轮往返，随后只能靠 `grep` 兜底。

**建议**
1. 让语义检索类工具的失败**显式化**：工具层返回错误（如 `search-unavailable: judge 451`）而非空结果集；
2. 修复/替换 judge 通道，或按区域配置可用模型；
3. 若保留 codebase-memory-mcp 的强制建议：把 `project` 的取值（或发现方式）写进 `AGENTS.md` 一行导航指针，或让工具缺省推断当前工作区 —— 否则该指针是空转（见 M7）。

### H2 仓库唯一的静态检查没有被任何自动化运行

【事实】`typecheck` 存在且本轮**真实捕获 2 个类型错误**；`package.json` 的 `test` 只跑 `bun test`，worktree 内无 CI 配置、无 git hook。

**影响**：本轮我之所以没有把带类型错误的提交交出去，纯粹因为票据文本写了“TypeScript 变化执行 typecheck”。换一个不写这句话的票据，就会产出“测试全绿 + `tsc --noEmit` 红”的提交，而没有任何机器会拦。

**建议**（按仓库既有形态，最小成本优先）
1. 让测试入口等同验收：`test` 脚本改为 `tsc --noEmit && bun test`，或新增 `check` 脚本并在 CI 中作为必过项；
2. 加一个 pre-commit / pre-push hook 跑 `bun run typecheck`；
3. 若 origin 已有 CI，则把它接到每个 ticket 分支（本轮无法验证是否已存在）。

### H3 交给 agent 的 worktree 未安装依赖，第一次运行测试必然失败

【事实】`node_modules` 不存在，首轮测试以 `Cannot find package 'yaml'` 告终，`bun install` 用时约 2s。

**影响**：所有 agent 都要花一个失败往返去分辨“环境问题”与“代码问题”，且这在语义上极像“测试坏了/代码坏了”。

**建议**：worktree 交付流程增加一步 `bun install`（幂等、2s）；或在 `docs/agents/testing.md` 的 “Select a tier” 表前加一行“本 worktree 交付时已安装依赖 / 若 `node_modules` 缺失先 `bun install`”。
