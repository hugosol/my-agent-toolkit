# 子会话观察的进程模式复用与 pi 正常退出收口

Status: ready-for-agent
Labels: ready-for-agent
Contract: [已批准契约](contract.md)

## Problem Statement

在 pi 异步委派中，操作者看到子代理已经完成，但 `/budget detail` 中仍可能没有它的消费和运行耗时。已有调查确认：子进程收到执行 settled 后，framework 将 Round 结束确认安排到下一个 macrotask，而第三方 runner 随即处置会话并退出，确认没有执行，因而未交付 `round_end`，也没有完成该会话自己的消费提交。仅补一个主进程刷新入口或转发完成通知不能补回这部分消费。

即使子进程成功保存，Owner 所在进程仍需只读同步才能采用外部提交；子会话的运行中身份、Working/Idle 和上下文读数也不会自动跨越进程内存边界。仅凭第三方完成通知发现身份，无法在运行中展示子会话，尤其无法完整覆盖嵌套后代。

同进程路径通过每个会话自己的 binding 交付事实，并复用进程内业务实例与读数；跨进程路径各有独立内存。维护者需要集中复用进程差异，而不是为 OMP、pi 和未来 harness 复制通信、统计或展示逻辑。进程模式不能改变 Round、State follow 或消费归属的业务含义。

## Solution

提供共同的会话观察能力：实际子会话启动后主动向 Owner 登记，随后以事件驱动方式提供自身上下文和活动读数。同进程直接交付，跨进程使用 framework 管理的本机接入；Owner 采用读数并合并前端重绘。首轮消费尚未提交时也可以显示已经可靠登记的子会话，未知指标不填零。

响应计费 usage 仍在实际执行的进程内累计，各会话在自己的 Round 结束时自行提交。成功提交后通知 Owner 合并执行文件只读同步，IPC 不建立第二套消费权威。重连提供当前观察快照，并触发消费只读同步，以补齐未送达的提交提示。

pi 正常处置会话时，adapter 在可等待的宿主退出位置报告实际会话终止事实，由 framework 完成 Round 的结束确认或截断，并有界等待相关异步处理和保存，再清理并允许退出。此流程不等待 Owner 在线、确认或渲染。观察来源失效时撤销实时读数，但不推断 Idle、任务失败或成功，也不删除已知身份与已保存消费。

## User Stories

1. 作为 pi 操作者，我希望异步子代理正常退出前保存自己的消费，以便任务完成后不会漏账。
2. 作为 pi 操作者，我希望已有 settled、尚未执行结束确认的 Round 在退出时得到收口，以便 runner 的短寿命不会丢失最后一轮。
3. 作为操作者，我希望正常处置时尚未 settled 的活动按截断收口，以便已知消费能保存且不会伪称任务成功。
4. 作为操作者，我希望退出等待有明确上限，以便保存竞争或故障不会无限阻止进程退出。
5. 作为操作者，我希望保存失败或超时被明确报告，以便不会把未保存消费当作已成功提交。
6. 作为子会话使用者，我希望 Owner 不在线时仍能完成本地结算与正常退出，以便界面可用性不决定记账可靠性。
7. 作为主会话操作者，我希望子会话启动后就出现在代理树中，以便不用等任务结束才知道它存在。
8. 作为操作者，我希望首轮尚未提交的会话显示可靠身份和已有上下文，以便看到运行中的工作而不是空白列表。
9. 作为操作者，我希望缺少消费证据时指标保持未知，以便未提交不被解释成零消费。
10. 作为操作者，我希望每个子会话显示自己的当前活动读数，以便区分 Working、Idle 与观察不可用。
11. 作为操作者，我希望 Working/Idle 遵循共同 Round 语义，以便自动重试、工具执行和委派等待不会被提前显示为 Idle。
12. 作为操作者，我希望子会话上下文按可靠事件及时更新，以便了解其最近可用的上下文占用。
13. 作为操作者，我希望上下文携带对应模型，以便不会用错误的显示预算解释读数。
14. 作为操作者，我希望界面不必逐流式 token 重绘，以便并发子代理不会因无意义更新降低交互响应。
15. 作为嵌套子代理使用者，我希望孙会话直接向 Owner 提供观察，以便直接父进程不必充当消息中转。
16. 作为操作者，我希望代理树仍按真实直接父关系排列，以便直接交付 Owner 不会压平后代层级。
17. 作为操作者，我希望续跑复用同一实际会话行，以便新的 run 或进程不会重复登记消费主体。
18. 作为操作者，我希望首次接入能收到当前观察快照，以便连接建立前已经开始的活动也能正确显示。
19. 作为操作者，我希望重连能恢复当前可用读数，以便不必等下一次状态变化才能修复界面。
20. 作为操作者，我希望迟到消息或旧连接退出不会覆盖新来源的读数，以便续跑和重连不会让界面倒退。
21. 作为操作者，我希望连接失效后撤销 Working 和上下文读数，以便界面不残留永久 Working 或伪实时数据。
22. 作为操作者，我希望断连不被解释为 Idle 或执行失败，以便通信问题不冒充执行事实。
23. 作为操作者，我希望断连后仍保留可靠身份、父关系和已保存消费，以便暂时通信失败不会让历史统计消失。
24. 作为操作者，我希望消费成功提交后 Owner 自动采用外部记录，以便无需自己再产生消费或提交才能看到子代理结果。
25. 作为操作者，我希望消费通知丢失后能在重连时对齐文件，以便已保存记录不会永久不可见。
26. 作为操作者，我希望多个提交提示合并刷新，以便并发子会话不会导致每条通知都重复读取整份消费文档。
27. 作为操作者，我希望同步过程中到达的新提交提示不被遗漏，以便合并不会永久漏掉最后一次更新。
28. 作为操作者，我希望每笔请求只由实际执行会话累计一次，以便 Owner 的远端观察不会导致重复计费。
29. 作为操作者，我希望不同统计周期的数据不因重连或刷新混合，以便迟到通知不会带回已关闭周期的在途消费。
30. 作为子会话使用者，我希望 State follow 仍读取 Owner 当前权威值，以便单进程和多进程有相同控制语义。
31. 作为 Owner 使用者，我希望子会话不能通过观察或 follow 通道修改我的 State，以便事实报告不获得控制权限。
32. 作为扩展维护者，我希望没有 follow 字段的扩展也能观察子会话，以便观察能力不被 State 继承偶然关闭。
33. 作为操作者，我希望切换 brief/detail 不会丢失子会话观察，以便展示偏好不决定采集寿命。
34. 作为 OMP 使用者，我希望现有同进程功能保持一致且无需建立 IPC，以便修复 pi 不增加不必要的连接开销。
35. 作为 pi 使用者，我希望前台和后台子会话使用相同统计与展示规则，以便委派模式不会改变指标含义。
36. 作为未来 harness adapter 维护者，我希望复用进程交付与观察管理，以便只实现本宿主事实映射和子入口接线。
37. 作为维护者，我希望宿主事件、语义事件、观察消息和计费事实各自清晰，以便消息转发不形成重复派发、回环或第二套 Round 判断。
38. 作为维护者，我希望旧接入和错误目标被拒绝，以便多个扩展、Owner 和进程并存时不会串接会话观察或 State。
39. 作为维护者，我希望正常退出、重连、断连和并发均有可归因的运行证据，以便测试通过不被误称为所有宿主和系统都已认证。

## Implementation Decisions

### 已确认的职责划分与复用目标

- 复用轴是实际会话与 Owner 的进程位置，不是 harness 名称。OMP 当前子会话以及 pi 前台路径采用同进程方式，pi 后台路径采用跨进程方式；同一 harness 可以有两种路径。
- 各会话仍有自己的 binding 和 context。同进程共享的是明确复用的业务实例、State 与按会话登记的读数，不是所有会话共用一个 context 对象。
- 已确认的架构方向是共同的会话观察接口，下面支持同进程直接交付和跨进程本机接入。同进程不强制序列化、建 socket 或模拟网络队列。
- adapter 负责宿主真实身份、祖先关系、原生生命周期、执行事实、上下文采集入口、扩展子入口及可等待处置位置。framework 负责共同语义、交付与观察来源管理；扩展 shared logic 保留业务统计和展示规则。
- 通信模块不猜测宿主子代理、不判断任务成功、不另造 Round。pi 原生 agent_start 是执行开始事实，不能把子会话创建成功直接当作 Working。实际会话启动登记与每轮执行开始分别表达。
- 本规格记录对话已确认的职责划分，不新增接口方法、协议帧、模块布局或测试 seam；这些由后续契约工作依现有实现确定。

### 身份与观察寿命

- 子 binding 取得可靠实际会话身份后主动登记；实际 session 身份、提供方 run 身份和进程身份不可互换。续跑可能换 run/进程而复用同一实际会话。
- 每个后代直接向 Owner 所在进程交付观察，保留其真实直接父关系，不要求父代理中转。Owner 是 State 所属主会话和观察汇集位置，不是所有子会话的记账代理。
- Owner 身份由 adapter 使用宿主可靠事实解析；无法解析时不得从名称、目录形状或 PID 猜测。现有 pi 祖先身份锚点解析可复用，定位文件不承载业务值。
- 首次接入及有效重连先提供当前可用身份与观察快照，之后发送变化；不重放历史 Turn/Round，不凭快照补账。重连可重新采集当前上下文。
- 更新按实际会话与有效来源归属。重复、迟到或失效来源不能覆盖更新来源；旧连接关闭不能清除新来源提供的读数。具体来源身份和顺序机制留待契约确定。
- 正常撤销和接收侧观察到的关闭/错误均使所属来源失效。接收侧 framework 可以本地通知失效，不依赖将退出的子进程成功发出最后一条消息。
- 失效撤销实时活动与上下文读数，但不删除可靠身份、父关系或已保存消费。仅实时登记且未提交消费的身份在本次 Owner 运行中保留，不为其新增持久化。
- 断连是观察不可用，不是 Idle、进程死亡或执行异常证明；连接仍在的卡死不在本方案检测保证内。

### 事件驱动的读数与展示

- 上下文从本会话 context 提取 tokens 及对应 provider/model 等已声明读数，不传 context 对象、函数、完整对话或模型文本。
- 以会话启动、消息结束、执行结束作为已确认的初始采集事件集合；相同读数不重复发布。是否需要其他宿主公开事件补足模型切换等变化，需在契约阶段核对事实，不承诺当前集合覆盖所有原生变化。
- Working/Idle 由 framework 的 Round 转换产生并按变化交付。接收端将它们作为远端观察，不再次驱动本地计费生命周期。
- 事实及时接收、内存及时采用，展示请求允许合并；不得为了合并重绘而丢弃影响结算的本地生命周期事实。
- 代理树采用已保存会话与实时登记会话的并集，按实际身份合并、按直接父关系排列；首轮未提交也能出现，缺失消费不填零。
- 不增加持续轮询、逐流式 token 发布或运行耗时持续跳动。上下文展示是最近可靠采集值，不承诺每个流式 token 的瞬时值。

### 两种读取模式与 State follow

- 实时观察消息携带当前值，Owner 直接采用到内存，不为活动或上下文更新读取消费文件。
- 响应计费 usage 留在执行进程，由本地扩展逐响应累计；实际会话自行结算、保存，Owner 不重复记账或代写。
- 消费提交成功后发出刷新提示，不携带用于直接采纳的消费累计。Owner 合并提示执行只读同步；同步期间又收到提示不能丢失后续刷新需求。
- 初始存储加载和重连时的只读同步覆盖已持久化事实；重连同步不以是否收到上次提交提示为条件。断线期间允许暂时保留上次同步结果，不增加轮询。
- 只读同步与既有存储基线、统计周期及本地未提交累计的保护规则一致，不强制提交其他会话在途消费，不把刷新当作初始化，不把旧周期未提交数据带进新周期。
- follow 保持使用时读取 Owner 当前权威 State，而不是永久初始化快照。同进程直接读，跨进程利用 framework 本机接入获取值及变更；一次语义处理内相关读取共用取得的快照，不要求每个 getter 独立通信。
- State follow 与子会话观察独立声明和管理，可以复用底层载体，不以 follow 字段存在与否决定观察是否启用。brief/detail 不建立或拆除观察来源。
- 子会话不可远端写 Owner State。已有 State 缺值默认值与恢复政策不因新增观察而改变。
- 复用 Windows 命名管道/POSIX 本地 socket 的框架本机接入方向；定位与消息分离，使用显式 runtime directory，校验完整目标与接入寿命，不把地址/PID 视为身份或存活证明。不新建文件消息队列、目录扫描或任意 RPC。

### 正常处置与 Round 收口

- adapter 在可等待的正常会话处置位置提供该实际会话的终止事实；framework 产生 Round 结束或截断并等待相关异步处理，adapter 不绕过共同语义自行伪造正常完成。
- 已有 settled、尚待延后确认的 Round 在处置时完成确认，不再依赖进程退出后不可能执行的下一 macrotask。
- 有 open Round 但没有 settled 时按截断收口，保存已可靠计入消费，不推算缺失 usage，不认定用户任务成功；运行耗时继续遵循已知测量及完整性政策，不伪造完整区间。
- 收口是实际会话处置的共同规则，不是 model-cost 另订阅宿主 shutdown 补账。普通 transferred 或查看位置切换不能仅因此强制关轮。
- 顺序为：实际会话处置事实、Round 收口、等待 handler 与自身保存、成功提交提示、释放观察/连接/binding、shutdown 返回。已完成的收口与保存不重复执行。
- 本地保存不依赖 Owner 可达，不等待 Owner 确认或绘制。通知失败不回滚已成功提交文件，保存失败不发送提交成功提示。
- 等待有界，复用既有保存约束，不重置在途保存预算、不额外重试、不固定 sleep。现有提交排队与互斥默认总预算为 15 秒，不将其误称为所有 I/O 已有整体截止；整体收口截止的具体接线由契约明确。
- 保存失败或整体截止超时必须明确报告未完成；不得声称提交成功。正常处置保证不扩张到强杀、崩溃、断电。

## Testing Decisions

- 已有调查提供本缺陷的失败证据：pi 后台子进程收到 settled，但下一 macrotask 前已经进入 shutdown，没有 round_end；只加固定延迟的临时探针能恢复保存。这是因果线索，不是允许保留 sleep 的实现方案。
- 既有测试先例包括 framework 的 Round 映射/合成、本机接入、多扩展子入口登记，以及 model-cost 的 pi 上下文、运行缺口和累计子代理耗时测试。可从 `tests/framework/round-events.test.ts`、`tests/framework/pi-round-mapping.test.ts`、`tests/framework/pi-background-rounds.test.ts`、`tests/framework/local-access.test.ts`、`tests/model-cost/pi-session-context.test.ts`、`tests/model-cost/pi-runtime-gaps.test.ts` 和 `tests/model-cost/subagent-runtime.test.ts` 查阅约定；不得据此提前决定新测试 seam。
- 使用既有真实 pi 子代理 smoke：`bun scripts/pi-subagent-smoke.ts --background-only --expect-pi-version 1.3.0` 为已记录失败场景，前台对应运行已有通过记录。实施应先确认当前失败，再观察修复后后台退出前实际提交与 Owner 可见结果；历史通过不替代新代码验证。
- 需要实际进程运行证据，不能仅用进程内 mock 证明 IPC 或退出等待正确；也不能仅以提供方完成通知证明 model-cost 已保存。
- 验证须覆盖首轮提交前出现、活动/上下文更新、嵌套、续跑、重连快照、失效清读数、旧来源不清新来源、消费不重复累计、提交提示合并及同步中新增提示、未 settled 的截断、Owner 不可达仍能保存退出、失败/超时不虚报成功。
- OMP 与 pi 前台必须有对应实际表面的回归观察，确认共同规则和无需 IPC 的同进程路径；不以 pi 后台通过推断 OMP 已验证。
- UI 验证需要观察实际 detail 表面，不能仅比较内部 registry。性能证据应区分采集/通知、重绘与退出等待；确认无固定延迟和无多余持续刷新，不声称未经测量的最优效率或零开销。
- 遵循项目测试分层及共享工作树运行协调。TypeScript 变化执行 typecheck；完成时覆盖所属分区、受影响消费者和真实宿主运行；最终集成按项目约定执行。具体 promises、测试落点和覆盖分配由 `/to-contract` 决定。
- 真实宿主优先复用调查中的本机兼容端点和临时存储隔离方式；不依赖付费模型调用，不写操作者真实消费与会话数据。当前调查仅覆盖 Windows、pi 1.3.0；其他宿主版本和 POSIX 必须分别报告运行证据或验证限制。

## Out of Scope

- 接入实际第三个 harness；本次目标是让其未来复用通信机制，不预造第三个宿主事实映射。
- 任意频道消息总线、通用远程方法调用、模型文本传输、远端 Owner State 写入。
- 由 Owner 代替子会话累计或保存消费；通过 IPC 消费快照建立第二份权威；新建账本或 Round/Turn 持久化明细。
