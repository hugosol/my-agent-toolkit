## Retrospective

# 复盘：ticket 04 connect-bot 失败、恢复与准入（TDD 实现轮）

范围：本 ticket 的实现轮（session `01a1603b…`），基于本对话与工具结果；不含父 session、集成轮或人工验收。事实、推断、未验证分别标注。以下均为建议，本轮未执行。

## 1. 高：裸工作树没有依赖与隔离 harness，跨工作树拷贝成为唯一可行路径

**事实**：worktree 初始没有 `node_modules`，也没有 `.cache/omp-baseline`；`ensureIsolatedHarness` 会按 `repoRoot` 安装 18.5.0，而本机已有的安装位于 ticket-03 worktree（`../hyper-ticket-BPSgaH`）。实际执行了 78MB `node_modules` 与 861MB `.cache/omp-baseline` 的拷贝，拷贝耗时约 16s。
**影响**：所有 S2 真实验证在完成这一步之前不可执行；来源是另一个票据的 worktree，存在被其清理或改动的不确定性（本会话中该 worktree 仍存在，长期可用性未验证）。
**建议**：在 ticket 派发说明或 `docs/agents/testing.md` 中给出工作树 bootstrap 步骤；更彻底的是让隔离 harness 安装可跨 worktree 共享（只读、版本固定、字节一致性已由 baseline 校验），例如支持共享 prefix 的环境变量或 junction，而不是每个 worktree 安装/拷贝 861MB。**未验证**：现有 `isolatedHarnessLayout` 是否无需改代码即可支持共享 prefix。

## 2. 高：基线分支带红测试进入集成，缺少按票据的消费者门禁

**事实**：本 ticket 从 `2ba8db8` 开始时，`bun test tests/framework/startup-requirements.test.ts` 为 6 pass / 1 fail：`connectBotOmp` 的 `observeSessionContext` 在 `on` 缺失的 surface 上直接 `pi.on.bind` 抛 `TypeError`；该测试期望框架报告 `registration failed`。修复后 7 pass / 0 fail。该问题由 peer 06 的 IRC 提醒才被主动复现，并非本 ticket 初始验证清单直接发现。
**影响**：集成分支的既有红测试会污染后续票据的“分区绿色”判断；若没有 peer 提醒，可能被当作外部/无关失败。另有一个记录层面的 caveat：`tests/connect-bot` 分区运行发生在 assembly 诊断修复之前，最终以“聚焦套件在修复后重跑”补充说明。
**建议**：为每个 ticket 增加合并前门禁：跑该 ticket 声明的分区 + 明确列出的 consumer 套件（本案例至少 `tests/framework/startup-requirements.test.ts`、`tests/framework/implementation-startup.test.ts`）；并把“最后一次生产代码改动后重跑所属分区”写进完成契约，避免出现“分区跑在修复前”的 caveat。**推断**：没有看到 CI/hook 在跑这些命令；worktree 根目录没有 `.github`，但未做完整审计。

## 3. 高：外部 herdr-bot 配置漂移让真实面板用例长期红，红不再是代码信号

**事实**：`tests/connect-bot/support/herdr-bot.ts` 生成的测试 TOML 被当前可用的 herdr-bot 拒绝：`missing field herdr`；`bun test tests/connect-bot` 为 151 pass / 5 fail，`tests/harness-dock/connect-bot-startup.test.ts` 最终为 6 pass / 1 fail，失败均为真实面板用例（`herdr-bot did not bind within 20000ms`）。该外部问题已在 `framework/docs/harness-support.md:124` 记录。
**影响**：每次全量/分区运行都有无法通过的红；agent 需要额外 triage 才能确认“不是本次改动”，验收证据被噪声稀释。
**建议**：固定/更新真实面板 fixture 的 schema 或二进制 revision；把真实面板互操作用例单独成文件或加显式环境 gate（缺兼容面板时 skip 并报告原因），让脚本化 S2 用例可以独立保持绿色；把 `missing field herdr` 这一已知签名写进 `docs/agents/testing.md` 或 support helper 的 docstring。**未验证**：是否存在可直接替换的兼容 herdr-bot revision。

## 4. 中：缺少共享的会话文件/旧载荷测试支持，header/title-slot 语义被重复推导

**事实**：新增 dock 用例第一次完整运行 4 pass / 3 fail，其中 2 个是 helper bug：`sessionIdOf` 取 `entries[0]?.id`，但宿主 JSONL 以 title slot 行开头（loader 用 `splitTitleSlot` 剥离），session header 不是第一行；改为查找 `type === "session"` 后通过。另有 S1 `failingPanel` 首次把操作者的重试也答成失败，导致等待超时；改为只失败第一次 register 后通过。最终经过一次完整运行和两次过滤/最终重跑。
**影响**：真实会话运行时间被重复消耗；同类 helper 在多个套件重复实现，容易再次踩到格式/时序细节。
**建议**：在 `tests/harness-dock/session-log.ts` 增加 `sessionHeaderOf(log)`、`statePayloadsOf(log, type)`、`appendCustomEntry(file, …)` 这类共享助手；把“脚本化 panel（含 fail-then-accept 序列）”做成共享 support，而不是每个套件各写一份。**推断**：共享助手能让本次两个 helper bug 在编写时就有现成正确语义。

## 5. 中：dock 运行窗口靠 IRC 协商，`wait` 无法阻塞在 peer 上

**事实**：本会话广播 10 个 peer，收到 integrate-01/02/03/07、05、06 的多轮 hold/free 消息；`wait` 在 peer 仍在跑全量时返回 “Nothing to wait for”，agent 只能用 `Get-CimInstance Win32_Process` 观察活跃的 `bun test` 进程。最终 dock 运行是在部分 peer 释放、integrate-01 全量重跑仍待启动的窗口内执行的；期间其他 worktree 仍有真实宿主进程。
**影响**：协商消耗多轮上下文；窗口判断依赖 peer 自觉与进程列表，容易出现重叠或空等。`docs/agents/testing.md` 的 quiet-window 规则没有区分“共享状态”和“CPU 负载”，而 peer 明确说明不同 worktree 的 `.cache` 互不共享、只竞争机器资源。
**建议**：在 `docs/agents/testing.md` 给出一个共享的 dock window 机制（例如 `.cache/dock-window` 锁文件，含 owner/开始时间/heartbeat，或由集成协调者统一分发真实宿主窗口）；并明确 quiet window 针对的是机器负载还是共享状态。如果宿主能暴露 peer 的活跃负载查询，也能替代 IRC 轮询。**推断**：文件锁比 IRC 更可阻塞、可观测。

## 6. 中：票据/契约没有点名 assembly 的框架消费者用例

**事实**：本 ticket 的 checkbox 只说“受影响消费者”，没有列出具体套件；`tests/framework/startup-requirements.test.ts` 直到 peer 提醒才被加入验证。connect-bot assembly 的改动直接影响该测试的“no lifecycle subscription”分支。
**影响**：assembly/装配类改动容易漏掉框架层的绑定诊断回归。
**建议**：在 /to-tickets 的票据模板或 contract 的 coverage 表中增加 `Consumers:` 行，按改动类型点名套件（assembly → `tests/framework/startup-requirements.test.ts`、`tests/framework/implementation-startup.test.ts`；真实宿主 → 对应 dock 文件）。这是流程工件，不是代码。

## 7. 中：P19 人工确认命令是 bash 形状、含占位符

**事实**：ticket 的 P19 人工部分记录了 `PI_CODING_AGENT_DIR="$TEMP/..."`、`$PWD` 和 `<model>` 占位符；本轮未执行该命令，实际 OMP 终端的失败反馈和 marker 缺失仍未验证（符合契约的人工保留项）。
**影响**：用户可能需要在 PowerShell 下自行改写命令/补 model，增加人工轮摩擦；命令是否可直接运行未验证。
**建议**：在 `framework/README.md` 或 ticket 模板中提供 PowerShell 与 bash 两种形态的隔离启动命令，并用仓库已有的 `DOCK_MODEL_SELECTOR`/用户配置消除 `<model>` 占位；或提供一个只打印“已填好路径的命令 + 预期观察”的小脚本。**未验证**：`PI_CODING_AGENT_DIR="$TEMP/..." bun ...` 在目标终端可直接启动并显示预期错误。

## 8. 低：各套件各自实现 panel double / wait helpers，重复且易错

**事实**：本次向 `tests/connect-bot/startup-modes.test.ts` 与 `tests/harness-dock/connect-bot-startup.test.ts` 追加用例时，分别复制/扩展了 panel 记录、`waitFor`、状态载荷读取等 helper；两处新 helper 都出现过一次作者错误（见 #4）。
**影响**：维护两份等价逻辑；修正一个语义（如 fail-then-accept、header 定位）需要在多处同步。
**建议**：给 reviewer 一条判断规则（不是机械 lint）：“新增测试套件优先复用/抽取现有 support；只有语义确实不同时才另写。”若 repo 更倾向每套件自包含，则在 `docs/agents/testing.md` 记录“共享 helper 的边界”，避免两种约定并存。

## 9. 低：工具经济——codebase-memory 未使用，Windows PowerShell 引号产生大段噪声

**事实**：本会话读了多个 >100 行的源码区间（binding/registration/state/host session-manager），未使用 codebase-memory 的 outline/snippet；一次 PowerShell 进程查询因 bash 先展开 `$_`，输出了大量重复错误。
**影响**：前者可能多读了可先 outline 的内容；后者直接浪费上下文。
**建议**：若该 repo 已索引，在 `AGENTS.md`/`docs/agents/` 加一个 navigation pointer 指向 codebase-memory 的用法；在宿主工具说明中给出 Windows 下 PowerShell 使用单引号的提示（或直接建议用 `bash` 单引号包裹）。**未验证**：本 worktree/仓库是否已在 codebase-memory 中索引，以及 outline 是否覆盖这些文件。
