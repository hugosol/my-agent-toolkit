# 复盘：03-connect-bot 启动模式 TDD 执行

## 结论摘要

本票实现已完成并提交（`263916c`），最终 typecheck 通过，connect-bot 非真实面板分区 137/137 通过。主要改进空间不在业务代码，而在 **worktree 初始化、真实面板前置条件、重复测试工具** 三类环境问题；它们让 TDD 的第一次红并非行为红，也把真实面板验证拖到实现末期才暴露。

## 建议（按严重度）

### 1. 高：worktree 初始化应预装依赖并建立 codebase-memory 索引

**事实**：本 worktree 首次运行 `bun test` 直接报 `Cannot find package 'yaml'`；随后执行 `bun install --frozen-lockfile` 安装 14 个包才得到真正的行为红。另一方面，codebase-memory 的 `list_projects` 有 27 个项目，但不含本 worktree；`index_status` 首次以空参数调用因缺少 `project` 失败，之后 agent 改用 `read`/`grep`/`bash`（本会话共 47 次 `read`、162 次 `bash`）。

**建议**：
- 在 ticket worktree 创建流程中加入 `bun install --frozen-lockfile`，并让 `bun test` 前置检查在依赖缺失时给出“先安装依赖”的明确错误，而不是导入错误。
- 为每个 worktree 自动执行 `index_repository`，或在 `AGENTS.md` 加一个稳定的 worktree 项目名约定和一条“未索引时先索引”的指针。这样“读大文件前先看 codebase-memory 大纲”的指令才真正可用，而不是在未索引 worktree 中静默退化。

**影响**：避免把环境红误判为行为红，减少大范围手工阅读。

### 2. 高：真实面板测试需要前置条件检查和版本兼容处理

**事实**：
- `tests/connect-bot` 全量运行结果：142 pass / 7 fail，7 个失败全部来自 `startHerdrBot`。
- 不设置 `HERDR_BOT_BINARY` 时，默认路径 `C:\Users\hugos\AppData\Local\Temp\herdr-bot\...` 不存在。
- 设置 `HERDR_BOT_BINARY=E:/Developer/myhub/herdr-bot/backend/target/release/herdr-bot.exe` 后，当前 sibling 构建要求配置包含 `[herdr]` 段，而 `tests/connect-bot/support/herdr-bot.ts` 仍写旧 schema，启动报 `missing field herdr`。
- 这两次失败分别耗时约 20 秒启动超时；全量 connect-bot 套件耗时约 118 秒，新增 dock 文件约 55 秒。
- 因此 P16 的“真实隔离面板读侧”和 P18 的真实面板确认最终只能标记为环境限制，未完成。

**建议**：
- 在 `docs/agents/testing.md` 明确：connect-bot 的 `budget-regression`、`harness-exit-budget`、`panel-registration-lifecycle`（以及新增的 real-panel dock 用例）需要 `HERDR_BOT_BINARY` **且配置 schema 与冻结版本匹配**；缺失时这是已知限制，不应逐个用例重复报错。
- 增加一个 `package.json` 脚本（例如 `check:panel`）做单次 preflight：启动二进制、检查 `--config` schema 和 `GET /api/sessions/events`，然后给出“可用/不可用/需要哪个版本”的结论。
- 若希望兼容新旧 sibling 构建，可让 `writePanelConfig` 通过显式环境开关选择 schema；默认仍保持冻结基线，避免改变既有测试语义。
- 票面若把真实面板列入验收，应在实现前执行 preflight，并把它写进 `Blocked by`/环境前提，而不是实现末期才发现。

**未验证**：本机是否存在与冻结测试辅助器兼容的旧 herdr-bot 构建；未找到。

### 3. 中高：把重复的测试辅助函数收敛到共享支持模块

**事实**：
- 本会话中 `withCapturedStderr` 在至少 7 个测试文件中重复实现。新写的版本在对象字面量中先计算 `diagnostics: chunks.join("")`、后调用 `run()`，导致捕获永远为空；随后通过临时 debug 测试和脚本才定位，最终改为先执行 `run()` 再读取 chunks。
- `waitFor` 同时存在于新增单元测试和 dock 测试中，且一个返回 `void`、一个返回 `boolean`；单元测试版本最初没有超时，导致一次断言得到 `undefined` 而不是失败。

**建议**：
- 在 `tests/support/` 或 `tests/connect-bot/support/` 提供经过自测的 `captureStderr(run)`、`waitFor(condition, timeoutMs)`、`waitUntil(asyncCondition)`，所有套件引用同一实现。
- 这是机械重复导致的确定性 bug，适合集中化，而不是写一条“记得先调用 run()”的文字标准。

### 4. 中：源码扫描测试不要固定实现文件路径

**事实**：`tests/connect-bot/native-timer-boundary.test.ts` 原先把“assembly 真的触达原生 timer”固定为 `harnesses/omp.ts` 必须包含 `ctx.setInterval`。本次把共享 OMP 装配抽到 `harnesses/omp-assembly.ts` 后，该用例和 `native-session-boundary` 的配套扫描一起变红；前者改为扫描 `omp-assembly.ts` 后通过。

**建议**：
- 当规则是“只有 harness 目录可以触达原生表面”时，扫描整个 `harnesses/` 子树并断言至少一个文件匹配，而不是绑定具体文件名；另保留一个“入口文件是薄 re-export”的检查。
- `native-session-boundary` 成功阻止了新 assembly 枚举 `session_switch`/`session_branch` 的写法，说明该 guardrail 有价值。可在测试注释里补一句“包装全部事件，而不是枚举原生生命周期名”，让规则意图更易遵守。

### 5. 中：human-led 证据应产出可执行脚本，而不是事后手工拼命令

**事实**：本票要求为 P18 准备 OMP 隔离启动命令、可控场景、终端截图/录制。最终报告只能引用 dock 测试和 S1 latch 用例，并明确“实际终端 marker 显示留给用户确认”；没有产出独立的、可重复运行的终端验收脚本。

**建议**：
- 增加一个 `scripts/connect-bot-startup-acceptance.ts`：启动一个延迟/拒绝 register 的本地面板，materialize 隔离部署，打印可直接粘贴的交互式 OMP 启动命令，按回车或超时后释放 receipt；脚本同时打印“未完成/成功前后”的时间顺序提示。
- 在 ticket 模板中把 human-led 证据的“可执行入口”列为交付物，避免验收阶段再手工构造环境。

**未验证**：该脚本是否能覆盖用户实际终端的所有显示差异；需要用户实际运行确认。

### 6. 低：统一 TypeScript 库目标与运行时能力

**事实**：本次使用 `Array.prototype.at` 触发 10 个 `Property 'at' does not exist` 类型错误，改为下标访问后通过。仓库的 `tsconfig` lib 与 Bun 运行时能力不完全一致。

**建议**：若仓库偏好 ES2022，加入对应 lib；若偏好下标风格，在静态检查或简短风格说明中明确。当前 typecheck 已能捕获，优先级低。
