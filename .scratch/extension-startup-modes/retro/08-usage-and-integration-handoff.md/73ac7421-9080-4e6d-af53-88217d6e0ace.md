## 建议（按严重度）

### 1. 视觉验收缺少“可执行的捕获路径”（高）

**事实**：ticket 要求为 P8/P9/P18/P19 准备终端截图或录制；最终交付只有命令、场景和自动结果，四个视觉判断均标为 unverified，没有帧或图像。仓库已有 `scripts/pi-tui-acceptance.ts` 和 `scripts/support/terminal-screen.ts`，能为 model-cost 捕获真实 TUI 的帧、屏幕文本和可选图像；启动模式的四个 runbook 没有指向它们，agent 直到收尾搜索才发现。

**建议**：在 `docs/agents/testing.md` 增加“启动模式视觉材料”小节，指向现有捕获设施；为 codebase-tools/connect-bot 各提供一个 `--prepare` 捕获入口（或最小脚本），用 dock provider/panel 起真实 TUI，把 frames/screenshots 落到 `.cache/...`，runbook 只负责让用户确认渲染。若决定保持 human-only，则在 runbook 明确写“用户负责录制，agent 只提供命令”，消除 ticket 文本与交付的歧义。

**边界**：现有脚本对 model-cost 已验证；能否直接复用到两个启动模式是推断，未执行验证。捕获的是渲染输入，不是人工视觉确认；人工确认仍必须保留。

### 2. 新写的 H1d 验收 runbook 本身没有被执行（高）

**事实**：H1d 新增约 80 行 shell：部署副本、独立 herdr-bot 配置、端口改写、隔离状态启动。它按 `tests/harness-dock/connect-bot-startup.test.ts` 的部署过程写成，但本会话没有运行其中任何一条；实际运行的是测试自带的临时部署和临时端口。自动行为已验证，runbook 的复制路径、端口和配置步骤未验证。

**建议**：把 H1d 的 setup 抽成脚本或测试 helper，runbook 引用它；或把该 runbook 的 setup 作为文档检查的一部分执行一次（即使只到面板启动和目录/配置存在）。这样人工验收不会因 runbook 自身错误而浪费一轮。

**边界**：未观察到 runbook 失败；风险是推断。部署布局经过了推理，但没有真实执行。

### 3. 没有 `check:docs`；链接/示例检查是临时脚本（中高）

**事实**：`docs/agents/testing.md` 明确要求 documentation-only 变更做 link/example checks，但 `package.json` 没有对应脚本，仓库也没有 checked-in 的 docs 检查。本会话用内联 Python 检查，第一次报 88 个失败，绝大多数是 `#L` 源码行锚点、显式 `<a id>` 锚点和仓库外引用；修正规则后才是 486 链接/0 失败。

**建议**：新增 `scripts/check-docs.ts` 和 `check:docs`：解析仓库 Markdown，跳过外部链接和 `#L` 行锚点，接受 `<a id>`，对缺失文件/锚点失败；对现有 7 个无关坏链先修复或 allowlist。可进一步提取 fenced `bash` 命令，替换占位符后检查仓库相对路径/入口是否存在——保持结构性检查，不建立固定措辞断言，符合本 ticket 的约束。把该脚本接入 `typecheck` 或 pre-commit。

**边界**：whole-repo 扫描发现的 7 个失败是既有且与本 ticket 无关（归档 `.scratch` 链接、model-cost glossary 锚点）；新检查需要基线或先清理。

### 4. “发布的示例”与自动化证据没有固定映射（中）

**事实**：agent 手工把 README 的启动示例映射到测试：OMP manual root → `tests/framework/deployment.test.ts`；OMP auto codebase-tools → `startup-modes-dock.test.ts`；connect-bot → `connect-bot-startup.test.ts`；单选/组合/混用 → `startup-modes-loading.test.ts`；pi → 两个 smoke 脚本。该映射只存在于最终报告，仓库里没有表。

**建议**：在每个 extension README 的 Startup modes 旁加一张很小的 verification map（示例 → 测试/脚本 → 观察点），或放到 `docs/agents/testing.md`。这是导航指针，不是断言复制；下次执行不必重新推导“哪个测试算执行了发布示例”。

**边界**：映射本身是事实；哪些示例必须逐字执行、哪些可用等价隔离运行替代，仍应由 ticket/契约说明，文档表不能替代该决定。

### 5. codebase-memory 指令是 no-op（中）

**事实**：用户提示两次要求“grep/search 前考虑 codebase-memory”“读 >100 行源码前先看声明大纲/片段”；本会话没有出现 `list_projects`、`index_status`、`search_graph` 或 `get_file_outline` 调用，实际使用 `grep`、`read`、`sed`。指令没有改变行为。

**建议**：把 permissive 措辞改成具体触发和 fallback，并放到持久文件（AGENTS.md 或 `docs/agents/`）：符号/声明查找 → `search_graph`；>100 行源文件 → `get_file_outline`；若 `index_status` 未就绪，明确报告并回退到 `grep`/`read`。在 worktree bootstrap 中加一次 `index_status` 检查。若该 MCP 对 Temp worktree 不可用，直接删除这条指令，避免每轮付费却不生效。

**边界**：推断——Temp worktree 可能未被索引；本会话没有检查 `index_status`，因此不能断言工具不可用，只能断言指令未被触发。

**边界**：宿主可能在仓库外执行检查；本会话只核实了仓库内没有 checked-in guardrail，未核实远程 CI。

### 8. 验收索引与持久证据分散（低中）

**事实**：P8/P9 在 codebase-tools README，P18/P19 在 connect-bot README，framework README 只新增了 connect-bot H1d 链接；根 README 的 H1 行仍写“interactive TUI acceptance, codebase-tools”，没有列出 connect-bot 的 H1d。验证日志在 `.cache/verification/`（gitignored），完整结果只在本轮最终报告里。

**建议**：在 framework README 或 `docs/agents/testing.md` 加一张 promise → runbook → 自动测试 → 人工状态 的小表（避免重复可变状态，状态可链接到 runbook 的“unverified until confirmed”）；同步根 README 的 H1 行，说明两个 consumer 的视觉 runbook。明确 ticket 验证记录的权威位置：若工作流报告是权威，就在 testing.md 写明；否则给一个 checked-in evidence 约定。

**边界**：宿主可能保存最终报告；未验证其持久化位置。小型表只做索引，不复制测试断言或历史计数。

### 9. 工具选择：shell 读取替代 `read`/`glob`（低）

**事实**：本会话多次用 `sed -n` 读取文档/源码区间，用 `ls`/`find` 列文件，尽管 `read` 和 `glob` 是专用工具。`read` 的区间语法 `path:start-end` 不常见，可能是部分回退的原因；agent 对另一些文件确实用了 `read`。

**建议**：在 AGENTS.md 或工具约定中加一行示例（文件区间 → `read path:10-40`；文件树 → `glob`），或接受“快速区间用 shell”并删除与专用工具偏好的冲突。影响小，仅在工具经济性上值得统一。

**边界**：这是过程观察，不是错误；不影响本次正确性。
