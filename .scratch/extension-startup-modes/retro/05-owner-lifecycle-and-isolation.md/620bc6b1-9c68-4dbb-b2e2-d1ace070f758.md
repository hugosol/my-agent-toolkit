## 建议（按严重度）

### 1. [高] herdr-bot 真实面板不可用时应快速失败，并与常规分区分离

**事实**：`tests/connect-bot` 的 5 个失败和 `connect-bot-startup` dock 的 1 个失败都在 `startHerdrBot` 阶段发生，错误指向 sibling checkout 的 release 二进制无法解析 `tests/connect-bot/support/herdr-bot.ts` 写出的配置（`listen_addr` 顶层字段，二进制要求 `herdr` 字段）。失败前固定等待 20s，且 `bun test tests/connect-bot` 因此无法作为“分区绿”的证据。

**推断**：sibling 的 herdr-bot 二进制已更新配置 schema，而测试支持仍按旧 schema 生成 TOML；这是外部依赖漂移，不是本票代码回归。

**建议**：
- 在 `startHerdrBot` 中监听子进程的提前退出与 stderr 中的解析错误行，匹配到时立即失败并输出原始 stderr；不要只依赖 20s bind 超时。
- 把真实面板互操作测试拆成独立的命名分区（例如 `test:interop`）或环境变量门禁，net 常规 `test:connect-bot` 只跑受控 panel double 的用例；在 `docs/agents/testing.md` 说明该分区的 external prerequisite。
- 增加一个 preflight：打印解析到的 herdr-bot 路径、调用 `--version`（若支持）并做配置 schema 探测，让“面板不可用”在 1 秒内成为一条明确的环境结论。

**未验证**：是否存在可用的旧版二进制；在当前二进制上补上 `[herdr]` 配置是否即可恢复全部互调用例。

### 2. [高] codebase-tools 的 OMP 装配无法在 S1 组合测试中导入，导致 P32 只能落在 S2

**事实**：新增 S1 组合消费者测试时，导入 `entrypoints/omp/codebase-tools` 立即报错 `Cannot find module '@oh-my-pi/pi-utils' from .../extensions/codebase-tools/harnesses/omp-assembly.ts`。该装配在模块顶层导入 `logger`，而该包只在真实宿主运行时可用，repo 的 `node_modules` 没有它。结果是原计划的 S1 两消费者组合测试被删除，P32 的组合证据只保留在 S2。

**推断**：这是宿主专属依赖泄漏到可单元测试的装配层，属于隐藏依赖；不是测试写法错误。

**建议**：
- 把 logger 变成可注入或可缺省的能力，或把宿主专属导入收进一个只在真实宿主路径加载的模块，使 OMP 装配可以在 `bun test` 内导入。
- 如果短期不重构，应在 ticket/contract 的 seam 说明中明确：codebase-tools 的组合观察只能在 S2 进行，P32 的 S1 面不可用；避免后续执行者重复尝试。
- 为两个消费者的组合增加一个 S1 测试支持模块（例如共享 marker/port double），让“纯声明消费者 + 外部效果消费者”的隔离可以在更轻的层验证。

**未验证**：重构导入后是否仍保持真实宿主中的 logger 行为；是否与 02/04 票据的装配改动冲突。

### 3. [高] 跨分区的回归只在事后全量 framework 分区才暴露

**事实**：本票运行 `tests/framework` 时发现 `tests/framework/startup-requirements.test.ts` 的“native registration failure”用例已红：connect-bot 的 OMP 上下文包装在装配时提前执行 `pi.on.bind(pi)`，在缺少 `on` 的宿主表面上抛出，绕过了 framework 的 registration failure 路径。该问题不来自本票新增代码，修复后 7 pass。会话中没有出现 CI 或预合并门禁执行该分区的证据。

**推断**：若每个票据只跑自己的 partition，跨分区的装配/生命周期回归会一直留到集成阶段；当前分支能发现它，是因为本票主动跑了 framework 分区。

**建议**：
- 在集成分支设置一个 pre-merge guardrail：至少运行 `tests/framework`、`tests/connect-bot`、`tests/codebase-tools`（或 `bun run test`），并在失败时阻止合并。
- 在 ticket 模板的完成标准里列出“受影响跨分区”，而不是只写“所属分区”；本票的验收标准已接近这个要求，可以把它固化到模板。
- 对“框架注册失败路径”这类跨层行为，保持现有 framework 用例作为守门测试；本票已修复装配并复用了该用例，不需要新增重复测试。

**未验证**：仓库是否已有 CI 配置或预合并 hook；本次会话只观察到没有运行证据，不能据此断定不存在。

### 4. [中] 长测输出被 `tail` 截断，失败证据需要二次重建

**事实**：`bun test tests/connect-bot 2>&1 | tail -40` 只保留了 5 个失败中的 2 个名字和总计；随后通过 grep `startHerdrBot` 的使用位置、再运行排除文件的方式才确认失败集合与 143 pass。`docs/agents/testing.md` 已经写明“长跑输出保存到 run-specific log”，但本次没有按该条执行。

**建议**：
- 增加命名脚本（例如 `test:connect-bot`、`test:interop`），脚本内部把输出 tee 到 `.cache/test-runs/<timestamp>-<partition>.log`，并在结尾打印日志路径；这比继续依赖测试文档的提醒更可靠。
- 如果 harness 能自动把完整命令输出保存为 artifact，优先在工具层做；本次 agent 最终用 `eval` 手动构建文件列表并捕获输出，说明缺少现成的 partition runner。
- 在失败摘要中打印每个失败的文件名与测试名（即使只取尾部），避免计数之外的证据丢失。

**事实补充**：`package.json` 有 `test:framework`、`test:codebase-tools`、`test:dock`，但没有 `test:connect-bot`；本票的 owning partition 没有命名脚本。

### 5. [中] connect-bot 测试支持代码在新旧文件中重复

**事实**：新增 `tests/connect-bot/startup-lifecycle.test.ts` 复制了既有 `startup-modes.test.ts` / `registration-lifecycle.test.ts` / `off.test.ts` 中的 `envelopeOf`、`panel`、`bound`、`waitFor`、`settleAll`、marker/area 读取等辅助逻辑；S2 文件也复制了 area/notices/capture 解析辅助。单个文件都可读，但同一约定的副本已经分布在至少 4 个文件。

**推断**：下一次协议字段或 panel double 形状变化时，这些副本会产生漂移；属于可维护性成本，而不是本次行为错误。

**建议**：
- 抽出 `tests/connect-bot/support/wire-panel.ts`（envelope、scripted panel、held request、settle）与 `omp-area.ts`（marker/area/notice 读取），各测试文件只保留场景数据。
- 在 code review 规则中加一条判断性标准：同一测试约定出现第三份副本时抽取；不要为一次性场景提前抽象。

### 6. [中] 新建 worktree 没有依赖，首次测试以模块缺失失败

**事实**：本票首次运行 `bun test` 立即报 `Cannot find package 'yaml' from framework/core/config.ts`；执行 `bun install --frozen-lockfile` 后恢复。ticket/worktree 启动说明里没有提到这一步。

**建议**：
- 在 ticket harness 的 worktree bootstrap 中检查 `node_modules` 是否存在，缺失时自动执行 `bun install --frozen-lockfile`，或在 ticket 模板的“开始前”列出该命令。
- 与测试文档放在一起，因为它直接影响“第一条红测试”是否可信。

### 7. [中低] S2 断言使用了累计计数，正常业务流量会改变它

**事实**：S2 首轮运行有 2 个断言失败：request capture 期望至少 6 而实际 5（slash command 不产生模型请求），panel `state` 期望 1 而实际 4（每轮 turn 的 working/awaiting-input 状态报告也走同一通道）。agent 改为明确请求数 5，并把 P7 的 state 数量断言改为“编辑后 marker/register 不变”。

**推断**：对共享通道使用绝对累计计数会把无关但合法的流量误判为回归；属于测试写法问题。

**建议**：
- 在测试编写规范中加一条：优先断言事件值/顺序/相对增量，或先记录基线再比较；只有在通道被隔离时才用绝对计数。
- 对 panel 协议测试，按 `kind` + `data.value`/`reason` 组合过滤，而不是按 kind 总数断言。

### 8. [中低] 运行归属需要更显式

**事实**：完整 `tests/connect-bot` 分区结果（150 pass / 5 fail）产生于装配修复之前；修复后只重跑了 17 个非面板文件（143 pass）和 9 个受影响文件（66 pass）。最终报告中虽然分别列出了这些结果，但“完整分区”与“修复后子集”的对应关系需要读者自己拼接。

**建议**：
- 测试脚本在日志头打印 `git rev-parse --short HEAD` 和工作树 dirty 状态；汇总报告直接引用“哪个 commit 的哪个分区”。
- 最终报告把“最后一次完整分区”和“最后一次受影响子集”标成不同证据行，避免把修复前的结果当成修复后的分区绿。

**未验证**：修复后完整分区中的 5 个面板失败是否仍完全由外部 herdr-bot schema 引起；从代码路径看装配修复不影响真实宿主（`on` 存在），但本次没有重跑那 3 个面板文件。

### 9. [低] codebase-memory 索引被创建但从未使用

**事实**：会话开始调用了一次异步 `index_repository`，之后没有查询索引状态，也没有使用 `search_graph`/`trace_path`；代码探索全部通过 `find`/`grep`/`read` 完成。工具提示要求“调用 grep/search 前考虑 codebase-memory”，本次的考虑结果是实际未使用。

**建议**：
- 对小仓或本 repo 的常规 TDD，删除这条常驻提示，避免每次执行都产生一次无收益的索引调用；如果保留，把它改成一个可执行的触发条件（例如“需要跨文件调用链时先 `trace_path`”），而不是泛化的“考虑”。
- 如果要继续维护索引，给索引调用加一个明确的使用步骤，否则它属于上下文/工具预算的 no-op。

### 10. [低] `git commit -m` 中的反引号被 shell 执行

**事实**：提交信息里写了 `` `on` ``，bash 将反引号当作命令替换，输出 `error: command not found: on`，提交信息中该词丢失；随后用 `git commit --amend` 修正。

**建议**：
- 提交多段说明时使用 `git commit -F -` 配合 heredoc，或写入临时 message 文件；避免在双引号参数中放反引号。
- 这不是代码问题，但属于工具使用规范，可以放进 agent 的提交步骤说明。

### 11. [低] harness-dock 窗口靠人工 IRC 协调

**事实**：本票与 peer `04` 通过消息互相等待 dock 运行窗口；双方都遵守了串行约定，但也产生了几次等待和状态确认。

**建议**：
- 提供轻量的 dock 运行锁（例如 `.cache/harness-dock.lock` 带 owner 和 pid/time），或在测试文档中给出“先询问、后运行”的标准消息模板；只有在并发 dock 运行确实会互相影响时才值得引入。
