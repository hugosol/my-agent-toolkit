**推断与限制**

分散消息没有提供一个所有执行者共用的窗口所有者与队列，增加了等待、过期授权和重复协调风险。日志不足以独立判定本票三条 Pi smoke 是否与全局运行重叠，也不能把同伴报告的重叠直接归因为本票测试失败；本票最终分区均通过。

**建议**

由工作流宿主维护机器级验证令牌，涵盖同一机器上的所有 worktree 与集成代理，而不只覆盖同级实施代理。令牌记录当前持有者、运行范围、排队顺序和代次；启动昂贵运行时取得令牌，进程结束后统一释放。重新排队时废止旧代次授权，避免代理继续执行已经失效的“可以开始”消息。

保留现有 testing 文档作为规则权威；代理只需取得和释放令牌，不再自行拼接全局队列。若已有调度设施，应接入它，而不是再建一份人工状态表。

**完成判据**

## 2. 高：在测试设计入口显式区分“扩展效果”与“框架保留路径”

**事实**

本轮 disposal 场景经历了两次语义修正：先将同一 assembly 的多个 binding 改成独立 assembly；随后观察到释放后 local toggle 仍会追加 State，便向 Main 报告“既有缺陷”。约八秒后，代理读到 `framework/behaviors/binding.ts:503–505` 的既有明确说明：扩展实现及其能力停止交付，但框架自己的 local toggle 仍可达，于是撤回缺陷判断。

最终测试分别验证了 authored directed command 停止、prompt callback 停止，以及 local toggle 的既有保留行为，没有为满足错误预期去改产品代码。这一点应保留。

**建议**

在已有生命周期参考资料中提供一个紧邻相关规则的导航入口：设计 disposal／多 binding 测试时，先定位 assembly、binding、实现实例各自的所有权，以及停止交付规则的适用对象。入口应指向现有权威规则或消费测试，而不是复制实现注释形成第二份契约。

TDD 的“设计前置”记录可增加一个紧凑字段：**被停止的对象及其所有者**。测试失败后，先区分 fixture 错误、与既有契约冲突、真实回归，再决定修正场景或升级缺陷。保行为重构仍允许 characterization 直接 green；导入错误、配置 fixture 错误和所有权误设不计为有效行为 red。

**完成判据**

新的生命周期测试在运行前即可说明：共享 assembly 与独立 assembly 有何区别、哪条路径必须停止、哪条路径按原契约保留。预期修正有独立契约依据，而不只依据“当前实现就是这样”。

## 3. 中：把已有类型检查变成可靠 guardrail，并机械检查显式 `any`

**事实**

- 本轮初写测试使用了显式 `any`，由宿主风格提醒后修正。
- 后续新增 handler 的隐式 `any` 被现有 `bun run typecheck` 捕获；修正后重新通过。
- 配置 fixture 最初把 `config.path` 写成 `file`，导致合法配置场景被拒绝；一次批量文本替换又生成 `path: file: document(...)`，编辑工具立即报告语法错误，随后修复。
- 已读取 `package.json`：仓库已有 `typecheck`，串联 TypeScript 与 `check:authoring`，不需要另造一套类型检查命令。常见仓库 CI、hook 与 lint 配置路径检索未发现文件；未核验仓库外 hooks 或平台外部 CI，因此不能断言整个环境完全没有门禁。

**建议**

优先将现有 `typecheck` 接入仓库可见的提交或 CI guardrail。对显式 `any` 这类固定语法模式，采用 TypeScript AST 或现有 lint 设施的确定性检查，并纳入同一检查入口；不把它转写成要求 reviewer 凭记忆执行的规范。

测试中的声明对象优先在边界使用明确类型或 `satisfies`，尽早暴露字段拼写错误。测试失败仍由行为断言负责，类型检查负责消除 fixture 的结构性噪声。

**完成判据**

本轮出现的显式 `any`、隐式 `any`、声明字段误拼和语法损坏，都能在既定自动入口得到可定位诊断；正确代码继续复用现有检查链，不重复运行两套同义检查。

## 4. 中：在 worktree 交付时提供可读取的前置事实，避免用 Git 写操作探测状态

**事实**

代理未尝试读取本地冻结样例，就根据未展开的目录概览向 Main 报告样例缺失，随后读取了集成 checkout 中的样例。后来执行 `git cherry-pick 68030a9`，工具报告该提交已为空；代理 skip 后才直接读取本地样例，确认前置基线早已存在。没有证据表明此次空 cherry-pick 丢弃了工作，但这是一段可避免的版本控制操作与协调往返。

另一个前置问题是首次运行测试时缺少 `yaml`，执行 `bun install --frozen-lockfile` 后测试才可加载。

**建议**

由 worktree 创建／交付流程提供一次性前置结果：依赖是否已安装、基线是否已包含、冻结样例的本地入口。其值来自真实环境，不在长期文档中手工缓存提交号或临时目录。

代理侧采用一个可检查的完成条件：实际成功读取本票需要的本地样例，且依赖加载可用后，再进入行为验证。只有精确读取失败时才调查缺失原因；目录概览未展示子项不等于文件不存在。确认提交是否已包含应采用只读查询，而非尝试 cherry-pick。

**完成判据**

新 worktree 的实施代理能在开始测试前确认依赖与样例入口；已有基线不会引发空 cherry-pick，也不会因为目录折叠而改读集成工作区。

## 5. 中：给检索与批量编辑工具增加“降级”和“紧凑返回”两条路径

**事实**

- 首次 `find` 的 22 个 judge 请求全部因地区不可用返回 HTTP 451；稍后另一次 `find` 又发生同样失败，涉及 19 个请求。
- 一次图搜索返回零结果，但后续精确文件 outline 可以正常返回声明；零结果本身不足以证明代码不存在。
- 批量导入修正通过 Eval 打印了完整 edit 返回对象，带出每次修改的 `oldText/newText` 等详情，产生约 51 KB、2262 行输出；之后改为只打印 `.text`，输出明显收敛。
- 批量 import cutover 使用 AST proposal 并显式 apply，成功完成 18 处替换；相较之下，后续普通文本替换曾引入语法错误。

**建议**

检索工具对会话内已确认的服务级不可用状态做短路，明确给出精确文本／路径检索的降级路线；图搜索空结果则保留查询限制，不将其解释为不存在。

Eval 中调用 edit 等工具时默认返回精简状态、定位与差异摘要，把完整快照留给按需 artifact。跨文件 import 变更继续采用本轮已奏效的 AST proposal／apply 路径；不再通过输出整份编辑对象证明修改成功。

这些属于工具契约与确定性处理，不需要向全局代理指令追加更多禁止句。

**完成判据**

同类服务级失败在同一会话内不再重复触发整批远端请求；批量修改的默认输出不包含整份旧／新源码，仍能按需追溯每项改动与失败。
