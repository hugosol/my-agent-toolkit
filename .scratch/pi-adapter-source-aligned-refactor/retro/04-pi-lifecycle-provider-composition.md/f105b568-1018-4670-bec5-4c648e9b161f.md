# Ticket 04 TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 子会话 JSONL 中的实施记录，截止原实现轮首次 `yield`；未读取父会话或其他代理的执行历史。其他代理的情况只引用本会话实际收到的消息，不据此推定其完整执行过程。本轮未修改文件，也未重跑验收。

本次有值得保留的实践：迁移前取得 **104/0** 行为基线，没有把缺依赖造成的失败算成产品 red；新增用例经过公开 assembly；最终 focused **114/0**、framework **665/0**、Pi 消费分区 **91/0**；四项真实 Pi smoke 分别通过 **32、17、15、11** 项观察。报告也保留了联合消费方运行的 **137 pass / 2 fail**，没有用后续绿色结果覆盖它。

主要改进机会不是增加“更认真测试”的规则，而是让运行调度、迁移前置条件和证据归属由环境直接保证。以下按严重度排序。

## 1. 高：把真实宿主运行窗口变成统一租约，而不是代理间口头接力

**事实。** 本会话依据前序代理释放窗口的消息，于 **16:51:21–16:55:11 UTC** 在一个阻塞 `eval` 调用中顺序执行四个 smoke。期间收到 integration-01 表示全仓测试仍在运行、窗口此前没有释放的消息。该消息时间戳为 **16:51:05**，但在会话记录中出现在整批工具结果之后；04 随后明确披露可能存在跨运行负载。此后又通过 Main 排队，至 **17:19** 才开始最终分区检查。

**判断。** 消息接力无法可靠表达所有 worktree 共用的机器资源占用，长阻塞工具调用又使调度变更不能及时影响下一条命令。四次 smoke 全部成功，并不证明获得了严格的 quiet window；会话没有证据表明重叠导致了具体失败。

**建议。** 在宿主测试启动器中提供跨 worktree 的统一租约，implementation 与 integration 代理使用同一资源名。每次启动昂贵命令时由启动器原子取得租约、登记运行身份，进程结束后释放。四条 smoke 分成四次受控启动，使调度变更能在命令之间生效。已有 `docs/agents/testing.md` 只需指向这一入口，不再增加一层群聊约定。

**完成标准。** 两个 worktree 同时申请时只有一个昂贵运行能够启动；每份日志都能关联租约身份及持有区间；取消或异常退出不会永久占用资源。

## 2. 高：联合运行失败时，自动保存“失败现场”，而不仅保存最终日志

**事实。** 最终联合消费方命令出现两项缺少消费记录／文档的失败。随后在隔离 clone 中，相同命令使用原始 Pi adapter 得到 **139/0**；在同一 clone 内仅替换 `adapters/pi` 为本票实现后仍为 **139/0**；原 worktree 的 Pi 单独分区又为 **91/0**。原联合运行的不稳定原因没有确认，报告如实保留了这一限制。

**判断。** 这些结果支持“隔离环境中未复现源码回归”，但不足以证明原失败属于既有缺陷、纯负载问题或测试间污染。隔离 clone 的绿色结果没有重现原 worktree 的完整失败现场。

**建议。** 扩展现有测试运行入口，在非零退出时自动保留运行清单：完整参数、cwd、源与 fixture 身份、相关配置解析位置、provider artifact、实际测试顺序，以及本次创建的临时目录索引。先冻结原失败的可观察外部条件，再做单变量比较。完成报告由同一运行清单生成，明确区分“实现已提交”“该命令失败未解释”“隔离比较通过”，避免靠人工在长报告中维持这些区别。

**完成标准。** 原失败与比较运行可以逐项核对变化条件；没有复现原条件时，报告保持“未归因”，而不是自动降级为基线失败或全绿。

## 3. 中：保行为迁移使用“迁移前后同一 tracer”，新增场景先证明前提成立

**事实。** 104 项旧用例基线先于源码修改，这是合理的保行为起点。但新增公开 assembly 场景是在主要来源拆分完成后加入。释放隔离测试先因错误读取 Turn delivery 的 `session` 字段失败，修正为 `turn.session` 后，又因两份 requirement 使用同一个 canonical child path 而失败。最终改用不同的真实 entry，并补上“两份 integration 均已成功”的断言后通过。

**判断。** 这两次失败来自测试观察面或场景前提，不能充当检测到产品违规的 red。最终报告对此区分正确。更好的前置安排能够减少在迁移后的新结构上同时调试测试与实现。

**建议。** 在现有 TDD 的保行为分支中采用短循环：先为当前承诺选定同一个公开 seam 场景，在旧实现上确认它确实到达目标条件，再迁移对应完整职责，最后用原场景观察新实现。隔离／释放场景先断言双方真实接入成功，再观察释放后的行为。对于旧实现已经满足的承诺，保留“基线成立”的分类，不制造产品 red。

**完成标准。** 每个新增保行为场景都能说明：目标违规是什么、哪项前提保证该违规可发生、什么消费结果能区分它；setup／fixture failure 与产品行为失败分开记录。

## 4. 中：复用现有类型检查，并让路径迁移使用可解析的导入变换

**事实。** 会话已读取 `package.json`：仓库具有 `bun run typecheck`，并串联 authoring check。批量拆分后，该检查实际捕获了仍指向旧 `domain/session/turn` 和旧 subagent 模块的导入。另一次测试中的 `delivery.session` 字段错误先以运行时 TypeError 暴露；当时使用的是 `bun test … && bun run typecheck`，测试失败后类型检查没有执行。

**判断。** 这里不是缺少新的编码规范；现有确定性检查已经能处理其中的机械错误。问题在于文本式迁移没有完整重定位导入，以及检查顺序让部分类型错误先进入了运行时调试。

**建议。** 导入重定位由 TypeScript 解析或已有 AST 工具按目标模块身份计算，而不是只调整相对目录深度。迭代入口在行为测试前执行现有类型检查，或独立收集类型检查与测试结果，避免前一项失败遮蔽后一项。不为这些机械错误增加 reviewer 的判断性规则。

**完成标准。** 移动文件后所有内部导入都可解析；测试对公开 delivery 的字段访问先经过类型检查；原行为断言保持不变。

## 5. 中：任务启动时明确工作树拓扑与跨票 cutover 契约

**事实。** 早期协调按可能共享文件的方式讨论 ownership；随后 02 明确说明 worktree 相互隔离。04 为保持自身可验证，保留尚未由 02／06 迁移的旧类型、State、Provider、UI imports，并在交接中要求集成方把新文件的这些引用映射到其他票的新路径。

**判断。** 本票在独立 worktree 中可通过验证，不等于组合后的导入图已完成 cutover。把这类差异主要放在聊天和报告中，会给集成留下重复发现调用方的成本。

**建议。** 宿主派单时直接提供机器生成的工作树拓扑：哪些源码隔离、哪些外部资源共享。跨票移动通过一份可消费的 cutover 清单表达旧路径、新路径、owner 与前置提交；集成工具据此完成确定性重定位，再运行现有类型和导入边界检查。此清单只表达迁移动作，不建立第二份运行时能力表。

**完成标准。** 集成方不需要回读聊天即可处理已声明的路径移动；assembled tree 中的旧实现、旧引用及未完成映射都有明确检查结果。

## 6. 中：把 worktree 初始化和查询可用性做成一次 preflight

**事实。** 最初搜索将 Pi adapter 定位到不存在的 `framework/adapters/pi`，随后还尝试了其他不存在的目录。语义 `find` 的 25 个 judge 请求全部因区域限制返回 451；对另一个索引根的图搜索则返回零结果且标记截断。第一次测试又因缺少 `yaml` 失败，执行 frozen-lock 安装后才取得有效基线。一次仓库根搜索还带出了本票范围外的 ticket 内容。

**判断。** 这些都不是产品缺陷。它们说明任务开始时，实际源码根、索引适用范围、工具健康状态和依赖是否就绪，没有被环境作为可靠事实交付。

**建议。** worktree 创建后执行一次轻量 preflight，输出实际仓库／源码根、当前索引对应的根、依赖就绪状态和可用查询后端。区域性 451 应触发本轮工具降级，直接使用本地符号／文本查询。代码搜索默认限定生产及测试源码根；单票任务仅在显式需要时进入其他规划材料。这些信息由环境生成，不缓存进越来越长的全局 AGENTS。

**完成标准。** 第一次行为基线不再被缺依赖阻断；不会把其他根的零搜索结果当作当前 worktree 不存在实现；范围外 ticket 不进入默认代码搜索结果。

## 7. 低：证据归档一次完成，并自动检查报告引用是否随提交交付

**事实。** 本次实机验证正确使用了单一 pi-subagents **0.78.0** 的隔离 deployment，没有修改正式配置中的 **0.80.0** 路径；也记录了真实子会话身份和启动条件。但代理需要手工复制 deployment、计算 hash、从临时目录重新定位 launch metadata，再写入证据。首次提交后，还需显式 `git add -f` 日志并 amend，才把报告引用的完整日志纳入提交。

**判断。** 本次最终进行了补救，没有证据表明最终提交漏交日志。风险在于同样的手工流程下，报告引用与实际交付内容可能分离。

**建议。** 让既有 dock/smoke 入口输出统一的 artifact manifest，直接列出实际 host/provider 身份、配置解析结果、run roots、child identity、启动条件与日志路径。归档前检查 manifest 引用是否都能在交付包或 staged 文件中解析；对仅保存在本机临时目录的材料明确标为外部保留。版本和路径从实际运行中读取，避免另建人工维护的环境说明副本。

**完成标准。** 从 manifest 能直接找到本次 child journal 与 launch evidence；提交前即可发现被忽略的日志；配置选择与实际加载 artifact 的不一致被显式记录。

## 建议落点与边界

优先落地 **统一运行租约、失败现场清单、确定性导入重定位**。它们是机械问题，应由宿主或仓库检查承担，不应转化为更多“注意协调”“仔细检查”的常驻指令。保行为 tracer 的执行分支适合放在现有 TDD／testing 指引中，并由现有导航指针到达，无需新建技能或扩大全局 AGENTS。

本会话没有检查 CI 与 Git hooks 的完整配置，因此本复盘**不判定仓库缺少全局 guardrail**。联合消费方两项失败的根因、真实运行重叠的具体影响，以及最终独立集成结果，均不在现有证据中得到确认。
