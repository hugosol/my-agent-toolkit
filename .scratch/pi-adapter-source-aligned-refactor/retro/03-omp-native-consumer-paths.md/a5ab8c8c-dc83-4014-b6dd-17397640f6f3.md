# TDD 执行复盘建议

## 范围与结论

本复盘只依据指定 ticket 的执行 JSONL，包括其中实际收到的协作消息、工具调用和返回结果；没有读取父 session 或其他执行者的对话。另只读查阅了本工作树的 `package.json`、`docs/agents/testing.md`、`tsconfig.json`、`.gitignore` 及 panel 测试辅助文件，用于判断建议是否重复已有机制。没有修改文件或重跑验收。

本轮值得保留的做法是：迁移前运行了 107 个相关测试；历史 State 样例来自重构前 journal，而非新实现自写自读；人为改错 State entry 名称后，历史恢复测试确实失败，恢复后通过；最终区分了完整分区失败、定向复验通过、结构供给和真实宿主证据。**不应把本轮所有失败都算作有效的 TDD red：若干失败来自测试假设、异步驱动或环境前提，而非产品行为违约。**

以下建议按影响程度排序。

## 1. 高：让昂贵验收窗口成为机器级租约，而不是聊天中的“空闲”判断

**事实**：`docs/agents/testing.md` 已要求昂贵运行串行协调。本票也多次申请、释放窗口。但在 16:55 收到的协作消息中，04 报告：其运行期间才获知独立集成者仍有全局 test／harness-dock 运行。之后 Main 才明确统一执行顺序，本票等待轮转后完成最终实机验证。

**判断**：缺口不是少写了一条“请协调”，而是窗口状态未覆盖 ticket 执行者和独立集成者。关于重叠，当前证据是本票收到的报告；没有独立检查其他进程，也不能据此认定本票的失败由并发负载导致。

**建议**：由宿主或现有工作流提供一个跨 worktree、包含集成任务的昂贵运行租约。运行器携带持有者、运行 ID、进程和释放状态；未取得租约的重型运行进入队列。聊天只负责交接说明，不再承担互斥机制。具体使用说明放在现有 testing 文档，无需扩充全局 `AGENTS.md`。

**完成标准**：两个执行者同时申请时，只有一个能启动重型子进程；异常退出能释放或明确暴露失效租约；日志能说明运行时由谁持有窗口。

## 2. 中：把安全壳要求变成可发现、可执行的测试环境前提

**事实**：完整 consumer 分区的一个失败是 `history-interop.test.ts` 的 `安全壳` 诊断断言。辅助文件支持 `HERDR_BOT_BINARY`，默认则选择相邻 checkout 的 release binary。直到后续协调消息给出已有安全壳 binary，最终指定该环境变量的定向运行才通过。安全断言始终保留，失败发生在请求 shutdown monitoring 之前。

**判断**：这是环境前提识别过晚，不是应该放宽断言的产品缺陷。辅助文件已经解释 binary 的解析方式，再写一份路径说明会形成缓存；真正缺少的是“涉及 shutdown 的测试必须选择安全实现”这一分支入口。

**建议**：在现有测试辅助入口或运行包装中显式声明 shutdown 测试所需的安全能力。启动相关场景前验证所选 binary 的安全身份，缺失时给出明确的环境失败和选择方式；保留原来的运行期安全断言。文档仅增加指向该入口的条件性导航，不硬编码本机绝对路径，也不自动跳过测试算通过。

**完成标准**：缺少安全前提时，在触发 shutdown 相关操作前失败；使用已存在的安全实现可以运行原场景，且不减少其行为断言。

## 3. 中：为 OMP seam 测试提供“契约导航”，减少把测试假设误判为产品 red

**事实**：本轮先后出现了几类测试假设问题：

- 假设 init 与 reminder 的文本可区分，实际资源内容相同；
- 对请求中的用户文本做完全相等比较，未考虑 OMP 的原生 metadata 包装；
- 最初要求 disposal 后 framework-local toggle 也停止，后来才读到 `binding.ts` 明确保留这条本地 State 路径；
- 原生命令测试在 action 真正进入前就断言 `started`，后改为显式入口 barrier。

这些问题最终均有对应来源支撑修正；没有通过修改生产行为来迎合错误预期。历史 State 测试另有真正的故障注入证据。

**建议**：在现有 `docs/agents/testing.md` 中增加一个短的 OMP seam 导航分支，分别指向历史 journal／请求观察、实现释放与本地 toggle、异步 action barrier 的既有用例或权威说明。保留语义的单一来源，不复制资源正文和实现细节。对“修改预期”的记录，采用三个字段即可：原假设、独立来源、仍要捕获的违约行为。

**完成标准**：新增测试能明确说明失败属于行为违约、驱动／fixture 错误还是环境缺失；修正观察方式后，仍能解释并验证原验收承诺，而不是仅展示绿色结果。

## 4. 中：共享文件 ownership 使用已有账本，并通过一次明确确认收敛

**事实**：01 的交接已明确 03 持有公共 native facade／index 等职责。随后 03 与 05 仍多次交叉发送 ownership 和目录提议，出现双方分别说自己或对方持有 types／port／index，以及嵌套与非嵌套路径的往返。最终依靠多次 `FINAL` 和 ACK 才收敛。

**判断**：这不是缺少更多沟通，而是缺少对已有权威分配的稳定引用。重新创建第二份人工 ownership 表也会增加漂移风险。

**建议**：复用现有职责账本。共享改动开始前，由已指定的 owner 发出一次完整变更提案：目标路径、导出、调用方改写责任和前置提交；另一方只确认或列出差异。ownership 变更应明确指向被替代的决定，由协调者确认，不用“以我最新一条为准”竞争消息时序。

**完成标准**：每个共享文件只有一个当前编辑 owner；接收者可以从一条确认后的记录判断自己该改哪些调用方，不必重建整段 IRC 时间线。

## 5. 中：把 AST 修改包装成有身份的事务，并压缩默认返回

**事实**：一次 Eval 循环为多个文件生成了 16 份 AST proposal，并打印了包含重复 diff、参数和结果细节的大段返回。随后 resolve 需要逐份处理；连续相同的合法 resolve 调用还触发了工具循环保护。另一次文本抽取因 CRLF 与字符串匹配不符得到空片段，直到后续 edit 返回 `old_string must not be empty` 才显露。

**建议**：优先改善工具和操作入口，而不是增加编码标准：

- proposal 返回明确 ID、文件数、替换数和简短摘要；详细 diff 按需展开；
- apply／reject 明确绑定 proposal ID，或提供原子批处理，避免隐式 pending 队列与循环保护冲突；
- 声明迁移优先使用语法结构；需要文本抽取时，先检查匹配数量和非空条件，再进行文件删除或覆盖。

**完成标准**：多文件变更无需模型逐个猜测当前 pending proposal；正常批量确认不触发重复调用保护；抽取不到目标时，在修改文件前清晰失败。

## 6. 中：让证据导出直接保存原始流，并区分“错误说明”与“读取成功”

**事实**：保存静态检查输出时，无界 raw read 返回了一段 404 字节的“读取被阻止”说明；调用方仍把它写进了预期的 JSON 报告文件。后续读取发现问题，改用有界 raw read 才保存到实际报告。提交时，`.gitignore` 的 `*.log` 又使证据目录中的日志未随首次 add 入库，之后通过显式强制添加补交。

**建议**：由宿主提供直接导出／复制 artifact 的入口，或让运行器在执行时就把 stdout、stderr 和退出码写入已约定的证据位置。读取受阻应返回可判定的失败状态，而不只是普通文本。证据保存结果同时列出“已生成”和“已纳入交接”的文件，保留路径应遵循仓库规则，避免每次依靠临时 `git add -f`。

**完成标准**：被阻止或截断的读取不能被当作完整报告保存；无需让模型搬运整份静态报告；最终交接包含预期日志，并能追溯到命令、退出状态及运行源状态。

## 7. 较低：接线已有轻量检查，不为机械问题再增加文字规则

**事实**：`package.json` 已有 `typecheck`，并串联 `check:authoring`。本轮它实际捕获了 readonly-array 断言类型问题和当前 TS 配置不支持的 `findLastIndex`，最终检查通过。因此这里不是缺少新的类型检查器。只读查找未发现仓库可见的常规 CI workflow 或 Git hook 配置；全局 hooks、外部 CI 及其他托管门禁没有核实。独立集成阶段本身也已存在，不能据此宣称完全没有 guardrail。

**建议**：先确认现有集成流程是否稳定调用这些命令；若没有仓库级轻量门禁，优先接入已有 `typecheck`／authoring，而不是增加“记得检查 API 可用性”等全局指令。重型真实宿主套件继续走统一窗口，不放进每次提交的快速检查。

**完成标准**：不兼容当前 TS 配置的机械错误由现有命令确定性阻止；无需 reviewer 再承担同一项语法判断。是否新增门禁，应以外部 CI／hooks 的实际调查结果为前提。

## 8. 较低：为不可用搜索服务和非当前 worktree 索引提供明确降级路径

**事实**：首次 `find` 的 26 个 judge 请求全部因区域限制返回 451，工具明确表示这不构成“没有实现”的证据。随后 agent 使用其他查询继续定位。MCP 项目列表中没有当前 worktree 的条目，导航使用了主 checkout 的索引；早期还曾在 `framework/adapters/omp` 范围查询，而实际 adapter 位于仓库根的 `adapters/omp`。

**建议**：工具入口暴露当前 worktree 与索引项目的对应关系、覆盖和新鲜度；找不到当前索引时明确提示其用途仅为导航。对确定的服务不可用返回采用健康状态和快速降级，避免继续扇出相同失败请求。仓库入口导航复用现有文档，不再维护一份始终加载的目录清单。

**完成标准**：一次调用即可辨认查询的是哪个 checkout；451 能直接引导可用的文件／字面量查询；索引缺口不会被解释为代码不存在。本轮未观察到因此改错代码，也未验证服务在其他运行中是否持续不可用。

## 建议的取舍

优先处理**验收窗口、真实测试环境前提和工具事务／证据导出**，它们比继续增加代理禁令更直接地改善可重复性。TDD 文档已有 design-before-red、独立预期和故障敏感性要求，本轮更需要的是让相关原生契约容易到达，而不是重复这些原则。

本次没有 reviewer 执行的直接证据，也没有足以证明某条全局指令是 no-op 的对照运行，因此不建议据此新增 `CODING_STANDARDS.md` 规则，或泛化删改全局代理指令。以上均为改进候选，未在本轮实施。
