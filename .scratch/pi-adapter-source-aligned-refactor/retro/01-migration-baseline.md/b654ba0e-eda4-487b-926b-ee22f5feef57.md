# 本票执行复盘建议

## 范围与结论

本复盘只依据指定 ticket 子 session 的实施历史：从读取 `01-migration-baseline.md` 到提交 `68030a9` 并交接，时间为日志中的 16:00–16:36 UTC。未读取父 session，也不把复盘阶段收到的其他代理消息作为实施轮证据。本轮只提出建议，未修改实现、配置或指令，未重跑验收。

这是**基线与分析票**，不是行为修复票。没有新增生产行为，因此不应为了展示 TDD 而人为制造 red。本次值得保留的做法是：实际运行已有覆盖、保存重构前有效 State、使用独立字面预期、区分受控响应与真实接通，并明确保留失败。改进重点在环境预检、证据交付和可复用执行设施。

## 1. 高：把“证据可交付”做成确定性门禁

**事实**：16:34 的首次提交只包含 22 个文件，并出现 JSONL 等文件将被转换为 CRLF 的警告。随后读取 `.gitignore` 才发现全仓忽略 `*.log`。代理补充证据目录局部 `.gitignore`、`.gitattributes`，重新暂存并 amend，最终提交包含 43 个文件。

**风险推断**：首次提交时，本地存在、文档已引用的原始日志并未随提交交付；冻结样例的工作区哈希也不能单凭本地校验保证后续 checkout 的字节一致。此次及时补救了，但同类问题不适合依靠代理阅读提交摘要后发现。

**建议**：在现有检查体系中增加轻量的“证据交付检查”，由 pre-commit 或 CI 执行：

- 从运行清单及 artifact manifest 检查所有引用文件均已进入待交付版本。
- 对需要保留原始字节的样例检查 Git 属性，并对暂存内容验证哈希。
- 检查运行记录指向的日志存在，允许失败日志正常交付。

这属于机械检查，不应转化为一条新的 reviewer 风格规则。检查应面向分析产物，不另建运行时能力清单。

**完成标准**：日志被忽略、冻结字节被转换或引用未暂存时，提交前出现具体文件诊断。

## 2. 高：真实宿主运行前先生成只读环境预检结果

**事实**：代理在 16:01 已读到 `harness-support.md`，其中包含 Windows 上 Node 24 的已知 libuv 问题及 Node 22 的已验证路径；16:09 仍使用默认 Node 24 执行 Pi smoke，34 项检查后遇到 `UV_HANDLE_CLOSING`、子进程 exit 9。随后定位已有 Node 22，换环境运行才通过。另一个 close-out 脚本因固定期望 1.2.0、实际安装 1.4.0 而整命令失败。

本票还发现：smoke 显式加载仓库的 `pi-subagents@0.78.0`，原共享配置却把 registration loader 指向用户安装的 0.80.0。最终报告正确限制了接通声明，但这一差异是在基线运行展开后才识别。

**建议**：扩展既有版本验证设施，提供只读 preflight，集中输出：

- 实际 CLI、Node/Bun 路径和版本，以及已知适用限制。
- 当前脚本的版本断言及其是否接受显式 candidate expectation。
- provider extension 实际加载位置与 adapter 配置解析位置，各自的版本和 realpath。
- 所需 baseline/patch artifact 是否已存在；缺失时说明哪些场景可继续。

预检只报告事实和不一致，不修改正式配置、不静默切换 provider、不补装可选补丁。常驻指令只需要一个触发明确的指针，例如“真实宿主验证前，执行只读环境预检”；细节留在现有 runbook。

**完成标准**：昂贵运行开始前即可确定正在验证哪一个组合；不适用组合被明确选择为候选观察，或换用已验证环境，而不是隐式采用 PATH 默认值。

## 3. 中高：让测试设施显式区分“复用”与“物化”

**事实**：consumer 分区中的 `ensureIsolatedHarness` 在新 worktree 内首次物化了 OMP 18.5.0。代理是在运行后检查 `.cache` 时确认这一副作用。之后为避免安装补丁，又读取 materialization guard，并将本地 cache prefix junction 到已有 frozen artifacts，完成 dock 基线。

**边界说明**：历史证明发生了未打补丁基线的物化，没有证据表明修改了正式宿主或执行了补丁安装。本复盘不把二者混为一谈。

**建议**：给现有 dock 增加明确的“仅复用已有 artifact”运行模式；需要物化时由单独的准备阶段执行。测试选择阶段同时报告可能的安装、写入与外部进程副作用。借用已有 cache 的路径和校验方式由设施统一处理，避免每张票重新研究 guard 并手工建 junction。

**完成标准**：只复用模式下，缺失 artifact 得到清晰的环境缺口报告，不会因调用普通测试命令隐式安装；已有 artifact 仍经过原 frozen-byte 校验。

## 4. 中：复用可执行的基线记录器，减少多层命令字符串

**事实**：本票自行在 Eval 中组合进程、日志和运行清单。历史 State 采集第一次因 Windows 将 `bun` 解析为 `.cmd` 而拒绝特殊字符参数；改用 `bun.exe` 后成功。后续证据校验又因嵌套字符串中的正则转义丢失产生语法错误，修正命令后才真正开始断言并通过。

**建议**：把通用的进程记录能力放入现有 `scripts/support/` 或 dock 支持层：明确解析真实可执行文件、保留 argv 数组、统一记录开始/结束时间、退出状态与日志。复杂采集逻辑复用现有公开 driver，而不是把长脚本反复嵌入 `--eval` 字符串。临时采集逻辑与长期公共设施的边界仍需维护者判断，不必为一次性场景创建通用框架。

**完成标准**：Windows shim 解析和参数传递有确定性覆盖；执行器语法/启动失败与被测行为失败分别记录。基线命令可以直接复现，而非先修复命令转义。

## 5. 中：补齐现有检查的接线，并收紧“检查通过”的含义

**事实**：仓库已有 `typecheck`、`check:authoring`、`check:integrations` 和分层测试命令。本次实际执行了这些检查。复盘读取常见的 `.github/workflows/`、`.githooks/`、`.husky/`、lefthook、pre-commit 配置位置，未找到文件。

**未验证项**：没有检查用户级 Git hooks 或外部 CI 服务，不能据此断言整个开发环境绝无门禁；能确认的是，在本次可见的仓库常见位置没有发现这些接线。

**建议**：先确认是否存在仓库外门禁；若没有，优先把现有轻量检查及上面的证据交付检查接入提交/CI，而不是另写一套编码规则。昂贵 real-host suites 继续按既有测试分层和 quiet-window 策略运行，不全部塞进每次提交。

本票的自制证据校验验证了链接、哈希、两端 State 字面结果，以及职责 owner、配置用例的数量。它没有证明职责分析语义完整，也没有证明每条配置样例都经过了对应公开 assembly。代理已经在账本中列出部分覆盖缺口，这一点应保留。

**完成标准**：机械检查报告准确描述所验证的关系；“18 行职责、10 条配置存在”不被包装成语义穷尽证明。实际来源归属、共享职责切分和 seam 是否覆盖承诺，交给独立 reviewer 做判断性审查。

## 6. 较低：改善工具发现与长文档的按需读取

**事实**：首次 `find` 的 25 个 judge 请求全部因区域 451 失败；代理正确转用其他搜索，没有将失败解释为不存在。图查询又经历了外部项目选择和一次空结果。部分目录枚举展开了与目标无关的缓存内容；多份长文档先以较大范围加载，再回到具体段落。

**建议**：

- 工具层识别确定性的区域不可用状态，直接返回可执行的替代路线，减少同一次搜索内继续派发同类失败请求。
- worktree 初始化时提供准确的代码图项目、root 和覆盖状态；引用其他 checkout 的图时明确其仅作导航，当前 worktree 源码仍是依据。
- 保留现有文档单一事实来源，在 harness runbook 前部提供“Pi/OMP、候选版本、可选补丁、provider 接通”的分支导航；按当前分支读取，不复制版本表到全局指令。

**完成标准**：代理能从当前运行目标直接到达所需段落和代码范围。这里更需要改善指针和工具返回，而不是扩充本已简短的仓库 `AGENTS.md`。
