# 10: 双角色身份、配置与隔离验收

**What to build:** 对完整双角色实现执行跨角色验证并修正缺陷，证明实际独立自动装配、原生身份归属、稳定配置、会话隔离与依赖方向。基础机制随角色票实现，本票不是推迟基础实现的借口。通过 S1 与 P5 获批非运行架构审查交付。

**Delivers:** P1、P2、P3、P5、P6、P7、P8

**Blocked by:** 08：不确定动作与错误结果保真

**Status:** ready-for-agent

依据：[获批契约](../contract.md)及其继承的 spec。仅交付 toolkit，不修改后端、不新增自主重试或第二套状态机。

## Acceptance criteria

- [ ] 分别在实际 omp 加载 manager-chat 与 node-chat，观察独立 ID、自动启用、manager 的 run／collect 与 node 的 report 工具集合及调用，不用声明或模拟注册代替。
- [ ] 不加载 connect-bot 时，两个角色有效关联的请求仍被后端接受，且不创建额外上报连接。
- [ ] 两个隔离 Session 用不同原生身份并发请求；取消一个不取消另一个，后续各自独立请求仍可用。
- [ ] 联合观察实际工具参数与请求，故意让 sessionId 不同于 Owner key、名称和 cwd；覆盖正常、无关联、歧义与跨角色调用，保留后端结果。
- [ ] 缺失原生身份时不以名称或目录替代；工具不新增模型填写的 Run、execution、接收者或身份归属字段。
- [ ] 两个不同临时 cwd 放置误导性配置，两个角色仍使用明确装配的 endpoint 与预算，不按独立 ID 错误推导默认目录。
- [ ] 对缺失、不可解析、无效业务配置分别观察可识别失败与无回退请求，不把未启用或空结果当成功。
- [ ] 执行依赖与架构审查：角色依赖 common，common 不依赖角色，framework 不认识 Run 协议；发现入口薄，不复制 connect-bot 私有客户端，不制造空层。运行成功不能代替本项。
- [ ] 修正发现的问题，执行所属分区、受影响消费者、真实宿主 dock 与 TypeScript typecheck，记录准确环境及验证范围。
