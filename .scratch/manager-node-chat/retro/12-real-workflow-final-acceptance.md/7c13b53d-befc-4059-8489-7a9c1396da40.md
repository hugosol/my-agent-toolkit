本复盘仅依据指定 ticket 执行会话，从读取票据到提交 `dd3dcd0`、返回阻塞结果为止。父代理及其他代理的消息只作为**本会话收到的信息**引用，不据此评价它们的完整执行过程；后续重试也不在本次分析范围内。

本票主要是最终验收与证据汇总，不是新增业务实现。没有新增重复测试或人为制造 red，本身符合票据与 TDD 对“既有行为已满足”的处理要求。真正未闭合的是两项不同问题：**真实 P28 环境不可执行，以及本轮 canonical 全仓检查失败**。Agent 最终没有把它们包装成完成，也没有提前提交 H1，这一点应保留。

## 1. 高：把真实验收的环境前提纳入派发输入，而不是由最终执行者重新发现

**事实。** 票据依赖列出了 02、10、11，但本轮仍需检查 Herdr CLI、环境变量及后端配置才能发现：当前 agent 不在 Herdr 管理的 pane 内，没有已提供的隔离路由上下文。`herdr --skill` 明确要求相应上下文；Main 随后确认没有已授权隔离环境。P28 因而在真实 Chat 启动前停止。可执行文件存在、受控 dock 已通过，都不能解除这一阻塞。

**建议。** 在真实协作票据的派发输入中附带一份最小的**环境前提凭据**：

- 已授权隔离上下文的引用及作用范围；
- 后端实际如何路由到该上下文；
- 独占数据根和资源清理归属；
- 真实模型访问的可用性结论，凭据内容留在环境中；
- 已核实的单节点前置证据，或明确的未满足项。

尽量复用已有 OPERATIONS 的准备章节，由派发器传引用与结果，不另造一套部署文档。导航指针应直接以分支触发，例如：“**真实协作验收：启动前读取隔离环境前提；前提不满足时完成离线检查并报告阻塞。**”

**完成判据。** Agent 在尝试启动服务或 Chat 前，能够一次确定“可执行”或“缺少哪项前提”；任务调度能够区分环境阻塞与值得重新执行的实现失败。

**边界。** 这不是要求 Agent 猜测可用 endpoint、接管默认会话或要求用户执行技术验收。隔离授权和可用访问由环境提供，后续配置、运行、取证与清理由 Agent 完成。

## 2. 高：把已经写明的持久化观察约束变成可执行防线

**事实。** 本轮已读取 `docs/agents/testing.md`；其中已有明确要求：观察真实文件发布及锁清理，不以固定事件循环轮数代表磁盘完成。实际 canonical 结果仍为 `1746 pass / 9 fail / 3 errors`。随后读取的 `pi-period-reset.test.ts` 中，`savedDocument` 仍以最多 1000 次 `harnessTask` 结束等待；三个相关失败发生在约 194–239ms，而不是完整五秒观察窗口。另三个 runtime-gap 用例达到五秒 deadline，并出现 publication 取消相关的未处理错误。

**建议。** 优先增加确定性防线，而不是再给 AGENTS.md 增加同义规则：

1. 对持久化验收 helper 做一次针对性审查，识别“有限 nextTask/setImmediate 次数代替发布观察”的具体模式；若模式足够固定，用仓库现有 authoring/check 链接入定向检查。
2. 对实际发布观察机制增加受控延迟场景：文件系统发布晚于若干事件循环轮次时，观察仍有效；发布完成且锁释放时结束；deadline 或 teardown 时资源被释放，相关拒绝被所属调用接收。
3. 保留原断言及 deadline。用真实发布条件替换不可靠同步，而不是放宽门槛。

**完成判据。** 受控的延迟发布能够区分“正确等待”与“提前耗尽轮数”，teardown 场景无悬空观察或未处理拒绝；再按既有入口做最终回归。

**推断与未验证项。** 有限轮次等待是本轮直接观察到的脆弱点，但不能据此认定它解释全部九个失败。loader 和两个 dock teardown timeout 的根因未被本次执行证明，也不能统一归因于机器负载。

## 3. 中高：让验收证据的解析与归属具有固定契约

**事实。** 本轮自行编写了日志解析和证据清单逻辑。第一版按“最近出现的文件标题”归属结果，没有在最终失败汇总处停止，输出曾把九条汇总失败附加到最后一个 `consumer-regression.test.ts` 分组。随后 Agent 为 `failures.json` 修正了边界。选定的 40 文件、147 pass / 0 fail 子集没有包含那个被误归属的 consumer 分组，因此没有证据表明最终这项子集数字已被污染；但临时解析器确实暴露了误归属风险。

**建议。** 将最小的证据采集/解析能力收敛到已有测试支持或报告链，而不是每张票临时重写：

- 先核实当前 Bun 的机器可读报告能力；可用时直接消费稳定格式。
- 若仍需解析文本，为重复失败摘要、hook 失败、无名测试、测试间错误和多文件输出建立固定样例。
- 报告同时保留完整退出状态、文件/用例归属、受测来源与环境，以及选定 coverage 的范围。
- 无法可靠归属的记录明确保留为未归属，不猜测它属于最后一个文件。

**完成判据。** 同一份失败摘要不会被计数两次；canonical 的非零退出不会被局部通过覆盖；每个汇总数字能追溯到原始记录。

这项建议应落在确定性检查与工具支持中，不应变成要求 reviewer 手工核算每份日志的新标准。

## 4. 中：终端提交协议由工具 schema 强制执行

**事实。** 实现轮要求每个 workpool 提交带数字 `key`。本次末尾实际调用的是只有 `error` 的 `yield`，缺少 `key: 1`；工具仍接受并返回 `Task aborted`。这是一个可机械检查的协议偏差。

**建议。** 由工具 schema 或宿主调用校验强制要求 `key`，并拒绝缺失或错误类型；错误消息返回允许的完整调用形状。若工作流需要区别“已有提交、部分检查完成但外部前提阻塞”与执行异常，应在既有结果模型中明确表达这一区别，而不是让代理自行创造字段或靠长段文字传递。

**完成判据。** 缺失 key 的提交在进入工作流状态变更前被拒绝；合法阻塞交接能够保留提交、已验证范围与缺失前提。

**边界。** 本次确有 P28 阻塞和全仓失败，不能因此建议改报成功。也不能从 `Task aborted` 单独推断宿主对本票产品状态作了什么最终判断；该宿主内部行为不在已读取证据中。

## 5. 中：在真正运行 smoke 的子进程环境中做依赖预检

**事实。** 仓库已有 `smoke:http-transport`，不是缺少检查入口。第一次从 Python subprocess 启动时，`Bun.spawnSync` 找不到 `openssl`，退出 1，行为断言尚未执行。随后 shell 的 `where.exe` 能找到已安装 OpenSSL；只给实际子进程 PATH 加入对应目录后，原 smoke 得到 29 passed / 0 failed。

**建议。** 在既有 smoke 入口或统一执行器中，用与实际运行相同的 launcher、cwd、env 检查外部依赖，并给出明确的前置错误。解析到的二进制位置、版本及必要的进程级环境调整随证据保存；不依赖交互 shell 与 Python/Bun 进程恰好拥有相同 PATH，也不把本机绝对安装路径写成通用配置。

**完成判据。** 缺失依赖在启动行为场景前被识别，报告清楚地区分“前置未满足”和“行为断言失败”。

本轮已经正确区分这两种失败，环境改进的目标是让这种区分由入口稳定提供，而不是让每个 Agent 临时诊断。
