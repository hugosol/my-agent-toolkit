## 1. 高：让长期回归测试脱离临时票据材料

**事实**：framework 分区运行约 75 秒后，唯一失败来自 `pi-native-consumers.test.ts` 的历史重启用例。它通过 `historicalBranch()` 读取 `.scratch/pi-adapter-source-aligned-refactor/implementation/01-baseline-artifacts/pi-state-before.jsonl`，在本 worktree 中得到 `ENOENT`。该错误和路径均保存在本票验收日志中。

**判断**：这是测试输入的可再现性缺口，不是本票 collect 行为失败。长期测试依赖临时实施目录，会把环境准备问题推迟到回归阶段，也使“干净 worktree 能否运行测试”依赖隐含材料。

**建议**：将仍被长期测试消费的固定样例迁入受版本控制的测试 fixture 目录，由测试直接引用。若材料必须生成，则提供唯一、明确的生成入口，并在运行前报告缺失输入；不要用空样例或跳过用例代替。

**完成标准**：全新 checkout/worktree 在按公开入口准备依赖后，可取得这些样例并运行原历史行为断言，无需复制其他票据的 `.scratch` 目录。此建议应进入测试资产与准备流程，而非新增一条要求代理记住路径的全局指令。

## 3. 中：让 S1 dock 直接呈现 red 的层级与原始原因

**事实**：安装依赖后，第二次 tracer 的实际输出是 `JSON Parse error: Unexpected identifier "Tool"`；注册 collect 后，同一 tracer 通过。记录将该失败解释为宿主缺少 collect 工具。这个解释与随后的接入改动及 green 一致，但失败输出本身没有直接展示清晰的“目标工具未执行”诊断。

**判断**：缺失接口可以成为有效的初始 red；问题不在于它不是业务断言失败，而在于当前 helper 把宿主工具错误进一步压成 JSON 解析错误，增加了区分接口缺失、执行失败和非法响应的成本。前一次依赖缺失则只能算 setup failure，不能算行为 red。

**建议**：在既有 S1 dock helper 中，先从真实会话的公开工具执行结果识别目标工具及执行状态，再解析正文；失败时保留工具名称、宿主原文与解析上下文。沿用当前真实工具 seam，不替换为模拟注册或私有业务 helper 测试。TDD 证据按 setup、interface、behavior 三类记录即可，无需再添加一份重复的流程文档。

**完成标准**：缺少 collect 时直接指出目标工具未执行或宿主拒绝；非法后端 JSON 仍能被区分为解析失败；原有业务断言继续通过真实工具结果观察。
