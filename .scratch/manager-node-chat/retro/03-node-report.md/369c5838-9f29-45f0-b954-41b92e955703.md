# 本票 TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 子会话的 JSONL、其中的工具结果，以及只读核对的仓库检查入口；未采用父会话或其他执行者的实现结果。本轮没有修改文件、执行建议或重跑验收。

本次有有效的 tracer：首个实际宿主测试在实现前因报告 HTTP 请求数为 0 而失败，随后验证了实际请求、原生身份和返回结果。保存、通知、诊断三个分支在实现已满足条件后逐个补测并通过；TDD 指引允许验证已满足的行为，无须为每个分支制造失败。最终记录包含所属分区 5 项通过、真实后端 dock 1 项通过、启动策略消费者 20 项通过及最终 typecheck 成功。主要改善空间是：宿主边界的验收解释、静态检查的运行位置、外部测试产物的可复现性，以及探索工具的失败与披露方式。

以下建议按风险优先级排列。“事实”指本会话可直接观察的记录；“推断”不作为已发生的产品缺陷。

## 1. 高：把宿主 schema 差异变成明确的验收分支

**事实**：首个 report 测试先因默认 discoverable 工具未出现在首个模型请求中而失败，装配随后增加 `loadMode: "essential"`。下一次失败显示实际 schema 多出 OMP 的 `i` 字段；执行者查阅宿主实现并向 Main 说明后，将断言改为过滤 `i` 再核对业务字段。

**风险推断**：本次有宿主源码依据，不能据此认定验收被削弱；但如果以后每个 ticket 都现场修改字段过滤规则，“只接收正文”容易在 authored schema、模型 wire schema、执行参数之间产生不同解释。

**建议**：在现有 dock 的 schema 观察辅助代码中集中这项区别：先保留原始 wire schema，再识别已知宿主元数据，最后对业务字段做严格断言。对 `i` 的识别应核对宿主来源和预期形状，而非永久按名字忽略。首次发现新的宿主字段时，先完成验收解释，再调整预期；无法归入既有约定的差异交由契约持有者决定。

**完成判据**：未知字段或角色自加身份字段仍使测试失败；已确认的宿主追踪元数据有明确来源，且原始观察证据不被规范化过程丢弃。这是边界语义判断，适合由审查者核对，而不是增加一条泛化的编码禁令。

## 2. 高：把已有 typecheck 放在昂贵宿主验收之前，并确认自动护栏已接线

**事实**：`package.json` 已提供 `bun run typecheck`，同时运行 TypeScript 与 authoring 检查。最后一组命令先运行角色分区、真实后端 dock 和启动消费者，随后才发现新增辅助代码的 `String.replaceAll` 不被项目当前 lib 支持；整组耗时 84.90 秒。改为兼容写法后，相关 dock 与 typecheck 均通过。

**事实边界**：本轮只读查找没有发现仓库内的 `.github` 工作流、`.husky` 或 pre-commit 配置；尚未核查外部 CI、全局 hooks 或其他托管护栏，因此不能断言所有自动护栏都不存在。

**建议**：复用现有 typecheck，不为 `replaceAll` 再写风格规则。新增或修改 TypeScript 测试辅助代码后，先运行静态检查，再启动真实宿主验收。维护者同时确认现有命令是否已由 CI 或提交护栏自动执行；若未接线，优先在现有 CI 入口接入该命令。

**完成判据**：类似的 lib/API 不兼容在启动昂贵宿主批次前暴露；提交或集成路径有可追溯的自动检查结果。已有 `docs/agents/testing.md` 已要求 TypeScript 变化运行 typecheck，宜改进执行顺序和接线，而非继续扩写 AGENTS.md。

## 3. 中：让真实后端测试产物具备新鲜度和独占性

**事实**：真实后端 dock 首次启动失败，已有 `safe_shutdown_shell` 二进制拒绝当前源码所定义的 `collect_wait_seconds`。执行者随后构建 `safe_shutdown_shell` 和 `herdr-fixture`，约 19 秒后构建成功，再运行 dock 通过。测试驱动当时仅检查二进制是否存在。

**风险推断**：文件存在不足以证明它与当前协议一致；重建同级 checkout 的共享 target 产物，也可能影响其他执行者对测试环境版本的归属判断。本会话没有证据证明实际发生了并发覆盖。

**建议**：把后端测试产物准备纳入现有 dock 的环境准备分支，记录源码版本或内容指纹、构建命令和实际二进制路径。需要重建时使用独占构建目录，或在受协调的准备阶段生成可复用、固定身份的测试产物；在测试消费期间保持产物不变。可借鉴仓库已有 `ensureIsolatedHarness` 的产物定位方式，无须新建业务测试平台。

**完成判据**：陈旧产物在角色行为测试前被识别；失败能区分“环境准备不满足”与“report 行为不满足”；同一运行的二进制来源可复查。

## 4. 中：为“新增 OMP 原生工具”提供条件式导航指针

**事实**：探索过程先阅读了 connect-bot 的声明与装配，但该扩展没有所需的原生工具注册示例；随后又定位宿主的 `registerTool`、注入的 TypeBox builder、工具发现策略和 intent 处理。过程中还尝试读取不存在的 `entrypoints/startup/modes.ts`。

**建议**：在现有装配或宿主开发参考中加入一个条件清晰的指针，例如：“新增 OMP 原生工具时，查阅所测宿主版本的 `ToolDefinition`/`registerTool`，并核对 schema builder、工具发现及宿主参数处理。”指向现有宿主源码定位或参考章节，不缓存整份 API，也不把这些细节放进每轮必读的 AGENTS.md。

**完成判据**：新增原生工具可以直接到达真实接口来源；仅修改 Prompt 或配置的执行者不需要加载这组材料。具体成员名和默认值仍以所测宿主版本为权威。

## 5. 中低：让语义搜索遇到确定性授权错误时快速降级

**事实**：首次 `find` 为一个问题发起了 28 次判断请求，全部返回相同的 HTTP 451 地区不可用错误，最终没有任何候选被判断。后续执行者改用 grep、目录定位及图工具继续探索，没有把失败误当作不存在。

**建议**：工具层将这类确定性、提供方级错误视为本轮不可用信号，停止同批后续判断请求，并返回可操作的结构化降级信息。后续行为查询可直接进入可用的本地搜索路径；不需要每个执行者自行推断服务是否恢复。

**完成判据**：一次确定性授权失败不会扩成整批相同失败；结果明确区分“无法搜索”与“没有匹配”。无需新增仓库代理指令来重复工具本应表达的状态。

## 6. 低：把机械风格反馈改为短诊断，把例外判断留给审查

**事实**：本会话收到多次完整风格说明注入，涉及具体 `ReturnType`、inline cast、真实计时器和 tiny function。部分提示促成了局部修正；但真实计时器用于观察外部 OMP 子进程的有界重试窗口，代码随后补充了例外理由；TOML 路径辅助函数也存在多个调用点，不能仅凭一行函数体认定违规。

**建议**：机械模式继续由确定性检测负责，优先只输出位置、命中模式和规则指针；完整解释仅在需要判断例外时披露。把真实外部进程计时等例外的合理性交给审查者，不将其变成实现阶段反复加载的长文。不要为这些机械模式再增加一组 CODING_STANDARDS.md 文字禁令。

**完成判据**：同一规则不会在实现上下文中反复展开整段说明；允许的例外仍可被记录和审查，真正的机械违规仍有定位式诊断。
