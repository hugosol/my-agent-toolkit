**建议**

优先复用 `bun run typecheck`，在项目采用的 CI 或提交护栏中自动执行；昂贵的真实宿主验收继续使用既有独占窗口。这样可在 dock 验收前发现编译目标不兼容，避免再写“不要使用某个新 API”的文字规则或重复实现检查器。

**完成标准**

## 2. 中等：让 dock 证据绑定一次工具调用，避免从可变会话历史中事后取值

**事实**

- 首轮真实效果 dock 为 **2 pass / 1 fail**。失败发生在取消后的第二次显式 report：`JSON.parse(toolText(node))` 无法解析结果。原辅助函数把历史中所有 tool 消息拼接起来，单次报告场景没有暴露这个假设。
- 执行者随后改为提取最新结果，并扩展同一 Session 的显式报告能力；最终分区与受影响消费者均通过。
- 同轮还修正了证据记录时机：原先在后续 status 调用后再次读取 `lastToolResult()`，却将其标作 cancellation；后来在取消时保存结果，再执行查询。
- 初期输出中的 `historyError` 曾显示为 `{}`，后续改为直接断言字符串并输出了实际路径诊断。

**推断**

这些现象共享一个风险：测试断言和证据输出在不同时间读取会话级“最新结果”，容易把多次调用混在一起。`historyError` 变成 `{}` 的具体机制没有在本票中被独立复现，不能据此认定为 Bun matcher 缺陷。

**建议**

后续演进 dock 设施时，优先提供调用级观察结果：一次显式调用对应一次结果、调用标识和原始文本，证据在下一次调用及断言处理前固定下来。断言使用解析值，日志保留原始值；继续从真实角色工具边界观察，不另开私有业务测试入口。

保留本票“取消 → 同 Session 显式新报告”的回归场景即可，不需要再添加一个重复验证辅助函数内部实现的测试。

**完成标准**

连续两次工具调用以及取消后的新调用，都能独立取得对应结果；输出的 cancellation 始终来自被取消的那次调用，诊断字段保留实际后端值。
