# Ticket 10：TDD 执行复盘建议

## 范围与结论

本复盘只依据指定 ticket 执行 session 的对话、工具调用及返回结果；没有读取父 session 或其他票据执行历史，也没有重跑验收。另只读核对了仓库现有检查入口及常见 guardrail 文件位置，未修改任何文件。

**已观察到的结果：**实现轮提交 `3a26238`，新增跨角色验收及证据记录。最终所属分区为 15 pass，真实宿主与消费者 dock 为 43 pass，公共 HTTP/connect-bot 分区为 203 pass，TypeScript 与 authoring 检查通过。没有运行全仓回归；独立集成是否完成不在本次历史的证明范围内。

本票主要验证已经存在的生产行为。TDD 指引允许这种情况下直接验证既有实现，**不应为凑齐 red→green 而故意破坏产品**。值得改进的是：早期多次失败来自环境、预期形状和场景准备，而不是测试捕获了指定行为缺陷。

## 1. 高：让 fixture 先证明“场景已到位”，再判断目标行为

**事实**

同一个真实宿主身份用例连续暴露了三类假设错误：

- 预期后端拒绝正文是 `{error:{code:…}}`，实际是顶层 `{code,message}`。
- 预期成功工具结果显式包含 `isError:false`，实际成功帧省略该字段。
- 尝试通过正常 dispatch 制造身份歧义，但后端拒绝复用原生身份，目标进入 failed，未形成预期歧义。

这些失败随后分别通过读取权威返回形状、改用实际 HTTP 状态，以及在隔离后端持久化数据中明确注入歧义来修正。最终没有通过改生产代码迁就错误 fixture。

最初还有 `expect(id).not.toBe(\`main:${id}\`)` 这种由输入自行构造对照值的断言；后续改成读取公共 Session witness 的实际 Owner key，才建立了独立观察。

**建议**

把现有 TDD 的“design before red”落实为一个简短的 **fixture gate**，不再新增泛泛的“认真核对”规则：

1. 为当前场景确认必要的 wire/宿主事实，引用权威实现位置或既有独立样例，不从工具名称猜返回 envelope。
2. 场景准备动作结束后，先断言准备结果确实建立了目标条件，再进行目标断言。HTTP 200 本身不能代表 dispatch 已成功关联。
3. 身份和归属对照值从独立公共观察取得。需要损坏状态才能到达的分支，显式标注故障注入及其证明边界。

这属于 fixture 设计与证据独立性的判断，不适合再写一份重复的编码标准。复用现有 TDD 反模式规则，让验收测试审查逐项回答：“含有命名违例的实现，是否仍能通过此场景？”

**建议的完成标准：**准备条件未成立时，用例明确报 setup 未达到条件；只有条件成立后的差异才归为行为 red。既有正确行为直接 green 时，也能指出独立预期与实际观察各自来自哪里。

## 2. 高：把 worktree 预检与失败路径清理放在启动真实进程之前

**事实**

第一次宿主运行因 worktree 缺少 `node_modules/yaml`，在部署复制阶段报 ENOENT；随后才执行 `bun install --frozen-lockfile`。最初测试在建立 `try/finally` 之前就启动 backend、transport 和 dock，后续编辑才把成功取得的资源逐个纳入 cleanup。

**推断，未验证：**第一次 setup 中途失败具有遗留已启动 backend 的风险；历史没有进程退出或资源清理证据，不能断言实际发生了泄漏。

**建议**

在既有真实宿主测试支持中增加一个轻量预检入口：检查锁定依赖、所选宿主以及后端执行产物是否可用，缺失时在启动任何进程前给出具体原因。预检不自动改配置，也不重复安装已经满足的依赖。

资源获取后立即登记释放动作，并通过公开 fixture 启动入口的失败路径回归覆盖“backend 已启动、后续 dock 建立失败”。让失败清理成为测试支持的行为保证，而不是每个业务用例靠记忆补齐。

**建议的完成标准：**缺依赖时不启动 backend；后续 setup 失败时，已获取进程、连接和临时目录都有可观察的释放结果，且原始 setup 错误被保留。

## 3. 中：接通已有 typecheck 的早期 guardrail，而不是新增 API 禁令

**事实**

本次先运行了多轮真实宿主用例，较后才首次执行 `bun run typecheck`。检查一次发现 3 个文件、6 项诊断，包括 ES2020 目标库不含 `Array.at`/`findLast`，以及一个隐式 any。修正后 typecheck 通过。

仓库已有 `typecheck`，并串联 `check:authoring`；`docs/agents/testing.md` 也已要求 TypeScript 迭代后运行该检查。问题不是缺少检查命令或缺少文字规定，而是没有在早期循环形成约束。

**Guardrail 可见范围：**只读检查未发现 `.github/`、`.husky/`、`.githooks/` 等常见仓库内配置，`package.json` 也未显示 hook 安装脚本。全局 Git hooks、外部 CI 或其他托管平台配置未验证，不能据此断言完全没有自动门禁。

**建议**

优先复用现有 `bun run typecheck`：让首个 TypeScript tracer 的便宜检查先于昂贵宿主循环，并在确认没有等效外部门禁后接入 CI 或提交门禁。不要为这次问题另造禁止 `.at` 的文档规则，也不要为让测试通过而抬高既有 target。

**建议的完成标准：**测试/support 代码的目标库或类型错误能在真实 OMP 启动前被现有检查拒绝，提交路径也有可核对的失败结果。

## 4. 中：把 quiet window 从“已请求”变成可确认的运行资格

**事实**

session 中先向 Main 请求真实宿主 quiet window，随后就开始多轮 focused 宿主运行；可见的明确排队安排出现在后面的正式分区验收之前。正式验收结束后，本代理按要求直接通知 ticket 11 接手窗口。

**未验证：**没有证据表明早期运行实际与其他昂贵 suite 重叠，也没有据此可归因的测试失败。这里暴露的是协调状态不明确，而不是已经证实的负载故障。

**建议**

复用现有协调机制，让真实宿主运行具有明确的“申请→获准→释放”状态；focused 宿主用例同样归入该范围。等待获准时继续写代码或进行便宜静态工作。若此工作流频繁使用，可把资格做成 dock runner 可检查的租约，而不是继续增加 AGENTS.md 禁令。

**建议的完成标准：**日志能区分申请与获准；每次昂贵运行都有对应资格及释放记录，调用方无需把沉默推断为许可。

## 5. 低：对确定不可用的搜索服务做能力降级

**事实**

首次 `find` 调用内部发起 25 个 judge 请求，全部因地区限制返回 HTTP 451，没有得到任何判断。代理之后改用 grep、文件结构及 codebase-memory 工具继续探索，没有把失败当成代码不存在。

**建议**

在工具宿主层对“地区不可用”这类确定性错误设置 session 级能力状态：首个明确拒绝后停止同类 fan-out，并返回可用的替代检索路径。这是工具能力问题，不应让每张票据重复发现，也不需要新增项目导航文档。

**建议的完成标准：**一次确定性拒绝即可触发降级；失败结果明确说明尚未完成搜索，不生成不存在结论。

## 6. 低：沿用既有证据导出，减少从长终端输出手抄验收事实

**事实**

多次工具结果中的实际请求、报告和时序 JSON 被截断，需要转向完整 artifact；最终证据文档手工整理了命令、计数、身份和环境信息。现有 Prompt dock 已有可选证据导出机制，因此并非完全缺少留证基础。

**建议**

优先扩展既有导出路径，保存本类验收的 run-specific 结构化事实：命令与退出码、源码/执行产物标识、受控条件、请求及连接关闭观察。长期文档保留证明边界、架构判断及复核入口；单次运行明细由导出记录承载，避免再造一套日志平台或反复复制可查询配置。

**建议的完成标准：**独立集成人员能从同一运行记录复核摘要；终端截断不需要重跑 suite，也不需要从多个截断片段重建结果。

## 建议保留的实践与未验证范围

本次后续修正体现了值得保留的做法：生产实现正确时不制造无意义 red；以真实 Session witness 取代自推 Owner 值；区分真实宿主、真实后端与受控 provider/Herdr 条件；单列 P5 架构审查；按所属分区、消费者和类型检查报告实际结果，而未宣称全仓通过。

以上六项均为环境改进建议，本轮未执行。没有证据评价独立 reviewer 或集成代理的执行质量，也不据本票的受控技术验收推断真实模型完成 P28 工作或 H1 人工判断。
