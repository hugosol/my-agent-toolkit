# 04-manager-state-actions：TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 执行 JSONL，截止首次实现交付；未读取父 session 或其他票据执行历史。本轮只读取证据、提出建议，没有修改文件或重跑验收。

**已观察结果**：六个动作分别经历缺失能力的 red → 实现 → green；额外参数测试发现并推动修复了真实宿主参数修复行为。最终所属分区及对应 dock 为 **13 pass、0 fail、204 assertions**，TypeScript 与 authoring 检查通过，随后提交 `d2484ea`。以下建议针对未来执行环境，不表示这些已修复问题仍留在交付中。

## 1. 高优先级：把宿主参数修复纳入角色工具的兼容门禁

**事实**：参数测试中，带额外 `sessionId` 的 status 调用返回了正常结果；进一步观察实际 HTTP，预期 1 次请求却收到 2 次。改用 closed union 后仍失败。执行代理随后查阅实际安装的 OMP 18.5.0 validator，最终保留未知键供运行时白名单拒绝，参数测试以 95 条断言通过。证据见执行历史 L308、L372、L387、L393、L406。

**风险推断**：只检查声明是否为 closed schema，或只直接调用工具的 execute，无法发现宿主在进入 execute 前删除字段、把非法调用修复成合法动作的行为。

**建议**：复用现有真实 OMP dock，将“非法参数是否产生实际请求”作为角色工具及宿主候选版本的兼容检查。测试预期保持为业务结果，而非固定某种 schema 写法；保留既有 manager 字面样例，避免另建重复矩阵。其他工具是否受影响应另行取证，本次历史不能证明它们存在同一缺陷。

**完成标准**：添加身份或不适用字段的模型调用明确拒绝，实际 HTTP 请求数不增加；宿主升级导致这一性质变化时，现有验证入口失败。

## 2. 高优先级：无额外副作用的证据窗口，从动作前开始

**事实**：第一轮综合验证已达到 13 pass、200 assertions，但部分测试在 complete、fail、pause 执行之后才读取外部调用基线。这会漏掉动作内部已经发生的额外副作用。代理随后将基线前移到动作之前，并补充实际 HTTP 路径序列断言，最终验证增加至 204 条断言。证据见 L448、L451–L478。

**风险推断**：动作后 150ms 没有新调用，不等于“该动作及随后窗口没有附加调用”。首次 green 未充分区分这两个命题。

**建议**：在现有 TDD 测试设计参考中，把这类场景收敛为一个证据结构：**动作前基线 → 显式动作 → 有界观察 → 请求与事实差异**。这是测试语义的判断问题，适合审查代理核对，而不是新增一条匹配 `Bun.sleep` 的语法禁令。必要时，用临时注入的即时额外请求证明测试能变 red。

**完成标准**：每个“没有额外派发、终止或重试”的断言覆盖动作执行本身，且能识别发生在工具返回之前的违规调用；结论仍限定于已观察窗口。

## 3. 中优先级：把现有检查接到持续门禁，而非新增一套检查体系

**事实**：执行历史中的 `package.json` 已提供 `typecheck`、`check:authoring`、测试分区和 dock 入口；本票实际调用并通过了相关检查。复盘时，在当前 worktree 的常见仓库位置未找到 `.github/workflows`、`.githooks`、`.husky` 或所查询的 lint 配置。**这不能证明不存在仓库外 CI、全局 hook 或其他平台门禁；这些接线未验证。**

**建议**：先确认现有平台是否已运行这些命令；若尚未接线，优先使用已有 TypeScript、authoring 和所属分区命令建立确定性门禁。真实宿主及后端 dock 应沿现有测试分层安排到具备对应环境的执行节点，不把外部依赖缺失伪装成通过。

本轮出现过、且由已有提醒纠正的具体 `ReturnType<typeof managerDock>` 写法属于机械模式；若该规则需要持续执行，应落到确定性检查，而非继续扩充 reviewer 的散文规则。短暂出现的双逗号语法错误则已由现有 TypeScript 能力覆盖，无需再造检查。

**完成标准**：能指出每个现有检查由哪个门禁执行，失败会阻止交付；环境前置失败与业务断言失败分别显示。无需以本轮手工执行成功代替接线证据。

## 4. 中优先级：让 dock 失败先展示原始工具结果，再解释 JSON

**事实**：六个动作初次 red 多次显示为 `JSON Parse error: Unexpected identifier "Tool"` 或 `"Validation"`，原因是测试 helper 直接将宿主的文本拒绝交给 `JSON.parse`。后续参数诊断又先关注文本，再补上 HTTP 次数断言，才明确证实非法调用确实产生了新请求。

**建议**：增强现有 dock helper 的失败呈现：保留原始工具文本、当前字面输入及对应传输观察；预期结构化业务结果时，再执行 JSON 解析。原始拒绝仍是失败证据，不应被包装成虚构的业务 JSON 成功结果。诊断补充后，优先呈现“是否发生请求”，再解释结果文本。

**完成标准**：缺失工具、宿主参数拒绝、工具运行时拒绝和后端 JSON 拒绝可以从一次失败输出中区分；最初的 missing-interface red 与后续业务断言证据分别可见。

## 5. 中优先级：由 worktree 准备阶段明确依赖与后端位置

**事实**：首次测试因 `node_modules/yaml` 不存在而失败；执行 `bun install --frozen-lockfile` 后才进入真正的缺失工具 red。真实后端测试则显式使用 `HERDR_BOT_REPO=E:/Developer/myhub/herdr-bot`，而已有 helper 的默认位置是仓库同级 checkout。

**建议**：在现有 worktree 准备流程提供最小 preflight：依赖安装状态、实际后端 checkout、所需安全壳与 fixture 可执行文件。把可执行性判断留给环境准备，不混入每个行为测试；把外部 checkout 位置作为运行环境信息传入，避免复制机器路径到各测试。

**完成标准**：首次 TDD 测试失败能够归类为环境未就绪或业务 red；环境错误直接列出缺失依赖及已有修复命令，而不是让代理从复制文件异常追查。

## 6. 中优先级：语义搜索遇到不可用提供方时，采用会话级降级

**事实**：首次 `find` 的 28 个 judge 请求全部返回提供方 HTTP 451，未产生判断；后续另一轮 `find` 的 20 个 judge 请求又全部以同类原因失败。工具明确说明“不是不存在的证据”，代理随后通过其他读取与搜索方式继续推进。

**建议**：在搜索工具或调度层识别这类明确的提供方不可用错误，短路后续同源批量请求，并提示可用的 graph、文件名或字面搜索路线。恢复探测应有明确触发条件，避免把每个新查询都当作重新尝试整批请求的理由。该行为适合工具层实现，不值得在每个仓库的 `AGENTS.md` 中重复说明。

**完成标准**：一次明确的区域不可用错误后，同会话同源查询不再启动整批注定失败的 judge；降级结果仍区分“未判断”与“没有匹配”。
