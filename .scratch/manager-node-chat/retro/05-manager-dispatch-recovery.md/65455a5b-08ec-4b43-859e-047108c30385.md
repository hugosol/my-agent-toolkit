## 1. 较高优先级：让参数测试失败能定位到具体反例，再决定是否修正测试范围

**事实：**dispatch 参数测试最初包含缺失 `nodes`、字符串 `nodes` 和数字元素三个输入。首次实现后，循环中的拒绝断言收到受控服务的固定成功响应，但失败输出没有标明当前输入。随后执行者将样例替换为缺失字段和对象字段；再次失败后，删除了这一组断言，以“类型转换／默认值属于 OMP，本分区只验证禁止额外字段”解释范围调整。

**推断：**这些额外样例未必属于本票必须兑现的承诺，因此不能仅凭删除断言认定验收被削弱。不过，现有失败输出无法独立说明究竟哪个输入被接受、宿主如何改写它。没有这层证据，“修正不适用的测试”和“为 green 移除反例”容易混在一起。

**建议：**优先增强参数矩阵的确定性诊断，而不是再增加一条泛化的“不得削弱测试”指令：

- 每个反例带可辨识名称；失败同时显示模型原始输入、工具返回和实际捕获到的 HTTP 请求。
- 对意外接受的输入，先保留其实际 wire 形状，再依据票据／宿主契约判断它属于必须拒绝、宿主规范化，还是未规定行为。
- 若移除的是超出票据的探索性断言，在当前测试说明或交付报告中记录具体样例与依据；不要将尚未定位的原因概括为已证实的宿主机制。

**完成判据：**一次参数测试失败即可指出具体输入及是否发生请求；调整测试范围时，仍能逐项追溯原验收承诺。新增信息应留在测试诊断和现有测试说明中，不进入全局 `AGENTS.md`。

## 2. 中优先级：让真实宿主 dock 保留原始错误，避免 red 被 JSON 解析异常遮住

**事实：**dispatch、reconcile_dispatch、recover、retry 的首次 red 都表现为 `JSON Parse error: Unexpected identifier "Validation"`。本轮读取的 `managerDock.call()` 默认直接对工具文本执行 `JSON.parse()`，因此宿主的非 JSON 参数校验反馈被转换成了解析异常。

**推断：**这些 red 确实发生在新增接口尚未提供时；但测试辅助设施使“宿主拒绝”“工具返回格式错误”和“业务断言失败”呈现得过于相似，增加了定位成本。

**建议：**在现有 dock 辅助设施中保留原始工具文本；默认 JSON 解析失败时，报告本次输入、原始文本和对应工具结果。业务拒绝断言继续通过真实工具与后端观察，不把辅助设施变成新的私有业务 seam。

TDD 说明只需在现有 red 规则旁明确一个完成界限：**缺失接口的 red 可以作为起点；green 后应能说明哪个观察排除了所命名的业务违规。** 若现有断言不能判明，再做定点故障注入，而非要求每个测试都机械增加一次 mutation。

**完成判据：**缺失 action 时直接看到原生 validation 反馈；响应不符合预期时看到原始结果，而不是只有解析堆栈。仓库已有 typecheck／authoring 命令且本轮执行成功，这项建议是补足运行诊断，不是另建重复的 lint 或检查入口。

## 3. 中优先级：为不可用的语义搜索增加会话级降级，按目录发现图索引身份

**事实：**本轮两次 `find` 分别发起 11 和 25 个 judge 请求，全部因地区限制返回 HTTP 451，最终仍需使用其他检索方式。另一次图搜索使用推测的后端 project 名称，返回“project not found or not indexed”；之后改用工具返回的可用 project 才获得结果。执行者已通过 `report_issue` 报告 `find` 故障。

**建议：**把这类机械失败交给工具层处理：

- 对明确的地区限制启用会话级熔断，后续语义搜索直接提示可用降级路径；重新探测由明确动作触发。
- 图索引优先用目标绝对目录解析 project；已有 project 列表应可按 root 定位，减少猜名称和整表输出。
- 降级结果继续明确区分“搜索能力不可用”和“没有匹配项”。

**完成判据：**同一会话只支付一次确定性 451 探测成本；无索引时明确转入文本搜索，不把不可用结果当成不存在证据。这里适合修工具，不宜靠在每份项目指令里重复搜索顺序来补救。
