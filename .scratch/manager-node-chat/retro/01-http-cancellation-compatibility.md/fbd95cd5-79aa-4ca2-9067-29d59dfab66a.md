# TDD 执行复盘建议

## 范围与结论

本复盘仅依据本 ticket 的执行对话及工具结果；没有读取父 session 或其他票据的执行历史。本轮只阅读证据，未修改文件或重跑验收。

本次有真实的 red → green：预取消测试先因请求错误成功而失败，等待响应头取消测试先因得到 `timeout` 而非 `cancelled` 失败；随后分别实现并转绿。首次 `yaml` 缺失被作为环境错误处理，安装锁定依赖后重新取得行为 red，没有把导入失败当作 TDD 证明。正文取消还进行了临时故障注入、观察失败、恢复实现并确认通过。

主要改进空间不是再增加“遵守 TDD”的指令，而是让**验收证据能够排除指定的资源与竞争错误**，并让临时 worktree 在执行前获得可复现的验收环境。

## 1. 高：资源释放测试需要区分“立即取消清理”和“原超时最终清理”

**事实**

新增测试通过公共 HTTP interface 调用真实 loopback 传输，并在 fixture 清理前等待对端 `close`，方向正确。但等待响应头、TLS 连接、未完成正文测试分别使用了约 `200ms`、`1000ms`、`1000ms` 的请求预算；取消之后只等待断线事件，没有建立“断线必须先于原请求预算耗尽”的独立界限。

正文故障注入移除了原生 abort 监听，并替换正文阶段信号。该测试确实失败，但失败点是返回了错误的终止原因，尚未走到后面的断线等待。

**推断与风险**

如果某个错误实现立即返回正确的 `cancelled`，却把连接留到原请求预算耗尽才关闭，现有测试仍可能通过。当前证据证明了正确实现运行中发生过关闭，也证明测试能识别一种正文取消故障；还没有充分证明它能识别票据明确排除的“提前返回、遗留活动请求”。这不是已经发现实现泄漏。

**建议**

在独立验收环节为 P20 增加一个明确的资源释放判别：请求预算明显长于测试的清理观察上限，取消后对端必须在该上限内关闭，并且关闭证据先于 fixture teardown。上限属于真实网络集成测试的 watchdog，不用固定 sleep 充当阶段同步。

针对这个判别做一次定向故障注入：保留正确的取消结果与原始原因，但让传输延迟到原预算才清理。观察测试因资源未及时释放而失败，恢复后确认通过。复用现有 TDD skill 的“命名违例 → 检验敏感性”要求即可，无需新增另一份重复规则。

**完成标准**：上述“正确取消结果、错误资源生命周期”的变体稳定失败，正确实现通过，失败原因明确指向连接仍活动。

## 2. 高：竞争归因承诺尚缺少竞争发生时的测试证据

**事实**

`caller TimeoutError is cancellation, while the client budget remains timeout` 验证了两个重要行为：调用方提供的 `TimeoutError` 仍归为 `cancelled`；客户端预算耗尽仍归为 `timeout`。但后一段是在 `await request(...)` 已返回后才调用 `laterCaller.abort(...)`。

最终报告中的对应说明也是“后续 caller abort 不覆盖已采用的超时原因”。这能证明已返回结果的稳定性，不能单独证明请求尚未结算时两个终止条件竞争的归因。

**推断与风险**

实现可能正确，但报告对“终止条件竞争”的覆盖宽于实际场景。只验证两个串行触发，难以排除结算阶段用较晚状态覆盖较早原因的错误。

**建议**

将该验收项的独立检查分成“来源分类”和“竞争归因”两部分。保留现有来源分类测试；竞争部分要求请求仍未对调用方结算时，确实出现多个候选终止条件，并有可独立确定的先后关系。只通过获批 S2 interface 进入，真实传输机制留在路径中；若现有公开观察面无法可靠构造某种顺序，应明确记录覆盖边界，而不是用返回后的 abort 替代。

独立验收者应尝试一个“按后来已 aborted 的信号重新分类”的定向变体，确认竞争场景能拒绝它。

**完成标准**：证据能分别说明哪个终止条件先被采用、另一个何时发生，以及最终结果为什么保留前者；普通来源分类通过不再等同于竞争覆盖通过。

## 3. 中高：临时 worktree 缺少验收前置准备，回归在业务断言之前失败

**事实**

本轮出现了三类可定位的环境问题：

- 首次 focused run 缺少 `yaml`；执行 `bun install --frozen-lockfile` 后恢复。
- framework 分区为 **722 pass / 1 fail**，唯一失败是历史测试读取缺失的 `.scratch/pi-adapter-source-aligned-refactor/implementation/01-baseline-artifacts/pi-state-before.jsonl`。
- 受影响消费者检查为 **195 pass / 7 fail**；七个失败均在复制缺失的 `herdr-bot/meta-data/bot-options.toml` 时发生，未进入目标行为验证。

之后才检查到 `HERDR_BOT_METADATA` 配置入口；对实际 backend checkout 的搜索也未找到该文件。历史 JSONL 在尝试查找的源 checkout 路径同样不存在。代理如实保留了这些失败，没有制造替代 fixture。

**建议**

将 worktree 的验收前置准备收敛到一个可执行入口，由派票环境或测试启动器调用：检查锁定依赖、所选分区要求的 fixture、后端安全测试二进制和元数据路径，并一次列出缺项及解析来源。

永久回归依赖的历史 JSONL 应进入可版本化的测试 fixture 位置，或由可复现、带版本约束的准备步骤提供；`.scratch` 不宜成为长期验收唯一的不可恢复输入。后端元数据继续使用已有 `HERDR_BOT_METADATA` 机制，检查其内容与待测后端的对应关系，而不仅确认二进制存在。

在 `docs/agents/testing.md` 的相应分支增加一个紧凑的前置准备指针即可。命令、环境变量和路径规则由启动器与配置持有，避免文档再复制一份清单。

**完成标准**：新建临时 worktree 后，相关验收能运行到行为断言；若依赖确实不可得，启动前一次报告缺项，并将受影响检查明确标为尚未验证，而非在多个测试中重复报初始化错误。

## 4. 中：已有 typecheck 有效，但可见仓库缺少自动执行入口

**事实**

`package.json` 已有 `typecheck`，同时运行 TypeScript 与 authoring 检查。本轮它抓住了两个真实问题：

- `signal` 可能为 `undefined`：`TS18048`。
- 将 `Promise.withResolvers<void>().resolve` 直接传给 `response.write` 的回调参数导致重载不匹配：`TS2769`。

代理修复后，最终 typecheck 通过。复盘读取的仓库中未找到 `.github/workflows`、`.husky` 或匹配的 lint 配置；worktree 的 `.git` 是间接位置，因此仅凭本轮搜索不能断言没有仓库外 hooks 或托管平台检查。

**建议**

优先把已有 `bun run typecheck` 接入仓库管理的提交或 CI guardrail，而不是新增“注意可空变量”“注意回调签名”等文字规范。CI 可同时运行环境可复现的测试分区；需要真实 backend 或宿主的检查单独声明依赖，准备成功后执行。

对于本轮触发的 `Promise.withResolvers` 等固定语法偏好，如需要强制执行，也应由确定性检查承担；判断性的测试质量审查仍交给独立验收者。

**完成标准**：错误签名或可空访问即使通过 Bun 运行测试，也会在自动合入检查中被拦截。现有 typecheck 是权威入口，不再建立第二套同义检查流程。

## 5. 中低：搜索服务不可用与 worktree 索引身份应由工具层提前处理

**事实**

首次 `find` 因模型服务返回区域限制 `451`，共 **27 个 judge 请求失败、0 个候选完成判断**。代理之后改用字面搜索找到实现，没有把搜索失败误判为代码不存在。

图工具列出的是其他临时 worktree 与主 checkout 的项目；随后读取声明大纲时选择了主 checkout 的索引。实际源码仍从当前 worktree 阅读，但记录中没有看到这些大纲对应当前 worktree 的覆盖或新鲜度确认。

**建议**

工具层对区域限制等确定性的服务不可用响应设置短路：一次确认后，当前请求直接返回可操作的降级路径，避免继续向同一不可用后端扇出。

图查询入口优先按当前 worktree 的绝对根路径解析项目身份，并显示是否精确匹配。没有匹配或新鲜度无法确认时，将其他 checkout 的大纲标为导航提示，源码事实继续来自当前 worktree；项目解析和降级信息由工具返回，避免代理每轮列举大量项目后手动推断。

**完成标准**：不可用服务不再产生同类批量失败；跨 worktree 的索引身份清晰可见，未确认的索引不会被当作当前源码证据。

## 应保留的做法

- **以真实行为取得 red**：环境错误修复后，再观察预取消和等待取消的独立预期失败。
- **通过获批接口测试资源**：公共 request 驱动真实 loopback 连接，资源关闭在 fixture teardown 前观察。
- **对已有满足项补证，而非制造失败**：后续 TLS、完整正文等场景验证已有实现覆盖；正文额外使用定向故障注入检查敏感性。
- **维持证据分层**：6 个新增测试通过、29 项 HTTP smoke 通过、最终 typecheck 通过，与两组仍有环境失败的回归分别报告；S2 受控 HTTP 证据没有冒充实际 omp 生命周期或真实后端等待释放证据。

本轮没有独立 review 的执行记录，因此以上问题不归因为“reviewer 漏检”；也没有足够证据认定全局指令需要扩写。优先改进验收判别、环境准备和自动 guardrail，比继续增加常驻指令更直接。
