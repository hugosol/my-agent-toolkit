# 本票 TDD 执行复盘建议

## 范围与结论

本复盘仅依据指定 ticket 子会话的 JSONL、其中的文件读取和工具结果，不使用父 session 或其他票据的执行历史。

**事实**：本票最终只提交了长期文档与导航，提交为 `0ee743d`。既有 S1 演练实际运行后得到 1+3 个用例通过；第一次演练因当前 worktree 缺少 `node_modules/yaml` 失败，安装依赖后通过。该失败是环境准备失败，不能算作行为测试的 red。文档票复用已有行为覆盖、检查链接与示例，而不制造新的 red，是合理选择。

以下建议按对后续执行的影响排序；均为建议，本轮未实施。

## 1. 中：把 worktree 就绪检查放在真实宿主演练之前

**事实**：执行者先在独立导出的部署目录成功安装依赖，随后却在尚未安装依赖的 ticket worktree 启动演练。直到 `cpSync` 读取该 worktree 的 `node_modules/yaml` 时才收到 ENOENT。此时已经取得真实宿主检查的 quiet window。执行者随后正确安装依赖、复验，并在手册中明确了安装所在的 checkout。

**建议**：由 ticket 启动器或现有 dock 启动入口完成一次与实际测试 cwd 绑定的环境预检：确认依赖从该 checkout 可解析、后端所需构建产物存在，并输出将使用的源码根与宿主版本。依赖安装在申请昂贵检查窗口之前完成；缺少依赖时给出精确到目录的安装命令。

**完成标准**：全新 worktree 能在启动 OMP 前得到明确的就绪结果；另一份部署已安装依赖不会使当前 checkout 被误判为就绪。保留本票已经补充的操作说明，不再向全局 AGENTS.md 重复添加准备事项。

## 2. 中：将临时文档检查整理为可复用的确定性检查

**事实**：本次链接与示例检查通过临时 Python Eval 编写，检查器自身先后出现两次误判：

- 未识别 `<a id="version-verification">`，把有效显式锚点判为不存在。
- 将 PowerShell 的 `2>&1` 当作测试文件路径。

修正检查器后，最终报告为 66 个本地链接/锚点、15 个 JSON 样例、2 个 TOML 角色条目及文档测试路径检查通过。这些是检查器问题，不是产品缺陷。

**建议**：优先查找并复用仓库已有 Markdown/示例检查入口；若没有，将本票真正需要的检查收敛到一个版本化命令，而不是让每个文档票重新实现解析器。至少用固定夹具覆盖有效显式锚点、真实断链、JSON/TOML 语法错误，以及带重定向的 shell 示例。命令示例只做明确声明的语法或路径检查，避免用字符串切分模拟通用 shell 解析。

**完成标准**：同一命令可重现检查范围；有效样例通过，故意损坏的链接或示例失败，并指出文件位置。

**证据边界**：本会话读取的 `package.json` 包含 `check:authoring`、`check:integrations` 和测试/typecheck 命令，但未列出文档检查命令。历史没有检查 CI 或 hooks，不能据此断言仓库完全没有文档 guardrail。接线前应先核实已有检查链，而不是直接新增另一套。

## 3. 中：让文档审查与脚本化协议演练分别承担明确的证明责任

**事实**：复用的 `role-guidance-rehearsal.test.ts` 实际调用真实 OMP 工具与后端，并读写真实材料；但 recover、retry、complete 等决策由测试预先写定。它检查了部分注入指引文本，却不读取新写的 OPERATIONS 手册来选择动作。最终记录也明确声明 provider、Herdr CLI、工具选择和材料内容受控，没有将技术演练宣称为 H1 通过。

**推断**：脚本通过可以证明预设操作的结果，但对手册中错误的动作选择说明未必敏感。例如，若手册误写 recover 的效果，原测试仍可能通过。这不是本次已经发现的文档错误，而是证据可检出的范围。

**建议**：在已有独立审查环节增加一个按分支完成的审查判据：部署、预算、通知失败、recover/retry 和人工交接，每个分支都对应手册操作、权威协议依据及实际观察。脚本结果负责证明协议行为；审查负责证明手册的顺序、前提和选择规则与该行为一致。沿用现有集成审查，不必为此新增一套模型验收系统。

**完成标准**：每个分支都能区分“命令执行通过”“处置说明经核对”“仍依赖人的整体使用判断”；手册中的关键错误不会仅因测试全绿而被跳过。

## 4. 中低：由宿主在交接时归档原始证据

**事实**：本票将约 1.9 MB 的演练 JSON、成功日志、初次依赖缺失日志和构建日志保存在系统临时目录；长期记录保存关键观察、源码版本、文件大小和 SHA-256。这使文档本身可以独立理解，但原始证据路径仍可能被临时目录清理影响。

**建议**：在 ticket 交接阶段，由宿主将原始证据归档到按 run_id 关联的受控产物位置，并提供稳定的 artifact 引用。长期文档继续保留简洁结论和证明范围，不把完整 provider 请求复制进仓库，也不让临时绝对路径承担唯一复核入口。

**未验证项**：本会话没有显示宿主是否另有自动归档机制，也没有证据证明原文件已经丢失，因此这是保留策略建议，不是已发生的数据丢失结论。

## 5. 低：让检索服务的确定性不可用尽早降级

**事实**：首次 `find` 的 30 个判定请求全部返回地区限制 451，没有产生可用命中。执行者随后利用目录、README、文档地图和精确读取继续完成任务，并向工具问题通道报告故障，没有把检索失败当作代码不存在。

**建议**：在工具层对地区限制等确定性不可用响应快速中止同次后续判定，并返回明确的替代路径：已知文件名走 glob，已知字面量走 grep，已知文档入口直接读取。若能维护当前工作树与索引项目的对应关系，也应由工具提供，减少列出全部项目后人工选择的工作。

**完成标准**：服务确定不可用时不继续消耗同类判定请求；降级结果明确表达“未完成检索”，而不是“没有匹配”。无需再给 AGENTS.md 添加一条长期故障说明。
