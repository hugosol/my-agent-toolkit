### 1（高）票据 worktree 不带依赖，第一道自动检查就被卡住

**事实**：`ls node_modules` → `No such file or directory`（本 worktree 全新，`package.json` 的 `pi-subagents` 等依赖未安装）。我通过 `ls` 另两个票据 worktree 发现 `hyper-ticket-vHdMLq/node_modules/pi-subagents` 存在，再 `cp -r` 55MB 才跑起第一条测试。`bun run typecheck`、`bun test`、真实宿主脚本全部依赖它。

**影响**：这不是一次性的几秒，而是一个**可能诱导错误路线**的岔口：没有网络或不懂偷邻居依赖的执行者要么跳过全部自动检查（本轮验收的基础），要么去 `bun install`（未知网络状态、可能改变 lockfile）。

**建议**：worktree 创建步骤里显式 provision（`bun install --frozen-lockfile` 或软链主 worktree 的 `node_modules`）；若保持手动，在 `docs/agents/testing.md` 顶部加一条**指路**：“票据 worktree 不含 `node_modules`；用 `<主 worktree>/node_modules` 共享或就地安装”。这属于工作流/宿主层，不是代码问题。

### 2（高）真实宿主的运行缺一条前置断言：被测扩展到底绑上了没有

**事实**：第一次真实运行（131s）与第二次（70s）都表现为“父轮不关”，我先按框架文档推断是「一次重检错过了静止窗口」（推断），直到我自己在脚本里加的诊断把真因打出来：`modelCost: configuration error (config) … declares no "codexQuotaTtlMs"`（我生成的隔离 `config.yaml` 漏了该字段，生产装配根本没绑定）+ `piBackgroundRounds: this session's background work cannot be read: … a session-liveness registry this entry did not publish`（模块局部 `Symbol()` 的 bug，见 §5）。两条真因都不是「Round 合成出错」，却都伪装成同一个行为症状。

**建议**（可机械化，优先做）：
- 在 `tests/harness-dock/` 放一个共享的 pi 运行 precondition：「本次运行的被测扩展真的绑定了、并收到了自己的 session」——例如让 fixture 在绑定时写一行证据、或断言隔离存储里出现该会话记录——任何 Round 断言之前先过这一关。当前缺陷是：**失败形态与业务失败同形**，一行断言能省两次昂贵真实运行。
- 把「隔离 layout + 必需 config 字段」收进共享 helper（见 §6），从构造上消灭漏字段。

### 3（高）仓库没有 CI，也没有观察到 pre-commit hook；检查全靠执行者自觉

**事实**：`ls .github/workflows` → 不存在；`.git/hooks`（本 worktree）无自定义 hook；`.husky`/`lefthook.yml`/`.pre-commit-config.yaml` 均不存在。也就是说 `bun run typecheck`、`bun test` 只在有人记得时运行。
**未验证**：linked worktree 的 hook 目录指向主仓库 `.git`，所以「主仓库也没有 hook」是**推断**，未核对。`.github` 不存在于本次 checkout ⇒ 仓库无 CI workflow（事实）。

**建议**：加一条最便宜的 guardrail——pre-commit（或一个 `bun run check` 聚合脚本 + CI job）跑 `typecheck` + 快速分区。真实宿主/dock 分区（`test:dock`、`scripts/*-smoke.ts`）成本高，不该进 hook，但**类型与框架分区**进 hook 能挡住本轮已出现的两类错误（类型引用写错、context 成员漏接）。

### 4（中）`docs/agents/testing.md` 的指路词指向了执行者看不到的东西

**事实**：testing.md 写“Read `package.json` for existing script names”。本会话里我用 `read package.json` 得到的是 **`package.json: my-agent-toolkit` + `dependencies: 5`——没有 `scripts`**（工具摘要的形状），因此我从未看到 `test:dock`、`test:framework` 等名字，只按票据里出现的 `bun run typecheck` 与手写 `bun test tests/...` 行事。事后 `node -e` 才看到 12 个脚本。

**建议**：把分区命令直接**内联**进 testing.md 的表格（`bun run test:framework`、`bun run test:dock`、`bun run typecheck`、`bun run test`），并删掉/弱化“去读 package.json”的指路——这是典型的“缓存查不到就等于没有”的案例（环境是事实来源，但工具摘要把它藏了）。顺带：本轮因此**从未运行 `test:dock`**，若该分区与本改动相关（framework adapter 变更），这是本票的一处执行缺口。

### 5（中）跨模块图共享的键必须用 `Symbol.for`——建议进标准（判断类）

**事实**：我一开始用模块局部 `const REGISTRATION_TABLE = Symbol(...)` 作为自发布注册表的成员键。真实宿主上崩溃：`this process already carries a session-liveness registry this entry did not publish`，因为 **pi 为每个扩展入口各建一套模块表**（production entrypoint 与 round fixture 各持一份 `nicobailon.ts` 实例，各自的 `Symbol()` 不同）。改成 `Symbol.for(...)` 后正常；这条仅**真实宿主**能发现，S1 假件永远测不出（我事后补的「另一份模块图的注册表」用例可以——它需要测试自己用 `Symbol.for` 写注册表，属于白盒但值得保留）。

**建议**：`CODING_STANDARDS.md`（审查期读，非实现期）加一条判断规则：“用于进程级协调的 `globalThis` 槽位/注册表成员键用 `Symbol.for`；模块局部 `Symbol()` 只用于本实例私有状态”。机械化很难（需语义判断），但配合 §2 的真实路径前置断言，这类错误下次会更早暴露。

### 6（中）真实宿主脚本的 layout 胶水正在复制，且“已合入脚本的记录”阻止了就地重构

**事实**：`scripts/pi-subagent-smoke.ts`（05）与我的新脚本各自内联了 `isolateHome`/`configRootFor`/写 child entry（约 90 行），并且**都把必需 config 字段重复书写一遍**——这正是 §2 里我漏写 `codexQuotaTtlMs` 的土壤。我没有重构 05 的脚本来共享（它在 05 的证据文档里被引为「可重跑入口」，改动会让那份记录失效），于是选择了复制。

**建议**：
- 抽出 `scripts/support/pi-run-layout.ts`（写入隔离 home、config root、child entry，以及必需 config 字段的唯一来源），两个脚本都消费它；新脚本用 `scripts/support/` 已在目录结构里存在的位置。
- 在 `docs/agents/testing.md` 记一条工作纪律：“已记录在证据文档里的脚本不要就地改；先把可共享部分抽到 `scripts/support/`，两边同步迁移，避免让既有记录失效。”这把本次的取舍从「两难」变成「照规则做」。

### 7（中）票据的「执行与证据约束」没有点名受影响的真实宿主消费者与其耗时

**事实**：testing.md 要求票完成时纳入「共同契约消费者」，本改动的影响面包括 `scripts/pi-subagent-smoke.ts`（05：目标提供方在位时主会话仍要正常保存，恰好依赖“登记失败也不阻塞关轮”的语义）。我没有跑它：本会话在软预算（200 请求）到点、被要求收尾时，真实宿主脚本刚迭代完第 4 次。

**建议**：票据模板的「执行与证据约束」在真实宿主类票据里**点名**要跑的消费者命令与大致耗时（例：`bun scripts/pi-subagent-smoke.ts` ≈ 数分钟，含一个已知会崩的前台阶段），让执行者先把它排进时间预算，而不是留到「最后再跑」。另可把「真实宿主票据」的 token/请求预算预期写进票据元数据。

### 8（低）保活协议的“消费侧”是推断出来的，票据/规格没给指针

**事实**：ticket/spec 只说「沿用 nicobailon 版本化公开保活协议」，而该协议**只有 `register`、没有查询入口**；因此“消费”意味着一方必须**自己发布注册表槽位**并接住提供方的登记。我在读完 `spec §8`、`lighthouse/08`、`research/08`、`decision/08` 之后，还要去第三方源码 `node_modules/pi-subagents/src/integrations/pi-web-session-liveness.js` 与 `docs/extension-api.md` 的 “Host session lifetime and completion wakes” 段才敢确定，并额外权衡过“要不要链式转发他人注册表”（最终按“不覆盖他人槽位”落地）。

**建议**：在票据的权威来源清单里加一条**导航指针**（指到上述工件文件与文档段落，以及“只有 register”的事实），省掉下一位执行者重新推导这一核心设计前提。这属于低成本、高杠杆的指路。

### 9（低，宿主/工具层）两处工具摩擦，各浪费 1–2 次调用

- `bash` 的 `ready` 参数只接受对象或 `null`，我两次传 `false` 被拒（`ready: false` → validation failed），每次都要重发。
- 对长测试用 `async: true` 被拒（“Service mode does not accept async or timeout”），只能改为前台运行并等后台投递。

**建议**：若可改，`ready: false` 与 `async: true`（配 `timeout`）应被接受或给出“传 `null` / 去掉 `async`”的**可直接照抄**的修法提示；本会话里错误信息虽准确但需要一次额外往返。

### 附：本轮值得保留的做法（供后续票据复用）

- **dock 的捕获端点 + 隔离 run root + `pi-session.ts`** 让“两个真实后台委派 + 唤醒”这类场景能在约 31 秒内可重跑地断言；`session.stderr()` 前缀证据行 + `frameMark`/`frames()` 是够用的观察面。
- **在脚本里自带失败诊断**（把 probe 证据行、本扩展诊断、async 状态、frame 尾部一次打出）是本轮从“两次整轮真实运行查不出的真因”走到“一次定位”的关键；建议把这种 `reportDiagnostics` 作为真实宿主脚本的模板片段（与 §2 的前置断言配套）。
