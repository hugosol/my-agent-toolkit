## 1. **[高] Windows CRLF 检出令真实宿主 dock 套件与 lockfile 校验静默失配，且报错指向错误方向**

**事实**
- `bun test tests/harness-dock`：**45 pass / 12 fail**（57 tests / 23 files / 102s），全部失败发生在**装配阶段**，其中 10 条为 `(unnamed)`：`error: ...host-patches\omp-18.5.0-viewed-session\patch.diff touches no file`（`tests/harness-dock/host-patch-artifact.ts:224`）。
- 独立探针（同一解析器函数，临时文件）：`CRLF as checked out: 0 files; LF normalised: 8 files`。
- 另一条失败：`bun.lock` 磁盘 sha = `7f5c82e6…`，记录值 = `9e9f4833…`；**把行尾规范化为 LF 后与记录值完全一致**，且等于 `HEAD:bun.lock` 的 blob sha。
- 第三类失败（`controlled session > starts the isolated artifact…`，1.2s 后失败）同样卡在补丁物化。

**判断** **[推断]** 该 worktree 以 CRLF 检出（`patch.diff` 的 `file` 输出明写 “with CRLF line terminators”），而 dock 按 LF 写死：`patchTouchedFiles` 用 `split("\n")` + `/^diff --git a\/(.+?) b\/(.+)$/`，行尾残留 `\r` 时（`. ` 不匹配 `\r`）一个文件都匹配不到；lockfile 校验同样按字节 sha 比对 LF 记录值。**未验证**：未 `git config core.autocrlf`、未检查其他 Windows worktree 是否同样失败、未验证修复后 dock 是否转绿（复盘轮不执行）。

**建议（按代价排序）**
1. 仓库根加 `.gitattributes`：`*.diff -text`（补丁产物按字节保存）、`bun.lock text eol=lf`（或全局 `* text=auto eol=lf` + 显式例外），这是**确定性守卫**，一次治好补丁解析与 lockfile 哈希两处。
2. 同时把两处读取改为行尾鲁棒（解析前 `replace(/\r\n/g,"\n")`；哈希前同样规范化），让环境漂移不再变成谜题。
3. 让 dock 的失败信息带上“行尾/检出策略”提示，替代现在的 `touches no file`（该措辞把人引向“补丁文件坏了”，本轮我先怀疑的是仓库 artifact，不是 CRLF）。
4. 落点：`.gitattributes`（新）+ `tests/harness-dock/host-patch-artifact.ts`、`tests/harness-dock/baseline.ts`；影响面覆盖**任何在 Windows 上跑 dock 的票**（本图 20/21/23/24 都会撞上）。
