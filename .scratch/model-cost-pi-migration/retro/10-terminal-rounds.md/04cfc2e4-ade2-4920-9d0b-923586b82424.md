## 1. 仓库没有 guardrail：跨分区破坏只能靠运气发现（severity: high）

**事实**：本票在 `framework/adapters/omp/round.ts` 增加了一个原生订阅（`message_end`）。`bun run typecheck` 全程绿；但 `bun test tests/connect-bot`（另一个 OMP 消费者）从 51 pass 变成 **91 fail**，崩溃点是 `tests/connect-bot/support/omp-double.ts` 的 `on()` 把未建模事件塞进 `sessionHandlers[event]`。我是**主动**跑了那个分区才发现的；若按 `docs/agents/testing.md` 的"所属分区 + 受影响消费者"口径只跑 framework/model-cost，这个破坏会带到集成分支。

**事实**：仓库根目录没有 `.github/`（无 CI workflow）、没有 `.husky/`（无 pre-commit）；`package.json` 有 `test` / `typecheck` / `test:*` 脚本，但没有 `lint`、`check`，也没有任何 lint 依赖（devDeps 只有 `@types/node`、`bun-types`、`typescript`）。所以"改到别处就红"这件事在提交/推送时**没有任何自动兜底**。

**建议**（机械化，最便宜的形式即可）：
- 加一个 `package.json` 的 `check` 脚本（`bun run typecheck && bun test`），并在 CI（新增 `.github/workflows/check.yml`，无则最简 `on: [push, pull_request]`）或本地 pre-commit 钩子里调用它。
- 若嫌全量 `bun test` 慢，钩子至少跑 `typecheck` + `tests/framework` + `tests/model-cost` + `tests/connect-bot`（本次事故的分区集合），全量留给 CI。
- 注意：`typecheck` **单独不足以**兜住本次事故（见第 2 条），所以检查里必须包含测试运行，不能只加类型检查。

## 2. 模拟原生面的 test double 接受任意事件名，新订阅以运行时崩溃而非编译错误暴露（severity: high）

**事实**：受影响的两个 double 都写成 `on(event: string, handler: never): void` 并内部按 `if (event === ...)` / 索引到 `Record` 分发（`tests/connect-bot/support/omp-double.ts`、改动前的 `tests/framework/round.test.ts` 同形）。`string` 形参使对象字面量满足 `OmpExtensionApi` 的全部重载，于是**适配器新增一个订阅时类型系统全绿**，错误推迟到运行时，而且是 `undefined is not an object` 这种无指向的签名（既没说是哪个事件，也没说该 double 缺哪一项）。

**建议**（机械化）：
- 这类 double 的 `on` 不要放宽到 `string`：按被模拟接口的**真实重载**声明（或 `satisfies` 该接口），让"新增订阅"变成编译错误。
- 若确实需要接收未知事件，默认分支抛具名错误（例如 `this surface does not model the native event "<name>"`），并显式列出已建模集合。
- 更彻底：适配器导出"原生事件名"的联合类型（`framework/adapters/omp.ts` 已有 `OmpRoundEventType` 这种局部联合），double 用 `switch` 穷尽它，新增事件即编译失败。这是把一次 91-fail 事故变成一行编译错误的杠杆点。

## 3. 缺"宿主事实"导航：一次真实宿主运行因事实缺失而白跑（severity: medium-high）

**事实**：我给 `scripts/pi-terminal-round-smoke.ts` 假设"被取消的轮结束后，提供方对本会话的结果通知会唤醒并启动一次新 run"（依据是 ticket 09 的真实证据：唤醒接续原轮）。第一次 smoke 跑到阶段 2，**等了 90 s 超时**（整轮 124 s 失败）；诊断 frames 只有 `message_start/message_end`（`customType=subagent-notify`）与 widget 帧，**没有** `agent_start`。也就是说：RPC 模式下这条唤醒没有自行启动执行，只追加了结果。

**推断**：原因是提供方对"被取消会话"的唤醒持有（held）行为，而该行为带 `hasUI` 条件；本宿主 RPC 模式仍**发布** UI 通道（能看到 `extension_ui_request` 帧），因此该条件满足。[推断] 我没有在运行中直接读出 `ctx.hasUI` 的值。
**事实**：这条 `hasUI` 条件与"held 期间只追加、下一次 agentStarted 解除 hold"我**在跑之前就读过**（`.scratch/model-cost-pi-migration/research/08-round-boundary-facts.md` §4），但仍按"RPC/headless ⇒ 无 UI"的先验写了脚本——说明缺的不是原始证据，而是**把宿主事实挂在会被读到的位置**。

**事实**：同一轮里还有一次事实搜寻成本——"每个宿主用什么事实表示活动终局"。我先后查了 pi 的 `agent-session.ts`/`extensions/types.ts`、oh-my-pi 的 `agent-session.ts`/`shared-events.ts`/`lifecycle-mirror.ts`/`agent-session-types.ts`，最后发现答案就在手边：**两个适配器的 `turn.ts` 里早已有 `outcomeOf(message)`**（`stopReason` 的封闭三值映射），pi 另有 `agent_settled.aborted`；OMP 的扩展事件面**没有** abort/error 字段。

**建议**：
- 新增 `tests/harness-dock/README.md`（或 `docs/agents/testing.md` 的一节）记录**加载事实**，每条一两行：每个 driver 的模式（`pi-session.ts` RPC、`session.ts` OMP）、各模式是否发布 UI 通道（`hasUI` 语义）、固定提供方的保活/唤醒语义与其工件路径（`node_modules/pi-subagents`，以及 `PI_SUBAGENTS_TEMP_ROOT` 下的 status/replay 位置）、`resolvePiCli` 的来源（安装版 pi / `PI_CLI`）。这是 pointer 级材料，成本一行，回报是少一次 2 分钟的真实运行。
- 新增一条**宿主事实**指针（可放 `framework/docs/harness-support.md` 顶部或 `docs/agents/` 新文件）：两个宿主扩展面类型定义的路径（`E:/Developer/myhub/pi/...core/extensions/types.ts`、`E:/Developer/myhub/oh-my-pi/...extensibility/extensions/types.ts`），并点明"扩展面上表示活动终局的只有 assistant 消息的 `stopReason`（+ pi 的 `agent_settled.aborted`）"。
