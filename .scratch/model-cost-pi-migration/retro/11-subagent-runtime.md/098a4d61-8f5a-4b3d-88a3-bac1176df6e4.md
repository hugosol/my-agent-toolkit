## 1. （最高）Windows checkout 的 CRLF 让整套真实宿主 dock 无法启动

**事实**：第一次跑 dock 时瞬间失败——

```
error: .../host-patches/omp-18.5.0-viewed-session/patch.diff touches no file
      at ensurePatchArtifact (tests/harness-dock/host-patch-artifact.ts:267)
```

`patchTouchedFiles` 用 `/^diff --git a\/(.+?) b\/(.+)$/` 逐行匹配；本 worktree 的 `core.autocrlf=true` 把 index 里本是 LF 的 blob 落成 CRLF，而 JS 的 `.` 不匹配 `\r`、`$` 只在输入末匹配，于是**每一行都匹配不到**。用 `git -c core.autocrlf=false checkout` 也不够（git 认为工作区无变化），必须 `rm -f host-patches/*/patch.diff` 后再 checkout 才重新物化 LF；之后两套 dock 立刻正常。

**为什么算最高**：这条路径是「真实宿主证据」的唯一入口（本票 P24 的 Coverage 明确要求真实宿主活动）。它不在任何测试断言里报出语义失败，而是把整套 dock 变成启动即崩，且诊断需要读解析器源码 + 查 `core.autocrlf` + 比对 blob 换行。

**建议**（机械修复，二选一或都做）：
- 仓库加 `.gitattributes`：`host-patches/**/*.diff -text`（或 `*.diff text eol=lf`），让这些工件永远以 LF 检出；
- 或让 `patchTouchedFiles` 容忍 CRLF：`/^diff --git a\/(.+?) b\/(.+?)\r?$/`（并给该函数一个单元用例，喂 `\r\n` 文本）。

推断（未验证）：任何在 Windows + `autocrlf=true` 下新建的工作区都会复现，因此其它 ticket 的 dock 证据可能依赖当时 checkout 的偶然状态。
