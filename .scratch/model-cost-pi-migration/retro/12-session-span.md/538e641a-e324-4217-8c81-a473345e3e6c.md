### 1（最高）「一次进程一份扩展配置」这条宿主事实，必须在测试约定里对测试作者可见

**事实**：`framework/core/config.ts` 的 `validatedConfigs` 以 definition id 为键、进程级缓存，源码注释也写明「one entry per extension per process」。本会话先按生产装配 `modelCostPiHarness(repo)` 为每个测试准备独立临时仓库/存储根，单跑本文件 4 个用例全绿；一旦与整个模型分区同进程运行，`bun test tests/model-cost` 得到 **380 pass / 4 fail**，失败原因正是本文件被别的套件先绑定过的配置覆盖（保存写进了别的根）。我随后改用「镜像生产装配 + 测试自述 storageDir」才恢复 **384 pass / 0 fail**，代价是本文件的 S2 证据不再经过 `modelCostPiHarness` 本身。

**影响**：这是本票最大的隐性成本——单文件绿 ≠ 分区绿，只有当最后跑分区时才暴露；且它把「装配路径的证据」与「span 语义的证据」拆到了两个文件里。

**建议**：在 `docs/agents/testing.md` 增加一条面向测试作者的约定，措辞围绕既有的 **one extension, one configuration per process** 概念：任何在同一进程内自己设定存储根的套件，要么成为该扩展在本进程的第一个绑定，要么在测试内自述 `config`；并说明这样做的代价（该套件不再压测生产装配对象）。这是文档缓存，不是新检查——环境真相（`config.ts`）已存在，只是躺着没人读到。

### 2（高）假时钟套件与 pi 的「下一个任务」契约：三条实测事实值得写进同一个文档

**事实**（均为本会话实测）：
- Bun 1.4.2 下 `vi.useFakeTimers({ toFake: ["Date"] })` 会连 `setTimeout` 一起 fake（`toFake` 未生效，`advanceTimersByTime(0)` 后才触发）；且 `bun-types` 的 `useFakeTimers` 类型**不含** `toFake`，写成 `toFake` 会让 `bun run typecheck` 报 TS2353。
- 纯 `await setImmediate` 循环会**饿死 timer phase**：`setTimeout(0)` 永不触发（/tmp 实验 t1、t2），而 pi 的 `nextTask` 正是 `setTimeout(0)`（`framework/adapters/pi.ts`），框架的 Round 结束重检靠它。
- 文件协调以 25 ms 轮询（`framework/modules/files.ts` 的 `IN_USE_RETRY_MS`/`WAIT_POLL_MS`），因此每次等待回合至少要把假时钟推进 25 ms，保存才会落地；`advanceTimersByTime(n)` 还会把假时钟多推 1 ms（`n+1`），故断言宜取「自己的时钟读数」而非硬编码绝对时刻。
- Bun 1.4.2 没有 `vi.setSystemTime`；`useFakeTimers({ now })` 可设初值。

**影响**：这些是我在「用例看似挂死/保存永不发生」上花掉的第二大时间块，且全部靠反复试错与临时探针（多次新增/删除 `zz-*.test.ts`、临时给 `files.ts`/`round-events.ts`/`request-accounting.ts` 插桩再 `git checkout` 还原）得来。

**建议**：在 `docs/agents/testing.md` 收拢成一小节「faked clock + harness next task」，用上面的三个词锚定：**next task**（框架等待的位置）、**25 ms poll**（文件协调）、**fake clock advances**（推进即触发）。同节给出一句「等待用回合循环，不用时长」的正向写法。这既是导航指针也是缓存：环境代码（`files.ts`/`pi.ts`）已是唯一真相，缺的只是指向它的可见性。
