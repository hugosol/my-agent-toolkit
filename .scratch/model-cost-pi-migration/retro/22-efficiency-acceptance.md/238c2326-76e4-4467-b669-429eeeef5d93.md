## 1. 严重度高：仓库没有任何 guardrail 接线（事实）

**代价**：本轮的每一次验证（typecheck、真实宿主分区 104 例 / 221.93s、`tests/framework` 481 例、`tests/model-cost` 463 例）之所以发生，是因为票据与派发指令要求，而不是因为环境会拦住问题。仓库自己的 `docs/agents/testing.md` 已经把 tier 定义得很清楚（迭代=受影响文件；票完成=所属分区+共同消费者；集成=`typecheck` + `bun run test`），但这条规则只靠 agent 自觉执行。

**代价**：每一轮都在**未变的产品面**上重跑真实宿主分区（§13 与我都是 104 例 / ~222s）与多次采样/对照，另外还有 3 个 `.scratch/` 证据提交（`5714ddc`/`570c7ee`/`7274cb3`/`cbfc63c`/`62dd204` 中至少 4 次是本轮这种性质）。本轮的接管成本（读票 + 读 75 KB 证据 + 重跑）里，真正产生新信息的只有第 4 条那一件事。

**建议**：

## 3. 严重度中高：`core.autocrlf=true` 且缺 `.gitattributes`，制造了一个每轮都要重新踩的常驻陷阱（事实）

**事实**：`git config --get core.autocrlf` = `true`；仓库没有 `.gitattributes`。工作树里 `bun.lock` 与两份 `host-patches/*/patch.diff` **每轮**都以 ` M` 出现，而它们的带过滤器 hash 与 `HEAD` blob 逐字节相等（本轮实测 `cc3c49a6…`/`ff98fd25…`/`b652e639…`，CR 行数均为 0）。证据 §2 记录：CRLF 检出会让 12 个 dock 基线/补丁用例按 “patch touches no file” 失败，靠把这三份文件改写成 LF 字节才恢复 93/104 pass；§12/§13/§14 每一轮都要再写一遍“不要 checkout/restore 这三份文件”。

**代价**：每个接手 agent 都要花回合做这套 triage，并在交接里留下一段警告；任何一次善意的 `git checkout -- .`、`git stash` 或 IDE 的“revert”都会静默把分区打红（而且是 12 例这种极难直接联想到换行的失败签名）。另外工作树长期“脏”会污染采样工件自报的 `changedPaths` 字段，也让“树是否干净”这个判断每轮都要重新解释。

**建议**：加 `.gitattributes` 把这三条路径（或干脆 `*.diff`、`bun.lock`）标成 `-text`，或在仓库配置里设 `core.autocrlf=false`。这是一次编辑换掉每轮的一段文字与一次潜在误操作。

## 4. 严重度中：证据里的 revision 引用没有任何检查，交付报告指向了不可达提交（事实，本轮唯一实质修复）

**事实**：上一轮保存的 A/B 归因报告 `logs/22-takeover-g-ab-subannounce-comparison.txt` 把被测 revision 记为 `3f547df`；该提交是被那一轮自己改写掉的临时提交——`git cat-file -t 3f547df` 是 commit，但 `git rev-list --all` 不含它、`git merge-base --is-ancestor 3f547df HEAD` 为假，即**交付分支上不可达**，读者无法回到那棵树复核。我写了一个只读脚本对整份证据做统计：**引用到的 25 个提交里 2 个不可达**（同一提交的短/长两种写法）。

**建议**：
- 加一个 `scripts/` 下的只读审计（跑一遍约 4.4 s）：对证据文件里出现的每个 revision 判可达（祖先于分支或落在 `git rev-list --all` 内），不可达即失败。这类“报告里的机器可读引用”是机械可查的，正好该由检查承担，而不是每轮靠人读出来。
- 定一条约定：**临时注入/临时 revision 必须随证据保存补丁**，不能只留 revision hash——临时提交被改写是这种工作流的自然归宿，而补丁不会失效。本轮按这个做法重做（`logs/22-takeover-h-ab-subannounce-injection.diff` 969 B + 被测 revision 就是交付提交 `cbfc63c`，注入出现在工件的 `uncommitted paths` 里），一次采样就复现了同样的结论（可达差异仍只有 `main-child-concurrency draws 33 -> 30` 一行，其余可比图与语义交付逐项不变），并留下 `sha256` 还原证据。

## 6. 严重度低：Windows 上的 `bun -e` 转义陷阱浪费了一个回合（事实）

**事实**：本轮用 `bash` 执行 `bun -e '<多行脚本>'` 时得到 `error: failed to execute command 'bun': batch file arguments are invalid`（Windows 批处理参数限制），随后改用 eval 的 Python 才完成同一件事。

**建议**：在仓库 `AGENTS.md` 或宿主的环境说明里加一句指针式约定——“Windows 上一次性脚本走 eval（Py/JS）或写临时文件，不要用带引号/换行的 `bun -e`”。这条是纯导航成本，一行换一个回合。
