## 2. 真实宿主套件的失败信息被 teardown 掩盖 + 陈旧 run root 堆积 + 没有静默窗口机制

**事实**

- 首次分区运行 2 例失败，报的是 `EBUSY: resource busy or locked, rm '<run root>'`，栈为 `tests/harness-dock/run-root.ts:40`（`dispose()` 里的 `rmSync(root, {recursive:true, force:true})`）← `tests/harness-dock/model-cost-modes.test.ts:319`。
- 读源码确认：`model-cost-modes.test.ts` 的 `startRun` 是 `try { … await ControlledSession.start(…) } catch (error) { capture.stop(); runRoot.dispose(); throw error }` —— **`dispose()` 抛错时，`throw error` 永不执行**，于是真正的主错（会话启动停滞）被 `EBUSY` 顶替。同一文件两例声明的预算是 240,000 ms，而报告时长是 90,052 ms，说明 90 s 那个界不是用例自己的预算。
- 两例单跑 6.71 s 通过、整分区重跑 104/0 / 220.12 s 通过（同一源状态、本票不改产品代码），即首跑是环境型停滞。
- `%TEMP%` 当时有 863 个 `omp-dock-*` run root；本轮自己的两个失败 root 里文件被我删净后仍留下空目录 + 一条悬空 link（`user-home/.bun/install/cache/yaml/2.9.1@@@1 -> …/yaml@2.9.1@@@1`），MSYS `rm` 报 `Permission denied` 删不掉。
- `docs/agents/testing.md` 写了"Agree on a quiet window with peers for real-host or full-repository runs"，但仓库/工作流里没有任何可查询的机制（无锁、无队列、无运行登记）。

**推断（未验证）**

- 首跑 2.07× 时长（480.60 s vs 220–232 s）与 2 例各 90 s 停滞，最可能是机器/文件系统层面的外部负载（其它 agent 的真实宿主套件、杀毒扫描，或 863 个 temp 目录造成的 FS 压力）。本会话只能证明"同源状态重跑稳定通过"，**证明不了**载荷来源。
- 悬空 link 现象（删 target、留 link）会沉淀成空目录垃圾；863 个陈旧 root 里可能有一部分正是这样来的。

**建议**

1. **（机械、收益最高）修 teardown 语义**：`dispose()` 应为 best-effort（捕获自身错误、把次生错误挂到主错上，例如 `try { dispose() } catch (e) { error.cause ??= e }`），保证 `throw error` 仍执行。规则可写成一行评审标准："拆除失败不得顶替主失败，两者都要报"。本轮为定位这一点多花了 2 次套件重跑 + 约 1.5 min 的读栈/读源码。
2. **让真实宿主会话自证时序**：`ControlledSession.start` 若等待某种就绪信号，应在停滞时打印"等的是哪一步、等了多久、界是多少"。本轮拿不到 90 s 的归属，只能标注为未验证。
3. **run root 生命周期**：套件启动时按年龄清扫陈旧的 `omp-dock-*`（或给 root 加"属主进程已消失"标记），并在失败后用 `fsutil reparsepoint delete` / 非递归删除处理 link（正是 §17.3 已记录的教训），避免 link 悬空与垃圾堆积。
4. **给 `docs/agents/testing.md` 那句"quiet window"配上机制**：一个工作树内的运行锁（超时等待 + 明确提示"另一个真实宿主套件正在运行"）或运行登记文件。没有机制时，这句话对 agent 是**空指令**（行为等价于不存在），要么给机制，要么删。

## 3. 自动化检查（guardrail）缺失：仓库自带命令，但没有一处自动执行它们

**事实**

- 本工作树根无 `.github/`（无 CI workflow）、无 husky/pre-commit、无其它 hook 配置；`package.json` 有 `typecheck`/`test`/`test:dock`/`test:framework` 脚本，但**没有** `lint`。
- 全部验证在本轮与历史各轮都靠 agent 自己"记得跑"；本轮的分区运行是唯一一次覆盖真实宿主套件的检查，而它的失败（环境型）**不是**检查本身能区分的：命令退出码 1 与行为回归无法自动分开。
- 未检查远端是否存在其它 CI 配置（我只看了本工作树；`.github/` 若被跟踪则各 worktree 相同）。

**建议**

1. 低成本接线即可获得常驻 guardrail：pre-commit（或最小 CI job）跑 `bun run typecheck` + 受影响分区；这套命令已经存在，只差 wiring。
2. 对真实宿主套件区分"环境型失败"与"回归"：给这类套件加一个**可重试判定**层（例如 harness 级 1 次自动重试并在报告中标注 `retried`），否则每次环境抖动都会消耗一次人工归因（本轮约 8 分钟）。注意这与"不重跑以确认用户报错"的原则不冲突：这里重试的是**基础设施型**失败，且必须留痕。
3. 若采纳 §1 的静态状态，另可加一个极便宜的自检：票首行状态与未勾选项一致性检查（人类项未勾 + agent 项全勾 ⇒ 必须带"待人类"状态）。
