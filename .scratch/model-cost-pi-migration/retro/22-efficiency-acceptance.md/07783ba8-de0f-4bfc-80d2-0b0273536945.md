## 1（高）接手实例重复跑"已验证入口"——仓库已有复用规则，派发契约把它压过去了

- **事实**：本票的 Agent 侧在实例 1 就已交付完（`efb03e0` 实现 + `6420e21` 证据）。实例 2 在 `6420e21` 上重跑了全部入口（S1 采样 5 次、所属分区 `tests/harness-dock` 93 pass / 220.8s、`tests/model-cost` 463 pass、`tests/framework` 481 pass），记为证据 §8 + `385dd6d`。我在 `385dd6d` 上先证明了源状态未变（`git diff --name-only 6420e21 385dd6d` 只含 `.scratch/`），**仍重跑了** 1 次 S1 采样、2 次对照、真实宿主 3 例两次（12.76s / 12.17s），记为 §9 + `44a4b96`。写本复盘期间，同一个 worktree 的 `.scratch/model-cost-pi-migration/evidence/logs/` 里又出现了 `22-takeover-d-{typecheck.log,baseline.log,after.json,reproduction.txt,comparison.txt}`。
- **事实**：`docs/agents/testing.md` 已写明该规则：*"Reuse an earlier result only when the relevant source, fixtures, dependencies, and environment are unchanged; cite its scope and source state. Rerun after relevant changes, an unstable observation, or an explicit acceptance requirement—not just to reproduce a summary table."* 也就是说，规则不缺，缺的是"接手时该怎么做"的操作路径。
- **推断**：矛盾来自派发契约的措辞。本票派发写的是"自行负责本票验收并报告实际验证"，实现代理会把"负责验收"读成"必须亲自重跑一遍"（我也这么读了），于是每多一个接手实例就多一轮同结论的采样与宿主运行。**推断**：`22-takeover-d-*` 是第 4 个实例的同类复核（顺序由我两次列目录的时间差判定，非直接观测其进程）。
- **建议**：把接手契约改成正向句式——"接手时先用 `git diff --name-only <上轮 head> <本 head>` 证明源/夹具/依赖/环境未变；未变即复用既有证据并引用其 scope 与 source state；仅在源状态变化、观测不稳或票面明确要求时重跑"。可选地把这步机械化为一条 5 行命令（或票据模板里的固定段落），让"是否该重跑"由一条可核对的判据决定，而不是每轮重新判断。

## 3（高）证据日志可被静默截空：`process.exit()` + 管道

- **事实**：我用 `subprocess`（`stdout=PIPE`）跑 `bun run compare:efficiency …`，得到 **0 字节且 exit 0**；同一条命令经 `bash` 工具（PTY）打印出完整报告；改成"stdout 重定向到文件句柄"后得到完整 7879 字节日志。
- **推断（未验证到源码层）**：这些入口以 `process.exit(await main())` 收尾，而管道/套接字上的 stdout 写入是异步的，`process.exit()` 会丢掉未刷出的缓冲；写普通文件是同步的，所以不丢。
- **影响**：本工作流是证据中心的。我差点提交一份 0 字节的"对照复现"日志，**没有任何检查会发现它是空的**——它会被后来的复核者当作"报告为空"或"没证据"。
- **建议**：在 `docs/agents/testing.md` 的 "Keep runs attributable" 第 4 条（*"Save long-run output to a run-specific log…"*）旁补上本仓可用的正例："把 stdout 重定向到文件（同步）或使用 PTY；不要用管道收集一个以 `process.exit()` 收尾的 CLI 报告——会得到空文件。" 可选：在票完成/集成阶段加一条一行检查（被引用的每条日志非空、且含判决行）。

## 4（中高）三个受保护文件的 CRLF 陷阱，且失败信息不指向病因

- **事实**：该 worktree `core.autocrlf=true`；`bun.lock` 与两个 `host-patches/*/patch.diff` 在 `git status` 中恒为 ` M`，但内容与 HEAD blob 逐字节相同（我实测：文件大小 = `git cat-file -s HEAD:<path>`，`git hash-object --path=<path>` = HEAD blob id）。
- **事实（转述上一轮证据，未由我复现）**：上一轮 §2 说明 1 记录，这三份文件被检成 CRLF 时，dock 分区有 12 个用例以 `patch touches no file` 失败，需要手工改回 LF 字节才恢复。也就是说 **`git checkout`/`git restore` 这三份文件会打断 12 个测试，而症状看起来像产品缺陷**。
- **事实**：本仓没有 `.gitattributes`（已验证缺失）；但 `tests/harness-dock/baseline.ts` 已有 `verifyArtifactByteIdentity` / `sha256File` 与 `framework/docs/harness-baseline.json` 的 sha256，即"字节漂移"本身是可检的。
- **建议**：给 `bun.lock` 与 `host-patches/**/patch.diff` 加最小 `.gitattributes`（如 `bun.lock text eol=lf`、`*.patch.diff -text`），让检出字节稳定；并让 dock 的失败信息或基线检查直接点出"检出为 CRLF"。**未验证**：`.gitattributes` 能否完全消除该失败模式（我没有试改）。
