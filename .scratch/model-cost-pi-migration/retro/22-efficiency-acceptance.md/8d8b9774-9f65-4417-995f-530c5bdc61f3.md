## 1. 【事实+推断，严重度高】`core.autocrlf=true` + 缺 `.gitattributes`：每轮复发的 CRLF 陷阱，且带一个静默打坏 dock 用例的地雷

**【事实】** `git config --show-origin --get core.autocrlf` → `file:E:/Developer/myhub/my-agent-toolkit/.git/config true`（仓库自身配置，非本 worktree 局部）；仓库根无 `.gitattributes`。本轮 `git status` 恒显示 ` M bun.lock`、` M host-patches/omp-18.5.0-codex-response-boundary/patch.diff`、` M host-patches/omp-18.5.0-viewed-session/patch.diff`，而三者工作树字节与 `HEAD` blob 逐一相等（`git cat-file -s` 与 `git hash-object --path=` 均相等），是检出 stat 缓存现象。为此我花了两次工具调用核验，并必须在交接说明里写"不要 checkout/restore 这三者"。前 3 轮接手报告（§2 说明 1、§8 说明 2、§9）各自都记了同一现象，等于每轮都付一次税。

**【事实】** `tests/harness-dock/*-harness.ts` 与 `*-artifact.test.ts` 直接从工作树读 `host-patches/.../patch.diff`（`path.join(REPO_ROOT, "host-patches", …)`、断言 `patch.file` 的字面路径），并有 frozen record 对 patch 文件做 sha256 校验。**【推断】** 因此一旦有人 `git checkout -- host-patches`（清理工作树时最自然的反射），检出的 CRLF 字节会改变文件内容/校验值，静默打坏这 12 个 dock 补丁/基线用例。**【未验证】** 这次失败的具体数目与报错（12 例、"patch touches no file"）来自前几轮已提交证据，我本轮未复现。

**建议（确定性修复，一行配置）**：在仓库加 `.gitattributes`，对这些路径关闭文本转换，例如

```
bun.lock                    -text
host-patches/**/*.diff      -text
```

这会让检出直接得到 LF：`git status` 不再有假改动，也不用再靠 `git cat-file` 重写字节来救 dock 用例。等效替代：在创建工作树的脚本里对该仓库设 `core.autocrlf=false`（用户/仓库级，不动仓库内容）。**【未验证】** `.gitattributes -text` 的落地效果我未实测。

## 2. 【事实+推断，严重度高】复用规则只管"源有没有变"，不管"数字本身对不对"——一个错误读数穿过了三轮验收

**【事实】** `docs/agents/testing.md` 的复用段只要求 source/fixtures/dependencies/environment 未变即可复用，并明确说"不要只为复现一张汇总表而重跑"。三轮接手（§8、§9 以及本轮之前）都照此办：核对 `git diff --name-only` 只含 `.scratch/` → 判定"源状态未变" → 复用上轮数字。本轮我用一条**不同的方法**（`git ls-tree -r` + `git cat-file --batch` 逐 blob 数 `0x0a`，不经被测入口）复算，发现产品面复杂度 after 应是 **23773** 而非已发布的 **23772**（`framework/adapters/omp/session/facts.ts` 以空行结尾，实际 279 行被 `git grep -c ""` 读成 278），即 §4 的 `+4485` 应为 `+4486`。该错误在此前的提交里存活了三轮。

**【事实（同一根因的另一面，且是我自己的疏漏）】** 我本轮为了让"新旧一致"而重跑的 S1 采样与真实宿主效果计数，用的仍是**同一个入口/同一个记录器**；按上面的标准，那只是同一偏差的重复观测，不构成独立证据。序列/效果计数是否也存在同类口径错误，本轮**未验证**。

**【推断】** 团队里"重跑一遍 = 再确认一次"的直觉，在这里恰好掩盖了口径级错误：同一个工具只会重复自己的偏差。

**建议（`docs/agents/testing.md`，属于判断性流程规则，难自动化）**：在复用段补一条，措辞可以用一个 leading word 收口：

> **测量值**（区别于测试结果）在被采信前，至少要用**另一个方法**独立复算一次；用同一个工具再跑一遍只是同一观测。复用时同时说明"哪一项是独立复算的"。

这比"多跑几遍"更能挡住本次这类缺陷。

## 3. 【事实，严重度高】仓库自身没有任何 guardrail：`typecheck` / `test` 存在但没被接线

**【事实】** 仓库根没有 `.github`（连目录都没有）、没有其他 CI 配置、没有 lint 配置（无 biome/eslint/prettier）、`package.json` 里没有 husky/lefthook 之类的钩子管理；`package.json` 有 `typecheck` 与 `test`，但没有任何自动触发点。本轮我在一次 220s 分区运行中改了脚本，靠**自己记得**才 kill 重跑——若换成类型错误或测试红，不会被任何自动关卡拦住。

**【未验证】** 链接工作树看不到公共仓库的 `.git/hooks`，是否存在非 sample 钩子未核实。

**建议**：加最小 CI job（或让工作流在合入 gate 上强制）跑 `bun run typecheck` + `bun test`（分区串行），先把"已存在但未接线"的两个命令接上；需要 lint 再补 biome + `lint` 脚本。这是"检查已存在却没生效"的典型，不是新造轮子。

## 4. 【事实，严重度中高】对照入口的行计数规则没有任何测试，而缺陷恰好是"形状相关、聚合里看不见"

**【事实】** 全仓没有测试 import `scripts/efficiency-comparison.ts`（`grep` 结果里只有 `package.json`、脚本自身与证据文档引用它）；缺陷只在"以空行结尾的 blob"这一形状上出现，且只在**逐文件**比对 4 个 revision × 302 个模块时才暴露（唯一差异 1 行）。也就是说：跑得再多、聚合表看起来再稳定，都掩不住它。

**建议（确定性检查，替代规则）**：把行计数规则抽成可测的 seam，例如 `scripts/support/line-count.ts` 导出一个纯函数，再在 `tests/support/`（该目录已存在约定）加三条用例：

- `a\n\n` → 2 行（末行空行要算）
- `\n` → 1 行（整文件只有空行）
- `a`（无结尾换行）→ 1 行

这三条正对着 `git grep -c ""` 那类错误的三处行为，成本极小、形状判别力最高。

## 5. 【事实，严重度中】重活运行期间的树被改动，导致 220s 所属分区跑了两遍、被我 kill 两次

**【事实】** `docs/agents/testing.md` 已写明"运行结束前不得改动被测源码与 fixture"；我仍然在 suite 运行中先做了一次**真代码修改**（整理 ls-tree 解析循环），kill 重跑；随后又在一次运行中做了一次**注释修改**，再次 kill 重跑。两次都是我自己意识到"证据会被污染"才处理，靠的是记性而不是机制。

**【建议（优先给检查）】**：加一个很薄的包装入口（如 `scripts/partition-run.ts`）：跑前记录 `HEAD` + `git status --porcelain` 的哈希，跑后重新比对，漂移就打印 `tree changed mid-run: evidence not attributable` 并非零退出。同时把操作口径写进 `docs/agents/testing.md` 那句规则旁边："先把改动落成 commit 再开跑；要改就先 kill 当前运行。" 本次没有产生错误证据（污染轮我弃用了），但差一点就采信。

## 6. 【事实，严重度中】用户规则 `ts-set-map` 在合规代码上误报，注入的提醒有把正确 `Map` 推向 `Record` 的风险

**【事实】** 我对 `revisionLines` 的 `edit` 调用触发了该规则的 system-reminder；但规则正文说的正是"静态字符串键查表用 `Record`；动态/运行时插入删除用 `Map`"，而我的 `Map` 是从 git 输出运行时构建的，属合规用法。提醒以"后续工具调用必须遵守"的口径注入，一个不细读正文的实现者可能把动态 `Map` 改成 `Record`，造成真实回归。

**建议**：收紧触发条件到真正有问题的形状（例如对象字面量初始化的查表、或同一函数内多个字面 `.set()`），或让这类规则以非注入方式呈现，避免"规则为真、触发为假"。
