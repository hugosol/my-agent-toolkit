## 事实依据（本轮直接观察）

- **worktree 起点没有依赖**：第一次 `bun test tests/model-cost/pi-session-context.test.ts` 报 `Cannot find package 'yaml' from ...framework/core/config.ts`；`bun install` 后 13 个包装好，此后所有测试才可跑。`docs/agents/testing.md` 与票据都没提这一步。
- **`package.json` 的自动检查面**：只有 `test`/`test:framework`/`test:dock`/`test:codebase-tools` 等脚本、若干 smoke、以及 `typecheck`；**没有 lint 脚本、没有 `.github`（无 CI）、没有 pre-commit hook（`core.hooksPath` 未设，无 `.husky`/`.githooks`）、没有任何 linter 配置**。本票实际跑的是手工 `bun run typecheck` + `bun test <分区>`。
- **两个分区在本 worktree 因环境条件不可用**：`tests/harness-dock/*`（OMP dock）无法启动，原因是 `host-patches/omp-18.5.0-viewed-session/patch.diff` 被检出为 CRLF（报 `patch.diff touches no file`），19 的证据里也记了同一条件；`tests/connect-bot/panel-registration-lifecycle.test.ts` 有 5 例因缺 OMP bot 工件失败（`tests/connect-bot/support/omp-bot.ts` 抛 “omp bot binary” 不存在）。两者都与本票改动无关，但都会让“最终集成跑 `bun run test`”天然变红。
- **真实宿主脚本的用法在本机是错的**：脚本头写着 `bun scripts/pi-subagent-smoke.ts --pi <path>`，而 `--pi D:\nvm4w\nodejs\pi.cmd` 被吃到成 `D:nvm4wnodejspi.cmd`，报 “no pi CLI could be resolved from it”；可用形式是 `PI_CLI="D:/nvm4w/nodejs/pi.cmd"`（正斜杠/env）。脚本头没有提这个。
- **脚本头自述的限制与真实原因不符**：`scripts/pi-subagent-smoke.ts` 的头注释说“前台委派到不了后面的检查，原因是它复现的 stale-context 故障”；实际中断原因是**脚本自己的脚本化缺陷**（`respond` 对每个带 subagent 工具的请求都回委派调用 → run 永不 settle → 第 2 阶段 90s 超时直接终止整脚本）。我为定位它跑了 3 次真实宿主运行，最后加了 `delegationOnce` 才让脚本能走完。
- **上一票的“遗留故障”定位成本**：本票要修的那处 stale-ctx 问题，在 `evidence/05-subagent-facts.md` §3.3/§6.1 里已明确写“落在 pi 前端/装配线（[02]/[20] 范围）”。但票据本身只指向 contract 与 spec，没有指向 05 的这一节；找到它需要通读 05 全文。
- **TS 规则以“飞行中打断”形式到达**：`ts-no-tiny-functions`、`ts-no-any`、`ts-set-map`、`ts-no-return-type` 四条规则在我写完代码后由宿主注入，命中了刚写的 `widgetLines` 一行助手与 `ReturnType<typeof sessionHeader>`；两条各改一次并复跑。仓库里没有这些规则的可见来源（AGENTS.md/文档库里没有，也没有 linter 会拦）。
- **真实主机才暴露的两处缺陷**：39 文件/453 例 hermetic 分区在缺陷存在时全绿；两处缺陷（spawned session 自己的实例不做共同记账准备；会话结束后 Round 复检读失效 ctx）只在真实 pi 1.2.0 前台委派里出现，靠一个临时探针（`console.error` 到 stderr）才定位到“pi 每会话求值一次、同进程第二次求值”这一事实。

## 建议（按严重度）

### 1.（高）worktree 开局先 `bun install`，并把它写进测试约定
现象：首次测试因缺 `yaml` 直接失败，浪费一轮工具调用；`docs/agents/testing.md` 只说“跑 `bun test <file>`”。
建议：在 `docs/agents/testing.md` 的 “Select a tier” 上方加一行前置条件（例如：新 worktree 先 `bun install`——依赖由 `bun.lock` 固定），或在 worktree 派发流程里预装。指向性文案用环境事实而非复述 lockfile 内容。

### 2.（高）给仓库补一个真 guardrail，并把两条环境盲点集中记录
现象：仓库唯一的检查是手工 `bun run typecheck` 与 `bun test`；无 CI、无 hook、无 lint。同时两条环境条件（OMP dock 的 CRLF patch、connect-bot 缺 bot 工件）让“最终集成全绿”不可达，而每张票都要重新发现一次。
建议分两步：
- 在 `docs/agents/testing.md`（或 `AGENTS.md` 的 testing 指针正文）里集中记录这两条**本 worktree 的环境条件**及其表现（`patch.diff touches no file`；`omp bot binary`），并写明“这两条不算本票失败”。这正是“缓存环境查不到的东西”，符合 cache 的用法。
- 给不可用分区加守卫：`tests/harness-dock/*` 与 `tests/connect-bot/panel-registration-lifecycle.test.ts` 用 `test.skipIf(<环境不可用>)` 各自 skip，或把环境条件做成显式前置断言，使 `bun run test` 的红只剩真实回归。最小成本优先于新 CI 框架；若加 CI，就让它跑 `typecheck` + `test`。

### 3.（中）修真实宿主 smoke 的用法文案与失败诊断
现象：`--pi <path>` 在 win32 上吃反斜杠；脚本头自述的限制与实际中断原因不符；阶段失败直接抛异常终止，后续阶段不可见。
建议：
- 把脚本头的 Usage 改成 `PI_CLI=<path> bun scripts/pi-subagent-smoke.ts`（或说明用正斜杠），并在 `--pi` 解析处对反斜杠做规范化。
- 让每个 phase 包住自己的超时并在抛错时打印阶段名与已观察项（现在只有一个裸 `PiSessionError`）。
- 把“一次性委派”的脚本化提炼成共享 helper（本票新增的 `delegationOnce` 就是这个形状），避免下一个脚本再踩“每个请求都委派 → 永不 settle”。

### 4.（中）票据继承上票遗留阻塞时，带**节号指针**
现象：本票真正的入口条件是 05 §3.3 的遗留故障，票据只指向 contract/spec；通读 05 才找到。
建议：在票据模板或本类票据的 “Blocked by/执行与证据约束” 里加一条：若本票要结清某前票记下的遗留/已推迟缺陷，写一行 `见 evidence/<NN>.md §<节>`。这是最便宜的导航指针。

### 5.（中）让 TS 规则在写之前可见（或可检查）
现象：四条 `ts-no-*` 规则通过飞行中打断到达，命中已写代码，两次返工。
建议：把仓库要执行的规则放进实现代理会读到的地方（若已有 `CODING_STANDARDS.md` 之类的评审文件，则在其上给实现侧一个指针；否则把四条并入仓库 linter 配置）。纯机械规则（禁 `any`、禁 `ReturnType<typeof f>`、静态字符串表用 Record）优先落成检查，而不是靠代理记性。判定口径：能在写第一版时避免，就不要靠事后规则注入。

### 6.（低）为“承诺/症状 → 真实宿主入口”建一个小索引
现象：本票的判断几乎全部依赖真实 pi 运行（前台委派、退出、存储根对照），而入口分散在 `scripts/pi-model-cost-smoke.ts`、`scripts/pi-subagent-smoke.ts`、`scripts/pi-session-accounting.ts` 等多个脚本，各自头注释就是文档。
建议：在 `docs/agents/testing.md` 加一张短表：症状/承诺 → 脚本 → 运行方式（含 win32 的 `PI_CLI`）。这是把“环境里的昂贵查找”缓存成一行指针，而不是复述脚本内容。

### 7.（低，推断）大文件探索：给 codebase-memory 的 outline 一个指针
现象：本轮为读懂装配线连续 ranged-read 了 runtime.ts（671 行）、binding.ts（484 行）、adapters/pi.ts（804 行）等；宿主虽在每轮提示“先看声明大纲/符号片段”，但仓库文档里没有任何地方告诉实现代理这套工具的用法。
建议：在 `docs/agents/testing.md` 或 `AGENTS.md` 的探索段加一句指针（“读 >100 行源码前先取文件 outline/符号片段”），并说明 MCP 服务名。属推断：没有对照组证明它一定省 token，但本轮确实用 `grep -n` 手工模拟了 outline。
