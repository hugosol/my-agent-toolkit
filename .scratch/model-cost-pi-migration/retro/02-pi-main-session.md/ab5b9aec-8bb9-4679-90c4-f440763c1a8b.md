## 1（高）仓库没有任何自动守卫，pi 真实验证脚本也没接进脚本表

事实：根目录无 `.github`（无 CI workflow）、无 `.husky` 或任何已装 git hook、无 biome/eslint/prettier 配置；`package.json` 有 `typecheck`/`test` 等命令，但没有任何东西自动跑它们。同一事实的第二个面：`scripts/pi-codebase-tools-smoke.ts` 与新增的 `scripts/pi-model-cost-smoke.ts` 都**不在** `package.json` 的 `smoke:*` 列表里（现有表里有 `smoke:http-transport`、`smoke:model-cost-data` 等，唯独没有 pi 的两个）。

代价与推断：本轮我通过「用未改动的 HEAD 版本重跑」才发现 codebase-tools smoke 在 Windows 上早已失败（`exit 9`、`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)`）。事实是该脚本在改动前后一致失败；推断是它长期没有被任何自动流程执行，因此坏掉也不会有人知道，而后续每个跑到它的 agent 都要重新举证一次。

建议：
- 加一个最低限度的 CI job（或 pre-commit hook），只跑 `bun run typecheck` 与 `bun test`；两个迁移票已经依赖手工运行测试，这是全功能的常驻风险。
- 把两个 pi smoke 加进 `package.json`：`"smoke:pi-codebase-tools"`、`"smoke:pi-model-cost"`，让它们可被发现、可被同一守卫按「需要 pi 已安装」的条件（或 nightly）执行。
- 与本轮记录一致地记下已知失败：在 `scripts/pi-codebase-tools-smoke.ts` 头部的既有「不能断言」小节里补一条「Windows 上子进程关闭会得到 exit 9 + libuv 断言，改动前后一致」，避免下一个 agent 重新举证（我为此花了 3 次工具调用加一次临时文件复制）。

## 6（中）一个机械错误可以靠确定性检查提前发现：对象字面量的常量键

事实：我写下 `extraEnv: { PI_MODEL_COST_CONFIG_ROOT_ENV: actualRoot }`，本意是计算键。TypeScript 不报错（在对象字面量里这确实是合法属性名，长度为正确行为），`bun run typecheck` exit 0，错误只在真机上由 fixture 的**显式**环境变量守卫暴露（`PI_MODEL_COST_CONFIG_ROOT is required by the dock's pi model-cost fixture`），代价是 2 次真机运行加一次排查。
建议：若 repo 决定引入 lint（见第 1 条），把「对象字面量里出现全大写常量形键」判为需计算键的机械规则；这是固定语法模式，适合确定性检查而非 review 规则。若暂不引 lint，也可在 `CODING_STANDARDS.md` 加一条给 review agent 的判断点（优先级低于第 1 条，因为这类错误在真实路径上会立刻炸响）。

## 7（中低）工具经济：`package.json` 的读取被摘要化，长文件读法有成本

事实：`read package.json` 与 bash `cat package.json` 都返回摘要（scanner 视图），我在三次调用后才用 `node -e "…scripts"` 拿到脚本表；读长源文件时非 `:raw` 的 `read` 会省略中间行（本轮 `framework/adapters/pi.ts` 首次读就返回 `[…178ln elided]`），必须再读一次 `:raw` 区间。
建议：在 agent 常读的文档里给两条一行指针——清单文件用 `read package.json?q=.scripts`；长源文件直接按 `:raw` 区间读。这是工具层的小摩擦，但每轮都在付。

## 8（低）两条宿主规则的误报，值得在规则层面收敛

事实：`ts-no-tiny-functions` 在我写的 `report(signal, ctx)`（两个调用点、承载「共同框架 + 延迟静默读」的 lockstep 语义，且 OMP 侧存在同名同形的既有实现）上触发提醒；`ts-set-map` 在一个真正动态成员的 `Set<string>` 上触发提醒。两者都是规则按工具参数匹配、未考虑语义与既有同形代码的误报。
建议：规则里加入「与仓库内既有同形实现一致时不报」或「同名集合若含 `.has/.add` 动态成员则不报」的豁免；否则执行 agent 会为规避误报而偏离既有约定（我这次选择跟既有 OMP 写法保持一致）。
