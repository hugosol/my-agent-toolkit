## 1. 最高：仓库没有任何 guardrail，tsconfig 也未开死代码开关——本轮离"静默跳过秘密清除"只差一次自审

**事实**
- 工作树内不存在 CI 配置（无 `.github`，也无 `.gitlab`/`.circleci`），共享 gitdir 的 `hooks/` 只有 `.sample`，`core.hooksPath` 未设置。
- 没有任何 linter/formatter 配置（无 biome/eslint/prettier/oxlint），`package.json` 的 `scripts` 无 `lint`；已有 `typecheck`、`test`、`test:dock` 等脚本**没有任何东西自动运行它们**（"已存在但未接线"）。
- `tsconfig.json` 有 `strict: true`，但没有 `noUnusedLocals` / `noUnusedParameters` / `noUncheckedIndexedAccess`。
- 本票新增约 700 行脚本，唯一自动反馈是 `tsc --noEmit` 与我自己写的 9 个用例。首版草稿在 typecheck 全绿的情况下带着：未使用的参数（`recordOfCredential(_catalog, …)`）、同一 `instantsOf(at)` 的三次重复展开，以及一行 `const secrets = scenarios.flatMap(() => [])`——它让落盘前的秘密清除变成**静默 no-op**（类型上完全合法、被使用、可通过），只有我自己重读时才发现并重写。这个文件是本仓库唯一读取真实 provider 凭据的地方。

**建议**
1. 给 `tsconfig.json` 加 `noUnusedLocals`、`noUnusedParameters`（机械、确定性；先跑一次 `tsc --noEmit` 量出存量报错再决定一次性清理还是分批）。**[推断]** 存量会有一批报错，规模未测。
2. 为仓库加**一个** check 入口（例如 `bun run check` = `typecheck` + 快的分区测试），并至少接到一处：最小 CI workflow（`bun run typecheck` + `bun run test`）或 `.githooks/pre-commit`（`core.hooksPath` 指向仓库内目录），二者择一即可覆盖。**[推断]** 全量 `bun run test` 在当前树的稳定性未知（本票按票面要求未跑，属最终整合范围）；若采用 CI，建议 CI 跑全量、钩子只跑 typecheck + `tests/model-cost` 这类秒级分区，避免 100s+ 的 dock 分区卡住每次提交。
3. 针对"静默 no-op"这一类（合法但无行为）没有现成规则可一键覆盖；补上 `noUnusedLocals/Parameters` 与"报告类脚本的清除必须落在写盘前的一次调用上"这条**审查规则**（这条属判断类，放 `CODING_STANDARDS.md` 而非自动检查）。
