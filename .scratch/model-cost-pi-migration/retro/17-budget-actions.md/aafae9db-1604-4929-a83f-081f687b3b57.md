## 1（高）自动检查在本环境静默失效：host patch 解析器 × CRLF 工作树

- 事实：`tests/harness-dock/host-patch-artifact.ts` 的 `patchTouchedFiles` 逐行用 `/^diff --git a\/(.+?) b\/(.+)$/` 匹配；本机 `core.autocrlf=true` 让 `host-patches/*/patch.diff` 的工作树是 CRLF，而 JS 正则的 `.` 不匹配 `\r`，于是**任何** `ensureViewedSessionHarness` 的 dock 文件在 setup 阶段就抛 `…patch.diff touches no file`（首次运行 `tests/harness-dock/detail-tree.test.ts` 即如此）。整个 OMP 真实宿主分区在 Windows CRLF 工作树上跑不起来。
- 事实：冻结记录可作独立校验——`record.json` 的 `patches[].sha256` 等于该 patch 的 **LF** 字节哈希（本地比对：CRLF `057e01f6…`，LF `66195465…`，记录 `66195465…`），所以改回 LF 既能跑、又不破坏冻结校验；代价是 `git status` 显示该文件被改（本轮提交前已 `git checkout --` 还原）。
- 建议：修根因——解析器容忍行尾（分片后去掉行尾 `\r`，或正则用 `\r?$`）；外加 `.gitattributes` 对 `host-patches/**/patch.diff` 固定 `eol=lf` 防复发。这条比"补 CI"更值：LF 检出（典型 Linux CI）看不到该 bug。
- 未验证：`.gitattributes` 方案对既有 materialize 缓存前缀的影响未实测。

## 2（高）testing.md 只讲"跑哪一层"，没讲"跑起来需要什么"

## 4（中）缺一条"如何在 pi adapter 上写测试"的参考

事实：为把三个既有 pi 套件判断清楚，本轮自己反推出四条隐性事实，各花 1–3 轮：

1. 框架的已验证配置**按 extension id 每进程只读一次**（`framework/core/config.ts` 的 `validatedConfigs`）：套件因此自组部件而不绑 shipped 装配；同进程换 storage root 只能走运行时输入。
2. `pi-subagents` 的 required-child-extensions 注册表**按 sessionId 每进程只能注册一次**（`node_modules/pi-subagents/src/shared/required-child-extensions.js`）：任何要 `subagents` 模式的套件必须每用例不同 session id，否则第二次绑定结出 `failed`。既有 `tests/model-cost/pi-terminal-rounds.test.ts` 今天就因此在测试输出里反复打注册失败诊断（事实，非推断）。
3. 会话**身份**（名字/直接父）只由 `remember` 的调用者建立（turn 开始、用户输入、改名）或由已保存文档提供，单独的 `session_start` 不建立身份——本轮为此刻意在 P5 与 P47 各吃一次红（`presentation.of(target).form` 意外为 brief，因为身份未知同样答 brief）。
4. 接入模式只能由 provider 自己的发布通道（`subagents:rpc:v1:ready`）真实结出，`piAdapter` 没有注入点。

建议：把这四条写进 `docs/agents/testing.md`，或写一个 pi 测试参考文件并由 testing.md 指过去；把"要 subagents 模式⇒每用例独立 session id、用同一条发布通道结答案"写成短线导航指针。收益最大：本轮近一半探索成本属这一类。
