## 1（严重）仓库没有任何 guardrail，而 Windows worktree 的 CRLF 检出使真实宿主分区整体不可用

**事实**

- 仓库无 `.github/workflows`、无 `.githooks`/`.husky`、无 `.gitattributes`、无 lint 配置；`package.json` 只有 `test`/`test:dock`/`test:framework`/`typecheck` 等脚本，没有任何东西自动运行它们。
- 本 worktree 以 CRLF 检出，本轮 `bun test tests/harness-dock` = **45 pass / 12 fail**（173.6s）：12 条同属一类 —— 宿主补丁物化器与 lockfile/baseline 校验按 LF 写死（`host-patches/omp-18.5.0-viewed-session/patch.diff touches no file` ×8、`omp-18.5.0-codex-response-boundary/…` ×2、baseline 的 lockfile/artifact 检查 2 条）。ticket 04 的证据记录了同一失败类与同样计数（**事实**：我在自己的证据文件里引用它时核对过同环境事实，但**未验证**该记录的原始运行条件是否逐项相同）。
- 同一天同一脚本里还有一条既有 race：smoke 的 `filesUnder` 在写入方锁目录 `consumption.json.lock` 于遍历中消失时抛 `ENOENT`，本轮第一次跑 smoke 就死在 phase 1（与 ticket 14 无关的代码路径）。

**推断**：这两件事都不是本 ticket 引入，但每个在 Windows worktree 上跑 pi smoke 或 dock 分区的 ticket 都会各自重新发现一次、各自决定要不要在共享文件里打补丁 —— 同级的兄弟票 `03-request-pricing-roundsmd` 当时正在「Fixing flaky filesUnder helper」，即同一处 race 至少被修两遍。

**建议**

1. 加 `/.gitattributes`：`host-patches/*.diff -text`（或 `eol=lf`）与 `bun.lock text eol=lf`。一个文件、一次修复，直接消灭「dock 分区在 Windows 检出下不可用」这一类失败。
2. 给仓库一个 `check` 脚本（`bun run typecheck && bun test`），并由 pre-commit hook 或 CI 调用；dock 分区耗时且需要宿主工件，宜单独一条 job 并显式命名，而不是混进默认 `bun test`。
3. `filesUnder` 这类纯测试支撑的 race 由集成分支一次性落地（或由 smoke 作者在集成分支修），避免各票重复 hunks；本 ticket 的 hunk 是可弃的——只要集成分支有此修复，合并时可取其一。

**推断**：这是本次探索成本的最大单项来源（读取 spec/contract/前票证据/驱动与 dock 约定，约前 15–20 次工具调用都在找「pi 的真实宿主检查应该写在哪、怎么跑」）。

3. 顺手修正 `tests/harness-dock/index.ts` 的「唯一 import 面」表述，或把 `pi-session.ts` 一并从 index 导出。
4. 若希望真实宿主检查随 `bun test` 一起被守护，可把本 phase 也写成一个 `tests/harness-dock/pi-*.test.ts`（复用同一 fixture，CLI 缺失时 skip）；两种形态并存前先确定哪一种算权威，避免同一行为两处维护。

## 4（中）smoke fail-fast + 共享 helper 的 race：一次无关 flake 会毁掉整轮真实宿主证据

**事实**：本轮第一次 smoke 运行在 phase 1 因 `filesUnder` 的 `ENOENT` 中止，尚未进入本票的 phase；smoke 的 `observe` 在首个失败即 throw，后续 phase 不执行，运行根保留供检查。

**推断**：在真实宿主检查昂贵（本票 4+ 个 pi 进程、最终 10s，但早期调试每次约 4–20s；dock 分区 173s）的前提下，任何前序 phase 的 flake 都会让本票证据归零重跑。

**建议**

- 让 smoke 在捕获失败后仍继续执行后续 phase，最后一次性汇总所有失败检查（保留退出码非零）。分阶段独立运行（`--phase codex`）也可，使单票只跑自己的 phase 而不受前序 phase 影响。
- 与本票相关的一个次生事实（**未验证**）：中途有一次运行输出「43 中 41 条通过后停止」，我用过窄的 grep 过滤丢掉了错误正文，之后 5 次运行均干净，因此未确认那次的失败检查；最可能是当时草稿里另一处 null 处理（当时的类型检查也确有 `possibly null` 报错），但这是推断。建议 smoke 的失败行使用稳定前缀并单独成行，便于事后逐字取回。

## 5（中）仓库自带 TS 风格规则没有任何机械执行面，违规只在写完之后以提醒形式到达

**事实**：本轮收到 `ts-import-type`（探针里写了 `import("...").Type`）、`ts-no-return-type`（`ReturnType<typeof readdirSync<...>>`）、`ts-no-tiny-functions` 的规则提醒，均发生在代码已写入之后，导致我回头重写。仓库无 lint 配置、无 lint 脚本。

**未验证**：这些规则可能来自宿主级规则包而非仓库自身，机械修复的位置（仓库 lint vs 宿主）本轮未查证。

**建议**：按复盘准则分类——`ts-import-type` 是**机械**模式，应当由确定性检查兜住，而不是靠写后提醒再返工；仓库侧最便宜的落点是把可用 lint 与 `typecheck` 合成一个 `check` 命令（见候选 1），宿主侧则在派发时就把这类规则交给实现 agent，而不是让它在文件中途发现。`ts-no-tiny-functions` 是启发式判断（我的 `declaredTtlMs`/`entriesOf` 因此被标记），如果确实要保持机械执行，值得在检查里给出可操作的判定（哪些形态必然违规），否则同一处会被反复提醒。

**事实**：`scripts/pi-model-cost-smoke.ts` 与 `tests/harness-dock/pi-session.ts` 都被 ticket 14 修改；兄弟票 13（DeepSeek 余额认证与刷新闭环）同样需要「pi 解析 provider 凭据 + 初始化/结算触发刷新」的宿主验证，很可能落在同一驱动与同一 smoke 里。派发时我看到的 roster 显示 13 已在「等待归一化全局套件」的集成阶段。我在改这两个文件之前**没有**给 13 发消息（当时评估为「先做完再说」，本轮未发）。
