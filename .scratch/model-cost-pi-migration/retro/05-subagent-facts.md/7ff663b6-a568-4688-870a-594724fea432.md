# 复盘：ticket 05（pi 子入口接入与可靠会话事实）

范围：仅本 ticket 的 TDD 实现轮（`run_id 7ff663b6…`，session `01a14392…`）的对话与工具结果。标注 **事实 / 推断 / 未验证**；缺失历史不补造。只提建议，不改任何文件。

## 1. 最高严重度：锚定「哪个宿主组合被验证过」的指针缺失（导航）

**事实**

- 本仓库存在 `framework/docs/harness-support.md`，其首段自称是“harness/package version compatibility 的唯一权威”，该文件已读内容明确记录：pi `@earendil-works/pi-coding-agent@1.2.0` 的已验证组合用 **Node 22.19.0**；**Node 24.18.0** 在多请求/EOF 探针上触发 Windows/libuv `UV_HANDLE_CLOSING` 断言退出 9（各 10/10 次，**带扩展与不带扩展都发生**），并要求用 `PI_NODE=<Node 22.19.0 executable>` 运行该已验证 smoke。
- 自动加载的 `AGENTS.md` 只用指针指向 `docs/agents/{issue-tracker,triage-labels,testing,domain}.md`；`docs/agents/testing.md`（本轮的测试分层权威，我读了）**没有**提到 `PI_NODE` 或该组合限制，也没有指向 `framework/docs/harness-support.md`。
- 本轮 6 次真实宿主运行全部通过 `resolvePiCli()` 默认的 `PI_NODE ?? "node"` 启动，即 **Node 24.18.0**（我没有读 `framework/docs/harness-support.md`，也没有设置 `PI_NODE`；该文件我是在写复盘时才第一次打开）。
- 本轮实际观察到的失败有两类：一类有明确未捕获异常栈（扩展自身 stale-ctx 崩溃），另一类是两次 90–142 s “等到 `agent_settled` 超时、没有任何 frame”的静默挂起。

**推断**：后者与文档记录的 Node 24 多请求/libuv 缺陷高度吻合，因此本轮记录的真实宿主证据可能混杂了“不受支持的宿主组合”这一独立原因；`evidence/05-subagent-facts.md` 里的环境行（已经写明 node 24.18.0、未写它不受支持）正好落在该文档警告的“未经认证组合”里。

**未验证**：我没有用 Node 22.19.0 重跑任何阶段，因此**无法**区分两类失败各自的比例；也没有确认 Node 24 的缺陷是否会在我的隔离运行形态下命中。

**建议**：把这条权威接进常驻上下文——`AGENTS.md` 增一行前置词为“真实宿主/dock”的指针，或在 `docs/agents/testing.md` 顶部加一句“任何真实宿主/dock 运行前先读 harness-support 权威并把 `PI_NODE` 设为其已验证 Node”。这是本轮最便宜、影响最大的一处环境修改：一行指针就能改变一个 ticket 的整段真实验证的有效性。

## 2. 结构性 guardrail 缺失：`.gitattributes` 使 dock 分区在 Windows 检出下不可用

**事实**

- 仓库根目录清单中没有 `.gitattributes`（本轮 `ls -a` 实测）；`package.json` 只有 `test`、`test:dock`、`test:framework`、`test:codebase-tools`、`typecheck` 与若干 smoke，**没有 lint/check 脚本**。
- 也没有 `.github/workflows`（实测不存在），即**没有 CI**。
- 其他 ticket 的证据记录（`evidence/04-shared-storage.md` §8，属既有记录，本轮未复验）把 `bun test tests/harness-dock` 的 45 pass / 12 fail 全部归因于 CRLF 检出：补丁解析 `split("\n")` 残留 `\r` 后一个文件都匹配不到，`bun.lock` 的 sha 只有在行尾规范化为 LF 后才等于 HEAD blob。
- 本轮因此没有跑 dock 分区（ticket 的“所属分区 + 真实 dock 文件”完成层要求实际上不可执行），改为自写 `scripts/pi-subagent-smoke.ts`；dock 里可复用的只有 `startPiRun`/`PiSession`/`capture-server` 这几个模块。

**推断**：任何在 Windows 上做 pi/OMP 真实宿主工作的 ticket 都要么重复发现这条环境事实，要么绕开 dock 自建入口——本 ticket 两者都发生了。

**建议**：一行 `.gitattributes`（例如 `*.diff -text`，`bun.lock text eol=lf`，或按需 `* text=auto`）永久解除该阻塞；这条修复的收益按 ticket 计，而不是按文件计。

## 3. 真实宿主探索的程序与信息通道（工具经济）

**事实**

- 在写耐用脚本之前，我先做了约 6 次一次性真实 pi 运行（每次 15–140 s），其中第一次因为脚本化应答反复给出 tool call，产生了成百上千个 `subagent-artifacts/outputs/*/context.md` 清单；`PiSession` 只把子进程 stderr 留在内存里，两次运行的完整 stderr 被控制台截断后**只能再跑一次**才拿到诊断（每次约 2 分钟）。
- 为弄清 provider 的公开总线上到底发了什么，我又写了一个临时扩展 `.scratch/rpc-probe/`（未提交，已删）才拿到 `ready` 与 `ping` 应答的真实载荷形状。
- 现成的 `scripts/pi-model-cost-smoke.ts` 从不驱动一次委派，`tests/harness-dock` 也没有子会话的既有形态可抄，所以“子会话文件长什么样、provider 自己记哪些创建事实”全部从零探得。

**推断**：这段探索占了本轮预算的很大一块（本轮两次软预算告停中的一次，正是发生在真实宿主阶段）。

**建议**：
1. 让 dock 的 `PiSession`/`startPiRun` 把子进程的**完整 stderr 落盘**到 run root（一个文件），让控制台截断永远不再需要重跑；
2. 在 `docs/agents/testing.md` 加一条“新宿主路径”的短程序：**先写带 observation 阶段的耐用脚本、跑一次、再扩展；不要用一次性探针迭代**（本轮若照此执行，可省下相当比例的预算）；
3. 让 `scripts/pi-model-cost-smoke.ts` 或 dock 提供“委派一个真实子会话”的最小能力，使后来的 ticket 不必重抄一遍脚本化 tool call 与捕获端点用法。

## 4. 机械规则只在宿主内生效：缺 lint 与 CI（guardrail）

**事实**：本轮有 4 条机械规则在工具调用处被拦下并要求改写——`ts-no-test-timers`（我在测试里写了 `Bun.sleep(50)`）、`ts-import-type`、`ts-no-dynamic-import`、`ts-no-inline-cast-access`。每次我都按规则改对了，但每条都花了额外的一次往返；仓库里没有 lint 配置（根目录清单实测无 biome/eslint/oxlint 配置）也没有 CI，所以这套保证离开本宿主就消失。`bun run typecheck` 确实存在且抓到了真实错误（我把 `session.ownerKey()` 当成 API 写进了 fixture）。

**建议**：把机械子集下沉为真检查——一个 lint 步骤（导入形状、动态导入、内联断言访问、测试内真实计时器）加一个 pre-commit hook 或统一的 `bun run check`，与既有的 `typecheck` 并列，供各分区脚本调用；`tsc` 已验证有效，把 lint 拉到同一习惯即可。

## 5. 票面尺寸：一个 ticket 同时承载 S1 映射与 6 场景真实宿主矩阵（规划）

**事实**：本票的验收条目要求真实覆盖“自主委派、嵌套、同名并发、后台、续跑、取消、历史继承与进程变化”，另加真实改名与启动快照；上一轮 WIP 的报告结尾写“run budget exhausted（300 requests 强制停止）”，本轮我在 200 requests 的软预算处被要求收尾，真实宿主阶段同样没有跑完。两次连续运行都没能完成宿主半边。

**推断**：S1 映射（可在本机确定性完成）与逐场景宿主矩阵（每次运行数十秒到数分钟、且每次都要独立事实对照）不是同一量级的交付。

**建议**：把宿主场景矩阵拆成独立票（或按场景一票），保证 S1 部分能落地，而宿主场景可以被逐项完成并单独记录。

## 6. 宿主事实缺少仓内落点（信息访问）

**事实**：本轮使实现正确的关键宿主事实，来源全在第三方包与运行产物里：`node_modules/pi-subagents/docs/agents.md` 的“Required host extensions”一节（每个会话只允许一次登记、通常随 `session_shutdown` dispose）、`docs/extension-api.md` 的 RPC 段（`ready`/`request`/`reply:<id>` 与信封形状）、以及一次真实运行的 `{runId}_{agent}_meta.json`（`parentSessionId`、`launchResolvedExtensions.required=["model-cost"]`）。仓内原本没有一处记录“`ready` 带 session、而本扩展先 settle 时 `ping` 应答的 `session` 是空”的形状差异，也没有记录子会话文件首行 `parentSession` 的实际写法——这些只在被删掉的一次性探针与我本轮的 evidence 里。

**建议**：把这批按版本钉住的 provider 事实提升到 `framework/docs/harness-support.md` 的一节（它已经是这类权威的自然归属），或另建同目录页并由该文件/A`GENTS.md` 指针指向，避免每个触及子会话的 ticket 重新探一遍。
