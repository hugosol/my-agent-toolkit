## 发现（按严重度）

### 1. 一张票的体量与一次运行预算不匹配，导致"实现完成、验收为零"（严重）

事实：ticket 同时承载 P3（接入模式与四类失败诊断）与 P11/P12/P13（子会话身份/父/名字/启动快照），要求 S1/S2/S3 三层覆盖，且 P11 的真实路径矩阵含"同名并发、嵌套、后台、续跑、取消、历史继承、进程变化"。我的执行顺序是"先把全部框架面实现完再写测试"，于是预算在第一个测试之前耗尽：typecheck 绿、既有 framework 400 测试绿，但本票新增行为**没有任何测试**，也没有票级真实宿主证据。

推断：这不是单纯的个人节奏问题。契约把 P3 与 P11–P13 放在同一票，二者共享 seam 但工作体完全不同（前者是接入/协议/诊断接线，后者是原生事实映射 + 真机场景矩阵）；票内又隐含"重新走一遍研究轮的场景矩阵，只是换成经适配器"这一大块。

建议：
- 拆票：把"接入模式/只读接入结果/四类诊断与释放"（P3）与"子会话身份/父/Owner/名字/启动快照"（P11–P13）分成两张票，各自带自己的 S1 测试与真机入口。
- 若必须同票：把 P11 的场景矩阵写成票内可勾选的清单项（同名/嵌套/后台/续跑/取消/fork/进程变化各一行、各带自己的证据行），让实施者能一眼看出体量并排优先级，而不是把它当成一个复选框。
- 运行预算可预知时前置告知实施者，使其能按"最薄的一刀先真机验证"排序，而不是先铺满框架面。

### 2. 缺乏"装载性第三方事实"的落点文档（严重）

事实：本票全部设计都压在几个第三方公开事实上，而它们分散在契约外的原始来源里：`docs/agents.md`（公开 subpath `pi-subagents/required-child-extensions`）、`src/shared/required-child-extensions.js`（按 sessionId 注册、`requireForAllRunners`、重复注册即抛错、`dispose()` 语义）、`src/extension/rpc.js`（`subagents:rpc:v1:ready|request|reply:`，`ping` 返回 version/capabilities/session）、`src/runs/shared/child-session.js`（子会话 `sessionStartEvent.reason="startup"`、header `parentSession`=父**文件**）。仓库侧唯一入口是 lighthouse 03/04/07 的决策文档与 research 07 的 `harness/observer.mjs`——后者实际上是最省时间的单件（它直接给出公开 API 的调用形状）。我为这些事实读了解包后的 ~10 个第三方文件，并跑了两次真机探针。

推断：下一位做 pi 子代理轴的实施者会重复同一段逆向工程。

建议：新增一份 reference 文档（例如 `framework/docs/pi-subagent-provider.md`），记录：固定版本与工件、公开 subpath 与 `registerRequiredChildExtensions` 的输入/失败语义、版本化总线通道与 `ready`/`ping` 载荷形状、子会话 header/`reason`/改名事实、以及"如何零费用真机驱动一次委派"的入口路径（含 research observer 探针与 dock 驱动的指针）。再从 pi adapter 目录或 pi 子代理票据模板处放一行指针指向它——这些事实只被子代理轴需要，放指针而非写进 `AGENTS.md`。

### 3. "适配器必须 import 第三方模块"是一个未被任何权威认领的设计事实（中高）

事实：`framework/adapters/pi/nicobailon.ts` 用裸说明符 `import("pi-subagents/required-child-extensions")` 触达第三方；这要求该工件在**仓库自身**的解析范围内，因此我向 `package.json` 加了精确 pin 的 `dependencies` 并更新了 `bun.lock`（同时新增 5 个传递依赖）。契约/规格/ticket 都没有说这条 pin 由谁拥有——决策文档只说"使用第三方公开的 `registerRequiredChildExtensions`"，没说模块如何被解析到。

推断：这类"管道"决定会改变仓库级文件（并让每个并行 worktree 都需要重新 `bun install`），却最容易在实施时才被发现和临时决定。我在这一点上花了大量回合去确认"是否存在不依赖仓库依赖的触达方式"（结论：没有；settings/loader 都不向扩展暴露已加载扩展路径）。

建议：把该 pin 写进契约或组织决策的既定事实（"framework 的 pi adapter 在仓库依赖中固定 provider 工件版本"），并在票据里点名它会改 `package.json`/`bun.lock`，使集成分支与并行 worktree 有预期。

### 4. 缺少可复用的"真实 pi 子代理委派"驱动（中）

事实：仓库有 OMP 的脚本化委派先例（`tests/harness-dock/*`：`delegationStep`/`isOpeningRequest`/`async.enabled=false`），但**没有任何 pi 侧等价物**。我手写了一次性探针：猜 `subagent` 工具调用参数形状（`{agent:"delegate", task, async:false}`）、需要知道第三方自带 `agents/` 目录、并且第二个探针因为把"开头 user 消息"当作会话标记，导致第二次 prompt 又触发了一次前台委派，后台子进程路径整轮未被触发（一次真机运行白跑）。

建议：在 dock 里提供 pi 侧夹具/助手（脚本化 `subagent` 工具调用、agent frontmatter、`async` 开关、按 assistant 出现/消息数区分同一会话的先后 turn 的辅助函数），并把它写进一份 pi 子代理真机入口说明。这会让"后台/嵌套/续跑/取消"等场景从"每次手搓"变成"几行驱动"。

### 5. steering 行在上下文压力下成为 no-op：codebase-memory-mcp（中低）

事实：本轮上下文三次出现"调用 grep 或 search 前考虑是否用 codebase-memory-mcp / 读超过 100 行源码前先看声明大纲或符号片段"，而我**一次都没有调用**该 MCP：`framework/core/protocol.ts`（1526 行）我分三次整段读，第三方源码全部整段读，搜索全部用 `grep`/`read`。

推断：这是我自己的执行偏差，但对这条 steering 行而言等价于 no-op——它每轮都花注意力却不改变行为。两种收敛方向：(a) 若保留，就把触发条件写成可直接执行的动作（例如"读 >100 行的 `.ts` 前必须先 `get_file_outline`"）并确认该 MCP 在子代理的工具清单里确实可用（未验证）；(b) 若不可用或不打算维护，则删掉该行，省下常驻注意力。

### 6. 真实验证没有落到仓库的证据路径（中）

事实：ticket 明确要求"每次真实验证即记录源、版本/工件、OMP 补丁条件、环境、命令、结果和未覆盖项，不能等 25 才追补"。我跑了两次真机探针并拿到关键事实，但**没有创建 `.scratch/model-cost-pi-migration/evidence/05-subagent-facts.md`**，也只有从既有 `evidence/02-pi-main-session.md` 反推格式。探针脚本本身写在仓库外且是一次性的。

建议：在 `docs/agents/testing.md`（或票据模板）里给出证据记录的骨架（来源/工件/环境/命令/结果/未覆盖），并把"探针脚本放在仓库可复用位置"写成惯例——否则真机事实要么留不下来，要么随临时目录消失。

### 7. 工具 schema 报错指向错键（低，环境）

事实：两次 `bash` 调用因为多传了一个不存在的 `sandbox_permissions` 键被拒，错误信息是 `ready: ready must be an object (was boolean)`——它抱怨的是我并未书写的 `ready` 键，直到错误回显里看到 normalized 参数才定位到真因。

建议：设备参数校验在遇到未知键时点名该键（或直接拒绝未知键并列出允许键），而不是把归一化后的默认值当作出错项。任何 agent 都会踩到，修复成本很低。
