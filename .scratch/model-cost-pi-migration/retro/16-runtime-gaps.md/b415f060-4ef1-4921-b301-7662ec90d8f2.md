## 4.（Guardrail）真实宿主分区对行尾敏感，且既有惯例是「改工作树字节再还原」

**事实**：本 worktree 为 `core.autocrlf=true` 检出，`bun.lock` 与两处 `host-patches/*/patch.diff` 都是 CRLF。实测 `bun test tests/harness-dock/baseline.test.ts` → 5 pass / 1 fail，失败项为「`bun.lock`: recorded a5d37ab2…(LF blob) but found e7ed487b…」；`evidence/08` 记录过同一现象的另一半（补丁物化期 `patch.diff touches no file`），其当时的处理方式是**把三份文件还原成已提交 LF blob 字节跑测试、跑完再还原**。我这次没有改工作树字节，代价是基线检查留一条红。

**推断**：这是仓库/环境的长期缺陷（每票都要重新诊断一次），而「临时重写被检出的字节」这种绕过方式在共享 worktree 里对并行票有风险。

**建议**：确定性修复优先——加 `.gitattributes`（如 `* -text` 或至少 `*.diff text eol=lf`、`bun.lock text eol=lf`），或把基线校验改为对 LF 归一化后的内容取哈希；修复前，至少把该现象写入 `docs/agents/testing.md` 的「已知环境失败」小节，避免每票重复诊断。
