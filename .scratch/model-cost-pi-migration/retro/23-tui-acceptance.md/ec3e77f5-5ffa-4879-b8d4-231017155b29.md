## 候选改进（按严重度）

### 1. 共享仓库 config 的一处非法布尔值让**所有** worktree 的 git 全部失效（harness 层守卫）

事实如上：一个 `autocrlf = core.eol` 使每个 agent、每个 worktree 的 `status`／`log`／`commit` 全部失败，而失败信息指向 `core.autocrlf`，很有误导性；`-c` 覆盖与 `GIT_CONFIG_NOSYSTEM` 都救不了。建议两层：

- **写入侧**：修掉会写出该值的 harness 步骤（它是 19:53 写的），并在派发前做一次 cheap preflight（`git rev-parse --verify HEAD` 即可探活），失败就把「哪个文件、哪一行、怎么修」直接给到 agent，而不是让 agent 自己试错 4 次。
- **读取侧**：把「`-c core.autocrlf=...` 覆盖无效；用 `git config --file <repo-config> core.autocrlf true` 修」这条非直觉结论放进 harness 的 git 故障速查（不必进仓库 AGENTS.md，那不是仓库的事）。

顺带：该仓库**没有 `.gitattributes`**（我 `cat .gitattributes` → 不存在）。加一行 `* text=auto eol=lf` 能让行尾行为与每台机器的 config 无关，这类 config 损坏就不再影响 `status` 的判读。

### 2. codebase-memory-mcp 的索引指向主克隆（branch `pi-adapter`），不是 agent 的工作树

`list_projects` 显示该项目 `root_path = E:/Developer/myhub/my-agent-toolkit`、`branch = pi-adapter`；而本会话的工作树是 `C:/Users/.../hyper-ticket-1MhF6a`。派发词又明确要求「优先用 MCP 搜索/大纲、读大文件前先看符号大纲」，于是按指令行事会用**另一棵工作树/另一个分支**的符号与源码回答本树的问题，且本票新增的三个 `scripts/**` 文件在索引里根本不存在（`get_file_snippet` 类调用会空手而归）。建议：按 worktree 建索引（或把 worktree 并入同一 project 的 scope），并在派发词里写明「MCP 回答的是哪棵树/哪个分支；文件内容一律从本工作树读」。

### 3. 派发状态与工作树实况矛盾：「首次执行」vs 已有提交

本会话为此付出的成本是：先发现 git 挂了、修好、查日志与 worktree 注册表、读同票另一个实例的报告，才确认「不该重做」。真正的风险不是浪费而是**破坏**：一个把「首次执行」当真的 agent 可能覆盖既有文件、或按惯例 `reset`／重建分支（派发词里那句「不得 reset 丢弃既有工作」正是这个风险的补丁）。建议把结论前移：派发时带上一句事实化的前情，例如「该 worktree 可能已含本票前一轮的提交与证据；先 `git log --oneline -5` 与 `git status` 判定，既有提交视为已交付，只补缺口」。

### 4. 验收脚本的自动检查不在任何 `bun test` 分区里

本票的自动检查全部在 `scripts/pi-tui-acceptance.ts` 内（`accept:model-cost-tui`），`tests/model-cost` 与 `tests/harness-dock` 都不跑它；`bun test tests/harness-dock`（25 个真宿主文件）里也没有任何用例驱动 `Bun.Terminal`，即「真 TUI 帧」这条路径只有这个脚本覆盖。**未验证**：仓库是否有 CI 或 pre-commit 守卫会跑它/harness 分区（我没查 `.github/`）。若没有，这些检查只能靠人记得跑——建议把该脚本（或一个 1 帧的精简变体）挂进既有的 smoke/opt-in 层，并在仓库守卫里跑 `typecheck`。

注入 B 让 60 列帧丢掉 `Balance:`／`Span:`，但 `every amount the 120-column frame states is still whole at 60` 与 `every runtime marker …` **都没有失败**：它们只比较 `¥0…` 金额与 `Run:` 标记（`amountsOf` 还把 `¥Cache/In/Out：0:8:92` 这类按 `startsWith("¥0")` 过滤掉了）。真正抓住这次退化的是每宽度的内容检查。这不是缺陷（每宽度内容检查确实锚定了字面量），但读证据时容易把「宽度退化已覆盖」理解得比实际更宽。若要加固，把跨宽度比较的对象从「金额+Run」扩到每一件行尾字段（`Balance:`／`Span:`／比例列）即可；本轮只记录，不改代码。

### 6. pty-less 沙箱会静默降级交互入口

`pty requested but unavailable in this environment; ran without a terminal`：请求 pty 的调用被无声降级，于是 `--interactive` 看起来「成功」（exit 0、隔离根已建），却没画出任何 TUI。加上「人类半必须由人执行」这一条，agent 侧没法自证。建议：把 pty 可用性作为派发事实给出（或在降级时以非 0 退出/显著警告），让 agent 直接知道「交互观感不是你能跑的检查」，省掉一次注定无果的尝试。

### 7. 派发词的 context load 里有可省的重复

派发词内联了整篇 tdd skill 正文与票据的 AC/约束，而票据文件与 skill 文件都在本机可 `read`（宿主自己说「使用 read(skill://...)」）。每轮派发都付这份常驻成本，且票据内容读一遍文件就有。建议：skill 与票据改成**指针 + 一句触发条件**（front-load 触发词），把正文留在文件里按需读；这不改变 agent 的行为，只省每轮的窗口与注意力——若担心「不读就漏」，用指针对齐触发词即可。

### 8. 定位代码时别靠 grep 的行号，靠唯一内容

我的那次误判（把 widget.ts 的 `wrappedPieces` 当成 display.ts 的）成本是 2 次 read + 1 次 awk 核对。事实是工具没错：跨多文件搜索的结果按文件分节，我丢了分节头。可固化的习惯：**跨文件搜索结果一律把「文件头 + 行号」当成一个整体读**；要改代码就用唯一 `old_string` 定位（`edit` 本来就要求唯一），行号只用来读窗口。这条更适合放进实现轮的技能/派发提示，而不是仓库文档。
