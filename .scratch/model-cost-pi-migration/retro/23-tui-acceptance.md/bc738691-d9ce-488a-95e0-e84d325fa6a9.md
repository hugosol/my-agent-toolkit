## 1（高）新建 worktree 没有 `node_modules`，而固定工件正是仓库自己的路径约定——并伴随 `bun pm ls` 的假报告

**事实**：本 worktree 起初 `node_modules` 不存在（`read`/`ls` 均为空），但 `bun pm ls` 输出「node_modules (32 installed)」并列出 `pi-subagents@0.78.0`；随后 `ls -d node_modules`、`existsSync` 校验均为 false，而 `bun -e "require.resolve('yaml')"` 却从 `C:/Users/hugos/.bun/install/cache/` 解析成功。仓库自身的脚本路径约定是 `node_modules/pi-subagents/index.js`（`scripts/pi-model-cost-smoke.ts:177`、`scripts/pi-subagent-smoke.ts:59`），该路径在本 worktree **与主仓库 `E:/Developer/myhub/my-agent-toolkit/node_modules` 都不存在**（主仓库只有 7 个包）。本轮用 `bun install --frozen-lockfile`（13 个包 / 1.69s，`bun.lock` 字节未变，`git hash-object` 前后同为 `cc3c49a6…`）才让该路径成立。

**代价（可计量）**：约 6–8 次工具调用（`bun pm ls`、`bun -e require.resolve`、`ls`、`existsSync` 探针、cache 目录探查、从 cache 路径试跑 pi 失败）＋一次错误方向（先怀疑是 typebox peer 缺失，实际是「路径从未存在」）。

**建议**：
- worktree provisioning 阶段执行一次 `bun install --frozen-lockfile`（幂等、不改 lock、写到 gitignore 的目录），或在 `docs/agents/testing.md` 的「真实宿主运行」段加一句前置条件：*新 worktree 必须物化依赖后才能真正运行 pi 宿主路径（RPC/TUI/smoke）*。
- 同处记一句工具陷阱：**`bun pm ls` 报告的是 lockfile 图，不是磁盘上的目录**，判定「工件是否在位」用 `existsSync`/`ls`。这一条本轮直接造成了一次错误结论。

## 2（高）CRLF 检出制造的固定 10 例失败地板（前票已记录、本轮再次回避）

**事实**：本轮的 3 个新增文本件与证据文件在 `git add` 时全部打出 `LF will be replaced by CRLF` 警告；仓库没有 `.gitattributes`（`glob` 结果：`Skipped missing paths: .gitattributes`）。其它票的日志（如 `evidence/18-native-presentation.md`）反复记录：按检出原样跑全仓是 1131 pass / 17 fail，其中 10 例源于 `host-patches/*/patch.diff touches no file`（LF-only 切行）、2 例源于 `bun.lock` 按 LF blob 记录 sha。

**代价**：每张票的完成/集成运行都要做一次「归一三处工作区字节」的准备，否则失败清单里永久混着 12 例与改动无关的红，判定成本与误判风险都在。

**建议**：一次 `.gitattributes`（`host-patches/**/patch.diff text eol=lf`、`bun.lock text eol=lf`、`.scratch/**/*.md text eol=lf`）。前票明确把这件工作推给「装配/宿主验证范围」，但它是**一次性**投入、收益覆盖所有后续票，属本环境最高杠杆的机械修复。

## 7（中）批量同文替换的规则与工具文档互相矛盾

**事实**：系统提示写「NEVER use `sed`|`perl`|`python` via `bash` to issue individual edits; MUST use `edit`」，而 `edit` 工具自己的说明书明确把「Same replace in several files」列为 `sed -E -i 's/…/…/g' a.ts b.ts` 更高效的场景。本轮我三次用 `sed -i`：两次是跨文件**完全相同**的字面替换（证据/票内 `45 ok` → `46 ok`；一个 sha1 → 新 sha1），一次是工作树之外临时探针里的 `match === undefined` → `match === null`。

**建议**：统一措辞为「单点编辑一律 `edit`；**跨 ≥2 文件且替换串完全相同**的机械替换允许 `sed`」，避免每个 agent 各猜一次边界。

## 8（中）新写入的未使用导出没有任何机械检查

**事实**：`tsconfig.json` 只有 `strict`，没有 `noUnusedLocals`/`noUnusedParameters`；仓库也无 lint。本轮我在自审阶段删掉了自己刚写的死代码（`terminal-screen.ts` 的 `resize`/`text`、fixture 的 `cellRowsWith`/`framesOf`），删除前后各跑一遍 typecheck——说明这类残留只能靠人肉发现，且它们是「先写宽接口、后收敛」的必然副产物。

**事实**：两次 `bun -e` 直接失败：`error: failed to execute command 'bun': batch file arguments are invalid`（含 `>`、`<`、`[0-9;]` 等字符时）；改写成临时脚本文件后即正常。本轮因此多出两次失败调用与一次脚本落盘。

## 10（低-中）中途注入的项目规则是「非阻塞」，首稿必然违规

**事实**：本轮的 `ts-no-tiny-functions` 与 `ts-set-map` 两条规则都是在**写入已经发生之后**才随工具结果提示「rule configured not to interrupt → tool ran」。其中 `ts-set-map` 命中的是我用 `Map` 做静态 id 查表（按规则应 `find`/`Record`），我在后续调用里改成 `find`。`ts-no-tiny-functions` 同时点出「导出名/稳定契约」是允许的小函数场景，而仓库自有的 `scripts/support/detail-layout-fixture.ts` 正是靠这一豁免成立的。

**建议**：对新建文件（`write`）把这类规则置为**阻塞**或提前注入，省掉「写完再改」的一次往返；并把「导出 API / 测试接缝 / DI 边界」这类豁免写进规则文本，避免 agent 在仓库既有风格与本规则之间自行取舍。
