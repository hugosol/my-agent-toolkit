## 高

### 1. 机械型 TS 规则在首次写入之后才到达 → 整个 40KB 模块重写；仓库没有 lint 守卫

**事实**：本会话第一次 `write framework/modules/local-access.ts`（40689 bytes）成功返回后，宿主立刻注入 5 条项目规则提醒：`ts-set-map`、`ts-no-tiny-functions`、`ts-promise-with-resolvers`、`ts-no-return-type`、`ts-no-inline-cast-access`。我随后用另一次 `write` 把整个文件重写一遍以合规（同一份内容第二次计费）。
**事实**：`package.json` 的脚本只有 `test`/`test:dock`/`test:framework`/`test:codebase-tools`/`typecheck`/`smoke:*`/`verify:*`/`baseline:efficiency`——没有 `lint`/`check`/`format`。本会话看到的仓库根目录列表里没有 `.github/`。
**推断**：这 5 条都是**机械型**规则（固定语法形态、禁止的取值方式），本可由确定性检查在写入后立即失败，无需依赖"写完再提醒"。以 review 阶段的提示承担机械规则，等于把守卫放在了最晚、最贵的一环。
**建议**：把规则落成守卫——加一个 lint 配置（biome/eslint 任一即可表达上述 5 条）并接入 `package.json` 的一个 `check`/`lint` 脚本，写进 `docs/agents/testing.md` 的"tickets 完成层"。这样违规变成一条可执行失败，且 review agent 不必重复盯它。
**建议（备选额度）**：若规则集由 harness 的 builtin-defaults 拥有、仓库不便重复实现，至少在 `AGENTS.md` 的导航行里点明"仓库 TS 风格由 builtin 规则约束"，让执行者在**第一次写入前**就知道。

### 2. 整条本机接入协议由实现者现场发明，协议形状没有落在任何可引用的权威里

**事实**：spec 的 Implementation Decisions §6 只定约束（Windows 命名管道/POSIX socket、`runtimeDir` 显式、相对值按配置文件解析、定位与消息分开、单向推送 + 请求/应答、不开放通用 RPC），并明确"接口签名、内部算法及构建顺序"留给构建。本会话为此花了大量早期回合读 `spec.md`、`contract.md`、`lighthouse/04`、`research/04-local-transport-facts.md`，才定出：一进程一端点、席位=（extension, owner）、端点命名 `\\.\pipe\my-agent-toolkit-access-<random>` / `<runtimeDir>/access-<id>.sock`、定位记录 5 字段、`hello`/`welcome`/`read`/`value`/`changed` 帧、verification 为 32 随机字节、失败四分类 `no-location|endpoint-absent|refused|closed`。
**推断**：这些形状现在事实上成了标准——07 的 `follow` 读端必须照它接——但它们只存在于代码、测试与我的 evidence 文件里。下一个执行者若独立设计，就会得到第二套语义（正是契约"不静默漂移"要避免的）。
**建议**：把已定形状落成一份短的可引用工件（`framework/docs/` 一节或一份 ADR）：只写"线协议帧 + 命名 + 定位记录 schema + 失败分类 + 谁的寿命"，并在 `framework/docs/framework-capabilities.md#local-access-adapter-facing`（本票已写出该节）里指向它。这不需要新设计，只是把已有决定钉在权威位置。

### 4. 票据没有给出"seams under test"清单 → 测试后补，两轮补强

**事实**：tdd 技能要求"Test only at pre-agreed seams... No test is written at an unconfirmed seam"，但票据的验收条目按承诺（P42/P56）分组，没有列出被测 seam 或接口。我因此先写完 980 行模块、再写 843 行测试（水平切分）。
**事实**：随后的多轮故障注入中，首批 8 条里有 2 条 SURVIVED（"撤席不释放连接"被下一次 read 的席位守卫掩盖；"任意帧当 read 服务"因探针帧未带 `id` 而未被区分）。补强它们需要新增 API（`OwnerAccessCaller.ended()`）、给子进程夹具加读端模式与 `await-end`/`report` 握手、再加"两席位 + 真实读端"用例；另有一轮注入本身打偏、一轮记录形状需要重写为"带席位但无可读 endpoint"。共 12 条注入最终被杀死。
**推断**：先列 seam（同进程直读 / 跨进程读写 / 拒绝面 / 秘密收敛 / 装配门控 / 释放）会让这两处敏感性在设计阶段就暴露——`ended()` 这个 API 缺口本来就是第一个 seam 的问题。
**建议**：在 implementation 票据模板里加一个字段"**seams under test**（每个 seam 一句话：它捕获什么、漏掉什么）"，与验收条目并列。这是 tdd 技能已经要求、而票据未提供的输入；补上它，红测试就会自然先于实现出现。
