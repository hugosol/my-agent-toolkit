# pi 原生事实到 Round 边界的映射：Lighthouse

> Question and discussion: [pi 原生事实到 Round 边界的映射](../decision/08-pi-round-boundaries.md)

## Question

在固定 pi/nicobailon 接入下，如何以原生事件为主干，为每个实际会话映射 framework 的 Round 起止、持续与截断，并给出可交接的常见路径验收？本票决定映射策略，不交付生产适配或完整迁移。

## Discussion

### 确认来源与收敛过程

确认来源为本票会话，用户先要求“请开始ticket08”，最终对 Q11 验收清单回答“采用”。可恢复的关键确认如下：

- Q1“同意”：父 Round 的持续取决于父会话的待自动继续，不由子代理存活或结果到达单独决定。
- Q2“同意，我们需要避免发布定时任务round就一直不结束的问题”：未来独立触发不占住当前 Round；当前活动的延迟继续仍在同轮，不按延迟时长切分。
- Q3“同意”：后台子代理终态不等于父 Round 结束，父会话的结果继续也须纳入活动。
- Q4“采用”：认可本地活动、后台待续与可靠事实共同支撑关轮。随后以 Q6 的简化结构取代通用待续义务状态机。
- Q5 未批准。用户指出判断过于复杂，要求参考 OMP 的明确事件主干、只处理常见特殊情况；逐通知/逐请求证明模型读取结果的方案被放弃。
- Q6“同意，这个简化方案更清晰直接”：采用原生事件主干、一次延后检查与后台事实补充，不构造任意外部唤醒的通用系统。
- Q8“同意”：采用 adapter 内部装配注入，Round 映射不直接依赖第三方字段和协议。
- Q7 最终明确：“如果nicobailon已经承诺提供保活协议，我倾向于按照它的标准执行，不为一些极端情况再添加例外，设计机制，增加代码复杂度”。在公开协议已核实的前提下，选择现有保活协议；不批准此前候选的上游 Round 专用接口补充。
- Q9 用户要求选择简单方式，并询问后续子代理返回是否开新轮：采用原生终止结算后结束取消轮，后续真正开始执行才开新轮，结果追加本身不开轮。Q10“采用同样结束原则”：终态失败同样处理。
- Q11“采用”：确认下文常见场景验收清单及将 OMP 现有取消/失败差异交后续完整迁移方案核对，不默默扩大本票生产修改范围。

### 一、原生事件主干与正常关轮

公共 Round、Turn、Working、Idle 的含义沿用 [framework 术语](../../../framework/GLOSSARY.md)。按实际 session 区分 Round，父子各自独立；不按进程、run handle 或工具调用替代会话身份。

1. pi `agent_start` 映射为活动开始事实。没有开轮时由 framework 开轮；轮内再次开始视作继续，不因低层 run 重启另开一轮。
2. pi `agent_settled` 映射为结束候选，而不是把每个 `agent_end` 当成 Round 结束。pi 的原生循环负责工具、自动重试、压缩及原生排队续跑；adapter 不自行模拟这些循环。
3. framework 保持结束候选后在下一 task 重读静止条件的结构。正常结束需确认：pi idle、没有排队消息、所选提供方报告无后台活动/待发唤醒。
4. `agent_settled` 不是独立充分条件；后台等待期间父 Round 保持打开，结果触发的原生活动继续使用原 Round，直到再次满足关轮条件。
5. 不设置自己的静默窗口、定期轮询或超时关轮；后台事实也不直接发送公共 `round_end`。需要重检时仍经 adapter 的事实映射及 framework 合成，不建立第二套生命周期派发。

普通新输入在既有活动中被原生排队消费时沿用同轮；一个 Round 已结束后的实际执行开始进入新轮。用户任务是否在语义上彻底完成，不是关轮判据。

### 二、采用提供方既有保活标准，而非重建待续状态机

采用 nicobailon 公开的版本化会话保活协议，在 adapter 私有接入中消费其会话级活动查询。公开文档的范围包括运行中后台工作、未投递结果、待启动完成通知及父会话唤醒；未来 schedules、保留终态历史和 wait subscription 本身不使会话保持活动。静态证据与限制见 [事实核查](../research/08-round-boundary-facts.md)。

- 以提供方现有标准解释活动与不活动；不复制其内部结果队列、逐通知阶段或待续义务账簿。
- 不解析通知文字，不证明模型读懂/完成了哪个结果，不把 `message_start` 当作所有通知追加路径的必要事实。
- 接受协议已有的唤醒超时行为，包括空闲唤醒超过既有 10 秒期限未启动时不再保活。该正常返回可解除后台这一项阻塞，但仍须正常结束候选及本地静止检查，不能仅由期限流逝直接发出 Round 结束。
- 这明确取代本会话前期“任何超时都不能解除待续、必须独立证明每项结果已处理”的严格候选；理由是遵循提供方承诺、覆盖常见路径并控制复杂度。不是新增本地计时器或承诺任意极端路径都等价。
- 未注册、身份不匹配、接入失败或查询不可得不等于正常返回不活动；不得静默当作 false。沿用 [组织权威](04-third-party-adapter-organization.md) 的接入失败与诊断规则，不新增本轮自动发现/热切换机制。
- 无子代理模式检查本入口接入范围内的 pi 原生事实，不强制依赖 nicobailon，也不声称宿主全局不存在其他子代理。

本决定不要求修改第三方，不授权私有字段读取或长期 fork。若后续集成表明现有公开协议无法兑现本清单，应以具体证据返回既有 [选型重评规则](03-subagent-provider-choice.md)，而非预先设计额外兜底。

### 三、终止、结果晚到与恢复

- **显式取消**：以观察到本次活动的原生终止结算为准，结束本轮；不因后台仍活跃或保留队列而一直挂轮。不在按下停止键时抢先发布结束。
- **终态失败**：采用同样原则，使用 pi 原生结局及最终结算；不得把仍会原生重试的错误当作终态。`agent_before_settle.outcome` 可作为结局输入，但该边界仍可能继续，不能单独触发结束；后续继续须更新对应本次活动的结局。
- 终止分支不等待后台保活清空，但仍须确认被终止的本地活动已经结算，避免旧活动结局误用于后来的新活动。具体映射不要求新增公共结局字段或把错误分类推给业务。
- Round adapter 不额外停止子代理、清理其队列或唤醒父会话；这些行为交给宿主/提供方。
- 已结束轮不重新打开。晚到结果仅追加时不开轮；若它实际触发父会话执行，或用户随后输入启动执行，则原生开始进入新 Round。
- nicobailon 现有 UI 取消路径会保持唤醒暂停，直到下一次执行开始；该保证有 `hasUI` 条件，不泛化成所有 RPC/headless 路径都不唤醒。
- reload/恢复及缺失边界沿用 framework 截断/未知原则：不补造旧轮正常完成、不把离线间隔视作连续活动；恢复出的 Session 累计不等于一个恢复出的完整 Round。不要仅凭新的低层 `agent_start` 判断必须截断已知的正常继续。

### 四、adapter 内部 seam

沿用 [集中组织权威](04-third-party-adapter-organization.md)，不在本票重定义目录政策或复制公共接口：

- `framework/adapters/pi/nicobailon/` 集中识别、接入及转换公开保活协议，隐藏字段、注册协议、身份核对与释放。
- `framework/adapters/pi.ts` 负责薄装配，将一个小型的会话后台活动查询注入 `pi/round.ts`；最终内部命名由实现遵循现有约定。
- `pi/round.ts` 映射 pi 原生事件并组合原生 idle/pending 与注入的后台事实，不直接导入 nicobailon 的原生载荷或私有实现。
- framework behaviors 继续拥有身份、Round 转移、延后重检与 scope 分发；model-cost 只消费公共事件，保持既有会计与提交逻辑，不取得提供方 context/registry。

这不是新增公共提供方注册框架。第三方字段/读取方式变化原则上局限于私有接入，但若其语义不再满足需求，仍需重评，不能保证只改解析就能保留行为。公共 Round 定义并不依赖 nicobailon；本次 pi 子代理接入的事实来源依赖它。

### 五、已确认的可观察验收

| 场景 | 要求观察的结果 |
| --- | --- |
| 普通请求 | 一个实际会话一次开轮、一次关轮；正常结束发生在原生结算及延后检查之后 |
| 工具、自动重试、压缩及排队续跑 | 原生继续期间不提前关轮；最终结算才成为可确认的结束 |
| 前台子代理 | 父子有独立会话身份及各自 Round，不互相替代 |
| 后台委派及批量通知 | 父会话等待和通知交接不提前关轮；原生唤醒接续原轮；按提供方标准解释保活 |
| 嵌套、并发、同/独立进程 | 每个实际会话独立判断、无串轮；同进程不为此新增 IPC |
| 未来定时/周期任务 | 登记任务不占住当前轮；真正触发的实际会话执行走自身边界 |
| 取消/终态失败后晚到结果 | 旧轮终止；仅追加不开轮，真正开始执行才开新轮；原生重试不是终态 |
| 重载/恢复及协议不可用 | 不伪造旧轮正常结束，不把未知当无后台活动；接入/句柄按既有寿命释放 |

workflow/调度只检查选型权威已批准的适用路径，不增加产品硬要求；不承诺任意第三方或任意外部后台来源。后续需证明 framework 身份/事件与 model-cost Round 归属、保存触发一致，不能只展示原生事件。

### 六、证据级别与 OMP 差异

本轮主要为源码/公开文档核查，另对实际 `parent-wake.ts` 模块执行了无模型、注入时钟和宿主回调的窄范围 smoke，观察既有超时、取消保留通知和下次开始解除 hold。不是 pi 宿主/协议注册/framework/model-cost 的端到端通过，也没有复用先前付费限额。

固定来源、原生顺序、完整命令结果及局限见 [事实核查](../research/08-round-boundary-facts.md)。现有 pi adapter 仍拒绝 Round 观察，生产能力尚未实现。

现有 OMP adapter 的静止组合没有显式取消/失败豁免，framework 当前普通候选合成也不能被当作新终止分支已实现。此差异交 [完整迁移方案](../decision/05-complete-migration-plan.md) 核对公共语义/两端行为及实现范围；本票不默默授权额外 OMP 生产修改，不改写历史基线。

## Decision

采用 pi 原生开始/最终结算事件、framework 延后静止检查及 nicobailon 既有公开保活协议，形成覆盖常见路径的简化 Round 映射；取消与终态失败结束旧轮，后续实际执行开新轮。adapter 内部集中第三方事实并以小接口注入，规划范围完成，不代表生产迁移或完整兼容验证通过。

## User stories

1. 作为使用者，我需要工具、重试及后台结果继续保持合理的同轮归属，以便 Round 统计和保存不会因一次低层结束或短暂 idle 被提前切开。
2. 作为使用者，我需要未来定时任务不占住当前轮，并让取消/终态失败能结束活动，以便不会因未来任务或后台保活而一直显示未结束。
3. 作为维护者，我需要遵循提供方既有公开标准和 adapter 内部的小接口，以便无需维护逐通知/逐请求状态机，第三方变化集中处理。
4. 作为迁移规划者，我需要每实际会话、同/独立进程及故障路径的可观察验收，以便区分已批准设计与已实现/已验证能力。

## Preconditions

- [完整基线](01-capability-baseline.md)、[提供方选择](03-subagent-provider-choice.md)、[集中组织](04-third-party-adapter-organization.md)及 [固定工件验证](07-nicobailon-runtime-validation.md) 的范围和版本限制继续有效。
- 开发基点为 pi 1.2.0 / pi-subagents 0.78.0；公开保活协议需在实际装配及每种适用会话中接入，不能将文档存在视作注册成功。
- 公共语义/协议失败与正常 false 的区别保持不变；本决定只接受提供方本身已经约定的行为，不授权任意降级。

## Postconditions

- 本票原生事件、正常/终止/恢复路径、第三方事实路线及验收范围已决定，可供完整迁移方案消费。
- 逐请求阅读证明、通用待续状态机、Round 专用上游补充及自定义超时均不是当前路线。
- 实现和真实宿主验证由后续工作交付；OMP 现有终止映射差异仍须在完整迁移范围内核对，不是已经修复。

## Invariants

- framework 拥有 Round 公共语义和身份；adapter 只映射事实，业务不依赖第三方接口，不自行创建第二套 Round。
- 对齐既有 OMP 事件主干/延后静止检查结构及集中组织权威；采用 pi 自身更合适的最终结算事件，不要求两端原生事件名完全一致。
- 主/子会话、直接父、Owner、run/execution 不混用；子会话消费不因结果到达被重计入父 Round。
- 未知不等于 false/idle/零；正常保活返回按提供方公开标准解释，不宣称本方案证明全部极端路径。
- 无生产修改、安装切换、额外付费授权、长期 fork 或任意提供方插件系统。
