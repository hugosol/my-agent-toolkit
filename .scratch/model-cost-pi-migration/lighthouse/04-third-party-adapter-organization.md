# 第三方能力适配的集中组织与公共语义复用：Lighthouse

> Question and discussion: [第三方能力适配的集中组织与公共语义复用](../decision/04-third-party-adapter-organization.md)

## Question

确定 OMP 与 pi/nicobailon 子代理能力的公共职责、集中组织、小接口、装配、进程间接入、存储协调、寿命及失败行为。这里发布可交接的组织决定，不交付生产代码，也不替 [pi 原生事实到 Round 边界的映射](../decision/08-pi-round-boundaries.md) 决定原生事件的关轮判据。

## Discussion

### 确认来源与被取代的方案

本权威最初部分发布于提供方选型会话：用户确认 model-cost 内置其业务观察，不另建独立观察产品，并要求 OMP/pi 自行累计、JSON 保存子代理耗时。本次来源为用户“请开始ticket04”后的连续访谈，最终以 Q34“采用”结束组织方案确认。以下按问题及明确原话保存可恢复来源，而不把中间提案当作最终决定：

| 主题 | 当前决定与确认来源 | 被取代的旧约束或中间提案 |
| --- | --- | --- |
| 第三方机制的归属 | 用户对 Q1 纠正：nicobailon 能力应在 framework adapter 下，其他 extension 可复用；Q5、Q17 采用集中加载与公开入口方案 | 将 nicobailon 机制局限在 model-cost harness；“本轮不抽取任何公共子代理能力”的过宽说法 |
| 公共关系与统一路径 | Q7 同意抽出共性；Q9 同意统一替换，条件是“达到同样的目标，效率上没有明显差异，实现复杂度没有显著提高”；Q10 采用同进程/独立进程组织 | 除耗时外必须保留 OMP 旧实现路径；永久维护两套业务算法 |
| 数据与刷新 | Q11 确认持久化/非持久化区分；Q12 事件驱动且不得散落 refresh；Q20 补充内存先更新、事件触发写盘；Q22、Q24 采用集中按文档批处理与逐记录结果 | 刷新等同写入；所有变化立即争锁写盘；各 handler 各自维护读写 |
| State | Q21、Q23 允许 framework 集成；Q25 使用时获取；Q29、Q30 确认当前进程自动恢复、不重放失败操作；最终 Q31 明确同意缺值使用默认值并恢复读取 | 获取失败就让整个 extension 不可用；必须重载才能恢复；用旧缓存冒充成功；默认值兜底后再重放旧操作 |
| 耗时 | Q15 采用已知小计及不完整性；最终 Q32：“选择最简单的实现方式即可，子代理累计时长只是用作大体估算，不需要对应精确边界” | 精确执行器端到端测量；Q19 曾批准但后被简化方案取代的独立 execution 起止轴 |
| 接入模式 | Q4 不检查已有子代理数量；Q16、Q18 采用稳定接入模式，用户指定“无子代理模式”命名 | 将未安装当错误；公开“正在建立接入”阶段；运行中自动发现提供方或热切换 |
| 目录与通信 | Q33 两次明确要求配置值显式存在，不能使用代码默认目录；最终 Q34 采用本机 IPC、单向观察事件、State 请求/应答、文件只作持久化与定位 | 隐式 os.tmpdir/cwd 回退；以请求/应答文件队列传递运行中消息；extension 绕过 framework 自建通信 |

这些修订只改变当前目标与设计，不改写历史 OMP/pi 源码事实，不代表新能力已实现、兼容通过或完整迁移完成。耗时策略、公共组织及其修订只在本权威维护，消费者引用这里。

### 一、职责与目录

保留同一份 extension definition/shared-logic。组织如下：

```text
framework/
  adapters/
    omp.ts                    公开 OMP 接入
    omp/                      OMP 原生机制
    pi.ts                     公开 pi 接入
    pi/
      nicobailon/             第三方识别、加载、事实映射、登记与订阅
  core / behaviors            公共身份、父链、Owner、State、观察及生命周期
  modules                     无宿主/业务语义的文件协调与本机通信基础机制

extensions/model-cost/
  harnesses/
    omp.ts / omp/             OMP 薄装配、专属读取与绘制
    pi.ts / pi/               对称职责的 pi 薄装配、专属读取与绘制
  shared-logic/               计费、记录、耗时估算、业务存储及展示计算
```

- extension 不直接导入 `pi/nicobailon/`；该目录为 adapter 内部实现，不新增需要各 extension 手工拼装的独立提供方 adapter。
- Framework 不依赖 model-cost；model-cost JSON 不是公共身份、父链、Owner 或生命周期的事实源。
- 保持既有 StateStore 的权威值与写权规则；通信接线只接入权威读取，不建立另一份以业务文档或进程全局缓存为权威的 State。
- 关系算法与公共语义从 OMP 特有读取中分开，两端复用；原生 registry、事件与第三方文件/接口读取仍留在各 adapter。
- harnesses 不只是 UI：还可以有本扩展允许的专属 context 读取、实现选择和薄装配，但不夹带第三方机制或另一套业务规则。

### 二、公共子代理上下文及接口职责

身份、直接父链/Owner、子扩展接线、Owner State `follow`、必要寿命事实及观察分发作为一组 framework 公共子代理上下文能力集成。分组不等于单文件、庞大 facade、通用插件系统或任意 RPC。

| 接口面 | 调用者需要知道什么 | 隐藏在实现内的内容 |
| --- | --- | --- |
| 既有 `ompAdapter` / `piAdapter` 装配 | 扩展声明、实现工厂，以及需要加载到子会话的本扩展入口 | 第三方 required-child-extensions 调用、登记汇集、重复处理和释放 |
| 装配的只读接入结果 | 子代理模式或无子代理模式；明确的接入失败诊断 | 安装识别、接线检查、内部初始化阶段；不向 shared-logic 传 `nicobailonInstalled` |
| 既有公共观察/State 消费面 | 实际会话、父链/Owner、公共事件身份和来源；State 的既定读/写权限 | 同进程直达或跨进程传递、读取等待、连接恢复；不暴露原生 context/registry |
| 文件协调面 | 内存变更、哪些变更到提交边界、提交与同步结果 | 同文件合并、在途保护、一次协调发布及通知；不包含 Session/消费 schema |

同进程使用直接调用与共享业务实例；独立进程使用同一实现，处理本进程承接的实际会话，并经 framework 接入跨进程能力。无论哪种方式，公共观察仍走统一分发，不另建业务语义事件总线；来源和身份必须足以去重，观察不授予外部效果或 Owner State 写权。

根侧消费展示读取已保存记录并与本地未提交数据对齐，不把子侧计费、根侧收到的观察及 JSON 记录当成多份费用。来源识别和记账准入集中处理，不在每个 handler 散落远端判断。

第三方子扩展加载机制由 adapter 集中封装；装配只提供自身入口，不自动把所有主会话扩展加载给子会话。加载、State 继承和 MCP 可用性仍是不同条件。

### 三、模式、缺失与失败

- **无子代理模式**是正常受支持形态：本入口提供主会话功能，不断言整个宿主不存在其他子代理。
- **子代理模式**在所选提供方接入成功后成立。没有子代理记录时也允许 detail，不新增数量判断。
- 未启用提供方与实际接入失败分开；失败明确报告，不能包装成正常的无子代理模式。
- 模式在初始化完成时确定，不公开“正在建立接入”模式，不做提供方自动发现、安装、启用或热切换；配置变化通过正常新进程/重新接入生效。
- model-cost pi 装配根据这一个接入结果选择行为，不重复识别安装。无子代理模式下 `/budget detail` 提示后直接返回，不切换偏好、不执行后续 detail 逻辑；成功路径沿用原动作，其他 `/budget` 动作及 OMP 原路径不因此增加此分支。
- State 通信恢复是恢复已选接入，不是自动发现或切换模式；配置错误也不能被包装成成功的接入。

### 四、共同业务准备与寿命

- 同一业务实例共用一次必要准备，配置、有效消费基线及计费输入就绪后再处理相应记账事件；并发准备共享同一次结果，不重复读盘。
- 根侧余额/额度预取、主入口 UI 等效果与记账准备分开；独立子进程不因观察加载而重复启动根侧效果，不把子会话冒充 Owner 来调用根专用 initialize。
- OMP 同进程不为形式统一而多建实例、子进程或文件往返。共同代码处理本进程承接的 session，不维护按宿主区分的记账算法。
- Idle、一次活动结束或子代理暂时不工作，不销毁实际 session、历史和累计；续跑继续累计。同一 session 保留不要求承载它的物理进程一直存在。
- 不新增子代理回收、租约、资源池或引用计数系统。事件订阅、第三方登记及通信句柄只跟随所属接入的实际退出/重载/处置成对清理，不在注册成功后立即撤销，也不因子代理活动结束清理共享根实例。
- Framework 的 Owner、State 继承、实例 initialize/cleanup 与普通会话转移的公共含义保持不变。

### 五、持久化、只读同步与批量提交

数据按持久化要求而不是按进程划分：

- **持久化数据**：消费记录、累计耗时及相应完整性等，必须可靠保存、恢复并保持多进程一致性。
- **非持久化展示读数**：context、当前活动展示等，随已有事件顺便更新，不承诺硬实时、不为此增加固定轮询。缺少轻量可靠来源时可以逐项讨论暂不实现；不是已经批准任意字段全部省略。计费、Round 或 State 行为所需事实不能借此豁免。

统一流程是“变化先更新内存及只读展示，业务提交事件使相应变更获准提交，协调模块再发布”。读刷新与写提交是两个操作：

1. 按文档集中协调，同进程合并**已经获准提交**的变更，不把另一个尚未到边界的 session 在途消费顺便保存。
2. 写入继续复用 `framework/modules/files.ts` 的协调与原子发布，锁内读取现有文档并按业务合并；不整份覆盖内存快照，不另造锁。
3. 同文件并发请求合并处理；在途提交只确认实际提交的部分，期间的新变更不被旧确认清除。跨进程必要的互斥仍保留，不能声称批处理消除了所有加锁。
4. schema、统计周期、版本冲突、字段合并、归档和提交时机由业务拥有；消费文档与 Codex 估计文档不强制采用同一时机或同一失败策略。
5. 合并提交保留逐记录结果：周期一致且文件可用时，过期/冲突记录分别拒绝，有效记录可共同发布；文档不可用或发布失败则不能宣称任何记录已落盘。不自动重试拒绝项。
6. 归档/周期重置仍是有顺序和条件的独立事务，不混入普通 batch，也不强制保存其他在途数据。旧周期未提交数据不能通过刷新带入新周期。
7. 根侧允许在已有合适事件中读取外部已提交记录，无事件时可以暂时显示上次结果；绘制不读文件。`/budget detail` 等读刷新不等于强制写出待提交数据。
8. 只读同步和保存后的文档采纳共用对齐规则：同周期保护本地未提交累计，外部周期更换沿用既有重置处理，统一通知确实变化的展示结果。不能直接用有初始化语义的 `ConsumptionStore.load()` 作为日常刷新。
9. nicobailon 根侧完成/进程通知只能作为刷新提示，不能证明 model-cost 已提交，也不能让未保存数据出现。保存的业务触发仍须由正确的 Round 映射兑现。
10. 消费文档在运行中不可读、损坏或不合 schema 时沿用 Q13：报告并暂停该实例消费记账/保存，不当空文档、不覆盖、不反复修复；保留最后可靠结果时须表明暂停，不当作有效写入基线。下一次正常初始化才重新建立基线；独立 provider 功能不因此停用。State 通信的自动恢复不改变此规则。

### 六、State 使用时获取、默认值与恢复

- `follow` 在需要 State 的语义使用点获取 Owner 当前权威值，不用启动快照、持久化旧值或未经确认的缓存代替，尤其不得恢复 `memory` 字段。
- 同进程直接读取；独立进程的获取和有限等待由 framework 集中实现。同一语义处理内相关读取共用取得的快照，不让各底层 getter 独自通信。
- 无法取得值时按最终 Q31 使用框架规定默认值，不使整个 extension 因此进入不可用；不向 Owner 写回默认值，不声称读取成功。
- `inheritance: none` 原本就正常使用默认值，不强迫它读取远端 Owner。权威返回 false 也是正常值，不是获取失败。
- 暂时通信失败在当前进程自动恢复：同目标并发合并，单次操作有限等待，失败期间有间隔且退避有上限；成功后停止恢复任务。健康时不持续轮询。
- 身份不匹配、Owner 可靠结束等明确失效不靠重连绕过；通信断开本身不证明 Owner 结束。所属接入处置后停止恢复，不复活失效的旧效果句柄。
- 默认值兜底后已执行的操作不在恢复时重放。Q30 的不自动重放原则保留，但“因暂时 State 缺值直接令本次业务操作失败”的中间方案已由默认值兜底取代。
- 该边界采用上述简单策略，不为罕见故障继续扩展业务状态机。

### 七、本机通信与显式目录配置

- 跨进程运行中消息使用 framework 内部本机 IPC，不通过消费文件或请求/应答文件队列，不扫描目录接收消息。
- 观察事实单向按事件推送；State 当前值是按需请求/应答，二者共用 framework 管理的本机接入，不建立任意 RPC，不传递模型文本，不开放远端 State 写入。
- 使用 Windows 命名管道/POSIX 本地 socket 这类本机流；extension 不自行创建服务器、连接或处理协议。公开接口隐藏载体、连接及恢复细节。当前证据只实测 Windows 基础互通，不能据此认证 POSIX 或完整 State 集成。
- 定位信息与消息分开：接入描述只记录 Owner、端点及必要的本次接入校验信息，不记录 State 值或业务数据。不得将旧地址、PID 或连接关闭推断为当前 Owner 的身份/生死；必须核对目标及所属寿命，防止跨 Owner/旧接入误连，凭据不进入模型或日志。
- Framework 自己使用的目录从 `framework/config.yaml` **显式配置值**取得。沿用共享配置入口，新增目录项可命名为 `runtimeDir`；随仓库配置可以提供一个临时/可清理目录值，但缺失、空或非法时不能使用代码中的 `os.tmpdir()`、cwd 等兜底路径。
- 相对目录以该配置文件的位置解析；参与同一接入的进程须解析到一致目录。需要这项目录能力时明确报告配置错误，不静默回退、不把它当作普通重连可修复的配置。
- 文件型定位信息及 POSIX socket 等运行时文件受配置目录约束；Windows 管道名属于内核命名空间，不是另一个磁盘数据目录。不使用 model-cost 的 storageDir 作为 framework 运行目录。
- 配置变化按既有进程初始化规则生效，不自动发现/热迁移。不会因此改动现有 HTTP 配置的默认预算或其他配置语义。

### 八、耗时估算与完整性

最终目标是**子代理累计活动时长的大体估算**，采用最简单的共同实现，不追求执行器准备阶段或精确边界：

- 优先复用 Working/Round 等已有公共活动事实；不为计时单独新增 execution 起止轴，不消费第三方/OMP 算好的最终 duration，不为精确计时要求修改第三方接口。
- 统计模型、工具及活动中的委派结果等待，排除真正 Idle 和不同次活动之间的空闲；不要求精确覆盖排队、会话创建或扩展加载。Round 的计费语义不因估算而放宽。
- 不要求持续刷新运行中读数；活动结束时结算，续跑后累加，在同一消费统计周期内持久化与恢复，不只显示最后一次。
- 取消/失败有已观察活动时保留其已知估算。崩溃或缺失结束不补下次恢复前的离线时段。
- 已有可靠小计继续保留，并携带本周期“不完整”状态；没有已知测量就表示未知，不伪造零。后续成功不会抹掉先前缺口，周期重置才开始新的累计口径。估算精度和观测完整性是不同维度。
- 耗时模块封装累计、去重、周期、恢复和完整性；不新增覆盖余额、额度、耗时、消费基线的通用 LastGoodValue 策略框架。这些场景的更新与失败语义不同。真正共通的策略继续复用，如现有 `provider-refresh.ts`。

### 九、能力 checklist 与验证边界

以 OMP 子代理能力为 checklist，而不是要求两端函数/文件一一对称。每项列出现有能力、pi/nicobailon 对应事实与接线、公共消费者及验证证据；原 `omp/subagents.ts` 之外的身份、父链、Owner、State 和观察语义仍属于完整基线，不能漏掉。

- 明确标出本权威批准的替代项：旧宿主精确 duration/进度轴改为活动时长估算；不把未实现写成已通过。
- 主会话/子会话、前台/后台、嵌套、workflow/调度、续跑、取消/失败、恢复、同进程/独立进程都按适用路径核对。workflow/调度的硬要求边界沿用选型权威，不悄悄扩大。
- 新共同路径须达到相同目标、无明显效率退化、无显著复杂度增加；同进程不新增 IPC/逐事件读盘，独立进程不重复根侧效果。实现前后的锁次数、请求/事件成本、计费去重与故障恢复须由后续验收提供证据，不凭设计宣称达标。
- [完整迁移方案](../decision/05-complete-migration-plan.md) 承接完整功能、旧记录/新耗时状态处理、绘制、发现入口、必要实现及验收组合；本决定不批准清空旧账、迁移用户数据或安装切换。
- [Round 边界映射](../decision/08-pi-round-boundaries.md) 承接主/子会话活动与自动继续、取消、恢复的事实映射。耗时可以粗估，不代表计费 Round 可以提前关闭。

### 证据与限制

本次新增事实资产：

- [跨进程 State 读取与公开通道](../research/04-state-follow-facts.md)：静态核对；已知 Owner 不代表可读取其当前 State，现有 framework 无该跨进程读取入口。
- [消费刷新与提交触发](../research/04-refresh-trigger-facts.md)：静态核对及既有实测引用；现有 load 非运行时同步接口，第三方通知与消费提交无已证顺序。
- [两端执行边界](../research/04-execution-boundary-facts.md)：静态核对；研究分类不是已批准计时要求。最终估算口径不再以缺少准备阶段精确时刻作为必须补第三方接口的理由。
- [本机通信载体](../research/04-local-transport-facts.md)：含 Windows Node 24.18.0/Bun 1.4.2 四种独立进程 named-pipe echo 组合及退出行为的基础探针记录；不是 framework/State/身份安全/恢复集成测试。POSIX、跨用户访问控制和完整握手未实测。探针临时程序与进程已由研究任务清理。

本次没有生产实现、真实模型调用、正式配置变更、宿主安装或迁移切换。实际 framework/adapter 与 README 仍可能描述旧实现；这不是新方案已经运行的证据。

## Decision

在 framework 中集中提供子代理上下文与本机接入，按同进程/独立进程复用公共语义和业务实现；model-cost 保留业务记账、批量持久化及粗粒度活动耗时累计。确认稳定接入模式、State 默认值与自动恢复、显式目录配置和事件驱动同步；组织规划范围完成，完整 Round 映射、实现及迁移验收不因此完成。

## User stories

1. 作为 extension 维护者，我需要复用 framework 的身份、父链、Owner、State 与观察能力，以便接入新 harness 时只补原生机制，不复制业务或公共关系算法。
2. 作为 model-cost 使用者，我需要有/无子代理两种稳定接入模式，以便未启用提供方时正常使用主会话统计，detail 给出明确提示而不执行无意义切换。
3. 作为多进程记账的维护者，我需要内存先更新、按业务事件统一合并提交和只读同步，以便减少重复锁竞争，同时不覆盖他人记录、不重复计费或丢掉在途变化。
4. 作为使用 State follow 的扩展使用者，我需要在使用时读取 Owner 当前值，并在暂时失败时以默认值继续和自动恢复，以便子进程的启动时序不迫使我重启，恢复也不重复操作。
5. 作为子代理使用者，我需要跨续跑保存累计活动时长估算与观测缺口，以便获得足够有用的大体耗时，而不为精确执行器边界增加维护成本。
6. 作为机器配置维护者，我需要显式决定 framework 的运行目录，以便没有配置值时不会发生隐藏路径写入，业务存储与通信定位信息保持分离。
7. 作为迁移规划者，我需要对称的能力 checklist 和分层验证证据，以便统一新路径确实满足目标与效率/复杂度条件，不把接口规划或基础通信探针当成完整迁移通过。

## Preconditions

- 消费 [完整能力基线](01-capability-baseline.md)、[提供方选择](03-subagent-provider-choice.md) 与 [nicobailon 固定工件验证](07-nicobailon-runtime-validation.md)，遵守其公开事实、版本、路径及证据限制。
- 当前所需目录、State 跨进程读取、事件接入、只读同步与批量提交仍须实现，不能声称 framework 已经集成可用。
- 具体 pi Round/活动事实映射由独立边界票提供；实际迁移需完整方案和验收输入。

## Postconditions

- 本票的目录、依赖方向、接口职责、接线、模式、清理、错误及恢复方向已决定，可供后续方案消费，不再保留互相竞争的旧方案。
- 没有授权长期 fork、未批准宿主补丁、任意 RPC、生产迁移、清空消费数据或新付费验证。
- 后续实现必须保留统一路径的功能/效率/复杂度条件与基线 checklist，不以默认值或 UI 非硬实时为由隐去记账/生命周期缺口。

## Invariants

- 对齐 [Extension 开发地图](../../../framework/docs/extension-development-map.md)：同一声明/shared-logic，公共语义在 core/behaviors，宿主机制在 adapter，业务在 extension，装配和发现入口薄。
- `framework/core/state.ts` 继续是 State 权威与写权/寿命的拥有者；通信不持久化 memory State、不复活旧效果句柄，读取失败的默认值不反写 Owner。
- 观察不改变 State 继承、不授予效果权限；实际 session、直接父、Owner、查看目标与进程身份不能混同。pi 查看适用范围继续沿用选型权威。
- 费用继续来自自身请求锚价与计费实现，不使用第三方最终 cost；同一请求只计一次，统计周期及归档语义不被 batch/刷新改变。
- 文件发布复用 `framework/modules/files.ts`；JSON schema/提交资格/冲突裁决是业务规则。运行中消息与持久化、接入定位互不混同。
- 粗估耗时不是会话跨度、最后一次 duration 或精确执行器总时长；估算不代表观测完整，未知不等于确认零。
